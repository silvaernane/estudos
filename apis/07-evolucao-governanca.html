Versionamento e governança

Como evoluir, depreciar e governar APIs ao longo dos anos sem quebrar quem depende delas: versionamento, ciclo de vida, gateway, catálogo, style guide e API como produto.

Ao final você saberá
  • Explicar por que uma API publicada vira compromisso permanente (lei de Hyrum) e classificar qualquer mudança como breaking ou não
  • Escolher entre versionamento na URI, em cabeçalho, em media type ou por data, defendendo o trade-off
  • Evoluir uma API sem quebrar consumidores: expand/contract, tolerant reader, campos aditivos e feature flags
  • Conduzir depreciação e desligamento com Deprecation, Sunset, métricas por consumidor e política de suporte
  • Definir o papel do API gateway, do catálogo, do style guide e do lint automatizado, sem criar burocracia
  • Tratar API como produto e escolher entre governança centralizada e federada
1Intermediário

APIs são para sempre (ou quase)

Uma API pública, ou usada por qualquer time que você não controla, é um contrato com terceiros. Código interno você refatora num PR; uma API publicada você só consegue mudar com a cooperação de quem a consome, e essas pessoas têm outras prioridades, outros sprints e às vezes nem trabalham mais na empresa parceira. É por isso que mudar uma API é mais caro do que construí-la.

Lei de Hyrum

A formulação popular diz: com um número suficiente de usuários de uma API, não importa o que você prometeu no contrato; alguém vai depender de cada comportamento observável do sistema. Ordem dos campos no JSON, formato exato de uma mensagem de erro, o fato de a lista vir sempre ordenada por data, o tempo de resposta (alguém faz um sleep calibrado nele), o tamanho padrão de página. Nada disso estava na documentação, tudo isso virou contrato de fato.

Comportamento não documentadoComo alguém passa a depender deleQuando quebra
Lista de agendamentos vem ordenada por dataTela do parceiro exibe na ordem recebida, sem reordenarVocê adiciona um índice novo e o planner passa a devolver por id
Mensagem de erro "CPF inválido"Integrador faz if (msg.includes("CPF")) para decidir o fluxoVocê traduz ou reescreve a mensagem

O que isso muda no jeito de trabalhar

  • Publicar é decisão de produto, não de deploy. O que entra na resposta de hoje é o que você sustenta por anos.
  • Seja conservador no que expõe. Um campo que não existe nunca quebra. Retornar o objeto inteiro do banco "porque é fácil" transforma cada coluna em contrato.
  • Deixe explícito o que é garantido. Documente "a ordem não é garantida" e, se possível, embaralhe de propósito em ambientes de teste para que ninguém dependa dela.
  • Prefira códigos de erro estáveis ("codigo": "CPF_INVALIDO") a mensagens. A mensagem é para humanos, o código é para máquinas (erros em problem+json, módulo 01 desta trilha).
Regra de bolso

Tudo que sai pela rede e é observável será usado. Exponha o mínimo, documente o que é garantido e trate o resto como "pode mudar sem aviso", dizendo isso por escrito.

Na entrevista

"Por que versionamento é difícil?" Resposta sênior: porque o custo de mudar não está no seu código, está nos consumidores que você não controla. Cite a lei de Hyrum: qualquer comportamento observável vira contrato de fato, então o trabalho é reduzir a superfície exposta e planejar a evolução desde o primeiro dia.

Para gestores

Pergunte em toda revisão de design: "quem consome isso hoje? Quem vai consumir? Se precisarmos mudar daqui a 2 anos, quanto custa?" Um endpoint que nasce sem dono e sem consumidores mapeados é dívida técnica com juros altos. Cobre do time o hábito de expor menos: DTOs explícitos, nunca entidades do banco.

Este módulo continua o que foi visto sobre versionamento no 08-apis.html da trilha web (noções de /v1) e sobre contratos no módulo 02 desta trilha. Aqui o foco é a operação: como evoluir, comunicar, desligar e governar um conjunto de APIs ao longo dos anos.

2Intermediário

O que é (e o que não é) breaking change

Mudança breaking é a que pode fazer um consumidor correto, escrito conforme o contrato anterior, parar de funcionar sem alterar o código dele. A pergunta de teste é sempre: um cliente que funcionava ontem continua funcionando hoje, sem redeploy? O ponto de vista muda entre requisição (o que o cliente envia) e resposta (o que ele recebe): o que é seguro numa direção costuma ser perigoso na outra.

Tabela de classificação

Regra de bolso

Na requisição, aceitar mais é seguro e exigir mais quebra. Na resposta, devolver mais campos é quase seguro e devolver menos, mais nulos ou mais valores possíveis quebra. Em resumo: seja liberal no que aceita e conservador no que promete.

Detectando breaking changes automaticamente

Revisão humana falha. Se o contrato é OpenAPI (módulo 02), compare a versão do PR com a publicada no CI e falhe o build se houver quebra. Ferramentas como oasdiff e openapi-diff fazem isso.

name: api-breaking-check
on: [pull_request]
jobs:
  diff:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - name: Baixa o contrato publicado (main)
        run: git show origin/main:openapi/agendamentos.yaml > /tmp/base.yaml
      - name: Falha se houver breaking change
        run: |
          docker run --rm -v "$PWD:/w" -v /tmp:/t tufin/oasdiff \
            breaking /t/base.yaml /w/openapi/agendamentos.yaml \
            --fail-on ERR
Armadilha comum

"Adicionar campo não é breaking" é verdade só se o consumidor foi escrito para ignorar campos desconhecidos. Alguns geradores de cliente e configurações de desserialização (como FAIL_ON_UNKNOWN_PROPERTIES no Jackson) rejeitam. Escreva essa expectativa no guia de integração.

Na entrevista

Pedem uma lista de breaking changes. Organize pela direção: requisição (exigir mais, estreitar, remover) e resposta (remover, mudar tipo ou formato, afrouxar nulabilidade, novo valor de enum). Mencione que status code e ordenação padrão também contam, e que o CI deve rodar um diff do OpenAPI.

Para gestores

Defina por escrito o que o time considera breaking e quem pode autorizar uma exceção. Uma boa política: breaking change exige ADR curto, plano de migração e aprovação do dono da API. Mudança "pequena" sem diff automático é a causa mais comum de incidente com parceiro.

Estratégias de versionamento

Versionar é o último recurso, não o primeiro: cada versão em produção é uma API a mais para operar, testar, documentar e proteger. A ordem de preferência é (1) evoluir de forma aditiva sem nova versão; (2) versionar só quando houver quebra inevitável. Quando precisar, estas são as opções.

Host: api.clinica.example
Authorization: Bearer eyJ...

Api-Version: 2
Authorization: Bearer eyJ...
GET /pacientes/8841/agendamentos HTTP/1.1

GET /pacientes/8841/agendamentos HTTP/1.1

Versionamento por data na prática

No modelo popularizado pela Stripe, a primeira chamada de uma conta fixa a versão (uma data) vigente naquele momento; o cliente pode sobrescrever por requisição com um cabeçalho. Internamente o código responde sempre na versão mais nova, e uma cadeia de transformações de compatibilidade converte a resposta para a data do cliente.

// Cada migração converte a resposta da versão N para a versão N-1.
const migracoes = [
  { data: "2026-03-01", down: (r) => { r.status = r.status === "REAGENDADO" ? "CONFIRMADO" : r.status; return r; } },
  { data: "2025-11-10", down: (r) => { r.medico_nome = r.medico.nome; delete r.medico; return r; } },
];

function paraVersao(resposta, versaoCliente) {
  // aplica, da mais nova para a mais antiga, até chegar na data pedida
  for (const m of migracoes) {
    if (m.data > versaoCliente) resposta = m.down(resposta);
  }
  return resposta;
}
Armadilha comum

Versionar tudo junto ("v2 da API toda") porque um recurso quebrou. Você acaba mantendo 40 endpoints duplicados para mudar 1. Prefira versionar o recurso ou o campo afetado (novo campo, novo endpoint, novo media type) e reserve a "grande v2" para reescritas reais.

Regra de bolso

Versão major na URI (/v1, /v2) e evolução aditiva dentro da major. Não existe /v1.3 na URL: minor e patch são para o changelog, não para o roteamento.

Na entrevista

"Como você versiona?" Não responda só "na URL". Diga: evoluo de forma aditiva para evitar nova versão; quando há breaking, major na URI por ser a mais simples de rotear, medir e depreciar; conheço o modelo por data da Stripe e sei por que ele exige uma camada de transformação. Mostrar que versionar tem custo operacional é o diferencial sênior.

Para gestores

Defina o limite de versões em paralelo (ex.: no máximo 2 majors suportadas) e a janela mínima de convivência (ex.: 12 meses). Sem esse teto, o time passa a manter N versões e a velocidade de entrega cai. Versão nova só nasce com plano de desligamento da anterior escrito.

4Avançado

Evoluir sem quebrar

A forma mais barata de versionar é não precisar. Quatro técnicas, usadas juntas, cobrem a maioria das mudanças.

1. Expand / contract (parallel change)

Toda mudança incompatível é quebrada em três passos compatíveis. Exemplo: trocar medico_nome (string) por um objeto medico com id e nome.

{
  "id": "ag_7731",
  "medico_nome": "Dra. Helena Prado",
  "medico": { "id": "med_204", "nome": "Dra. Helena Prado" },
  "inicio": "2026-04-02T14:30:00-03:00"
}

2. Tolerant reader (leitor tolerante)

Princípio do lado do consumidor (Martin Fowler descreve o padrão): leia só os campos de que precisa, ignore o que não conhece, não valide o que não usa, trate enum desconhecido com um caminho padrão. Você, como provedor, exige isso no contrato e publica no guia de integração; sem essa regra, "campo aditivo" deixa de ser seguro.

function lerAgendamento(json) {
  // lê só o que usa; campo novo no JSON não faz diferença
  const { id, inicio, status } = json;
  return {
    id,
    inicio: new Date(inicio),
    // enum desconhecido vira um estado seguro em vez de exceção
    status: ["AGENDADO", "CONFIRMADO", "CANCELADO"].includes(status) ? status : "DESCONHECIDO",
  };
}

3. Campos aditivos e defaults seguros

  • Adicione campos novos como opcionais e com default que preserva o comportamento antigo. Ex.: ?incluir_cancelados=false como padrão se antes nunca vinham.
  • Em vez de mudar o significado de um campo, crie outro (valor_centavos ao lado de valor ambíguo).
  • Declare no OpenAPI quais enums são abertos (o cliente deve tolerar valores novos). Em Protobuf, a regra de ouro é nunca reaproveitar números de campo (módulo 03).
  • Use additionalProperties com consciência: um objeto "fechado" não deixa o provedor evoluir.

4. Feature flags e rollout gradual

Flags desacoplam deploy de lançamento: o código novo vai para produção desligado, é ligado para 1 % do tráfego, depois por consumidor, depois para todos. Para APIs, o mais útil é a flag por consumidor (identificado pelo client_id do token): você habilita o comportamento novo para o parceiro que topou testar primeiro.

// comportamento novo só para quem optou, e sempre com saída de emergência
function responderAgendamento(ag, ctx) {
  const base = { id: ag.id, inicio: ag.inicio, medico_nome: ag.medico.nome };
  if (flags.enabled("agendamento.medico-objeto", { client: ctx.clientId })) {
    base.medico = { id: ag.medico.id, nome: ag.medico.nome };
  }
  return base;
}
Armadilha comum

Esquecer o passo 3. APIs ficam com campo_v1, campo_v2 e campoNovo para sempre porque ninguém tem coragem de remover. Dê um dono e uma data a cada contract, abra o ticket de remoção junto com o de adição e use as métricas de uso (seção 5) para decidir.

Na entrevista

"Como renomear um campo sem derrubar ninguém?" Expand/contract: o passo 1 entrega os dois campos; o 2 migra consumidores e mede uso; o 3 remove quando o uso do antigo for zero. Cite que o tolerant reader no cliente e o diff de OpenAPI no CI sustentam isso.

Para gestores

Feature flag sem dono vira lixo em semanas. Estabeleça: toda flag nasce com data de remoção e responsável; revise a lista todo mês. E exija de todo breaking change um plano de três fases no desenho, antes do código.

5Avançado

Ciclo de vida e depreciação

Toda API nasce, vive e morre. Tratar o desligamento como parte do projeto (e não como emergência) separa times maduros dos demais: você precisa de estágios explícitos, sinais legíveis por máquina, dados sobre quem usa e uma política de suporte conhecida por todos.

Cabeçalhos Deprecation e Sunset

  • Deprecation (RFC 9745): informa que o recurso está depreciado, ou será. O valor é uma data no formato de Structured Fields (um timestamp Unix precedido de @). Depreciado significa "não use em código novo e planeje sair"; continua funcionando.
  • Sunset (RFC 8594): informa a data em que o recurso deixará de responder, no formato de data HTTP.
  • Ambos podem vir acompanhados de Link com rel="deprecation" (documentação da depreciação), rel="sunset" (política de desligamento) e rel="successor-version" (para onde migrar).
HTTP/1.1 200 OK
Content-Type: application/json
Deprecation: @1775001600
Sunset: Wed, 01 Jul 2026 00:00:00 GMT
Link: <https://docs.clinica.example/migracao-v2>; rel="deprecation"; type="text/html",
      <https://docs.clinica.example/politica-de-sunset>; rel="sunset",
      <https://api.clinica.example/v2/agendamentos/ag_7731>; rel="successor-version"

{ "id": "ag_7731", "medico_nome": "Dra. Helena Prado" }

Depois do Sunset, devolva 410 Gone com corpo de erro (RFC 9457) apontando a migração, em vez de cair num 404 ou timeout.

HTTP/1.1 410 Gone
Content-Type: application/problem+json

{
  "type": "https://docs.clinica.example/erros/versao-desligada",
  "title": "API v1 desligada",
  "status": 410,
  "detail": "A v1 foi desligada em 2026-07-01. Use /v2.",
  "migracao": "https://docs.clinica.example/migracao-v2"
}

Medir antes de desligar

Só se desliga com segurança o que se sabe que ninguém usa. Registre versão, endpoint e consumidor (o client_id do token ou a chave de API) em toda requisição e agregue.

-- Quem ainda chama a v1, em ordem de volume, nos últimos 30 dias
SELECT client_id,
       COUNT(*)                 AS chamadas,
       COUNT(DISTINCT endpoint) AS endpoints,
       MAX(ts)                  AS ultima_chamada
FROM   api_access_log
WHERE  api_version = 'v1'
  AND  ts >= CURRENT_DATE - INTERVAL '30 days'
GROUP  BY client_id
ORDER  BY chamadas DESC;

Comunicação

  1. Canal múltiplo: e-mail para contatos técnicos e de negócio, changelog, portal do desenvolvedor, cabeçalhos nas respostas. Um canal só falha.
  2. Datas absolutas e cronograma (anúncio, deprecação, brownouts, sunset), nunca "em breve".
  3. Guia de migração com antes e depois, ferramentas de teste e canal de suporte.
  4. Lembretes escalonados (12, 6, 3 e 1 mês e 1 semana antes) para quem ainda usa; o dado de uso diz quem.
  5. Brownouts: janelas curtas e combinadas em que a versão antiga responde erro de propósito, expondo quem ignorava os avisos antes do desligamento definitivo.

Política de suporte

ElementoExemplo de política
Versões suportadasAtual e a imediatamente anterior (máx. 2 majors)
Janela mínima entre deprecação e sunset12 meses para parceiros externos; 3 a 6 para consumidores internos
Correções na versão deprecadaSó segurança e bugs críticos; sem funcionalidade nova
ExceçãoProrrogação por escrito, com data final e custo explícito para o consumidor
Exceção de segurançaFalha grave pode forçar desligamento antecipado; o contrato deve prever isso
Armadilha comum

Anunciar o sunset só por e-mail para uma lista que ninguém atualiza. Em saúde é comum o contato técnico do parceiro ser um fornecedor terceirizado que já saiu do contrato. Confira os contatos e use também o canal da própria API (cabeçalhos e brownouts).

Na entrevista

"Como você desliga uma API em produção?" Anúncio com data absoluta; cabeçalhos Deprecation e Sunset nas respostas; métricas de uso por consumidor para saber quem falta migrar; contato direto com os maiores consumidores; brownouts; e por fim 410 Gone com link de migração.

Para gestores

O custo de manter uma versão antiga é real (infra, testes, segurança, atenção do time). Estime-o e leve ao produto para justificar a data de sunset. Cobre do time um painel de "consumidores restantes" por versão: é o indicador de risco do desligamento.

6Avançado

API gateway e API management

Um API gateway é um proxy reverso especializado, na frente das suas APIs, que concentra preocupações transversais. API management é a plataforma ao redor dele: portal do desenvolvedor, planos e chaves, analytics, ciclo de vida. Produtos comuns: Kong, Apigee, AWS API Gateway e Azure API Management (e também gateways para Kubernetes baseados em Envoy). Load balancers e proxies foram vistos no 06-backend-infra.html da trilha web; o gateway fica na camada 7 e entende de APIs.

O que o gateway deve fazerO que NÃO deve fazer

Roteamento por versão, host e caminho; canary e blue/greenOrquestrar chamadas entre vários serviços com lógica complexa (vira um ESB de novo)
Terminação TLS, CORS, validação básica de schema, WAFFazer transformações pesadas de payload sem dono nem teste
Emitir logs e métricas, propagar traceparent (módulo 08)Guardar estado de negócio
Publicar contratos no portal, emitir chaves, analytics por consumidorVirar gargalo ou ponto único de falha, sem alta disponibilidade e sem configuração versionada

Gateway como código

A configuração do gateway é código: fica no Git, passa por PR e é aplicada por pipeline. Exemplo ilustrativo (formato declarativo, no estilo do Kong):

services:
  - name: agendamentos-v2
    url: http://agendamentos.svc.cluster.local:8080
    routes:
      - name: agendamentos-v2-route
        paths: ["/v2/agendamentos"]

      - name: jwt

Armadilha comum

Gateway "inteligente demais". Ao colocar regras, scripts e transformações no gateway, o comportamento da API fica espalhado, sem teste e sem dono. A regra: o gateway é burro e rápido; a inteligência mora no serviço.

Na entrevista

"O que um gateway faz e o que não faz?" Faz o que é transversal e independente de negócio: autenticação, limites, roteamento, observabilidade, TLS. Não decide regra de negócio e não substitui autorização no serviço. Mencione alta disponibilidade e configuração como código.

Para gestores

Gateways comerciais cobram por requisição ou por instância, e o custo cresce rápido. Avalie lock-in (políticas proprietárias), operação (quem está de plantão para o gateway?) e o risco de ponto único de falha. A pergunta de compra: "o que ganhamos que um proxy bem configurado não daria?".

Inventário, catálogo e style guide

Não se governa o que não se enxerga. Em empresas com dezenas de sistemas (como um ecossistema Oracle e PostgreSQL de saúde), a primeira pergunta é "quais APIs existem, quem é o dono e quem as consome?". A resposta costuma ser decepcionante.

Inventário e catálogo

  • Inventário: lista viva de todas as APIs, inclusive internas e "sombra" (shadow APIs, as que ninguém registrou). Fontes: gateway, DNS, logs de acesso, repositórios, WAF.
  • Catálogo: o inventário com contrato (OpenAPI), dono, estágio do ciclo de vida, classificação de dados (contém PII? dado de saúde?), SLA, consumidores e link para a documentação. Pode ser o portal do API management, um catálogo de serviços (como o Backstage) ou até um repositório Git com um arquivo de metadados por API.
apiVersion: backstage.io/v1alpha1
kind: API
metadata:
  name: agendamentos-api
  description: Agendamento de consultas e exames
  tags: [saude, pii]
spec:
  type: openapi
  lifecycle: production        # experimental | production | deprecated
  owner: time-agendamento
  definition:
    $text: ./openapi/agendamentos.yaml
Armadilha comum

Catálogo preenchido uma vez e esquecido. Alimente-o automaticamente a partir do pipeline (publicar o OpenAPI é parte do build) e compare com o tráfego real do gateway para descobrir APIs sombra.

Style guide

Um guia de estilo responde às perguntas que se repetem em toda revisão, para que ninguém precise debatê-las de novo: nomes (plural, kebab-case ou camelCase), formato de erro (RFC 9457), paginação padrão, datas (ISO 8601 com fuso), IDs, filtros, idempotência, cabeçalhos obrigatórios, versionamento, o que é breaking. Parta de um guia público (Zalando, Microsoft e Google publicam os seus) e adapte; não escreva do zero.

Lint automatizado

Regra que está só em documento não é cumprida. Transforme o guia em regras executáveis sobre o OpenAPI, rodando no CI. A ferramenta mais comum é o Spectral.

extends: ["spectral:oas"]
rules:
  paths-sem-verbo:
    description: Caminhos devem ser substantivos
    severity: error
    given: "$.paths[*]~"
    then:
      function: pattern
      functionOptions: { notMatch: "/(criar|buscar|deletar|atualizar|get|set)" }
  operacao-com-id:
    description: Toda operação precisa de operationId
    severity: error
    given: "$.paths[*][*]"
    then: { field: operationId, function: truthy }
  erro-problem-json:
    description: Respostas de erro devem usar application/problem+json
    severity: warn
    given: "$.paths[*][*].responses[?(@property >= '400')]"
    then:
      field: "content.application/problem+json"
      function: truthy
npx @stoplight/spectral-cli lint openapi/agendamentos.yaml --ruleset .spectral.yaml

Revisão de design de API

O lint pega o mecânico; a revisão humana pega o resto: o recurso está bem modelado? É a API de que o consumidor precisa? Faça a revisão antes do código, sobre o contrato (design-first, módulo 02).

Na entrevista

"Como garantir consistência entre APIs de times diferentes?" Style guide curto, regras de lint no CI (Spectral), revisão de design de contrato antes do código e catálogo com dono. A ordem importa: automatize o que dá, revise o que exige julgamento.

Para gestores

Defina quem aprova: um grupo pequeno e rotativo de "API champions" de diferentes times, com SLA de resposta (ex.: 2 dias úteis). Revisão que leva 3 semanas faz o time desviar do processo. Métricas: tempo médio de revisão e % de APIs no catálogo com contrato e dono.

8Avançado

API como produto e governança

API como produto

Tratar a API como produto significa ter consumidores como clientes, um dono com visão de roadmap, documentação mantida, suporte e métricas. A mudança de mentalidade: o objetivo não é "entregar o endpoint", é que os consumidores consigam fazer o que precisam de forma rápida e confiável.

DimensãoO que existe numa API tratada como produto
ConsumidoresMapeados (internos, parceiros, convênios, apps), com contato técnico e de negócio, e conversa regular com os principais
DocumentaçãoReferência gerada do OpenAPI + guias de uso por caso (agendar, cancelar, consultar resultado) + exemplos executáveis + changelog
OnboardingSandbox com dados fictícios, chave de teste em minutos, collection pronta, status page
SLA/SLODisponibilidade e latência publicadas (módulo 08), suporte e canal de incidente definidos
Roadmap e mudançasChangelog, avisos antecipados, política de depreciação conhecida
Métricas de produtoConsumidores ativos, volume e taxa de erro por consumidor, adoção de versão, tempo até a primeira chamada

Métricas de adoção

  • Time to first hello world (TTFHW): tempo entre o consumidor receber acesso e fazer a primeira chamada com sucesso. Meta realista: minutos num sandbox; se levar dias, o onboarding é o problema.
  • Consumidores ativos (30 dias) e taxa de ativação (quantos dos que pediram acesso chegaram à produção).
  • Taxa de erro 4xx por consumidor: muito 400/422 de um consumidor indica documentação ruim ou contrato confuso; é feedback de produto.
  • Participação por versão: % do tráfego em cada versão, a métrica que dirige a depreciação.
  • Chamados de suporte por consumidor e tempo de resolução.
Regra de bolso

Se um parceiro precisa de uma reunião com sua equipe para fazer a primeira chamada, a documentação e o sandbox ainda não são bons o bastante.

Governança: centralizada vs federada

CentralizadaFederada
Quem decideUm time (arquitetura/plataforma) aprova tudoTimes donos decidem dentro de guardrails comuns; um conselho cuida das regras compartilhadas
ConsistênciaAltaBoa, se houver lint e padrões automatizados
VelocidadeBaixa: o time central vira filaAlta: autonomia com responsabilidade
RiscoBurocracia e desvios "por baixo do pano"Divergência se faltarem disciplina e ferramentas
Funciona bemEmpresas pequenas, APIs públicas críticas, setor muito reguladoOrganizações com muitos times de produto

Como não virar burocracia

  • Guardrails, não gates: o caminho certo deve ser o mais fácil (templates, geradores, lint no CI, pipeline pronto). Quem segue o padrão não pede autorização.
  • Revisão proporcional ao risco: API pública ou com dado sensível, revisão completa; API interna de baixo risco, só o lint.
  • SLA para o próprio processo: se a governança é lenta, será contornada.
  • Regras com motivo e dono: toda regra do guia tem uma justificativa de uma linha; regra sem justificativa é cortada.
  • Medir a governança: tempo de revisão, % de APIs conformes, exceções concedidas. Se ninguém mede, vira cerimônia.
Armadilha comum

Governança que só diz "não". Se o time aprova tudo no final, tarde demais, ou bloqueia sem oferecer alternativa, as equipes passam a subir APIs sem avisar. Cada "não" deve vir com um "faça assim".

Na entrevista

"Governança centralizada ou federada?" Resposta madura: federada com guardrails automatizados. Um grupo pequeno define padrões e ferramentas; cada time é dono das suas APIs e responde por elas; o mecânico vai para o CI e só o risco alto passa por revisão humana. Reconheça que em setor muito regulado ou API crítica pode valer mais centralização.

Para gestores

Cada API precisa de um dono nomeado (um time, não "a empresa") e de um contato de plantão. Pergunta de auditoria trimestral: "quais APIs não têm dono, contrato ou consumidores conhecidos?". Em saúde, adicione ao cadastro de cada API a classificação dos dados e a base legal (LGPD).

Cenários práticos

Cenário 1: desligar a v1 usada por um parceiro que não responde

Situação: a v2 está no ar há 14 meses. A v1 custa manutenção e tem uma falha de segurança conhecida e difícil de corrigir. Restam 3 consumidores; dois migraram. O terceiro, um laboratório parceiro, gera 8 % do tráfego da v1, não responde a e-mails e o contato técnico do contrato saiu da empresa.

O que fazer:

  1. Confirme o dado. Consulte o log por client_id: quais endpoints, que volume, quais horários (batch noturno?). Entenda o que quebrará antes de agir.
  2. Escale pelo lado comercial. Vá além do técnico: gerente de contas, contrato, jurídico, canal de suporte do parceiro, responsável de negócio. Registre cada tentativa com data. A cláusula contratual de depreciação é sua base.
  3. Use o canal da API. Garanta Deprecation, Sunset e Link em todas as respostas deles. Alguém, em algum momento, vê isso num log.
  4. Brownout combinado e anunciado. Janelas de 15 min a 2 h, crescentes, em horário de baixo risco clínico. É frequente o contato "aparecer" na primeira. Evite horários de atendimento e rotinas críticas, como a entrega de resultados de exame.
  5. Reduza o risco do desligamento. Se o dado é crítico (resultados de exame), ofereça uma ponte: um adaptador temporário v1 para v2 só para esse consumidor, com data final e custo para o parceiro. Ou prorrogue por escrito, com data final e mitigação de segurança (WAF, restrição de IP).
  6. Desligue com saída reversível. Na data, devolva 410 Gone com link de migração e mantenha o rollback no gateway por alguns dias (reabilitar só aquele client_id, se necessário). Registre no changelog e faça um post-mortem curto.
Regra de bolso

O desligamento forçado é a última etapa, com dados e registro do esforço de contato. Se a segurança está em jogo, o contrato deve permitir o corte antecipado; se não permite, é lição para o próximo contrato.

Cenário 2: o time quer renomear um campo "porque ficou feio"

Situação: o campo dtAgd será trocado por inicio, numa API com 6 consumidores externos.

O que fazer: perguntar qual é o benefício real; se for só estética, a resposta é "não vale o custo". Se for necessário (por exemplo, consistência com o style guide), use expand/contract com os dois campos por um período, meça o uso do antigo, anuncie a data e só remova na próxima major. Nunca renomeie no lugar.

Cenário 3: um bug de ordenação foi "corrigido" e três clientes reclamaram

Situação: a listagem de consultas passou a vir por id e não por data após um refactor. Ninguém documentou a ordem.

O que fazer: reverter ao comportamento anterior de imediato (o contrato real é o observável), registrar a ordem padrão no OpenAPI, adicionar um teste de contrato que a verifique e oferecer ?ordenar=data de forma explícita. Depois, em reunião sem culpados, ajuste o processo: mudanças de ordenação ou de default entram na lista de breaking changes do style guide.

Cenário 4: ninguém sabe quantas APIs existem

Situação: uma auditoria pede a lista de APIs que tratam dados de pacientes. Cada time responde de um jeito.

O que fazer: em 30 dias, monte o inventário a partir do tráfego (logs do gateway, DNS, load balancers) e dos repositórios; cruze com o que os times declaram; classifique por tipo de dado; atribua dono a cada uma. Depois, torne a publicação do OpenAPI no catálogo parte obrigatória do pipeline, para o inventário se manter sozinho. APIs sem dono e sem tráfego entram na lista de desligamento.

Cenário 5: a empresa quer "uma v2 de tudo" para limpar dívida

Situação: o time propõe reescrever a API inteira como v2 e desligar a v1 em 6 meses.

O que fazer: desafiar o escopo. Liste o que realmente quebra o contrato e o que é desejo de limpeza; priorize por valor para os consumidores. Muitas melhorias cabem de forma aditiva na v1. O que sobrar vai para a v2 com plano de migração, métricas de uso e orçamento de suporte da v1 já definidos. Uma v2 sem plano para a v1 vira "duas APIs para sempre".

Glossário

Lei de Hyrum
Com usuários suficientes, todo comportamento observável de uma API vira dependência de alguém, documentado ou não.
Breaking change
Mudança que pode quebrar um consumidor correto sem que ele altere seu código.
Expand / contract
Padrão de três passos (expandir, migrar, contrair) para fazer uma mudança incompatível de forma compatível.
Tolerant reader
Consumidor que lê só o que precisa e ignora o resto, tolerando campos e valores novos.
Versionamento por data
Cada consumidor fica fixado na data de sua integração; o provedor transforma respostas entre versões.
Deprecation (RFC 9745)
Cabeçalho que indica que o recurso está depreciado, ou será em data informada.
Sunset (RFC 8594)
Cabeçalho com a data em que o recurso deixa de responder.
Brownout
Indisponibilidade curta e combinada de uma versão antiga para forçar a atenção dos consumidores.
API gateway
Proxy que centraliza autenticação, limites, roteamento e observabilidade na frente das APIs.

Plataforma de portal, planos, chaves, analytics e ciclo de vida ao redor do gateway.
Style guide
Conjunto de regras de design de API da organização, idealmente executável como lint.

Ferramenta de lint para OpenAPI baseada em regras configuráveis.

11Avançado

Perguntas de entrevista

01O que é uma breaking change em API?

Uma mudança que pode quebrar um consumidor correto sem que ele altere o código: remover ou renomear campo, mudar tipo ou formato, tornar um campo de entrada obrigatório, remover valor de enum, mudar status code. Teste: um cliente que funcionava ontem continua funcionando hoje, sem redeploy?

02Adicionar um campo na resposta é breaking?

Em geral não, porque clientes bem escritos ignoram campos desconhecidos (tolerant reader). Mas se algum cliente usa desserialização estrita, quebra. Por isso o contrato deve dizer que campos novos podem aparecer. Novos valores de enum são mais perigosos que novos campos.

03Tornar um campo opcional ou obrigatório: qual a diferença na requisição e na resposta?

Na requisição, afrouxar (obrigatório para opcional) é seguro; apertar quebra quem não envia. Na resposta é o contrário: garantir presença é seguro; passar a permitir nulo ou ausência quebra quem assumia presença. Regra: aceite mais, prometa menos.

04Explique a lei de Hyrum com um exemplo.

Com muitos usuários, qualquer comportamento observável vira contrato de fato. Exemplo: a lista de agendamentos sempre vem ordenada por data, sem documentação; um parceiro exibe na ordem recebida; ao mudar o índice, a ordem muda e a tela dele quebra. Mitigação: expor pouco, documentar o que é garantido, aleatorizar o que não é.

05Quais as estratégias de versionamento e quando usar cada uma?

URI (/v2): simples, visível, fácil de rotear e medir; padrão para parceiros. Cabeçalho: URL limpa, porém invisível e exige Vary. Media type: versiona a representação, mais purista e mais difícil de operar. Por data (Stripe): consumidor fixado numa data, mudanças pequenas, mas exige camada de transformação. Minha preferência: major na URI com evolução aditiva dentro dela.

06Por que evitar versionar sempre que possível?

Cada versão em produção multiplica custo de manutenção, testes, segurança, documentação e suporte. Prefiro evoluir de forma aditiva e abrir nova versão só quando há quebra inevitável, com plano de desligamento da anterior já definido.

07Como renomear um campo sem derrubar os clientes?

Expand/contract. Passo 1: devolver campo antigo e novo. Passo 2: migrar consumidores, medindo o uso do antigo e comunicando o prazo. Passo 3: quando o uso zerar ou o prazo vencer, remover o antigo, de preferência numa nova major. Nunca renomear no lugar.

08O que é tolerant reader e por que importa para o provedor?

É o princípio de o consumidor ler apenas o que usa e ignorar o resto. Para o provedor, é a condição que torna as mudanças aditivas seguras; por isso ele deve exigir isso no contrato e no guia de integração, e testar com clientes de exemplo que tolerem campos novos.

09Como funcionam os cabeçalhos Deprecation e Sunset?

Deprecation (RFC 9745) avisa que o recurso está depreciado, com uma data em formato de structured field; continua funcionando. Sunset (RFC 8594) informa a data em que deixa de responder. Acompanham Link com rel="deprecation", sunset e successor-version. Após a data, respondo 410 Gone com problem+json apontando a migração.

10Como saber se é seguro desligar uma versão antiga?

Pela telemetria: requisições por versão, endpoint e client_id. Só desligo quando o uso é zero ou os consumidores restantes foram contatados e deram prazo. Antes, comunico por vários canais, uso cabeçalhos, brownouts e, se necessário, prorrogo por escrito com data final.

11O que é um brownout e quando usá-lo?

Indisponibilidade curta e anunciada da versão antiga (minutos a poucas horas) que força consumidores distraídos a perceber que ela vai sumir. Uso quando os avisos passivos não bastaram, em janelas de baixo risco, sempre comunicadas e crescentes.

12O que um API gateway deve e não deve fazer?

Deve cuidar do transversal: autenticação, rate limit, roteamento por versão, TLS, logs, métricas e propagação de trace. Não deve conter regra de negócio, orquestração complexa nem ser a única camada de autorização. Precisa de alta disponibilidade e de configuração versionada como código.

13Qual a diferença entre inventário e catálogo de APIs?

Inventário é saber o que existe (inclusive APIs sombra descobertas pelo tráfego). Catálogo enriquece com contrato OpenAPI, dono, ciclo de vida, classificação de dados, SLA e consumidores. O ideal é alimentá-lo pelo pipeline e conferir com o tráfego real.

14Como manter consistência entre APIs de vários times sem travar a entrega?

Style guide curto, lint Spectral no CI, revisão de design sobre o contrato antes do código e catálogo com dono. Automatizo o mecânico e reservo revisão humana para risco alto. Governança federada com guardrails e SLA para a própria revisão.

15O que significa tratar a API como produto? Que métricas você acompanha?

Ter consumidores como clientes, dono, roadmap, documentação, sandbox, SLA e suporte. Métricas: consumidores ativos, ativação, time to first hello world, taxa de erro 4xx por consumidor, participação por versão e chamados de suporte. Elas orientam prioridades e a depreciação.

16Governança centralizada ou federada? Como evitar burocracia?

Federada com guardrails: padrões e ferramentas comuns, times donos responsáveis. Evito burocracia com templates e lint, revisão proporcional ao risco, SLA para a revisão, regras com justificativa e medição (tempo de revisão, conformidade, exceções). Cada "não" vem com um "faça assim".

17Um parceiro crítico não responde e a v1 precisa sair. O que você faz?

Confirmo o uso por log, escalo pelo comercial e pelo jurídico além do contato técnico, uso cabeçalhos nas respostas, faço brownouts anunciados, ofereço ponte ou prorrogação por escrito com data final e, no prazo, devolvo 410 com link de migração mantendo rollback por consumidor. Tudo documentado, com a cláusula contratual como base.

18Como impedir que breaking changes cheguem à produção sem querer?

Contrato OpenAPI como fonte de verdade e diff automático no CI (oasdiff, por exemplo) que falha o build; testes de contrato com consumidores (módulo 08); política escrita do que é breaking; revisão obrigatória quando o diff acusa quebra; e telemetria por versão para detectar o que escapou.
