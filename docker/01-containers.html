Containers e arquitetura

Container não é uma máquina virtual pequena: é um processo comum do Linux com visão restrita do sistema e limites de consumo. Este módulo mostra o que realmente existe por baixo (namespaces, cgroups, camadas), como o Docker se divide em peças (CLI, dockerd, containerd, runc), o que é o padrão OCI e como instalar e rodar os primeiros containers entendendo cada passo.

Ao final você saberá
  • Explicar que problema os containers resolvem e comparar container e VM em isolamento, segurança e desempenho.
  • Demonstrar no terminal que um container é um processo do host, listar seus namespaces e ler seus limites de cgroup (v1 e v2).
  • Desenhar a cadeia CLI, API, dockerd, containerd, shim e runc e dizer o que cada peça faz e o que a OCI padroniza.
  • Diferenciar Docker Engine de Docker Desktop (incluindo a regra de licença), saber como o Docker roda no Windows e no Mac e citar alternativas que falam OCI.
  • Instalar o Docker, rodar hello-world, nginx e postgres e descrever passo a passo o que acontece em um docker run.
1Básico

O problema que os containers resolvem

Todo time de software já ouviu (ou disse) "na minha máquina funciona". A aplicação depende de muito mais do que o código: versão do runtime (Python, JDK, Node), bibliotecas do sistema (OpenSSL, libpq), variáveis de ambiente, arquivos de configuração, fuso horário, locale. Quando cada ambiente (notebook de cada dev, homologação, produção) acumula essas coisas por instalação manual, os ambientes divergem, e a divergência aparece como bug que ninguém consegue reproduzir.

Como era antes

  • Instalar na mão no servidor: o servidor vira um "floco de neve", único e impossível de recriar com exatidão. Duas aplicações no mesmo servidor brigam por versões de biblioteca (a aplicação A precisa de Python 3.8, a B de 3.12).
  • Documento de instalação: desatualiza no dia seguinte. Onboarding de dev leva dias.
  • Uma VM por aplicação: resolve o conflito, mas custa um sistema operacional inteiro por aplicação (RAM, disco, patches, boot lento).

O que o container muda

A ideia central é empacotar a aplicação junto com tudo o que ela precisa do espaço de usuário (runtime, bibliotecas, arquivos) em uma imagem imutável e versionada, e executá-la de forma isolada. O que não vai no pacote é o kernel: ele é o da máquina hospedeira. O mesmo artefato (identificado por um digest) roda no notebook, no CI e em produção.

# dois runtimes incompatíveis lado a lado, sem instalar nada no sistema
docker run --rm python:3.8-slim python --version
docker run --rm python:3.12-slim python --version
Python 3.8.x
Python 3.12.x

O que o container não resolve

  • Estado: o que o container grava na própria camada some quando ele é removido. Bancos de dados exigem volumes (módulo 05).
  • Segredos e configuração: continuam sendo problema seu (módulos 07 e 09).
  • Segurança automática: isolamento por container é mais fraco que por VM (seção 2) e uma imagem com biblioteca vulnerável continua vulnerável.
  • Compatibilidade de kernel e de CPU: container Linux precisa de kernel Linux; imagem arm64 não roda em amd64 sem emulação.
Armadilha comum: "Docker" e "container" não são sinônimos

Containers são um recurso do kernel Linux (namespaces e cgroups) que existia antes do Docker (LXC, Solaris Zones, FreeBSD jails têm ideias parecidas). O Docker popularizou a experiência: imagem em camadas, Dockerfile, registry, CLI simples. Hoje o formato é padronizado pela OCI e outras ferramentas (Podman, containerd, CRI-O) executam as mesmas imagens.

Na entrevista

"Container empacota a aplicação com suas dependências em uma imagem imutável e a executa isolada, compartilhando o kernel do host. Resolve a divergência entre ambientes e dá um artefato único que passa por dev, CI e produção. Não substitui volumes para estado nem é fronteira de segurança forte."

Para gestores

O ganho gerencial é previsibilidade: menos "só acontece em produção", onboarding em horas e deploy como troca de versão de artefato. O custo é uma nova camada para operar (registry, scan de vulnerabilidades, orquestração, política de imagens). Cobre do time que a imagem de produção seja a mesma que passou nos testes, identificada por tag de versão ou digest, nunca reconstruída por ambiente.

2Básico

Container x máquina virtual

Uma VM virtualiza o hardware: um hypervisor (KVM, Hyper-V, VMware, Xen) apresenta CPU, memória e disco virtuais, e dentro dela roda um sistema operacional completo com kernel próprio. Um container não virtualiza hardware: ele é um processo do kernel do host, só que com isolamento e limites. Por isso não há boot de SO nem kernel duplicado.

A prova mais simples de que o kernel é compartilhado:

uname -r                          # kernel do host
docker run --rm alpine uname -r   # kernel "dentro" do container
6.8.0-45-generic
6.8.0-45-generic

Mesmo número, porque só existe um kernel. (No Docker Desktop do Windows e do Mac, "o host" é a VM Linux do Docker; a seção 6 explica.)

Implicações de segurança

O processo dentro do container conversa diretamente com o kernel do host por syscalls. Uma falha do kernel (escalada de privilégio, escape de namespace) afeta o host e todos os outros containers. Em uma VM, o invasor precisa antes escapar do hypervisor, uma superfície muito menor. O Docker reduz o risco com várias camadas, todas ativas por padrão ou facilmente ativáveis:

  • Capabilities reduzidas: o "root" do container recebe só um subconjunto das capabilities do Linux (sem CAP_SYS_ADMIN, por exemplo). --cap-drop ALL deixa o conjunto mínimo.
  • Perfil seccomp padrão: bloqueia dezenas de syscalls perigosas ou raramente necessárias.
  • AppArmor (Ubuntu/Debian) ou SELinux (RHEL/Fedora): perfil de acesso obrigatório aplicado ao container.
  • Usuário não-root (USER na imagem ou --user), sistema de arquivos somente leitura (--read-only), --security-opt no-new-privileges.
  • User namespace remap e modo rootless: o root do container passa a ser um usuário comum do host. Não é o padrão do Docker.
  • Runtimes com isolamento reforçado: gVisor (runsc, intercepta syscalls em espaço de usuário) e Kata Containers (cada container dentro de uma microVM) trocam desempenho por uma fronteira mais forte.
Armadilha comum: --privileged e o socket do Docker

docker run --privileged desliga quase todo o isolamento (todas as capabilities, acesso a dispositivos). Montar /var/run/docker.sock dentro de um container dá a ele controle total do daemon, ou seja, root no host. O mesmo vale para quem pertence ao grupo docker no host. Trate ambos como acesso root (laboratório na seção 9).

Implicações de desempenho

  • CPU e memória: praticamente nativas. O container é um processo; não há tradução de instruções.
  • Disco: o sistema de arquivos em camadas (overlay2) tem custo em escritas pequenas e em arquivos grandes alterados (copy-on-write). Banco de dados e cargas de I/O intenso devem usar volume, que escreve direto no sistema de arquivos do host.
  • Rede: a rede bridge padrão usa NAT e veth; há um pequeno custo. --network host elimina o NAT (só em Linux) à custa do isolamento de rede.
  • Windows e Mac: os containers rodam em uma VM; bind mounts de pastas do host atravessam a fronteira da VM e são bem mais lentos que no Linux.
  • Início: um container sobe em milissegundos a segundos, o que viabiliza escalar sob demanda e rodar testes com ambiente novo a cada execução.
Regra de bolso

Mesma organização, mesma confiança entre cargas: containers. Código de terceiros ou de clientes diferentes no mesmo host: VM, microVM ou ao menos gVisor/Kata. Na nuvem os dois se combinam: containers rodam dentro de VMs.

Na entrevista

"A VM virtualiza hardware e tem kernel próprio, então isola mais e roda outro SO. O container é um processo isolado por namespaces e limitado por cgroups sobre o kernel do host: é mais leve e rápido, mas o isolamento de segurança é mais fraco. Por isso carga hostil vai para VM ou microVM."

Para gestores

Em saúde, dados sensíveis (LGPD) pedem atenção ao isolamento: separar por nó ou por VM os workloads de sensibilidades diferentes é uma decisão de risco, não de tecnologia. Cobre do time: usuário não-root, sem --privileged, sem montar o socket do Docker, e imagens escaneadas. Economia de infraestrutura com containers é real, mas não deve vir às custas de misturar cargas de confiança diferente no mesmo kernel.

3Básico

O que é um container de verdade

Não existe uma "chamada de sistema container" no Linux. Um container é uma combinação de recursos do kernel aplicados a um processo:

IngredienteResponde aMecanismo
O que o processo enxergaprocessos, rede, mounts, hostname, IPC, usuáriosnamespaces
O que o processo pode consumirCPU, memória, I/O, número de processoscgroups
Qual sistema de arquivos ele vêa raiz / da imagemmount namespace + overlayfs (camadas) e pivot_root
O que ele pode fazeroperações privilegiadas e syscallscapabilities, seccomp, AppArmor/SELinux

Namespaces: o que o processo enxerga

Um namespace dá ao processo uma visão própria de um recurso global do kernel. Os processos são criados já dentro de novos namespaces com a syscall clone (ou unshare, que move o processo atual; setns entra em um namespace existente).

NamespaceFlagIsolaEfeito no container
pidCLONE_NEWPIDárvore de processoso processo principal é o PID 1; não vê processos do host
netCLONE_NEWNETinterfaces, rotas, portas, iptablestem eth0 e lo próprios; porta 80 do container não conflita com a do host
mntCLONE_NEWNStabela de montagensvê a raiz da imagem, não o disco do host
utsCLONE_NEWUTShostname e nome de domíniohostname próprio (o ID curto do container)
ipcCLONE_NEWIPCmemória compartilhada SysV e filas POSIXnão compartilha IPC com outros containers (salvo --ipc)
userCLONE_NEWUSERmapeamento de UIDs e GIDsnão é usado por padrão no Docker: UID 0 do container é UID 0 do host. Ativado em rootless e userns-remap
cgroupCLONE_NEWCGROUPraiz da hierarquia de cgroups visívelo container enxerga seu próprio cgroup como a raiz (padrão em cgroup v2)
timeCLONE_NEWTIMEoffsets de relógio monotônicoexiste a partir do kernel 5.6; o Docker não o usa por padrão

cgroups: o que o processo consome

Os control groups organizam processos em hierarquias e aplicam limites e contabilidade de recursos. Quando você roda --memory 512m --cpus 1.5, o Docker cria um cgroup para o container e grava esses números nos arquivos de controle. Se o processo ultrapassa o limite de memória, o kernel aciona o OOM killer dentro do cgroup e o processo morre com SIGKILL (código de saída 137, seção do módulo 02).

cgroup v1 (legado)cgroup v2 (atual)

stat -fc %T /sys/fs/cgroup/      # cgroup2fs = v2 ; tmpfs = v1
docker info --format '{{.CgroupVersion}} {{.CgroupDriver}}'
cgroup2fs
2 systemd

O cgroup driver diz quem gerencia a hierarquia: systemd (recomendado em distros com systemd; o container vira um scope, como docker-<id>.scope) ou cgroupfs (o Docker escreve direto). O kubelet e o runtime precisam usar o mesmo driver.

Sistema de arquivos em camadas

A imagem é uma pilha de camadas somente leitura. Na hora de executar, o storage driver (normalmente overlay2, baseado no OverlayFS do kernel) monta uma visão unificada: as camadas da imagem são os lowerdir, uma pasta vazia por container é o upperdir (a camada gravável) e o resultado é o merged, que vira a raiz / do container via pivot_root dentro do mount namespace. O módulo 02 detalha camadas e copy-on-write; aqui basta saber que cada container tem um sistema de arquivos próprio, montado a partir da imagem.

Regra de bolso

container = processo + namespaces + cgroups + raiz montada por overlay + restrições de privilégio. Se alguém perguntar "o que roda dentro do container", a resposta é: o processo roda no host, só enxerga menos.

Na entrevista

"Container é um processo do Linux com namespaces (pid, net, mnt, uts, ipc, user, cgroup) que limitam o que ele enxerga, cgroups que limitam o que ele consome e um sistema de arquivos em camadas. Dá para ver o processo com ps no host e os namespaces em /proc/<pid>/ns."

Para gestores

Entender isso muda decisões: limites de memória e CPU não são opcionais em produção (sem eles, um container ruim derruba o servidor); "container como root" é root do host com restrições; e monitorar container é monitorar processo e cgroup, não "uma máquina". Pergunte ao time quais limites cada serviço tem e por quê.

4Intermediário

Laboratório: vendo o container como processo

Todos os comandos abaixo supõem um host Linux com Docker Engine (VM, servidor ou WSL 2 com o Engine instalado). No Docker Desktop, o "host" é a VM interna, não o seu Windows ou Mac, e esses comandos de inspeção do host não funcionam diretamente. As saídas são exemplos: PIDs e números de namespace variam.

1. O processo do container aparece no ps do host

docker run -d --name web nginx:1.27
docker inspect -f '{{.State.Pid}}' web          # PID do processo principal, visto do host
ps -o pid,ppid,user,cmd -p 2123 --ppid 2123     # o processo e seus filhos
ps -o pid,ppid,cmd -p 2101                      # o pai do processo principal
2123
  PID  PPID USER     CMD
 2123  2101 root     nginx: master process nginx -g daemon off;
 2150  2123 101      nginx: worker process
  PID  PPID CMD
 2101     1 /usr/bin/containerd-shim-runc-v2 -namespace moby -id 9f3c... -address /run/containerd/containerd.sock

Observações: o processo mestre é filho do containerd-shim, não do dockerd; o worker aparece com UID numérico (101) porque o host não tem um usuário com esse UID; docker top web mostra a mesma informação sem sair do Docker. Dentro do container, o mesmo processo é o PID 1:

docker exec web cat /proc/1/cmdline | tr '\0' ' '
nginx: master process nginx -g daemon off;

sudo ls -l /proc/2123/ns/
sudo readlink /proc/2123/ns/pid /proc/self/ns/pid      # container x shell do host
sudo readlink /proc/2123/ns/user /proc/self/ns/user    # user ns: igual!

... ipc    -> 'ipc:[4026532597]'
... mnt    -> 'mnt:[4026532595]'

Cada link aponta para um namespace identificado por um inode. Dois processos estão no mesmo namespace quando os números coincidem: o pid do container é diferente do do host, mas o user é o mesmo (container root = root do host, como visto na seção 3). lsns lista todos os namespaces do sistema. Para entrar no namespace de rede do container com as ferramentas do host:

sudo nsenter -t 2123 -n ip -br addr
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0@if12        UP             172.17.0.2/16

É o que o docker exec faz por baixo (e como depurar redes em imagens sem ferramentas), usando setns para entrar nos namespaces do processo.

3. Fazendo "à mão" com unshare

O unshare (util-linux) cria um processo em novos namespaces, o mesmo que o runc faz, só que sem imagem e sem cgroups:

sudo unshare --pid --fork --mount-proc --uts --net bash
# agora, dentro do novo shell:
ps aux                  # só 2 processos: bash (PID 1) e o ps
hostname teste-ns       # muda o hostname só neste namespace
ip link                 # só "lo", e desligada
exit
hostname                # o hostname do host continua igual
USER  PID %CPU %MEM    VSZ   RSS TTY  STAT START TIME COMMAND
root    1  0.0  0.0  10156  5120 pts/0 S    10:02 0:00 bash
root    8  0.0  0.0  10584  3328 pts/0 R+   10:02 0:00 ps aux

--fork é necessário para o PID namespace (o novo PID 1 é o filho), e --mount-proc remonta o /proc para o ps enxergar só o novo namespace. Faltam: um sistema de arquivos próprio (o --root com um rootfs extraído de uma imagem) e limites de cgroup. Juntar os dois é, em essência, o runc.

4. Limites de cgroup

docker run -d --name lim --memory 256m --cpus 0.5 nginx:1.27
ID=$(docker inspect -f '{{.Id}}' lim)

# cgroup v2 com driver systemd:
cat /sys/fs/cgroup/system.slice/docker-$ID.scope/memory.max
cat /sys/fs/cgroup/system.slice/docker-$ID.scope/cpu.max
cat /sys/fs/cgroup/system.slice/docker-$ID.scope/pids.max

# e de dentro do container (cgroup namespace: o cgroup dele é a raiz)
docker exec lim cat /sys/fs/cgroup/memory.max
268435456
50000 100000
max
268435456

256 MiB = 268435456 bytes. cpu.max é "quota período em microssegundos": 50000 de cada 100000 = meio núcleo. pids.max é max porque não foi definido --pids-limit. No cgroup v1 os caminhos seriam /sys/fs/cgroup/memory/docker/<id>/memory.limit_in_bytes e /sys/fs/cgroup/cpu/docker/<id>/cpu.cfs_quota_us. Com o driver cgroupfs no v2, o caminho é /sys/fs/cgroup/docker/<id>/. docker stats --no-stream mostra o consumo contra o limite.

5. A raiz do container é um mount overlay

docker inspect -f '{{json .GraphDriver.Data}}' web
docker exec web touch /criado-dentro
sudo ls "$(docker inspect -f '{{.GraphDriver.Data.UpperDir}}' web)"
{"LowerDir":"/var/lib/docker/overlay2/ab12...-init/diff:/var/lib/docker/overlay2/9c3f.../diff:...",
 "MergedDir":"/var/lib/docker/overlay2/ab12.../merged",
 "UpperDir":"/var/lib/docker/overlay2/ab12.../diff",
 "WorkDir":"/var/lib/docker/overlay2/ab12.../work"}
criado-dentro  etc  run  var  ...

O arquivo criado dentro do container está no UpperDir (a camada gravável do container); as camadas da imagem (LowerDir) não mudaram. Se o Docker usar o containerd image store em vez do graphdriver clássico, os campos e caminhos diferem: confira em docker info.

docker rm -f web lim      # limpar o laboratório
Armadilha comum: testar no Docker Desktop e achar que o host é o seu PC

No Windows e no Mac, ps, /proc e /sys/fs/cgroup da sua máquina não mostram os containers. Eles vivem na VM Linux do Docker. Para os laboratórios desta seção, use uma máquina Linux ou o Engine instalado em uma distro WSL 2.

Na entrevista

"Mostro que é processo: docker inspect -f '{{.State.Pid}}' dá o PID no host, o ps do host o enxerga, /proc/<pid>/ns mostra os namespaces e memory.max no cgroup mostra o limite. Com unshare eu reproduzo o isolamento sem Docker."

Para gestores

Esse conhecimento é o que separa quem usa Docker de quem consegue diagnosticar incidentes: "o container foi morto por OOM", "o cgroup limitou a CPU (throttling)", "a porta está presa em outro namespace de rede". Em revisões de incidente, peça evidências nesse nível (exit code, OOMKilled, docker stats), não "reiniciamos e voltou".

5Intermediário

Arquitetura do Docker e padrões OCI

O comando docker não cria containers. Ele é só um cliente HTTP. O trabalho passa por uma cadeia de componentes, cada um com uma responsabilidade, e essa separação existe para que partes possam ser trocadas (o Kubernetes usa containerd sem o dockerd, por exemplo) e para que reiniciar o daemon não derrube os containers.

ComponenteResponsabilidadeDetalhes úteis
docker (CLI)interpreta comandos e chama a API do daemonpode apontar para outro daemon: DOCKER_HOST ou docker context. Plugins: buildx, compose
dockerdAPI REST, imagens, build (BuildKit), redes, volumes, logs, pluginsescuta no socket Unix /var/run/docker.sock; configuração em /etc/docker/daemon.json
containerdbaixa e armazena imagens (em muitas instalações), gerencia snapshots e o ciclo de vida dos containersprojeto da CNCF; usado direto pelo Kubernetes; API gRPC
containerd-shim-runc-v2fica como processo pai de cada container; mantém stdio, repassa sinais e coleta o código de saídapermite reiniciar dockerd/containerd sem matar containers (com live-restore no dockerd)
runcruntime de baixo nível: cria namespaces e cgroups, configura rootfs, capabilities e seccomp e faz exec do processoimplementação de referência da runtime-spec da OCI; é um executável que roda e sai
Registryarmazena e distribui imagensDocker Hub, GHCR, ECR, ACR, Harbor, GitLab Registry (módulo 08)

O dockerd usa componentes auxiliares: o docker-proxy (para publicação de portas, em alguns casos), o libnetwork (redes bridge, overlay, macvlan) e regras de iptables/nftables (NAT e filtragem). O runtime pode ser trocado por container com --runtime (por exemplo runsc do gVisor, crun ou os runtimes do Kata), desde que falem a runtime-spec.

Padrões OCI

A Open Container Initiative (Linux Foundation) define três especificações. Graças a elas, uma imagem construída com Docker roda no Podman, no containerd e no Kubernetes, e qualquer registry compatível a distribui.

EspecificaçãoDefineNa prática
image-specformato da imagem: manifest, config (JSON) e camadas (tar compactado), todos endereçados por digest; index para várias arquiteturaso que docker build produz e docker push envia
runtime-speccomo executar um bundle: um config.json (processo, mounts, namespaces, cgroups, capabilities) e um diretório rootfso que o runc consome
distribution-specAPI HTTP de registries para enviar e baixar manifests e blobspor que docker pull, skopeo e crane conversam com o mesmo registry

      { "type": "uts" }, { "type": "mount" }, { "type": "cgroup" }
    ],
    "resources": { "memory": { "limit": 268435456 } }
  }
}

Repare como cada campo corresponde ao que foi visto na seção 3: lista de namespaces, limites de cgroup, usuário, capabilities e a raiz. Tudo o que o Docker faz em docker run converge para gerar esse arquivo.

Armadilha comum: expor o daemon sem proteção

O socket do Docker é uma API de administração do host. Expor o daemon em TCP (-H tcp://0.0.0.0:2375) sem TLS e autenticação equivale a dar root a qualquer um na rede; é uma causa clássica de invasão e mineração de criptomoeda. Para acesso remoto, use docker context com SSH (ssh://usuario@host) ou TLS mútuo.

Na entrevista

"A CLI fala com o dockerd por uma API REST no socket Unix. O dockerd cuida de imagens, rede, volumes e build, e delega o ciclo de vida ao containerd. O containerd sobe um shim por container, e o shim chama o runc, que cria namespaces e cgroups, executa o processo e sai. A OCI padroniza imagem, runtime e distribuição, e por isso as peças são intercambiáveis."

Para gestores

A arquitetura em camadas tem consequências operacionais: o dockerd roda como root e é um ponto único de falha e de ataque; atualizar o Docker em um servidor pode reiniciar containers (a menos que live-restore esteja ativo). Defina quem tem acesso ao socket, como ele é auditado e se rootless faz sentido para o seu ambiente. Padronizar em OCI evita aprisionamento em um fornecedor.

A licença do Docker Desktop

O Docker Desktop é gratuito para uso pessoal, educação, projetos de código aberto não comerciais e para pequenas empresas, definidas pela documentação do Docker como menos de 250 funcionários e menos de US$ 10 milhões de receita anual. Qualquer empresa que passe de um dos dois limites precisa de uma assinatura paga (planos Pro, Team ou Business) para uso comercial do Desktop. Como a condição é "e" para a isenção, basta uma empresa ter mais de 250 funcionários ou mais de US$ 10 milhões para exigir licença (subsidiárias contam pela empresa-mãe).

  • A regra vale para o Docker Desktop. O Docker Engine (Linux), a CLI e o Compose como software livre não exigem assinatura.
  • O Docker Hub tem termos e limites de uso próprios (por exemplo, limites de pull para usuários anônimos), independentes da licença do Desktop.
  • Os valores e planos mudam com o tempo. Antes de padronizar, confirme no site oficial (página de licença do Docker Desktop em docs.docker.com e a FAQ de preços) e envolva o jurídico.

Docker no Windows: WSL 2

Containers Linux precisam de kernel Linux, e o Windows não tem um. O Docker Desktop resolve criando uma VM Linux leve. O backend recomendado é o WSL 2 (Windows Subsystem for Linux), que roda um kernel Linux real sob um hypervisor leve do Windows, e o Docker Desktop instala nele uma distribuição interna ("docker-desktop") com o Engine. A CLI do Windows fala com esse daemon. Existe ainda o backend Hyper-V (legado) e o modo de Windows containers (outra coisa).

  • Desempenho: deixe o código do projeto dentro do sistema de arquivos do WSL (~/projetos), não em /mnt/c/.... Bind mounts do disco do Windows são muito mais lentos.
  • Memória: a VM do WSL 2 pode consumir muita RAM. Limite no arquivo %UserProfile%\.wslconfig, seção [wsl2], com chaves como memory, processors e swap, e depois rode wsl --shutdown.
  • Alternativa sem Desktop: instalar o Docker Engine dentro de uma distro WSL 2 (Ubuntu) com systemd ativado, exatamente como em um servidor Linux, e usar a CLI de lá.

Docker no macOS

O macOS também não tem kernel Linux: o Desktop executa uma VM Linux leve usando a virtualização do próprio sistema, e os containers rodam dentro dela. Pontos de atenção: em Macs com Apple Silicon (arm64) as imagens nativas são linux/arm64; imagens só amd64 rodam por emulação (Rosetta ou QEMU, conforme a configuração), mais lentas e às vezes com bugs. O --platform linux/amd64 força a arquitetura. O compartilhamento de arquivos entre Mac e VM também tem custo de desempenho.

Armadilha comum: "funciona no Docker Desktop, falha no servidor" (e vice-versa)

Diferenças típicas: arquitetura de CPU (arm64 no Mac, amd64 no servidor), permissões de arquivos em bind mounts (no Desktop o compartilhamento mascara UIDs), fim de linha, DNS e proxy corporativo, e o fato de que no Desktop a porta de um container fica acessível em localhost por um encaminhamento próprio. Teste a imagem final no mesmo tipo de ambiente da produção (CI em Linux).

Na entrevista

"Engine é o daemon e a CLI para Linux, de código aberto. Desktop é o aplicativo para Windows, Mac e Linux que embute uma VM com o Engine e tem licença paga para empresas com mais de 250 funcionários ou mais de US$ 10 milhões de receita. No Windows ele usa WSL 2, no Mac uma VM leve."

Para gestores

Licença é risco de conformidade. Se a empresa passa dos limites, cada desenvolvedor que usa o Docker Desktop comercialmente precisa de assinatura, e as auditorias existem. Opções: assinar (ganha SSO, gestão de configurações e suporte), ou padronizar uma alternativa sem custo de licença (Docker Engine em WSL 2, Rancher Desktop, Podman Desktop, Colima). Decida junto com TI e jurídico, e documente o padrão para o time, em vez de cada um instalar o que quiser.

Primeiro container: hello-world

docker run hello-world
Unable to find image 'hello-world:latest' locally
latest: Pulling from library/hello-world
c1ec31eb5944: Pull complete
Digest: sha256:...
Status: Downloaded newer image for hello-world:latest

Hello from Docker!
This message shows that your installation appears to be working correctly.
...

A imagem tem um único programa que imprime a mensagem e sai. O container vive o tempo que o processo principal viver. Ele terminou, mas ainda existe (docker ps -a mostra com status Exited (0)); a imagem fica no cache local.

O que acontece em um docker run

  1. A CLI monta o pedido. Lê as flags (-d, -p, -e, -v...), resolve o nome da imagem (hello-world vira docker.io/library/hello-world:latest) e envia a criação ao dockerd.
  2. O daemon procura a imagem localmente. Se não existe, faz o pull: pergunta ao registry o manifest da tag (se for um index multi-arquitetura, escolhe a variante da sua CPU), baixa o config e as camadas em paralelo, verifica o sha256 de cada uma e as descompacta no storage. É a saída "Pull complete".
  3. Create. O daemon combina a configuração da imagem (CMD, ENV, portas) com suas flags, cria a camada gravável (upperdir), aloca a rede (namespace de rede, par veth, IP na bridge) e deixa o container no estado created. Nenhum processo roda ainda.
  4. Start. O dockerd pede ao containerd, que sobe o shim, que chama o runc com o bundle: o runc cria os namespaces e cgroups, monta a raiz, aplica capabilities e seccomp, faz o exec do processo principal e sai. O estado vira running.
  5. Execução e saída. A CLI anexa stdout/stderr (a menos que seja -d). Quando o processo principal termina, o shim registra o código de saída e o estado vira exited. Com --rm, o container é removido em seguida.

Você pode assistir a esses eventos em outro terminal com docker events.

nginx: um servidor que fica no ar

docker run -d --name web -p 8080:80 nginx:1.27
docker ps
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080

docker stop web && docker rm web

Diferente do hello-world, o processo principal (nginx em primeiro plano) não termina, então o container fica Up. O -p 8080:80 publica a porta 80 do container na 8080 do host. Os logs são a saída do processo (stdout/stderr), por isso aplicações em container devem logar na saída padrão.

postgres: configuração por variável e dados em volume

docker run -d --name pg \
  -e POSTGRES_PASSWORD=senha_de_laboratorio \
  -p 127.0.0.1:5432:5432 \
  -v pgdata:/var/lib/postgresql/data \
  postgres:17

docker logs pg | tail -3
docker exec -it pg psql -U postgres -c 'select version();'
LOG:  database system is ready to accept connections
                  version
------------------------------------------
 PostgreSQL 17.x on x86_64-pc-linux-gnu, ...
  • A imagem oficial exige POSTGRES_PASSWORD na primeira inicialização. Sem ela o container sai na hora, e o docker logs explica que o banco não foi inicializado por falta de senha de superusuário.
  • -v pgdata:/var/lib/postgresql/data usa um volume nomeado: os dados sobrevivem a docker rm pg. Sem volume, a camada gravável é apagada junto com o container e o banco volta vazio. O caminho de montagem depende da versão da imagem (nas versões mais novas da imagem oficial a documentação recomenda montar em /var/lib/postgresql); confira a página da imagem no Docker Hub.
  • A tag postgres:17 fixa a versão principal. Nunca use latest em banco de dados: uma atualização de versão principal exige migração de dados.
Armadilha comum: -p 5432:5432 expõe o banco na rede inteira

Sem informar um endereço, -p publica em 0.0.0.0 (todas as interfaces). O Docker insere suas próprias regras de firewall e pode contornar o ufw/firewalld que você configurou. Para desenvolvimento, publique só no loopback (-p 127.0.0.1:5432:5432); entre containers, nem publique: use uma rede (módulo 05).

Na entrevista

"No docker run: a CLI chama a API; se a imagem não existe localmente o daemon faz pull (manifest, config e camadas por digest); depois cria o container (camada gravável, rede) e inicia pelo containerd, shim e runc. O container vive enquanto o processo principal viver."

Para gestores

Padronize o ambiente de dev em um comando (docker compose up, módulo 06) em vez de um manual de instalação. Defina regras mínimas já no primeiro dia: versões de imagem fixas (nada de latest), portas só em localhost, senhas fora do repositório e volumes para tudo que precisa persistir. Esses hábitos nascem nos primeiros containers que o time roda.

Exercícios

Laboratórios para fazer em um host Linux (ou WSL 2 com o Engine), de preferência uma VM descartável. Tente antes de abrir a resolução.

E1Suba um nginx e mapeie o container no host: PID, processo pai, usuário dos workers e namespaces. Qual namespace é igual ao do host?
docker run -d --name e1 nginx:1.27
PID=$(docker inspect -f '{{.State.Pid}}' e1)
ps -o pid,ppid,user,cmd -p $PID --ppid $PID
ps -o pid,cmd -p $(ps -o ppid= -p $PID)         # o shim
for ns in pid net mnt uts ipc user cgroup; do
  printf '%-7s' $ns; sudo readlink /proc/$PID/ns/$ns | tr '\n' ' '
  sudo readlink /proc/self/ns/$ns
done

O pai do processo mestre é o containerd-shim-runc-v2. Os namespaces pid, net, mnt, uts, ipc, cgroup têm números diferentes dos do host. O user é igual, porque o Docker não usa user namespace por padrão: o UID 0 do container é o UID 0 do host. Limpe com docker rm -f e1.

E2Rode um container com --memory 128m --cpus 0.25 --pids-limit 50 e prove os três limites lendo os arquivos do cgroup (host e container).
docker run -d --name e2 --memory 128m --cpus 0.25 --pids-limit 50 nginx:1.27
ID=$(docker inspect -f '{{.Id}}' e2)
D=/sys/fs/cgroup/system.slice/docker-$ID.scope
cat $D/memory.max $D/cpu.max $D/pids.max
docker exec e2 cat /sys/fs/cgroup/memory.max

Esperado (cgroup v2, driver systemd): 134217728, 25000 100000 e 50; dentro do container, 134217728. Se stat -fc %T /sys/fs/cgroup disser tmpfs, é cgroup v1: os arquivos são memory/docker/<id>/memory.limit_in_bytes, cpu/docker/<id>/cpu.cfs_quota_us (25000) e pids/docker/<id>/pids.max. Se o caminho não existir, o driver é cgroupfs (/sys/fs/cgroup/docker/<id>/). Confira com docker info --format '{{.CgroupDriver}}'.

E3Crie um "pseudo-container" com unshare (PID, UTS e rede) e verifique o que mudou. O que ainda falta para ser um container de verdade?
sudo unshare --pid --fork --mount-proc --uts --net bash
ps aux; hostname novo; ip link; exit
hostname

Dentro: o bash é PID 1, só há lo (desligada) e o hostname mudado não vaza para o host. Faltam: (1) um sistema de arquivos raiz próprio (extrair o rootfs de uma imagem e usar --root ou pivot_root), (2) limites de cgroup, (3) redução de capabilities, seccomp e LSM, (4) rede conectada (par veth com o host). Juntar tudo e ler um config.json é o que o runc faz.

E4Mostre que o kernel é compartilhado e que o "SO" do container é só a userland: rode alpine e ubuntu e compare uname -r e /etc/os-release com os do host.
uname -r
for img in alpine:3.20 ubuntu:24.04; do
  echo "== $img"; docker run --rm $img sh -c 'uname -r; . /etc/os-release; echo $PRETTY_NAME'
done

O uname -r é idêntico ao do host nas duas imagens; o PRETTY_NAME muda (Alpine, Ubuntu), porque o que a imagem traz são binários e bibliotecas, não kernel. Corolário: uma imagem que dependa de um recurso de kernel (módulo, sysctl, eBPF) depende do kernel do host.

E5(Segurança) Mostre por que o grupo docker equivale a root, usando um usuário comum com acesso ao Docker. Só faça em uma VM de laboratório.
id                                    # usuário comum, no grupo docker
docker run --rm -v /:/host alpine ls -l /host/etc/shadow
docker run --rm -v /:/host alpine sh -c 'echo "preso no host" > /host/root/prova.txt'
sudo cat /root/prova.txt              # confirma a escrita em /root do host
sudo rm /root/prova.txt

O usuário comum leu um arquivo reservado ao root e escreveu em /root, porque dentro do container ele é root (UID 0, sem user namespace) com o disco do host montado. Mitigações: modo rootless, userns-remap, controle estrito de quem está no grupo, e nunca montar /var/run/docker.sock ou / em containers de aplicação.

Cenários práticos de trabalho

Cenário 1: "funciona na minha máquina, falha em homologação"

O time usa Docker, mas o erro só aparece em homologação: uma biblioteca com comportamento diferente.

O que fazer: verificar se as duas pontas rodam a mesma imagem: comparar o digest (docker image inspect --format '{{.Id}}' api:1.4.2 e docker inspect --format '{{.Image}}' <container> em cada ambiente). Provável causa: homologação reconstruiu a imagem a partir do código, ou uma tag mutável (latest, 1.4) aponta para versões diferentes. Corrigir o processo: o CI constrói uma vez, publica a imagem com tag de versão/SHA e cada ambiente apenas a executa. Se as imagens forem iguais, o problema está na configuração (variáveis, volumes, rede, limites), e a comparação de docker inspect entre os dois mostra a diferença.

Cenário 2: o notebook do time no Windows está lento e sem memória

Devs reclamam que, com Docker Desktop, o notebook trava, o hot reload demora e o consumo de RAM (processo vmmem) passa de 8 GB.

O que fazer: (1) mover os repositórios para dentro do sistema de arquivos do WSL (~/projetos) e abrir o editor com a integração WSL, em vez de usar /mnt/c; (2) limitar a VM em .wslconfig (memory, processors) e executar wsl --shutdown; (3) subir só os serviços necessários e definir limites de memória no Compose; (4) revisar imagens pesadas e processos que ficam rodando. Documente o padrão para o time.

Cenário 3: pedido de 40 licenças e dúvida sobre o Docker Desktop

A empresa de saúde tem mais de 250 funcionários e os devs usam Docker Desktop sem assinatura. O financeiro pergunta se é preciso pagar.

O que fazer: verificar o enquadramento no texto oficial (menos de 250 funcionários e menos de US$ 10 milhões para a isenção; acima de qualquer um dos limites, assinatura para uso comercial) com o jurídico; levantar quem usa de fato o Desktop (Windows/Mac) e quem só usa Engine em Linux; comparar o custo de assinar (SSO, gestão central, suporte, Scout) com o de padronizar uma alternativa (Docker Engine em WSL 2, Rancher Desktop, Podman Desktop) incluindo o custo de suporte interno; decidir, registrar e comunicar um padrão único. Não deixe a decisão implícita.

Cenário 4: um parceiro quer rodar código dele na nossa plataforma

Uma parceira de laboratório pede para executar scripts de análise próprios na infraestrutura, em containers, no mesmo cluster dos serviços com dados de pacientes.

O que fazer: reconhecer que é código não confiável em um kernel compartilhado: um escape de container chegaria aos dados dos pacientes. Opções em ordem crescente de isolamento: pool de nós dedicado e isolado por rede (NetworkPolicy), sandbox de kernel (gVisor), microVM (Kata/Firecracker) ou VMs separadas; usuário não-root, sem --privileged, limites de CPU e memória, sistema de arquivos somente leitura, sem acesso à rede interna. Levar o desenho à segurança e ao encarregado de dados antes de começar.

Glossário

Container
Processo Linux isolado por namespaces, limitado por cgroups e com raiz própria vinda de uma imagem.
Imagem
Pacote imutável em camadas (sistema de arquivos + metadados) usado para criar containers.
Namespace
Recurso do kernel que dá ao processo uma visão própria de um recurso global (processos, rede, mounts...).
cgroup
Grupo de controle: limita e contabiliza CPU, memória, I/O e processos de um conjunto de processos.
overlayfs / overlay2
Sistema de arquivos que empilha diretórios; base do armazenamento em camadas do Docker.
dockerd
Daemon do Docker: API, imagens, redes, volumes e build; delega a execução ao containerd.
containerd
Runtime de alto nível (CNCF) que gerencia imagens e ciclo de vida de containers; usado também pelo Kubernetes.
shim
Processo que fica como pai do container (containerd-shim-runc-v2), mantém stdio e relata o código de saída.
runc
Runtime de baixo nível que cria namespaces e cgroups e inicia o processo; implementa a runtime-spec da OCI.
OCI
Open Container Initiative: define image-spec, runtime-spec e distribution-spec.
Registry
Servidor que armazena e distribui imagens (Docker Hub, GHCR, ECR, Harbor).
WSL 2
Subsistema do Windows para Linux com kernel Linux real em VM leve; backend padrão do Docker Desktop no Windows.
Rootless
Modo em que o daemon e os containers rodam sem privilégios de root no host, usando user namespaces.
Capabilities
Divisão dos poderes do root em permissões individuais (CAP_NET_ADMIN, CAP_SYS_ADMIN...); containers recebem só um subconjunto.
12Intermediário

Perguntas de entrevista

Responda em voz alta antes de abrir. Boa resposta: uma frase de definição, o mecanismo e um exemplo ou consequência prática.

01O que é um container?

Um processo do Linux executado de forma isolada: namespaces limitam o que ele enxerga (processos, rede, mounts, hostname, IPC, usuários), cgroups limitam o que consome e uma raiz montada a partir de uma imagem dá o sistema de arquivos. Não há SO próprio; o kernel é o do host.

02Qual a diferença entre container e máquina virtual?

A VM virtualiza hardware e roda um SO completo com kernel próprio sobre um hypervisor: isola mais, pesa mais e pode rodar outro SO. O container compartilha o kernel do host: é mais leve, mais denso e inicia em segundos, mas a superfície de ataque é maior (todas as syscalls). Em nuvem, usam-se juntos: containers dentro de VMs.

03Qual problema o Docker resolve?

A divergência entre ambientes. A imagem empacota aplicação e dependências, então o mesmo artefato roda no notebook, no CI e em produção. Também acelera onboarding, isola versões conflitantes e simplifica deploy e rollback (trocar a tag).

04Como provar que um container é só um processo do host?

docker inspect -f '{{.State.Pid}}' dá o PID no host; ps o mostra (filho do containerd-shim); /proc/<pid>/ns/ lista os namespaces; cat /sys/fs/cgroup/.../memory.max mostra o limite. Dentro, o mesmo processo é o PID 1.

05Quais namespaces o Docker usa?

pid, net, mnt, uts, ipc e cgroup por padrão. O user namespace não é usado por padrão (UID 0 do container é UID 0 do host); só com rootless ou userns-remap. O namespace de tempo existe no kernel desde o 5.6, mas não é usado por padrão.

06O que são cgroups e o que muda entre v1 e v2?

Mecanismo do kernel para limitar e contabilizar recursos de grupos de processos. Na v1, cada controlador tem sua própria árvore; na v2 há uma hierarquia unificada, com arquivos como memory.max, cpu.max e pids.max, melhor contabilidade de I/O e PSI. As distribuições recentes usam v2 por padrão, e o Docker a suporta desde a 20.10.

07O que acontece quando o container ultrapassa o limite de memória?

O OOM killer do cgroup mata um processo do container (SIGKILL). Se for o principal, o container sai com código 137 e docker inspect mostra OOMKilled: true. Soluções: achar o vazamento ou aumentar o limite. Sem limite, o processo pode esgotar a memória do host.

08Descreva a arquitetura do Docker.

A CLI envia requisições REST ao dockerd (socket Unix). O dockerd gerencia imagens, redes, volumes e build, e delega ao containerd. O containerd cria um containerd-shim por container, e o shim executa o runc, que cria namespaces e cgroups, inicia o processo e sai. O shim permanece como pai, mantém stdio e coleta o exit code. As imagens vêm de um registry.

09O que é a OCI e o que ela padroniza?

Open Container Initiative, sob a Linux Foundation. Define a image-spec (manifest, config, camadas por digest), a runtime-spec (bundle com config.json e rootfs, que o runc executa) e a distribution-spec (API de registries). Por isso imagens e runtimes de ferramentas diferentes são intercambiáveis.

10Docker Engine x Docker Desktop? E a licença?

Engine é o daemon e a CLI para Linux, código aberto. Desktop é um aplicativo para Windows, Mac e Linux que embute uma VM com o Engine, mais Compose, interface e extras. O Desktop exige assinatura paga para uso comercial em empresas com 250 ou mais funcionários ou mais de US$ 10 milhões de receita anual; menores, uso pessoal, educação e open source não comercial são gratuitos. Convém confirmar o texto atual no site do Docker.

11Como o Docker roda no Windows e no Mac, se containers precisam de kernel Linux?

Dentro de uma VM Linux leve: no Windows, o backend WSL 2 (kernel Linux real em hypervisor leve); no Mac, uma VM gerenciada pelo Desktop. A CLI no sistema hospedeiro fala com o daemon da VM. Consequências: bind mounts de pastas do host são mais lentos, a VM consome RAM e, no Apple Silicon, imagens amd64 rodam por emulação.

12Que alternativas ao Docker existem?

Podman (sem daemon, rootless por padrão, CLI compatível), containerd com nerdctl, CRI-O (runtime só para Kubernetes), Buildah e Skopeo para build e transferência de imagens, e Desktops alternativos (Rancher Desktop, Colima). Todos executam imagens OCI. O Kubernetes usa containerd ou CRI-O desde a remoção do dockershim na 1.24.

13Descreva o que acontece quando você executa docker run nginx.

A CLI chama a API; o dockerd verifica a imagem local; se não existe, faz pull (resolve a tag, baixa manifest, config e camadas, valida sha256); cria o container (camada gravável, rede, configuração mesclada); o containerd, via shim e runc, cria namespaces e cgroups e executa o processo do nginx. O container fica running enquanto o processo viver e a CLI anexa a saída.

14Por que o grupo docker é considerado equivalente a root?

Quem fala com o daemon pode criar um container como root (UID 0, sem user namespace) montando o / do host e ler ou alterar qualquer arquivo, ou usar --privileged. O mesmo vale para montar o docker.sock em um container. Mitigações: rootless, userns-remap, sudo restrito e auditado, e nunca expor o socket.

15Containers são seguros o suficiente para isolar clientes diferentes no mesmo host?

Não como única barreira. O kernel é compartilhado e uma vulnerabilidade de kernel permite escapar. Para multi-tenant com código não confiável, use VMs, microVMs (Kata/Firecracker) ou sandbox como gVisor, além de nós dedicados, rede segmentada, usuários não-root, capabilities mínimas e limites de recursos. Para carga de confiança igual, containers com as boas práticas bastam.

16Como você apresentaria ao time e à diretoria a adoção de containers? Quais riscos destacaria?

Benefícios: ambientes reprodutíveis, onboarding e deploy mais rápidos, melhor uso da infraestrutura e caminho para orquestração. Riscos e decisões: licença do Docker Desktop, segurança (imagens escaneadas, não-root, acesso ao socket, isolamento de dados sensíveis, LGPD), persistência de dados (volumes, backup), limites de recursos, observabilidade de logs e métricas, governança de imagens (registry, tags fixas, atualizações). Propor um piloto em um serviço de baixo risco, com padrões de Dockerfile e checklist de revisão, antes de generalizar.

17Um container Linux roda no seu Mac e dá erro "exec format error" no servidor. Por quê?

Arquitetura de CPU diferente: a imagem foi construída em arm64 (Apple Silicon) e o servidor é amd64, ou o contrário. Solução: construir para a plataforma de destino (docker buildx build --platform linux/amd64) ou publicar uma imagem multi-arquitetura (manifest list/index), e fazer o build final no CI em Linux. Outra causa de erro parecido: script de entrypoint com fim de linha CRLF. Detalhes de multi-arquitetura estão no módulo 02.
