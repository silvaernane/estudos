Do container ao Compose com várias imagens

O que você precisa saber de Docker para trabalhar no dia a dia e responder bem numa entrevista: como containers funcionam, como escrever Dockerfiles enxutos, como ligar vários serviços com Compose e o que fazer quando algo dá errado.

01Fundamentos

O que é um container

Um container é um processo comum do Linux rodando isolado: ele enxerga só o próprio sistema de arquivos, a própria rede e os próprios processos, e tem limites de CPU e memória. Não há um sistema operacional inteiro dentro dele. O kernel é o da máquina hospedeira.

Esse isolamento vem de dois recursos do kernel Linux:

  • Namespaces isolam o que o processo enxerga: PID (processos), NET (interfaces de rede), MNT (sistema de arquivos), UTS (hostname), IPC e USER (usuários).
  • cgroups limitam o que o processo consome: memória, CPU, I/O, número de processos.

No Windows e no macOS, o Docker Desktop roda uma VM Linux leve por baixo (WSL 2 no Windows), e os containers rodam dentro dela.

Que problema o Docker resolve

  • "Na minha máquina funciona": a imagem empacota a aplicação com suas dependências exatas. O mesmo artefato roda no notebook, no CI e em produção.
  • Ambiente de desenvolvimento rápido: subir Postgres, Redis e a API com um comando, sem instalar nada no sistema.
  • Densidade: muitos containers por servidor, porque não há um SO por aplicação.
  • Base para orquestração: Kubernetes, ECS e afins agendam containers.
Na entrevista

"Container é um processo isolado com namespaces e limitado com cgroups, que compartilha o kernel do host. A VM virtualiza o hardware e roda um SO inteiro. Container é mais leve e mais rápido; a VM isola mais."

02Fundamentos

Arquitetura do Docker

  • Docker CLI (docker): o cliente. Só envia pedidos por API REST.
  • Docker daemon (dockerd): recebe os pedidos e gerencia imagens, redes e volumes.
  • containerd: gerencia o ciclo de vida dos containers. O Kubernetes também o usa diretamente.
  • runc: o runtime de baixo nível que de fato cria namespaces e cgroups e inicia o processo.
  • Registry: onde as imagens ficam guardadas (Docker Hub, GitHub Container Registry, Amazon ECR, Harbor...).

Fluxo de um docker run nginx: o CLI pede ao daemon; se a imagem não estiver no cache local, o daemon faz pull do registry; containerd prepara o container; runc o inicia.

O formato de imagem e o runtime seguem os padrões da OCI (Open Container Initiative). Por isso uma imagem construída com Docker roda no Podman, no containerd e no Kubernetes.

Imagem x container

A imagem é um modelo somente-leitura: sistema de arquivos em camadas + metadados (comando padrão, variáveis, porta). O container é uma instância em execução da imagem, com uma camada gravável por cima e configuração própria (nome, rede, volumes). A relação é parecida com a de classe e objeto: uma imagem, vários containers.

Na entrevista

"Imagem é o pacote imutável; container é a imagem em execução, com uma camada gravável própria. Apagar o container apaga essa camada, por isso dados que precisam durar vão para volumes."

03Fundamentos

Imagens e camadas

Uma imagem é uma pilha de camadas somente-leitura. Cada instrução do Dockerfile que altera arquivos (RUN, COPY, ADD) cria uma camada. O driver de armazenamento (normalmente overlay2) empilha as camadas e mostra ao container um sistema de arquivos único.

  • Copy-on-write: quando o container altera um arquivo de uma camada inferior, o arquivo é copiado para a camada gravável e alterado lá. As camadas de baixo nunca mudam.
  • Compartilhamento: dez containers da mesma imagem ocupam o espaço da imagem uma vez, mais dez camadas graváveis pequenas. Imagens com a mesma base compartilham essa base.
  • Apagar numa camada posterior não diminui a imagem: se uma camada baixa 500 MB e a seguinte apaga os arquivos, os 500 MB continuam na imagem, apenas escondidos. Limpe na mesma instrução RUN que gerou os arquivos, ou use multi-stage (capítulo 7).

Nomes, tags e digests

registry.exemplo.com/equipe/api:1.4.2
└──── registry ────┘ └ repositório ┘ └ tag ┘

docker pull nginx                 # = docker.io/library/nginx:latest
docker pull nginx:1.27-alpine     # tag específica
docker pull nginx@sha256:3f1a...  # digest: aponta para um conteúdo exato
  • Tag é mutável: nginx:1.27 pode apontar para outra imagem amanhã (correção de segurança, por exemplo).
  • Digest é imutável: o hash do conteúdo. Para reprodutibilidade total, fixe o digest.
  • latest não significa "a mais recente". É só a tag padrão quando você não informa nenhuma. Evite em produção: você não sabe qual versão está rodando e um rollback fica impossível.
docker image ls                    # imagens locais
docker image history api:1.4.2     # camadas e o tamanho de cada uma
docker image inspect api:1.4.2     # metadados (CMD, ENV, portas, camadas)
docker image prune                 # remove imagens sem tag (dangling)

05Construindo imagens

Dockerfile, instrução a instrução

# syntax=docker/dockerfile:1
FROM node:22-alpine

LABEL org.opencontainers.image.source="https://github.com/exemplo/api"
WORKDIR /app

# ARG só existe durante o build; ENV existe no build e no container
ARG NODE_ENV=production
ENV NODE_ENV=$NODE_ENV PORT=3000

COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY . .

# não rodar como root
USER node
# documentação: não publica a porta
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD wget -qO- http://localhost:3000/health || exit 1

ENTRYPOINT ["node"]
CMD ["server.js"]
InstruçãoO que faz e o que costuma cair em entrevista
FROMimagem base. Pode aparecer várias vezes (multi-stage). FROM scratch = imagem vazia.
WORKDIRdefine (e cria) o diretório de trabalho. Prefira a RUN cd ..., que não persiste entre instruções.
RUNexecuta um comando no build e grava o resultado numa camada nova.
COPYcopia arquivos do contexto de build para a imagem. --chown= ajusta o dono; --from= copia de outro estágio.
ADDcomo COPY, mas também baixa URLs e extrai .tar locais automaticamente. Use COPY, a menos que precise disso.
ARGvariável de build (--build-arg). Não existe no container em execução. Um ARG antes do FROM só vale para o FROM.
ENVvariável de ambiente gravada na imagem; existe no build e em execução.
EXPOSEsó documenta a porta. Quem publica é -p no run ou ports: no Compose.
USERusuário das instruções seguintes e do processo do container.
HEALTHCHECKcomando que o Docker roda periodicamente para marcar o container como healthy ou unhealthy. A ferramenta usada (curl, wget) precisa existir na imagem.
ENTRYPOINTo executável principal do container.
CMDargumentos padrão (ou comando padrão, se não houver ENTRYPOINT). Substituído pelo que vier depois da imagem no docker run.

CMD x ENTRYPOINT

Com o Dockerfile acima:

docker run api                       # node server.js
docker run api worker.js             # node worker.js   (CMD substituído)
docker run --entrypoint sh -it api   # sh               (ENTRYPOINT substituído)
  • Só CMD: comando padrão, totalmente substituível. Mais comum para aplicações.
  • ENTRYPOINT + CMD: a imagem se comporta como um executável, e o CMD dá os argumentos padrão.
  • Padrão muito usado: um ENTRYPOINT ["docker-entrypoint.sh"] que prepara o ambiente e termina com exec "$@", passando o controle para o CMD.

Forma exec x forma shell

# forma exec: node é o PID 1 e recebe os sinais
CMD ["node", "server.js"]

# forma shell: vira /bin/sh -c "node server.js"
# o PID 1 é o sh, que NÃO repassa SIGTERM ao node
CMD node server.js

Atenção: no Dockerfile, # só é comentário no início da linha. Um comentário no fim de uma instrução vira parte dela.

Use a forma exec (JSON) em CMD e ENTRYPOINT. Com a forma shell, docker stop não consegue encerrar a aplicação de forma limpa.

.dockerignore

O docker build . envia a pasta inteira (o contexto de build) para o daemon. O .dockerignore exclui o que não deve ir: deixa o build mais rápido, evita invalidar o cache e impede que segredos entrem na imagem por um COPY . ..

06Construindo imagens

Cache de build

O Docker reaproveita uma camada se a instrução e tudo antes dela não mudaram. Para COPY e ADD, ele compara o conteúdo dos arquivos copiados. Quando uma camada muda, todas as seguintes são refeitas.

Por isso a ordem importa: coloque primeiro o que muda pouco (dependências) e por último o que muda sempre (código).

FROM node:22-alpine
WORKDIR /app
# qualquer alteração no código invalida esta camada e todas as seguintes
COPY . .
# então as dependências são reinstaladas a cada build
RUN npm ci
CMD ["node", "server.js"]
FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
# só roda de novo se package*.json mudar
RUN npm ci
# o código muda sempre, mas só esta camada é refeita
COPY . .
CMD ["node", "server.js"]

O mesmo vale para qualquer stack: requirements.txt no Python, pom.xml no Maven, go.mod/go.sum no Go, *.csproj no .NET.

Outras regras do cache

  • Junte comandos relacionados num só RUN e limpe na mesma instrução: 
    RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*
    apt-get update sozinho numa camada fica em cache e, semanas depois, o install tenta baixar versões que não existem mais.
  • O cache do RUN se baseia no texto do comando. RUN curl https://.../latest.tar.gz não baixa de novo se o texto não mudou. Use --no-cache para forçar um build do zero.
  • Cache mounts do BuildKit (o builder padrão desde o Docker 23) guardam o cache do gerenciador de pacotes entre builds, sem colocá-lo na imagem: 
    RUN --mount=type=cache,target=/root/.npm npm ci
  • No CI, cada build começa sem cache. Use --cache-from/--cache-to (por exemplo, cache no registry ou no GitHub Actions) para reaproveitar.
07Construindo imagens

Multi-stage builds

Compilar precisa de compilador, SDK, dependências de desenvolvimento. Rodar não. O multi-stage usa vários FROM no mesmo Dockerfile: um estágio constrói e o estágio final copia só o resultado. A imagem final fica pequena e sem ferramentas que só serviriam a um invasor.

# syntax=docker/dockerfile:1
FROM node:22-alpine AS base
WORKDIR /app

# 1. todas as dependências (inclusive dev), para compilar
FROM base AS deps
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

# 2. alvo de desenvolvimento: usado pelo Compose com hot reload
FROM deps AS dev
COPY . .
CMD ["npm", "run", "dev"]

# 3. compila TypeScript → dist/
FROM deps AS build
COPY . .
RUN npm run build

# 4. só dependências de produção
FROM base AS prod-deps
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

# 5. imagem final: sem código-fonte TS, sem devDependencies
FROM node:22-alpine AS prod
ENV NODE_ENV=production
WORKDIR /app
COPY --from=prod-deps --chown=node:node /app/node_modules ./node_modules
COPY --from=build     --chown=node:node /app/dist ./dist
COPY --chown=node:node package.json ./
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]
# syntax=docker/dockerfile:1
# 1. build do front-end (React, Vue, Angular...)
FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
ARG VITE_API_URL=/api
# gera /app/dist
RUN npm run build

# 2. só os arquivos estáticos, servidos pelo Nginx
FROM nginx:1.27-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
# a imagem do nginx já define CMD ["nginx", "-g", "daemon off;"]
# syntax=docker/dockerfile:1
FROM python:3.13-slim AS build
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

FROM python:3.13-slim
ENV PATH="/opt/venv/bin:$PATH" PYTHONUNBUFFERED=1
COPY --from=build /opt/venv /opt/venv
WORKDIR /app
COPY . .
RUN useradd --system app
USER app
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]
# syntax=docker/dockerfile:1
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY mvnw pom.xml ./
COPY .mvn .mvn
# camada de dependências, reaproveitada pelo cache
RUN ./mvnw -q dependency:go-offline
COPY src src
RUN ./mvnw -q package -DskipTests

# só o runtime (JRE), sem o JDK
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/target/*.jar app.jar
USER 1000
ENTRYPOINT ["java", "-jar", "app.jar"]
# syntax=docker/dockerfile:1
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /out/api ./cmd/api

# binário estático: imagem final de poucos MB, sem shell
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/api /api
ENTRYPOINT ["/api"]
  • docker build --target dev -t api:dev . constrói até um estágio específico. O mesmo Dockerfile serve desenvolvimento e produção.
  • O BuildKit só constrói os estágios de que o alvo depende, e constrói estágios independentes em paralelo.
  • Uma ordem de grandeza típica para Node: imagem de build com mais de 1 GB, imagem final alpine em torno de 150 a 200 MB. Para Go com distroless: menos de 20 MB.
Na entrevista

"Multi-stage separa build de runtime no mesmo Dockerfile. O estágio final copia só o artefato com COPY --from, então a imagem fica menor, mais rápida de baixar e com menos superfície de ataque, porque compilador e dependências de dev não vão para produção."

Boas práticas de imagem

Escolha da imagem base

VarianteExemploQuando usar
completa (Debian)node:22build; quando precisa de muitas ferramentas
slimpython:3.13-slimbom padrão para runtime: Debian enxuto, glibc

Checklist

  • Fixe versões: node:22.11-alpine, não node:latest. Builds reproduzíveis.
  • Não rode como root: USER node ou crie um usuário. Se o processo for comprometido, o estrago é menor.
  • Um processo principal por container: API num container, worker em outro, banco em outro. Escalam, reiniciam e registram logs separadamente.
  • Logs no stdout/stderr, não em arquivo dentro do container. O Docker (e o orquestrador) coletam daí.
  • Configuração por variável de ambiente, não embutida na imagem. A mesma imagem roda em homologação e produção (princípio do 12-factor app).
  • Nada de segredos na imagem: nem em ENV, nem em ARG (ambos aparecem em docker history), nem copiados por COPY . .. Para segredos de build, use RUN --mount=type=secret: 
    RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
# docker build --secret id=npmrc,src=$HOME/.npmrc .
  • Escaneie vulnerabilidades: docker scout cves api:1.4.2 ou Trivy (trivy image api:1.4.2), de preferência no CI.

O problema do PID 1

O processo com PID 1 tem tratamento especial no Linux: ele não recebe o comportamento padrão de sinais (se não tratar SIGTERM explicitamente, o sinal é ignorado) e é responsável por "recolher" processos filhos órfãos (zumbis).

  • Use a forma exec no CMD/ENTRYPOINT para que sua aplicação seja o PID 1, não um sh.
  • Trate SIGTERM na aplicação: pare de aceitar requisições, termine as que estão em andamento, feche conexões e saia (graceful shutdown).
  • Se a aplicação cria subprocessos ou não trata sinais, rode com um init mínimo: docker run --init (ou init: true no Compose) coloca o tini como PID 1.
  • Em scripts de entrypoint, termine com exec "$@" para o script ser substituído pela aplicação.
09Dados e rede

Volumes e bind mounts

A camada gravável do container é descartável: some com docker rm, e escrever nela é mais lento por causa do copy-on-write. Dados que precisam sobreviver ficam fora dela.

TipoSintaxeOnde ficaUso típico
Volume nomeado-v pgdata:/var/lib/postgresql/datagerenciado pelo Docker (/var/lib/docker/volumes)dados de banco e tudo que precisa persistir em produção
Bind mount-v ./src:/app/srcuma pasta específica do hostdesenvolvimento (editar código no host e ver no container), arquivos de configuração
tmpfs--tmpfs /tmpmemória RAMarquivos temporários ou sensíveis que não devem tocar o disco
 
docker volume create pgdata
docker volume ls
docker volume inspect pgdata
docker run -d -v pgdata:/var/lib/postgresql/data postgres:17
docker run -v "$(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro" nginx  # :ro = somente leitura

# sintaxe longa, mais explícita (equivalente)
docker run --mount type=volume,source=pgdata,target=/var/lib/postgresql/data postgres:17
Diferenças que caem em entrevista
  • Um volume nomeado vazio é preenchido com o conteúdo que a imagem tinha naquele caminho. Um bind mount esconde o conteúdo da imagem e mostra o do host.
  • Bind mounts dependem da estrutura de pastas do host: bons para desenvolvimento, frágeis em produção.
  • Permissões: o processo do container roda com um UID (por exemplo, 1000). Se a pasta do host pertence a outro UID, dá "permission denied".
  • No Docker Desktop (Windows/macOS), bind mounts atravessam a fronteira com a VM e são mais lentos. No Windows, mantenha o código dentro do WSL 2.
  • docker compose down -v e docker volume prune apagam os dados.

Backup de um volume

# sobe um container temporário que monta o volume e gera um .tar no host
docker run --rm -v pgdata:/dados -v "$(pwd)":/backup alpine \
  tar czf /backup/pgdata.tar.gz -C /dados .

Para bancos de dados, prefira a ferramenta do próprio banco (pg_dump, mysqldump): copiar arquivos de um banco em execução pode gerar um backup inconsistente.

docker network create app-net

A rede bridge padrão não tem DNS

Containers na rede bridge padrão (sem --network) só se falam por IP. Crie uma rede própria, ou use Compose, que cria uma rede por projeto automaticamente.

Publicação de portas

-p 8080:80              # host:8080 → container:80, em todas as interfaces do host
-p 127.0.0.1:8080:80    # só acessível da própria máquina
-p 80                   # porta aleatória no host (veja com docker port)
  • Containers na mesma rede se falam pela porta interna do container, sem precisar de -p. Publique só o que precisa ser acessado de fora (normalmente o proxy ou a API), nunca o banco em produção.
  • No Linux, o Docker escreve regras de iptables próprias: uma porta publicada pode ficar aberta para a internet mesmo com o firewall ufw bloqueando. Use 127.0.0.1: quando a porta só deve ser local.

"localhost" dentro do container

Dentro de um container, localhost é o próprio container. Dois erros clássicos:

  1. A API tenta acessar o banco em localhost:5432. Errado: use o nome do serviço, db:5432.
  2. A aplicação escuta em 127.0.0.1. Aí ela só aceita conexões vindas de dentro do próprio container, e o -p não funciona. A aplicação precisa escutar em 0.0.0.0.

Para acessar um serviço que roda no host: host.docker.internal (automático no Docker Desktop; no Linux, adicione --add-host=host.docker.internal:host-gateway).

11Compose

Compose: o essencial

O Compose descreve uma aplicação de vários containers num arquivo YAML: serviços, redes e volumes. Em vez de cinco docker run com dezenas de flags, um docker compose up.

services:
  api:
    build: ./api                  # constrói a partir de ./api/Dockerfile
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://app:dev@db:5432/app   # "db" = nome do serviço
    depends_on:
      - db

  db:
    image: postgres:17-alpine     # usa uma imagem pronta
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: dev
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data

Versões do Compose
  • docker compose (com espaço) é o Compose v2, um plugin do Docker CLI. docker-compose (com hífen) é o v1 em Python, descontinuado.
  • A chave version: "3.8" no topo do arquivo é obsoleta; o Compose atual a ignora e emite aviso.
  • O nome padrão do arquivo é compose.yaml. docker-compose.yml continua funcionando.

Quando o Compose recria um container

up compara a configuração atual com a do container existente. Se mudou (imagem, variável, porta, volume), recria; se não mudou, mantém. Alterar o código não muda a configuração: para uma imagem construída, use up --build.

Compose avançado

depends_on com condições

A forma curta de depends_on só garante a ordem de início: o banco foi iniciado, mas pode ainda não aceitar conexões. Para esperar ficar pronto, combine com healthcheck:

services:
  api:
    depends_on:
      db:
        condition: service_healthy                  # espera o healthcheck passar
      migrate:
        condition: service_completed_successfully   # espera terminar com exit 0
      redis:
        condition: service_started                  # o padrão da forma curta
  db:
    image: postgres:17-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s

Mesmo assim, a aplicação deve tentar reconectar sozinha (retry com espera): o banco pode cair e voltar depois que tudo subiu, e orquestradores como o Kubernetes não garantem ordem nenhuma.

O que acontece no docker compose up -d

  1. Constrói web e api. migrate, api e worker usam o mesmo contexto e alvo; o cache do BuildKit faz a imagem ser construída uma vez.
  2. Cria as redes agenda_frontend e agenda_backend e os volumes.
  3. Sobe db e redis e espera os healthchecks.
  4. Roda migrate; se sair com código 0, libera api e worker.
  5. Quando api fica healthy, sobe o proxy.
docker compose up -d --build           # desenvolvimento (com override)
docker compose watch                   # sincroniza código enquanto você edita
docker compose --profile debug up -d   # inclui o adminer
docker compose logs -f api worker
docker compose -f compose.yaml config  # confere a configuração de produção
TAG=1.4.2 docker compose -f compose.yaml up -d   # produção com versão fixa
Pontos para defender numa entrevista
  • Segmentação de rede: o proxy não alcança o banco.
  • Uma porta publicada em produção (a do proxy).
  • Migração como serviço separado, que roda uma vez, em vez de rodar dentro de cada réplica da API.
  • Mesma imagem, processos diferentes (api, worker, migrate): um build, um artefato versionado.
  • Healthchecks + depends_on com condição para a ordem de subida.
  • Senha em secret, não em variável de ambiente nem no git.

Registry, tags e CI

docker login ghcr.io
docker build -t ghcr.io/equipe/api:1.4.2 -t ghcr.io/equipe/api:sha-3f9c2e1 .
docker push ghcr.io/equipe/api:1.4.2

docker tag api:dev ghcr.io/equipe/api:1.4.2   # dá outro nome à mesma imagem

Estratégia de tags

  • Commit SHA (sha-3f9c2e1): rastreável, cada build é único. Ótimo para deploy.
  • Versão semântica (1.4.2, e opcionalmente 1.4 e 1 apontando para ela) para releases.
  • Nunca sobrescreva uma tag de versão já publicada. Para rollback, basta subir a tag anterior.
  • Promova a mesma imagem de homologação para produção, sem reconstruir: o que foi testado é o que vai para produção.

Pipeline típico de CI

  1. Build com cache (--cache-from/--cache-to).
  2. Testes rodando dentro da imagem ou com docker compose run --rm api npm test.
  3. Scan de vulnerabilidades (Trivy, Docker Scout); falha o pipeline em CVEs críticas.
  4. Push com tag do commit; em release, também a tag de versão.
  5. Deploy referenciando a tag (ou o digest).

Multiplataforma

# uma tag que funciona em servidores x86 e em ARM (Graviton, Mac M1+)
docker buildx build --platform linux/amd64,linux/arm64 \
  -t ghcr.io/equipe/api:1.4.2 --push .

Uma imagem construída num Mac com Apple Silicon é arm64 por padrão e pode falhar num servidor amd64 com "exec format error".

Segurança

O container compartilha o kernel do host. Uma falha no isolamento pode dar acesso ao host, então as camadas de defesa importam.

  • Usuário não-root na imagem (USER). Por padrão, root no container é o root do host com privilégios reduzidos.
  • Nunca --privileged sem necessidade real: dá acesso a todos os dispositivos e desliga quase todo o isolamento.
  • Montar /var/run/docker.sock num container equivale a dar root no host a ele: quem fala com o daemon cria um container privilegiado com o disco do host montado. Cuidado com ferramentas que pedem isso.
  • Reduza capabilities: cap_drop: [ALL] e adicione só o necessário.
  • Sistema de arquivos somente leitura: read_only: true com tmpfs onde a aplicação precisa escrever.
  • no-new-privileges: impede escalar privilégios via binários setuid.
  • Imagens mínimas e atualizadas: menos pacotes, menos CVEs. Reconstrua periodicamente para pegar correções da imagem base.
  • Imagens de origem confiável: oficiais ou verificadas; fixe versões.
  • Segredos via secrets do Compose/Swarm/Kubernetes ou um cofre (Vault, AWS Secrets Manager), nunca na imagem.
  • Modo rootless: o próprio daemon roda sem root. O Podman é rootless por padrão.
services:
  api:
    user: "1000:1000"
    read_only: true
    tmpfs: [/tmp]
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]

O driver de log padrão (json-file) não tem rotação: um container falante enche o disco. Configure limites por serviço ou no /etc/docker/daemon.json:

    logging:
      driver: json-file

"O Kubernetes abandonou o Docker?"

O Kubernetes 1.24 removeu o dockershim, a ponte que permitia usar o Docker Engine como runtime dos nós. Os nós passaram a usar containerd ou CRI-O diretamente. As imagens construídas com Docker continuam funcionando normalmente, porque seguem o padrão OCI. Para quem desenvolve, nada mudou.

18Entrevista

Perguntas frequentes de entrevista

Responda em voz alta antes de abrir. A resposta ideal tem uma frase de definição e um exemplo prático.

01Qual a diferença entre container e máquina virtual?

A VM virtualiza hardware e roda um SO completo com kernel próprio sobre um hypervisor. O container é um processo isolado por namespaces e limitado por cgroups, que compartilha o kernel do host. Container é mais leve (MBs, sobe em segundos); a VM isola mais e pode rodar outro sistema operacional.

02Qual a diferença entre imagem e container?

A imagem é um modelo imutável em camadas. O container é uma instância em execução dessa imagem, com uma camada gravável própria. Uma imagem pode gerar vários containers.

03O que são as camadas de uma imagem e por que importam?

Cada instrução que altera arquivos gera uma camada somente-leitura, empilhada via overlay2. As camadas são compartilhadas entre imagens e cacheadas no build. Importam para: tamanho (apagar numa camada posterior não reduz a imagem), velocidade de build (ordem das instruções) e velocidade de pull (camadas já baixadas não são baixadas de novo).

04CMD x ENTRYPOINT?

ENTRYPOINT define o executável; CMD define os argumentos padrão (ou o comando, se não houver ENTRYPOINT). Argumentos no docker run substituem o CMD; o ENTRYPOINT só muda com --entrypoint. Use sempre a forma exec (JSON) para o processo receber sinais.

05COPY x ADD?

Os dois copiam arquivos do contexto. ADD também baixa URLs e extrai arquivos tar locais. A recomendação é usar COPY, que é previsível, e ADD só quando a extração automática for desejada.

06ARG x ENV?

ARG existe só durante o build (--build-arg). ENV fica gravado na imagem e existe no container em execução. Nenhum dos dois serve para segredos: ambos ficam visíveis no histórico da imagem.

07O que é multi-stage build e por que usar?

Vários FROM no mesmo Dockerfile: estágios de build com SDK e dependências de desenvolvimento, e um estágio final que copia só o artefato com COPY --from. Resultado: imagem menor, pull mais rápido, menos vulnerabilidades. Também permite alvos diferentes (--target dev) no mesmo arquivo.

08Como você reduz o tamanho de uma imagem?
  • Multi-stage, levando só o artefato para o estágio final.
  • Imagem base menor (slim, alpine, distroless).
  • Instalar só dependências de produção.
  • Limpar caches na mesma instrução RUN (rm -rf /var/lib/apt/lists/*, --no-cache-dir).
  • .dockerignore para não copiar node_modules, .git etc.

Para conferir: docker image history mostra o tamanho de cada camada.

09Como acelerar o build?

Ordenar instruções do que muda menos para o que muda mais (copiar o manifesto de dependências e instalar antes de copiar o código), .dockerignore, cache mounts do BuildKit e, no CI, cache remoto com --cache-from/--cache-to.

10Como persistir dados? Volume x bind mount?

Dados fora da camada gravável. Volume nomeado é gerenciado pelo Docker, portável e o indicado para bancos. Bind mount liga uma pasta específica do host: ótimo em desenvolvimento para editar código, frágil em produção. tmpfs fica em memória. Volumes sobrevivem a docker rm e a compose down (mas não a down -v).

11Como dois containers se comunicam?

Colocando os dois na mesma rede definida pelo usuário (ou no mesmo projeto Compose), e usando o nome do container/serviço como hostname, que o DNS interno do Docker resolve. A conexão usa a porta interna do container; não precisa publicar porta. A rede bridge padrão não tem resolução por nome.

12A aplicação roda, mas não consigo acessar pela porta publicada. O que verificar?
  1. O container está de pé? (docker ps, não está reiniciando em loop)
  2. O mapeamento está certo? (-p host:container, com a porta em que a app realmente escuta)
  3. A app escuta em 0.0.0.0, não em 127.0.0.1?
  4. Logs da aplicação.
  5. Firewall ou outra coisa usando a porta no host.
13O que o depends_on garante?

Na forma curta, só a ordem de início, não que o serviço esteja pronto. Com condition: service_healthy e um healthcheck, espera ficar saudável; com service_completed_successfully, espera um serviço terminar com sucesso (migrações). A aplicação ainda deve tentar reconectar, porque dependências podem cair depois.

14Qual a diferença entre .env, env_file e environment no Compose?

O .env da pasta do projeto serve para interpolar ${VAR} no próprio arquivo Compose. env_file injeta variáveis de um arquivo dentro do container. environment define variáveis do container direto no YAML e tem precedência sobre o env_file.

15Como você trata segredos?

Nunca na imagem (nem ENV, nem ARG, nem arquivo copiado) e nunca no git. Em runtime: secrets do Compose/Swarm/Kubernetes montados como arquivo, ou um cofre (Vault, AWS Secrets Manager). Em build: RUN --mount=type=secret. Variáveis de ambiente são aceitáveis em muitos cenários, mas aparecem em docker inspect e podem vazar em logs.

16O container morre com exit code 137. O que significa?

128 + 9: o processo recebeu SIGKILL. A causa mais comum é falta de memória (docker inspect mostra OOMKilled: true); a correção é aumentar o limite ou achar o vazamento. Outra causa: docker stop esperou 10 s sem a aplicação encerrar, normalmente por CMD na forma shell ou aplicação que não trata SIGTERM.

17Por que não rodar o container como root?

O root do container é o root do host com algumas restrições. Se a aplicação for explorada e houver uma falha de isolamento (no kernel ou um volume sensível montado), o invasor ganha root no host. Com USER não-root, cap_drop e no-new-privileges, o estrago fica limitado.

18Por que não usar a tag latest em produção?

Porque é mutável e não diz qual versão está rodando. Dois servidores podem rodar versões diferentes com a mesma tag, e rollback fica impossível. Use versão semântica ou SHA do commit, e o digest quando quiser imutabilidade total.

19Quantos processos devem rodar num container?

Idealmente um processo principal (uma responsabilidade). API, worker e banco em containers separados escalam, reiniciam e geram logs de forma independente. Processos auxiliares do mesmo serviço são aceitáveis; nesse caso, use um init (--init/tini) para tratar sinais e processos zumbis.

20Docker Compose em produção: pode?

Pode, para aplicações pequenas num único servidor, com restart, healthchecks, limites de recursos e rotação de logs. A limitação é ser uma máquina só: sem alta disponibilidade entre hosts, sem auto-scaling, sem rolling update nativo. Acima disso, Kubernetes ou um serviço gerenciado (ECS, Cloud Run).

21O Kubernetes deixou de suportar Docker?

Deixou de usar o Docker Engine como runtime dos nós (remoção do dockershim na 1.24); usa containerd ou CRI-O. Imagens construídas com Docker continuam funcionando, porque seguem o padrão OCI.

22Como você colocaria uma aplicação legada num container?
  1. Levantar dependências: runtime, bibliotecas do sistema, variáveis, arquivos de configuração, portas.
  2. Tirar configuração e segredos do código para variáveis de ambiente.
  3. Logs para stdout.
  4. Dados persistentes (uploads, sessões em disco) para volumes ou serviços externos.
  5. Dockerfile multi-stage, usuário não-root, healthcheck.
  6. Compose com as dependências (banco, cache) para desenvolvimento e testes.
23O que é o contexto de build?

É o conjunto de arquivos enviado ao builder no docker build <caminho>. COPY e ADD só enxergam arquivos dentro dele. Um contexto grande deixa o build lento; o .dockerignore reduz o contexto e impede que arquivos sensíveis entrem.

24docker stop x docker kill x docker rm?

stop envia SIGTERM e, após o prazo (10 s por padrão), SIGKILL. kill envia SIGKILL imediatamente (ou outro sinal com -s). rm remove um container parado (-f força parando antes), descartando a camada gravável.

Como se preparar

Entrevistadores costumam aprofundar a partir das suas respostas. Ter feito na prática vale mais que decorar. Um roteiro de uma semana:

  1. Containers na mão. Suba um nginx e um postgres com docker run. Use exec, logs, inspect. Apague o container do postgres e veja os dados sumirem; repita com volume e veja ficarem.
  2. Seu primeiro Dockerfile. Containerize uma API pequena na linguagem que você usa. Meça o tamanho com docker image ls.
  3. Otimize. Reordene para usar o cache, adicione .dockerignore, transforme em multi-stage, rode como não-root. Compare tamanho e tempo de build antes e depois, e anote os números (eles viram uma boa história para a entrevista).
  4. Rede. Faça a API falar com o banco por nome numa rede própria. Provoque os erros clássicos de propósito: localhost no lugar do nome, app escutando em 127.0.0.1.
  5. Compose. Monte o projeto do capítulo 13 (pode ser com uma API mínima): healthchecks, migração como serviço, override de desenvolvimento, profiles.
  6. Quebre e conserte. Limite a memória até tomar OOM (exit 137), use CMD na forma shell e meça o docker stop, encha o log sem rotação.
  7. Publique. Faça push para o GitHub Container Registry com um workflow do GitHub Actions que constrói, escaneia com Trivy e publica com a tag do commit.
Na hora da entrevista
  • Responda com definição + exemplo concreto do seu trabalho ("no projeto X, a imagem tinha 1,2 GB; com multi-stage caiu para 180 MB").
  • Quando não souber, diga como descobriria (docker inspect, logs, documentação). Saber diagnosticar pesa tanto quanto saber de cor.
  • Mencione segurança e operação sem ser perguntado: não-root, segredos, tags fixas, healthcheck, limites. É o que diferencia quem usou Docker de quem leu sobre Docker.
