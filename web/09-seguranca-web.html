MÓDULO 09 · Avançado

Segurança de aplicações (AppSec)

As vulnerabilidades que mais derrubam sistemas web, como elas funcionam por dentro e como corrigir no código. Com o olhar de quem escreve o código e de quem cobra o time por ele.

Ao final você saberá
  • Explicar o OWASP Top 10 e usar a lista como vocabulário comum com o time.
  • Reconhecer e corrigir controle de acesso quebrado, injeção, XSS, CSRF e SSRF em código real.
  • Configurar CORS e cabeçalhos de segurança sem abrir brechas.
  • Tratar segredos, dependências e logs como parte da superfície de ataque.
  • Definir o que cobrar do time e como medir, em vez de depender de heróis.
1Intermediário

Mentalidade de segurança

Quase toda vulnerabilidade deste módulo nasce de uma suposição errada: "o usuário só vai mandar o que a tela permite", "só o nosso front-end chama essa API", "esse campo sempre é um número". O atacante não usa a sua tela. Ele fala HTTP direto com o servidor (veja o módulo 3) e manda o que quiser.

Quatro princípios

PrincípioO que significaExemplo no dia a dia
Nunca confiar na entradaTudo que vem de fora é hostil até prova em contrário: corpo, query string, cabeçalhos, cookies, nome de arquivo, resposta de API de terceiro.Validar no servidor mesmo que o front-end já valide.
Defesa em profundidadeVárias camadas independentes. Quando uma falha, outra segura.Consulta parametrizada + usuário de banco sem permissão de DROP + WAF + alerta.
Menor privilégioCada usuário, serviço e credencial recebe só o acesso que precisa, pelo tempo que precisa.A API de agendamento não lê a tabela de prontuários.
Falhar de forma seguraEm caso de erro, negar acesso e não vazar detalhes.Se o serviço de autorização cair, a requisição é negada. Stack trace nunca vai para o cliente.

Validação de entrada x codificação de saída

São duas defesas diferentes que muita gente confunde.

  • Validação de entrada acontece quando o dado chega. Confere tipo, formato, tamanho e faixa. Prefira lista de permitidos (allowlist): "CPF tem 11 dígitos" é melhor que "CPF não pode ter aspas". Validação reduz superfície, mas não sabe onde o dado vai ser usado depois.
  • Codificação de saída (output encoding) acontece quando o dado sai para um interpretador: HTML, SQL, shell, URL. Ela transforma caracteres especiais para que o interpretador os trate como texto. Depende do contexto de destino.

Um nome como O'Brien é válido e precisa ser aceito. Quem impede que ele quebre a SQL é a consulta parametrizada, e quem impede que ele quebre o HTML é o escape na hora de renderizar. Por isso a regra é: valide na entrada, codifique na saída, e use as duas.

Regra de bolso

Toda vez que um dado cruza uma fronteira de confiança (rede, processo, interpretador), pergunte: quem controla esse dado e o que o próximo componente faz com ele?

Na entrevista

Se perguntarem "como você evita injeção?", diga que valida a entrada por allowlist e, separadamente, usa APIs que separam código de dados na saída: consulta parametrizada, escape por contexto, execução sem shell.

Para gestores

Segurança que depende de cada dev lembrar de tudo falha. Cobre padrões do time: bibliotecas aprovadas para acesso a banco, templates com escape automático, middleware de autorização comum. O custo de padronizar uma vez é menor que o de revisar a mesma falha em cada PR.

OWASP Top 10: o vocabulário comum

A OWASP (Open Worldwide Application Security Project) é uma fundação aberta que publica guias de segurança de aplicações. O Top 10 é uma lista de conscientização das categorias de risco mais relevantes em aplicações web, montada a partir de dados de testes e de pesquisa com a comunidade. A edição 2021 é a mais citada em entrevistas e materiais de treinamento.

CódigoCategoria (2021)Resumo
A01Broken Access ControlUsuário faz o que não deveria: ver dados de outro, chamar função de admin. Ficou em primeiro lugar.
A02Cryptographic FailuresDado sensível sem criptografia ou com criptografia fraca, em trânsito ou em repouso. Veja o módulo 4.
A03InjectionSQL, comando de SO, NoSQL, LDAP. Na edição 2021, XSS passou a fazer parte desta categoria.
A04Insecure DesignFalha que nasce no projeto, antes de qualquer linha de código: fluxo de recuperação de senha fraco, ausência de limite de tentativas.
A05Security MisconfigurationConfiguração padrão, debug ligado em produção, bucket público, cabeçalhos ausentes.
A06Vulnerable and Outdated ComponentsBibliotecas, frameworks e imagens com vulnerabilidades conhecidas.
A07Identification and Authentication FailuresSenha fraca aceita, sessão que não expira, sem proteção contra credential stuffing. Veja o módulo 7.
A08Software and Data Integrity FailuresAtualização sem verificação de assinatura, pipeline de CI comprometido, desserialização insegura.
A09Security Logging and Monitoring FailuresAtaque acontece e ninguém vê, ou não há registro para investigar depois.

Saiba mais: edição 2025

A OWASP publicou uma edição 2025 do Top 10. Entre outras mudanças, ela deu destaque próprio às falhas na cadeia de suprimentos de software e incorporou SSRF à categoria de controle de acesso quebrado. Confira a lista atual no site da OWASP antes de usá-la em material oficial do time. Em entrevistas, saber a de 2021 e mencionar que existe a de 2025 costuma bastar.

Outras referências da OWASP

  • ASVS (Application Security Verification Standard): uma lista de requisitos verificáveis, organizada em níveis. O nível 1 é o mínimo para qualquer aplicação. O nível 2 é o recomendado para aplicações que tratam dados sensíveis, como dados de saúde. O nível 3 é para aplicações críticas. Serve como checklist de requisitos e de revisão.
  • Cheat Sheet Series: guias curtos e práticos por tema (SQL Injection Prevention, XSS Prevention, CSRF Prevention, Logging, Password Storage). É o primeiro lugar para consultar ao corrigir uma falha.
  • API Security Top 10: lista específica para APIs, com destaque para autorização por objeto. Veja o módulo 8.
Armadilha comum

Tratar o Top 10 como checklist de conformidade. Ele é uma lista de conscientização. "Passamos no Top 10" não quer dizer nada. Para requisitos verificáveis, use o ASVS.

Na entrevista

Cite as categorias pelo nome e dê um exemplo concreto de duas ou três. Mostrar que sabe que controle de acesso quebrado é o primeiro da lista, e por quê, vale mais que recitar os dez.

Para gestores

Escolha um nível do ASVS como meta (para dados de saúde, o nível 2 é a referência natural) e transforme os requisitos relevantes em critérios de aceite e itens do checklist de revisão. Assim "seguro" vira algo que dá para verificar.

3Intermediário

Controle de acesso quebrado e IDOR

Autenticação responde "quem é você". Autorização responde "você pode fazer isto, com este objeto". O módulo 7 trata dos mecanismos. Aqui o foco é a falha mais comum na prática: o código checa se o usuário está logado e esquece de checar se o recurso pertence a ele.

IDOR: referência direta insegura a objeto

IDOR (Insecure Direct Object Reference) acontece quando a aplicação usa um identificador vindo do cliente para buscar um objeto, sem conferir a permissão. Basta trocar /api/exames/1001 por /api/exames/1002 para ler o exame de outro paciente.

// GET /api/exames/:id
app.get('/api/exames/:id', autenticado, async (req, res) => {
  const exame = await db.exames.findById(req.params.id);
  if (!exame) return res.status(404).end();
  res.json(exame); // qualquer usuário logado lê o exame de qualquer paciente
});
// a busca já filtra pelo dono; o id do paciente vem da sessão, nunca do cliente
app.get('/api/exames/:id', autenticado, async (req, res) => {
  const exame = await db.exames.findOne({
    id: req.params.id,
    pacienteId: req.user.pacienteId
  });
  // 404 também quando o exame existe mas é de outro paciente: não confirma a existência
  if (!exame) return res.status(404).end();
  res.json(exame);
});

Outras formas da mesma falha

  • Escalada vertical: usuário comum chama POST /api/admin/usuarios porque a rota só esconde o botão no front-end.
  • Mass assignment: o endpoint grava o corpo inteiro e o usuário envia "perfil": "admin" junto com o nome. Corrija com lista explícita de campos aceitos.
  • Métodos esquecidos: GET checa permissão, PUT e DELETE na mesma rota não.
  • Confiança em campo do cliente: {"pacienteId": 77} no corpo em vez de pegar da sessão.

IDs aleatórios (UUID) dificultam adivinhar, mas não corrigem nada. O ID vaza em logs, links compartilhados e e-mails. A correção é sempre a checagem de autorização no servidor.

Regra de bolso

Negar por padrão. Centralize a autorização num middleware ou camada de serviço e escreva testes que tentam acessar o recurso de outro usuário. Esses testes pegam regressão que revisão humana deixa passar.

Na entrevista

IDOR é a pergunta clássica. Explique que a correção é verificar, a cada requisição, se o objeto pertence ao usuário ou se ele tem papel para acessá-lo, e que UUID sozinho só dificulta adivinhar o ID.

Para gestores

Em sistemas de saúde, IDOR expõe dados sensíveis de pacientes e é incidente comunicável pela LGPD (veja o módulo 10). Cobre testes automatizados de autorização para cada endpoint novo e inclua "quem pode acessar este recurso?" no template de PR.

Injeção: SQL, comando de SO e NoSQL

Injeção acontece quando dados do usuário são concatenados num texto que outro interpretador executa. O interpretador não sabe distinguir o que era código do que era dado. A correção, em todos os casos, é usar uma API que mantém os dois separados.

SQL injection

// busca de paciente por CPF
const sql = "SELECT id, nome FROM pacientes WHERE cpf = '" + req.query.cpf + "'";
const { rows } = await db.query(sql);
// consulta parametrizada: o valor vai separado do texto da SQL
const { rows } = await db.query(
  'SELECT id, nome FROM pacientes WHERE cpf = $1',
  [req.query.cpf]
);

Com a entrada clássica ' OR '1'='1, a versão vulnerável monta isto:

SELECT id, nome FROM pacientes WHERE cpf = '' OR '1'='1'

A condição é sempre verdadeira e a consulta devolve todos os pacientes. Na versão parametrizada, o banco recebe a SQL já compilada e trata o valor inteiro como um CPF literal, que não existe.

  • ORMs e query builders parametrizam por padrão, mas quase todos têm uma porta de saída para SQL crua. Revise esses pontos.
  • Nomes de tabela, colunas e direção de ORDER BY não podem ser parâmetros. Use allowlist: mapeie "data" para data_consulta e rejeite o resto.
  • Escapar aspas manualmente não é correção. Há casos de codificação e de contexto que escapam do escape.
  • Defesa em profundidade: o usuário de banco da aplicação não precisa de permissão para alterar esquema.

Injeção de comando de SO

const { exec } = require('child_process');
// exec passa a string inteira para o shell
exec('pdftotext ' + req.body.arquivo + ' saida.txt', callback);
// arquivo = "laudo.pdf; cat /etc/passwd"  -> o shell executa os dois comandos
const { execFile } = require('child_process');
// 1. o nome vem de uma allowlist de formato
if (!/^[a-z0-9_-]{1,64}\.pdf$/i.test(req.body.arquivo)) return res.status(400).end();
// 2. execFile não usa shell: cada argumento chega ao programa como um valor só
execFile('pdftotext', [path.join(DIR_LAUDOS, req.body.arquivo), 'saida.txt'], callback);
// melhor ainda: usar uma biblioteca no lugar de chamar um programa externo

NoSQL injection

Bancos como o MongoDB recebem consultas como objetos. Se a API aceita JSON e repassa o valor sem checar o tipo, o atacante envia um operador no lugar de um texto.

// POST /recuperar-senha/confirmar
// corpo enviado: { "email": "vitima@exemplo.com", "codigo": { "$ne": null } }
const pedido = await db.collection('recuperacoes').findOne({
  email: req.body.email,
  codigo: req.body.codigo   // vira "codigo diferente de null": casa com qualquer código
});
const { email, codigo } = req.body;
// valida tipo e formato antes de montar a consulta
if (typeof email !== 'string' || typeof codigo !== 'string' || !/^\d{6}$/.test(codigo)) {
  return res.status(400).end();
}
const pedido = await db.collection('recuperacoes').findOne({ email, codigo });
Armadilha comum

Achar que "usamos ORM, então estamos protegidos". A falha aparece justamente na consulta de relatório escrita à mão, no filtro dinâmico e na ordenação vinda da URL.

Na entrevista

Diga que a defesa primária é consulta parametrizada (prepared statement), que identificadores dinâmicos exigem allowlist, e que validação de tipo resolve a variante NoSQL. Cite menor privilégio no banco como segunda camada.

Para gestores

SAST (análise estática) pega bem a maioria dos casos de concatenação em SQL. Ligue no pipeline e trate esse tipo de achado como bloqueante. É uma das regras com melhor relação entre esforço e risco evitado.

5Avançado

XSS: cross-site scripting

XSS acontece quando a aplicação coloca dado não confiável numa página sem codificar, e o navegador o executa como script. O script roda com a origem do seu site: lê o que a página mostra, faz requisições autenticadas em nome da vítima e altera a tela. Cookies com HttpOnly não podem ser lidos pelo script, mas o atacante ainda age como o usuário enquanto a página está aberta.

TipoOnde o payload ficaExemplo
RefletidoNa própria requisição (URL, formulário). O servidor devolve na resposta.Página de busca que exibe "Resultados para X" sem escape. A vítima precisa clicar num link preparado.
ArmazenadoNo banco. Todo mundo que abre a página executa.Campo "observações" do agendamento, exibido no painel da recepção.
Baseado em DOMSó no navegador. O JavaScript da página lê uma fonte (URL, location.hash, postMessage) e escreve num ponto perigoso (innerHTML, eval).O servidor nunca vê o payload, então filtros no back-end não ajudam.

Refletido e armazenado

app.get('/busca', (req, res) => {
  res.send('<p>Resultados para ' + req.query.q + '</p>');
});
// /busca?q=<script>alert(1)</script>  -> o navegador executa o script
// use um template engine com escape automático ligado (EJS com <%= %>, Handlebars com {{ }}, JSX)
app.get('/busca', (req, res) => {
  res.render('busca', { termo: req.query.q }); // o template escapa < > & " '
});
// se precisar montar à mão, codifique para o contexto HTML:
function escHtml(s) {
  return String(s).replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;')
                  .replace(/"/g, '&quot;').replace(/'/g, '&#39;');
}

Baseado em DOM

// https://portal.clinica.com.br/#Maria
const nome = decodeURIComponent(location.hash.slice(1));
document.getElementById('ola').innerHTML = 'Olá, ' + nome;
// #<img src=x onerror=alert(1)>  -> executa
const nome = decodeURIComponent(location.hash.slice(1));
document.getElementById('ola').textContent = 'Olá, ' + nome; // texto puro, nunca HTML
// se precisar aceitar HTML de verdade (ex.: editor rico), passe por um sanitizador
// mantido pela comunidade, como o DOMPurify, antes de inserir

Escape por contexto

O mesmo dado precisa de codificação diferente conforme o lugar onde entra na página.

ContextoComo tratar
Corpo HTMLEscape de entidades HTML (&lt;, &gt;, &amp;). É o que o template faz por padrão.
Atributo HTMLSempre entre aspas e com escape de atributo. Nunca em atributos de evento (onclick).
URL em href ou srcValide o esquema (só https: ou caminho relativo; bloqueie javascript:) e use encodeURIComponent nos parâmetros.
Dentro de <script>Evite. Passe dados via atributo data-* ou JSON num elemento e leia com JavaScript.
CSSEvite dado do usuário em estilos. Se for inevitável, allowlist de valores.

Frameworks como React e Angular escapam por padrão. As portas de saída têm nomes que avisam: dangerouslySetInnerHTML, bypassSecurityTrustHtml, v-html. Procure esses nomes no código.

CSP: a segunda camada

A Content Security Policy é um cabeçalho que diz ao navegador de onde scripts e outros recursos podem vir. Com uma CSP estrita, um script injetado sem o nonce correto não executa, mesmo que o escape tenha falhado.

Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-R4nd0mPorResposta'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'
  • O nonce é um valor aleatório gerado a cada resposta e repetido em cada <script nonce="..."> legítimo.
  • 'unsafe-inline' em script-src anula boa parte da proteção contra XSS.
  • Comece com Content-Security-Policy-Report-Only para ver o que quebraria sem bloquear nada, ajuste e depois ative.
Armadilha comum

"É só um alert." O alert(1) é a prova de conceito. Um XSS armazenado no painel da recepção roda com a sessão de cada atendente que abre a tela, com acesso a todos os dados que ela mostra.

Na entrevista

Diferencie os três tipos, diga que a defesa principal é codificação de saída por contexto (de preferência automática pelo framework) e que CSP é a segunda camada. Mencione que HttpOnly protege o cookie, mas não impede o script de agir em nome do usuário.

Para gestores

Cobre uma regra de lint ou SAST que sinalize innerHTML, dangerouslySetInnerHTML e similares, exigindo justificativa no PR. Planeje a CSP como projeto: modo report-only, coleta de relatórios, ajuste, ativação. Em sistema legado, isso costuma levar semanas.

6Avançado

CSRF: cross-site request forgery

O navegador anexa cookies às requisições para um site conforme as regras do cookie, inclusive quando a requisição parte de outro site. CSRF explora isso: uma página do atacante faz o navegador da vítima enviar uma requisição que altera estado no seu sistema, e o cookie de sessão vai junto. O atacante não lê a resposta. Ele só precisa que a ação aconteça.

// aceita qualquer POST que traga o cookie de sessão
app.post('/conta/email', autenticado, async (req, res) => {
  await db.usuarios.update(req.user.id, { email: req.body.email });
  res.redirect('/conta');
});

// página no site do atacante:
// <form action="https://portal.clinica.com.br/conta/email" method="POST">
//   <input type="hidden" name="email" value="atacante@exemplo.com">
// </form>
// <script>document.forms[0].submit()</script>
// 1. cookie de sessão com SameSite
res.cookie('sessao', id, { httpOnly: true, secure: true, sameSite: 'lax' });

// 2. token anti-CSRF ligado à sessão, enviado num campo oculto ou cabeçalho
app.post('/conta/email', autenticado, async (req, res) => {
  if (!tokenCsrfValido(req.session, req.body._csrf)) return res.status(403).end();
  // 3. ação sensível pede reautenticação (senha ou MFA) antes de trocar o e-mail
  await db.usuarios.update(req.user.id, { email: req.body.email });
  res.redirect('/conta');
});

As defesas

  • Token anti-CSRF (synchronizer token): valor imprevisível gerado pelo servidor, ligado à sessão, que precisa voltar em cada requisição que altera estado. A página do atacante não consegue ler esse valor por causa da política de mesma origem.
  • Atributo SameSite no cookie: Strict não envia o cookie em nenhuma requisição vinda de outro site. Lax envia só em navegação de nível superior com método seguro (clicar num link, GET), não em POST de formulário cruzado. None envia sempre e exige Secure. O Chrome trata cookies sem o atributo como Lax, mas não conte com o comportamento padrão de todos os navegadores: declare explicitamente.
  • Métodos seguros sem efeito colateral: GET nunca altera estado. Com Lax, um GET que apaga registro continua vulnerável.
  • Checar Origin: rejeitar requisições que alteram estado com origem desconhecida é uma camada extra barata.

APIs que autenticam por cabeçalho Authorization: Bearer (token guardado pelo JavaScript, não em cookie) não sofrem CSRF clássico, porque o navegador não anexa esse cabeçalho sozinho. Em troca, ficam mais expostas a XSS, que pode ler o token. Essa troca é discutida no módulo 7.

Na entrevista

Explique que CSRF abusa do envio automático de cookies, que a defesa é token anti-CSRF mais SameSite, e que CORS não protege contra CSRF porque um formulário simples não passa por preflight.

Para gestores

A maioria dos frameworks web tem proteção CSRF pronta. Cobre que ela esteja ligada e que exceções sejam documentadas. Padronize os atributos de cookie de sessão num só lugar do código.

7Avançado

SSRF: server-side request forgery

SSRF acontece quando o servidor faz uma requisição para uma URL que o usuário controla. Funções comuns que abrem essa porta: "importar foto a partir de URL", webhooks configuráveis, gerador de PDF que busca imagens, pré-visualização de links. O servidor está dentro da rede. Ele alcança o que o atacante não alcança.

Por que os metadados de nuvem são o alvo

Provedores de nuvem expõem, num endereço link-local (169.254.169.254 na AWS, por exemplo), um serviço que informa à máquina dados sobre ela mesma, inclusive credenciais temporárias do papel (role) associado. Se a aplicação busca essa URL a pedido do atacante e devolve o conteúdo, o atacante recebe chaves com as permissões da máquina. O vazamento da Capital One em 2019 é o caso mais citado envolvendo SSRF e metadados.

Na AWS, o IMDSv2 exige um token de sessão obtido por PUT antes de consultar os metadados. Isso dificulta muito a exploração via SSRF simples. Exija IMDSv2 nas instâncias.

// importar foto do perfil a partir de uma URL
app.post('/perfil/foto-url', autenticado, async (req, res) => {
  const resp = await fetch(req.body.url);   // busca qualquer destino
  const img = await resp.arrayBuffer();
  await salvarFoto(req.user.id, img);
  res.status(204).end();
});
// url = http://169.254.169.254/latest/meta-data/iam/security-credentials/
const PERMITIDOS = new Set(['imagens.parceiro.com.br']);

app.post('/perfil/foto-url', autenticado, async (req, res) => {
  let u;
  try { u = new URL(req.body.url); } catch { return res.status(400).end(); }
  // allowlist de esquema e de host, em vez de tentar bloquear endereços ruins
  if (u.protocol !== 'https:' || !PERMITIDOS.has(u.hostname)) return res.status(400).end();
  const resp = await fetch(u, {
    redirect: 'error',                 // um redirecionamento poderia levar para dentro da rede
    signal: AbortSignal.timeout(5000)  // não deixa a conexão pendurada
  });
  // conferir Content-Type e limitar tamanho antes de salvar
  ...
});

Defesas em camadas

  • Allowlist de destinos sempre que possível. Bloquear "IPs internos" por lista de negados é frágil: há muitas formas de escrever um endereço, e o DNS pode resolver para um IP interno depois da checagem (DNS rebinding).
  • Se precisar aceitar URLs arbitrárias, resolva o nome, rejeite faixas privadas, loopback e link-local, e conecte no IP que você validou.
  • Não devolva a resposta crua ao usuário. Processe (ex.: valide que é imagem) e devolva só o resultado.
  • Rede: o servidor que busca URLs externas fica num segmento que não alcança serviços internos, com saída controlada por proxy ou regras de egress.
  • Nuvem: IMDSv2 obrigatório e papel da máquina com o mínimo de permissões.
Na entrevista

Defina SSRF, cite o serviço de metadados como alvo clássico e liste as defesas: allowlist, bloquear redirecionamentos, segmentação de rede e IMDSv2. Isso mostra que você pensa em código e em infraestrutura.

Para gestores

Mantenha um inventário das funcionalidades que buscam URLs informadas pelo usuário ou por parceiros. Cada uma deve ter dono e revisão de segurança. Peça ao time de infraestrutura a política de IMDSv2 e de egress como padrão da conta de nuvem.

8Avançado

CORS e cabeçalhos de segurança

O que CORS é e o que não é

A política de mesma origem (same-origin policy) impede que o JavaScript de uma origem leia respostas de outra. CORS (Cross-Origin Resource Sharing) é o mecanismo pelo qual o servidor relaxa essa restrição, dizendo quais origens podem ler as respostas. O módulo 5 mostra o preflight em detalhe.

  • CORS é aplicado pelo navegador. curl, Postman e scripts no servidor ignoram CORS completamente.
  • CORS não autentica nem autoriza ninguém. A API precisa de autenticação e autorização próprias.
  • CORS não impede que a requisição chegue ao servidor. Requisições "simples" (como um POST de formulário) são enviadas sem preflight; o navegador só bloqueia a leitura da resposta. Por isso CORS não protege contra CSRF.

O erro que vira vulnerabilidade

O navegador proíbe Access-Control-Allow-Origin: * junto com credenciais. Para "fazer funcionar", alguém reflete a origem recebida. Resultado: qualquer site lê respostas autenticadas da sua API usando o cookie da vítima.

app.use((req, res, next) => {
  res.set('Access-Control-Allow-Origin', req.headers.origin); // aceita qualquer origem
  res.set('Access-Control-Allow-Credentials', 'true');        // e com cookies
  next();
});
const ORIGENS = new Set([
  'https://portal.clinica.com.br',
  'https://app.clinica.com.br'
]);

app.use((req, res, next) => {
  const origem = req.headers.origin;
  if (origem && ORIGENS.has(origem)) {          // comparação exata, sem regex frouxa
    res.set('Access-Control-Allow-Origin', origem);
    res.set('Access-Control-Allow-Credentials', 'true');
  }
  res.set('Vary', 'Origin'); // caches não misturam respostas de origens diferentes
  next();
});

Outros erros frequentes: regex que aceita clinica.com.br.atacante.com ou atacanteclinica.com.br; aceitar a origem null (enviada por iframes em sandbox e arquivos locais); liberar CORS em toda a API quando só um endpoint precisava.

Armadilha comum

Ativar HSTS com includeSubDomains e max-age longo sem conferir se todos os subdomínios têm HTTPS. Os navegadores vão recusar os que não têm, e não há como "desligar" remotamente antes do prazo. Comece com max-age curto e aumente.

Na entrevista

Diga que CORS relaxa a política de mesma origem e não protege o servidor, e que refletir Origin com Allow-Credentials: true é o erro clássico. Cite três ou quatro cabeçalhos com a função de cada um.

Para gestores

Cabeçalhos de segurança são baratos e fáceis de verificar automaticamente. Configure-os num ponto central (proxy reverso, gateway ou middleware comum) e inclua um teste no pipeline que falha se algum sumir. Configuração de CORS deve passar por revisão, com lista de origens versionada.

Upload, path traversal e desserialização

Upload de arquivos

Sistemas de saúde recebem muitos arquivos: exames, laudos, documentos de identidade. Cada upload é uma entrada não confiável grande e complexa. Riscos: arquivo executável colocado em pasta servida pela web, HTML ou SVG com script servido do seu domínio (XSS armazenado), arquivo gigante que esgota disco, nome de arquivo com ../, malware repassado a outros usuários.

  • Limite tamanho no proxy e na aplicação.
  • Valide o tipo pelo conteúdo (assinatura do arquivo), não só pela extensão ou pelo Content-Type enviado pelo cliente. Aceite uma allowlist curta (PDF, JPEG, PNG).
  • Gere um nome novo no servidor (ex.: UUID). Guarde o nome original só como metadado.
  • Armazene fora da pasta pública, de preferência num storage de objetos privado, e sirva por um endpoint que checa autorização.
  • Sirva com Content-Disposition: attachment, Content-Type correto e X-Content-Type-Options: nosniff. Se precisar exibir no navegador, considere um domínio separado só para arquivos de usuários.
  • Faça varredura de malware quando os arquivos forem compartilhados entre usuários.

Path traversal

Acontece quando um nome de arquivo vindo do usuário entra num caminho do sistema de arquivos. Com ../, o atacante sai da pasta prevista.

// GET /laudos?arquivo=12345.pdf
app.get('/laudos', autenticado, (req, res) => {
  const caminho = path.join('/srv/laudos', req.query.arquivo);
  fs.createReadStream(caminho).pipe(res);
});
// arquivo=../../etc/passwd  -> /etc/passwd
const BASE = path.resolve('/srv/laudos');

app.get('/laudos/:id', autenticado, async (req, res) => {
  // melhor: o cliente manda um ID; o nome do arquivo vem do banco, após checar autorização
  const laudo = await db.laudos.findOne({ id: req.params.id, pacienteId: req.user.pacienteId });
  if (!laudo) return res.status(404).end();
  // defesa extra: confirmar que o caminho final continua dentro da pasta base
  const caminho = path.resolve(BASE, laudo.arquivo);
  if (!caminho.startsWith(BASE + path.sep)) return res.status(400).end();
  res.sendFile(caminho);
});

Desserialização insegura

Alguns formatos de serialização nativos (o pickle do Python, a serialização de objetos do Java, certos formatos de .NET e PHP) reconstroem objetos arbitrários e podem executar código durante a desserialização. Se o atacante controla os bytes, pode conseguir execução remota de código.

  • Não desserialize dados não confiáveis com formatos nativos de objetos. Prefira JSON com validação de esquema.
  • Se não houver alternativa, assine os dados (HMAC) e verifique a assinatura antes de desserializar, e restrinja as classes permitidas.
  • Fique atento a bibliotecas que desserializam por baixo dos panos: alguns parsers de YAML e XML têm modos inseguros. Em XML, desative entidades externas (XXE).
Na entrevista

Para upload, cite: allowlist de tipo pelo conteúdo, renomear, guardar fora do webroot, servir com cabeçalhos corretos. Para path traversal, diga que o ideal é não usar nome vindo do cliente; senão, normalizar e confirmar que o caminho fica dentro da base.

Para gestores

Crie um componente de upload comum para o time, revisado uma vez, em vez de cada sistema implementar o seu. Arquivos de pacientes têm dados sensíveis: defina retenção, criptografia em repouso e quem pode baixar.

Segredos, dependências e cadeia de suprimentos

Segredos no código e no git

Senha de banco, chave de API e chave de nuvem no código-fonte acabam em todo clone, em todo fork, nos logs de CI e no histórico do git. Apagar o arquivo num commit novo não apaga o histórico. Repositórios públicos são varridos por robôs em busca de chaves continuamente.

// config.js, versionado
const s3 = new S3Client({
  region: 'sa-east-1',
  credentials: { accessKeyId: 'AKIA...', secretAccessKey: 'wJalr...' }
});
// sem credencial no código: o SDK usa o papel (role) da máquina ou do container,
// ou variáveis de ambiente injetadas pelo cofre de segredos no deploy
const s3 = new S3Client({ region: process.env.AWS_REGION });

// .gitignore inclui .env; o repositório tem apenas .env.example com nomes, sem valores
  • Use um cofre de segredos (secrets manager do provedor, Vault) e credenciais de curta duração quando possível.
  • Ligue secret scanning no repositório e, se a plataforma oferecer, bloqueio no push.
  • Vazou? A ordem é: revogar e rotacionar o segredo primeiro, depois investigar uso indevido nos logs do provedor, depois limpar o histórico. Limpar o histórico sem rotacionar não resolve, porque a chave pode já ter sido copiada.

Dependências vulneráveis

A maior parte do código de uma aplicação moderna vem de bibliotecas de terceiros, e cada uma traz as suas próprias dependências (transitivas). SCA (Software Composition Analysis, análise de composição de software) cruza a lista de dependências com bases de vulnerabilidades conhecidas.

# pipeline de build
npm install            # pode resolver versões diferentes a cada build
npm run build
# pipeline de build
npm ci                 # instala exatamente o que está no package-lock.json
npm audit --audit-level=high   # falha o build se houver vulnerabilidade alta ou crítica
npm run build
  • Lockfile (package-lock.json, poetry.lock, go.sum) versionado garante builds reproduzíveis e que uma versão nova maliciosa não entre sem ninguém ver.
  • Atualização contínua com bots que abrem PRs de atualização. Atualizar um pouco toda semana é muito mais barato que pular três versões maiores de uma vez.
  • SBOM (Software Bill of Materials): inventário em formato padrão (SPDX ou CycloneDX) de tudo que compõe o software. Quando sai uma vulnerabilidade nova, o SBOM responde em minutos "onde usamos isso?".

Ataques à cadeia de suprimentos

  • Typosquatting: pacote malicioso com nome parecido com um popular, esperando um erro de digitação.
  • Dependency confusion: pacote público com o mesmo nome de um pacote interno, que o gerenciador acaba preferindo. Configure escopos e registros privados corretamente.
  • Conta de mantenedor comprometida: versão nova e legítima na aparência, publicada com código malicioso. Scripts de instalação (postinstall) rodam na máquina do dev e no CI.
  • Mantenedor infiltrado: o caso do xz-utils (CVE-2024-3094), descoberto em março de 2024. Ao longo de anos, alguém ganhou a confiança do projeto, virou co-mantenedor e inseriu um backdoor nas versões 5.6.0 e 5.6.1, escondido em arquivos de teste e no processo de build. O alvo era o acesso SSH em algumas distribuições Linux. Foi descoberto por acaso, por um engenheiro que investigava lentidão no login, antes de chegar à maioria das versões estáveis.

Defesas: lockfile, revisão de dependências novas (popularidade, mantenedores, atividade), registro interno espelhado, pipeline de CI com permissões mínimas, assinatura e verificação de artefatos, e SBOM. O módulo 10 mostra onde cada verificação entra no pipeline.

Na entrevista

Sobre um segredo vazado, a resposta certa começa com "rotacionar imediatamente". Sobre dependências, cite SCA no pipeline, lockfile, SBOM e um exemplo de ataque à cadeia de suprimentos, como o xz.

Para gestores

Defina política para dependências: quem aprova uma biblioteca nova, prazo para atualizar vulnerabilidades por severidade, SBOM gerado em todo build. Meça a idade das vulnerabilidades abertas em dependências. Se o número só cresce, o problema costuma ser falta de tempo reservado no planejamento. Comprar outra ferramenta não resolve isso.

11Intermediário

Logging seguro e proteção contra abuso

O que logar

  • Eventos de autenticação: login com sucesso e falha, logout, troca de senha, ativação e desativação de MFA.
  • Falhas de autorização (tentativa de acessar recurso de outro usuário é sinal forte de ataque).
  • Ações administrativas e mudanças de permissão.
  • Acesso a dados sensíveis: quem consultou o prontuário de qual paciente, quando. Em saúde, essa trilha de auditoria é requisito de negócio.
  • Erros de validação em volume anormal e eventos de rate limiting.

Cada evento com: data e hora em UTC, identificador do usuário, IP, ação, recurso, resultado e um ID de correlação que liga os logs da mesma requisição entre serviços.

O que nunca logar

Senhas (mesmo as erradas, que muitas vezes são a senha certa com um erro de digitação), tokens de sessão e de acesso, chaves de API, cabeçalhos Authorization e Cookie, números completos de cartão, e dados de saúde ou dados pessoais além do mínimo necessário. Logs costumam ter controle de acesso mais fraco que o banco e são copiados para várias ferramentas.

logger.info('tentativa de login', { email: req.body.email, senha: req.body.senha });
logger.debug('requisição recebida', { headers: req.headers, body: req.body });
// headers inclui Authorization e Cookie; body pode ter diagnóstico e CPF
logger.info('login_falhou', {
  usuarioId: usuario?.id ?? null,  // ID interno, não e-mail nem CPF
  ip: req.ip,
  motivo: 'senha_invalida',
  correlacao: req.id
});
// logger configurado para mascarar campos sensíveis por nome (senha, token, authorization, cpf)

Cuidado também com injeção em log: um valor com quebra de linha pode forjar uma linha falsa no arquivo. Logs estruturados (JSON) resolvem isso. Proteja os logs contra alteração e defina retenção.

Rate limiting e abuso

Nem todo ataque explora um bug. Muitos abusam de funcionalidades legítimas em volume: tentativas de senha, enumeração de usuários no "esqueci minha senha", disparo de SMS que gera custo, raspagem de dados, reserva de todos os horários de agenda.

  • Limite por usuário, por IP e por recurso, com limites mais estritos em login, recuperação de senha e envio de SMS.
  • Responda com 429 Too Many Requests e, se fizer sentido, Retry-After.
  • Mensagens genéricas evitam enumeração: "se o e-mail existir, enviaremos instruções".
  • Limites de negócio também contam: no máximo N agendamentos futuros por paciente.
HTTP/1.1 429 Too Many Requests
Retry-After: 60
Content-Type: application/json
Na entrevista

Liste o que logar e o que nunca logar, e mostre que você sabe que log é fonte de vazamento. Sobre abuso, cite rate limiting por usuário e por IP e mensagens que não revelam se a conta existe.

Para gestores

Defina um padrão de log de segurança para todos os serviços (campos, nomes de eventos, mascaramento) e centralize num SIEM ou ferramenta de logs. Pergunte ao time: "se alguém acessou o prontuário de um paciente indevidamente na semana passada, quanto tempo levamos para descobrir quem foi?".

Cenários práticos

1. Um pesquisador reportou por e-mail que consegue ver exames de outros pacientes

Agradeça e confirme o recebimento no mesmo dia. Peça os detalhes técnicos sem exigir nada em troca. Reproduza num ambiente de teste com contas suas. Se confirmado, trate como incidente: corrija (checagem de dono no endpoint), procure o mesmo padrão nos outros endpoints, consulte os logs para saber se houve acesso indevido real e acione o DPO para avaliar a comunicação à ANPD. Depois, publique um canal oficial para relatos (o arquivo security.txt, definido na RFC 9116, indica o contato) e agradeça ao pesquisador.

Para gestores

A pior reação é ameaçar o pesquisador. Ele é a alternativa barata a descobrir a falha pelo vazamento. Tenha uma política de divulgação de vulnerabilidades (VDP) antes de precisar dela.

2. Encontramos uma chave da AWS num repositório público

  1. Revogar e rotacionar agora. Desative a chave no console antes de qualquer outra coisa. Robôs encontram chaves em repositórios públicos em pouco tempo.
  2. Investigar uso. Consulte os logs de auditoria do provedor (CloudTrail, na AWS) pelo período em que a chave esteve exposta: criação de usuários, instâncias novas, leitura de buckets.
  3. Conter o que for encontrado. Recursos criados pelo atacante, outras credenciais criadas com a chave.
  4. Limpar e prevenir. Remover do histórico, ligar secret scanning com bloqueio no push, trocar chaves fixas por papéis (roles).

3. O pentest achou XSS armazenado no campo de observações; o time diz que "é só um alert"

Explique o impacto real: o campo aparece no painel da recepção, que mostra dados de todos os pacientes do dia. Um script ali age com a sessão de cada atendente. Corrija com escape no template, procure outros pontos de saída do mesmo dado (relatórios, exportações, e-mails) e planeje a CSP. Feche com um teste que injeta <script> no campo e verifica que sai escapado.

4. Um parceiro pede para "liberar CORS" na API

Pergunte primeiro se a chamada vem de um navegador. Integração servidor a servidor não precisa de CORS. Se vier de um front-end do parceiro, adicione a origem exata dele à allowlist, sem curinga e sem refletir a origem. Lembre que CORS não substitui autenticação do parceiro na API.

5. O time diz que não dá para corrigir as 400 vulnerabilidades do relatório de dependências

Não dá, e nem precisa de uma vez. Priorize: componentes expostos à internet, vulnerabilidades com exploração ativa conhecida, severidade crítica e alta. Muitas somem com uma única atualização de framework. Reserve uma fatia fixa de cada sprint e meça a tendência. O módulo 10 detalha a priorização.

14Avançado

Perguntas de entrevista

01O que é o OWASP Top 10 e qual é o primeiro item?

É uma lista de conscientização das categorias de risco mais relevantes em aplicações web, publicada pela OWASP. Na edição 2021, o primeiro é Broken Access Control: falhas de autorização como IDOR e escalada de privilégio. A OWASP publicou uma edição 2025, que, entre outras mudanças, incorporou SSRF à categoria de controle de acesso e deu destaque à cadeia de suprimentos de software.

02Como você previne SQL injection?

Com consultas parametrizadas em todo acesso ao banco, inclusive em SQL escrita à mão dentro do ORM. Identificadores dinâmicos, como coluna de ordenação, passam por allowlist. Como camada extra, o usuário de banco da aplicação tem só as permissões necessárias.

03O que é IDOR e como corrigir?

É acessar um objeto alterando o identificador na requisição, sem que o servidor confira se o usuário tem direito a ele. Corrige-se verificando a permissão em toda requisição, de preferência filtrando a consulta pelo dono, e cobrindo com testes que tentam acessar dados de outro usuário. ID aleatório não resolve.

04Quais os tipos de XSS e qual a defesa principal?

Refletido, armazenado e baseado em DOM. A defesa principal é codificar a saída conforme o contexto (HTML, atributo, URL, JavaScript), de preferência deixando o framework fazer isso automaticamente, e evitar APIs como innerHTML. CSP é a segunda camada.

05Cookie com HttpOnly resolve XSS?

Não. Impede que o script leia o cookie, mas o script continua executando na página e pode fazer requisições autenticadas, ler dados exibidos e alterar a tela. Reduz o impacto; a correção continua sendo codificar a saída.

06Como funciona CSRF e como se defender?

Uma página de outro site faz o navegador da vítima enviar uma requisição que altera estado, e o cookie de sessão vai junto. Defesas: token anti-CSRF ligado à sessão, cookies com SameSite=Lax ou Strict, GET sem efeito colateral e reautenticação em ações sensíveis.

07CORS protege minha API?

Não. CORS é aplicado pelo navegador e serve para relaxar a política de mesma origem, permitindo que certas origens leiam as respostas. Clientes fora do navegador ignoram CORS, e requisições simples chegam ao servidor de qualquer forma. A API precisa de autenticação e autorização próprias.

08Qual é o erro de configuração de CORS mais perigoso?

Refletir o cabeçalho Origin recebido em Access-Control-Allow-Origin junto com Access-Control-Allow-Credentials: true. Isso permite que qualquer site leia respostas autenticadas usando o cookie da vítima. O correto é comparar com uma lista exata de origens permitidas.

09O que é SSRF e por que é tão grave em nuvem?

É induzir o servidor a fazer requisições para destinos escolhidos pelo atacante. Em nuvem, o alvo clássico é o serviço de metadados da instância, que pode fornecer credenciais temporárias. Defesas: allowlist de destinos, bloquear redirecionamentos, segmentação de rede, IMDSv2 e papel com permissões mínimas.

10Cite cabeçalhos de segurança e o que cada um faz.

CSP restringe origens de scripts e recursos. HSTS força HTTPS. X-Content-Type-Options: nosniff impede MIME sniffing. frame-ancestors e X-Frame-Options evitam clickjacking. Referrer-Policy limita o que vaza no Referer. Permissions-Policy desliga APIs do navegador que a página não usa.

11Qual a diferença entre validação de entrada e codificação de saída?

Validação confere se o dado tem o formato esperado quando chega, de preferência por allowlist. Codificação transforma o dado conforme o interpretador de destino quando ele sai, para que seja tratado como texto. São complementares: dados válidos como O'Brien ainda precisam de codificação.

12Um dev commitou uma senha de banco no repositório. O que fazer?

Rotacionar a senha imediatamente, verificar nos logs se houve acesso indevido no período, e só então remover do código e do histórico. Em seguida, mover o segredo para um cofre e ligar secret scanning com bloqueio no push para evitar repetição.

13Como você lida com o risco de dependências de terceiros?

Lockfile versionado e instalação reprodutível no CI, SCA no pipeline com limite de severidade, atualização contínua com bots, SBOM gerado no build, critério para aprovar bibliotecas novas e atenção a ataques à cadeia de suprimentos como typosquatting e mantenedores comprometidos, como no caso do xz.

14O que não deve ir para os logs?

Senhas, tokens, chaves, cabeçalhos de autorização e cookies, dados de cartão e dados pessoais sensíveis, como informações de saúde, além do mínimo necessário. Logs devem registrar quem fez o quê, quando e com que resultado, usando identificadores internos.

15Como proteger um upload de arquivos?

Limitar tamanho, aceitar uma allowlist de tipos verificada pelo conteúdo, gerar nome novo no servidor, guardar fora da pasta pública, servir por endpoint com autorização e cabeçalhos corretos (Content-Disposition, nosniff) e fazer varredura de malware quando o arquivo é compartilhado.

16Como gestor, como você colocaria AppSec no dia a dia do time sem travar entregas?

Com padrões e automação: bibliotecas e componentes seguros por padrão, SAST, SCA e secret scanning no pipeline bloqueando só o que é grave, checklist curto no PR baseado no ASVS, e uma fatia fixa do sprint para correções. Meço vulnerabilidades abertas por idade e tempo de correção, e, quando uma falha se repete, corrijo o padrão ou o componente comum em vez de culpar quem escreveu.

17Um pesquisador externo reporta uma falha. Como você conduz?

Confirmo o recebimento rápido, agradeço, reproduzo em ambiente controlado, priorizo pela gravidade, corrijo e verifico se houve exploração. Mantenho o pesquisador informado e combino a divulgação. Se dados pessoais foram expostos, envolvo o DPO. Para o futuro, publico um canal oficial e uma política de divulgação.

18O que é desserialização insegura?

É reconstruir objetos a partir de dados controlados pelo atacante com formatos que permitem instanciar classes arbitrárias, o que pode levar a execução remota de código. Evita-se usando formatos de dados simples, como JSON com validação de esquema, e nunca desserializando objetos nativos vindos de fora.
