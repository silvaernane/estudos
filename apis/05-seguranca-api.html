MÓDULO 05 · Avançado

Segurança de APIs

Em uma API não há tela, formulário nem usuário "burro" no meio do caminho: quem chama é um programa que faz exatamente o que o contrato permite. Este módulo mostra onde isso quebra (autorização por objeto, propriedades, consumo, fluxos de negócio) e como o gestor cobra defesas que funcionam.

Ao final você saberá
  • Explicar cada item do OWASP API Security Top 10 (2023) com exemplo vulnerável, correção e cenário de saúde.
  • Distinguir API key, OAuth 2.0 client credentials, mTLS e JWT, e validar um JWT sem as falhas clássicas.
  • Desenhar autorização fina: escopos, papéis (RBAC), atributos (ABAC), checagem por objeto e políticas centralizadas.
  • Tratar validação de entrada e de saída, mass assignment, SSRF em webhooks, CORS e segredos.
  • Montar inventário, gateway, logs sem PII, testes (DAST, fuzzing) e um checklist de revisão para o gestor.
1Intermediário

Por que APIs são o alvo e o OWASP API Top 10

Um site tem uma superfície visível: telas, formulários, fluxos. Uma API expõe diretamente a lógica e os dados: cada endpoint é uma porta documentada (às vezes em um OpenAPI público), com identificadores previsíveis, JSON estruturado e nenhuma interface para "esconder" nada. O atacante não precisa de navegador: usa curl, um script ou um proxy como o Burp e testa milhares de variações por minuto.

  • Documentação gratuita. Contratos OpenAPI, SDKs e apps móveis (que podem ser desmontados) revelam rotas, parâmetros e campos.
  • Autorização é lógica de negócio. Nenhum scanner sabe sozinho que o paciente 124 não pode ver o prontuário do 123. Quem define isso é o seu código.
  • Automação. Enumerar IDs, repetir um fluxo de agendamento, raspar a base inteira: tudo vira um laço.
  • Muitos consumidores. Apps, parceiros, operadoras, laboratórios, integrações internas. Cada um é uma credencial a proteger e um cliente que pode ser comprometido.
  • Superfície que cresce sozinha. Versões antigas, endpoints de teste e rotas esquecidas continuam respondendo.
Saiba mais

A trilha web (módulo 09, OWASP Top 10 web) cobre injeção, XSS e CSRF. Aqui o foco é o que muda quando o cliente é um programa: o OWASP mantém uma lista própria, o OWASP API Security Top 10. A edição vigente é a de 2023 (a anterior é de 2019). Confira em owasp.org/www-project-api-security se saiu edição mais nova antes de citar em uma entrevista.

Padrão geral

Quase todos os itens seguem a mesma forma: o código confia em algo que veio do cliente (um id, um campo, uma URL, um número) ou em algo que o cliente "não deveria" fazer. A correção é validar no servidor, com política explícita. Um par rápido para API8 (configuração):

Na entrevista

"Cite os três mais importantes do OWASP API Top 10." Resposta sênior: BOLA (API1), porque é a falha mais frequente e nenhuma ferramenta a encontra sem conhecer o negócio; BOPLA (API3), que une exposição excessiva de dados e mass assignment; e consumo irrestrito de recursos (API4), que vira indisponibilidade e custo. Complete dizendo que a causa comum é confiar no cliente.

Para gestores

Use o Top 10 como linguagem comum em revisão de design: para cada endpoint novo, pergunte "qual item se aplica e qual é o controle?". Meça: percentual de endpoints com teste automatizado de autorização por objeto e número de achados de pentest por item do Top 10 em cada trimestre.

2Avançado

BOLA/IDOR: o prontuário do paciente errado

BOLA (Broken Object Level Authorization, também chamado IDOR) acontece quando a API recebe o identificador de um objeto e não verifica se aquele chamador pode acessá-lo. Estar autenticado não basta: o token prova quem é você, não que o objeto 124 é seu.

Em saúde, o dano é direto: dado sensível exposto, quebra de sigilo, comunicação obrigatória à ANPD e aos titulares, risco jurídico. É por isso que é o exemplo central deste módulo.

Código vulnerável e corrigido

// Express + PostgreSQL (exemplo)
app.get("/pacientes/:id/prontuario", requireAuth, async (req, res) => {
  // req.user.sub vem do token, mas ninguém o compara com :id
  const { rows } = await db.query(
    "SELECT * FROM prontuario WHERE paciente_id = $1", [req.params.id]);
  res.json(rows);
});
app.get("/pacientes/:id/prontuario", requireAuth, async (req, res) => {
  // 1) a regra de acesso é uma função única e testada
  const pode = await politica.podeVer(req.user, "prontuario", req.params.id);
  if (!pode) {
    audit.negado(req, "prontuario", req.params.id);
    return res.status(404).json({ title: "Não encontrado" });
  }
  // 2) só as colunas necessárias (veja a seção 5 sobre saída)
  const { rows } = await db.query(
    "SELECT id, data, resumo FROM prontuario WHERE paciente_id = $1",
    [req.params.id]);
  res.json(rows);
});

A regra não é só "o paciente vê o próprio": um profissional vê pacientes com vínculo assistencial ativo, um paciente vê o seu, um responsável legal vê o do dependente. Por isso ela vive em uma política (politica.podeVer), não espalhada em ifs.

Por que identificadores aleatórios não resolvem

Trocar /pacientes/124 por um UUID reduz a enumeração, mas não é controle de acesso: UUIDs vazam em logs, e-mails, links compartilhados e respostas de outras APIs. Use UUID/ULID por boa prática (não revelar volume nem ordem), mas sempre autorize.

404 ou 403?

Responder 403 confirma que o recurso existe. Para dados sensíveis, 404 evita que o atacante descubra quais ids são válidos. Decida e padronize; registre sempre a tentativa no log de auditoria.

Padrões de BOLA que passam despercebidos

  • Id no corpo ou em filtro: POST /exames {"pacienteId":124} ou GET /exames?pacienteId=124. O id não está no caminho, a falha é a mesma.
  • Objetos aninhados: /pacientes/123/exames/987 checa o paciente 123, mas o exame 987 pertence a outro.
  • Escrita e exclusão, não só leitura: cancelar o agendamento de outro paciente.
  • Operações em lote e GraphQL: um array de ids ou vários campos em uma consulta. Cada objeto precisa ser autorizado.
  • Exportações, anexos, URLs assinadas: o link do PDF do laudo funciona para quem o possuir? Por quanto tempo?
Armadilha comum

Confiar no gateway ou no front-end para isso. O gateway não conhece o relacionamento paciente-profissional-unidade. A checagem de objeto pertence ao serviço dono do dado, em todo endpoint, e deve ser coberta por teste automatizado.

Regra de bolso

Todo handler que recebe um identificador responde, no código, a: "quem está pedindo, o que quer fazer, em qual objeto, e por que isso é permitido?". Sem as quatro respostas, não passa na revisão.

Na entrevista

"Como previne IDOR?" Autorização por objeto no servidor em cada acesso, preferencialmente por política central e filtro na consulta; 404 para não revelar existência; testes automatizados com dois usuários (A tenta ler o objeto de B); IDs não sequenciais como camada extra, nunca como controle.

Para gestores

Exija um teste de segurança por endpoint na pipeline: "usuário A não acessa recurso do usuário B". Pergunta de revisão: "se eu trocar este id por outro válido, o que acontece?". Indicador: cobertura de testes de autorização por objeto nos endpoints que tocam dado de paciente.

3Avançado

Autenticação de máquinas: chaves, OAuth, mTLS e JWT

O módulo 07 da trilha web explicou OAuth 2.0, OIDC e JWT do ponto de vista do usuário que faz login. Em APIs o chamador muitas vezes é um sistema: o laboratório que envia resultados, a operadora que consulta elegibilidade, outro serviço seu. As escolhas aqui são outras (e é onde mora API2, Broken Authentication).

Comparativo de mecanismos

MecanismoBom paraLimites
API keyIdentificar o consumidor, medir uso, plano e cota; integrações simples de baixo risco.Segredo estático e compartilhável; sem escopo nem expiração nativos; vaza em log, repositório, app móvel. Não identifica o usuário final. Nunca em query string.
OAuth 2.0 client credentialsServiço para serviço (sem usuário). Token de curta duração com escopos.Ainda há um segredo do cliente a guardar; precisa de servidor de autorização; sem contexto de usuário.
OAuth 2.0 + OIDC (código com PKCE)Apps e usuários finais (paciente no aplicativo).Fluxo mais complexo; visto na trilha web.
mTLSParceiros regulados, B2B de alto risco; pode vincular o token ao certificado do cliente.Gestão de certificados (emissão, rotação, revogação); difícil em navegador; a terminação de TLS precisa preservar a identidade.
JWT assinadoToken autocontido validável offline, com claims e escopos.Difícil de revogar antes do exp; validação incorreta é uma das falhas mais comuns.
Token opaco + introspecçãoRevogação imediata e controle central; token que carrega pouco dado.Cada chamada (ou cache) consulta o servidor de autorização: latência e dependência.

Client credentials na prática

POST /oauth/token HTTP/1.1
Host: auth.exemplo.com
Authorization: Basic bGFiLWV4ZW1wbG86c2VncmVkbw==
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&scope=resultados.escrever
{
  "access_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6IjIwMjYtMTEifQ...",
  "token_type": "Bearer",
  "expires_in": 600,
  "scope": "resultados.escrever"
}

Observe expires_in: 600: dez minutos. Tokens de máquina devem ser curtos e com o menor escopo possível (resultados.escrever, não *). O cliente guarda o token em memória e pede outro ao expirar.

Validando um JWT corretamente

Receber um JWT e "decodificar" não é validar. A validação mínima:

  1. Algoritmo fixo. Configure no servidor os algoritmos aceitos (ex.: RS256 ou ES256). Nunca aceite o que o cabeçalho do token disser: alg: none e o ataque que troca RS256 por HS256 (usando a chave pública como segredo) vêm daí.
  2. Assinatura com a chave certa. Busque a chave no endpoint JWKS do emissor pelo kid; faça cache e re-busque quando aparecer um kid desconhecido (rotação de chaves), com limite de frequência para não virar vetor de DoS.
  3. iss igual ao emissor esperado (comparação exata).
  4. aud contém esta API. Sem isso, um token emitido para outro sistema funciona na sua.
  5. exp e nbf respeitados, com tolerância pequena de relógio (segundos, não minutos).
  6. Escopos e identidade. Verifique o que a rota exige (ex.: scope contém resultados.escrever) e, para usuários, a identidade em sub.
// Biblioteca "jose" (exemplo). Algoritmos e emissor são FIXOS no servidor.
import { createRemoteJWKSet, jwtVerify } from "jose";

const jwks = createRemoteJWKSet(new URL("https://auth.exemplo.com/.well-known/jwks.json"));

export async function validar(token) {
  const { payload } = await jwtVerify(token, jwks, {
    issuer: "https://auth.exemplo.com/",
    audience: "api-resultados",
    algorithms: ["RS256"],
    clockTolerance: 5,           // segundos
  });
  const escopos = String(payload.scope ?? "").split(" ");
  return { sub: payload.sub, escopos };
}
Armadilha comum

Guardar dado sensível no payload do JWT achando que está protegido: ele é só codificado em Base64URL, qualquer um lê. Outra: homologação e produção com o mesmo emissor ou as mesmas chaves, de modo que um token de teste vale em produção.

JWT autocontido ou opaco com introspecção?

JWT valida offline e escala bem, mas não se revoga: um token roubado vale até exp. Mitigação: validade curta (minutos), refresh controlado e uma lista de revogação para casos críticos. O token opaco com introspecção (RFC 7662) consulta o servidor de autorização a cada uso, o que dá revogação imediata em troca de latência e de uma dependência; um cache curto do resultado equilibra. Regra prática: JWT de vida curta entre serviços internos; opaco, ou JWT muito curto com checagem extra, onde o requisito é revogar rápido (acesso a dado de paciente por parceiro).

mTLS e tokens vinculados ao certificado

No mTLS o cliente apresenta um certificado e o servidor o valida contra uma CA confiável. Combinado ao OAuth (tokens vinculados a certificado, RFC 8705), um token roubado não funciona sem a chave privada do cliente. É a escolha usual quando o parceiro é regulado ou o impacto de abuso é alto. O custo é operacional: inventário de certificados, alertas de expiração, rotação automatizada.

Regra de bolso

Tokens curtos, escopo mínimo, audiência explícita, algoritmo fixo, segredos em cofre e rotacionáveis. Se o desenho depende de um segredo que "nunca muda", ele já falhou.

Na entrevista

"Quando usaria API key e quando OAuth?" API key para identificar o consumidor e aplicar cota em integrações de baixo risco; OAuth client credentials quando é preciso escopo, expiração e revogação centralizadas; mTLS quando o risco ou a regulação pede identidade forte do cliente. Diga que API key sozinha não é autenticação de usuário.

Para gestores

Cobrar: inventário de credenciais de integração com dono e data de rotação; tempo máximo de vida dos tokens; nenhuma chave em repositório (varredura de segredos na pipeline). Pergunta de revisão: "se este segredo vazar hoje, em quanto tempo o rotacionamos sem derrubar o parceiro?".

4Avançado

Autorização fina: escopos, papéis, atributos e políticas

Autenticar responde "quem é?". Autorizar responde "pode fazer isto, com este objeto, agora?". Em APIs a autorização acontece em três camadas e confundi-las é a origem de BOLA (API1) e BFLA (API5).

Escopo, papel e atributo

ModeloPergunta que respondeExemploLimite
Escopo (OAuth)O que este cliente/token foi autorizado a fazer em nome de alguém?agenda.ler, exames.escreverGrosso: não diz nada sobre qual paciente.
Papel (RBAC)O que alguém com esta função pode fazer?recepcionista, medico, auditorExplosão de papéis; não captura contexto (unidade, horário, vínculo).
Atributo (ABAC)Dadas as propriedades do sujeito, do recurso e do contexto, é permitido?"médico com vínculo ativo com o paciente, na mesma unidade, em atendimento em andamento"Mais poder, mais complexidade; exige dados de atributos confiáveis.
Relação (ReBAC)Existe uma relação entre sujeito e objeto?"é responsável legal de", "faz parte da equipe de"Precisa de grafo/serviço dedicado em escala.

Uma checagem completa combina os três: o escopo do token permite ler prontuário, o papel do usuário permite a função, e o atributo/relação confirma que aquele paciente está sob seus cuidados.

BFLA: autorização por função

BFLA (Broken Function Level Authorization) é acessar uma função que não deveria: rota administrativa, método mais poderoso (DELETE, PUT) ou endpoint "interno" exposto. Costuma nascer de rotas que foram protegidas só pela falta de um botão na tela.

DELETE /agendamentos/8841 HTTP/1.1
Authorization: Bearer <token de paciente>

HTTP/1.1 204 No Content        <- qualquer autenticado apaga
// negar por padrão: cada rota declara escopo + papel exigidos
router.delete("/agendamentos/:id",
  exige({ escopo: "agenda.escrever", papeis: ["recepcao", "gestor_agenda"] }),
  async (req, res) => {
    const ag = await repo.buscar(req.params.id);
    if (!ag || !(await politica.pode(req.user, "cancelar", ag))) {
      return res.status(404).end();
    }
    await repo.cancelar(ag.id, req.user.sub);   // soft delete + auditoria
    res.status(204).end();
  });
Armadilha comum

Papel dentro do token como única verdade. Se o papel muda (a médica sai da unidade), o token antigo ainda diz o contrário até expirar. Para ações sensíveis, consulte o estado atual (vínculo, status do profissional) na hora, ou mantenha tokens curtos.

Políticas centralizadas (resumo de OPA)

Quando as regras se espalham por dez serviços, ficam inconsistentes e impossíveis de auditar. A alternativa é separar a decisão (PDP, Policy Decision Point) da aplicação (PEP, Policy Enforcement Point: gateway ou o próprio serviço). O Open Policy Agent (OPA) é um motor de políticas de código aberto, com a linguagem declarativa Rego: o serviço envia uma entrada (quem, ação, recurso, contexto) e recebe permitido ou negado.

package saude.prontuario

default permitir := false

# profissional com vínculo ativo, na mesma unidade
permitir if {
  input.acao == "ler"
  "prontuario.ler" in input.token.escopos
  input.sujeito.papel == "medico"
  some v in data.vinculos[input.recurso.paciente_id]
  v.profissional_id == input.sujeito.id
  v.ativo
  v.unidade == input.recurso.unidade
}

# o próprio paciente
permitir if {
  input.acao == "ler"
  input.sujeito.papel == "paciente"
  input.sujeito.id == input.recurso.paciente_id
}

O ganho está na política como código: versionada no Git, revisada, testada com casos de teste e implantada separadamente. O custo é mais uma peça operacional (latência da consulta, disponibilidade, fornecimento de dados de vínculos). Para equipes pequenas, uma biblioteca interna de autorização bem testada pode bastar; a decisão de usar um PDP externo se justifica quando há vários serviços e requisitos de auditoria.

Princípios que valem em qualquer modelo

  • Negar por padrão. Rota nova sem regra declarada responde 403, não 200.
  • Menor privilégio nos escopos, nos papéis e nas contas de serviço (a conta do serviço de agenda não precisa ler prontuário).
  • Checar no servidor, no ponto de uso, nunca confiar em campo enviado pelo cliente ("papel":"admin" no corpo).
  • Separação de deveres e dupla aprovação em operações críticas (exportação em massa de pacientes).
  • "Quebra de vidro" auditada: acesso emergencial é permitido, mas registrado e revisado depois.
Regra de bolso

Escopo diz o que o app pode, papel diz o que a função pode, atributo/relação diz o que ESTE usuário pode fazer COM ESTE objeto. Falta uma das três, falta autorização.

Na entrevista

"RBAC ou ABAC?" Papéis para o grosso (quem trabalha em quê), atributos e relações para o fino (este paciente, esta unidade, este horário). Cite que a decisão deve ser centralizada e testável (política como código, ex.: OPA) e aplicada no serviço dono do dado.

Para gestores

Peça uma matriz de autorização por endpoint (rota x papel x escopo x regra de objeto), revisada a cada release. Meça: rotas sem regra declarada (meta zero) e tempo para revogar o acesso de um profissional desligado.

5Avançado

Validação de entrada e saída, consumo e fluxos de negócio

A API é um contrato: aceite só o que o contrato descreve e devolva só o que o consumidor precisa. O módulo 02 mostrou como o OpenAPI descreve isso; aqui ele vira controle de segurança.

Validação de entrada (allowlist)

  • Esquema: tipos, formatos, tamanhos, enums, additionalProperties: false. Rejeite com 400/422 o que não bate.
  • Limites: tamanho do corpo (ex.: 1 MB), profundidade do JSON, tamanho de arrays, tamanho de string, tipos de arquivo e tamanho em uploads.
  • Consultas parametrizadas sempre (SQL e Oracle com bind variables): injeção continua valendo, inclusive em filtros e ordenação.
  • Normalização antes de validar (Unicode, caminhos) e Content-Type checado: não processe XML se espera JSON.
components:
  schemas:
    NovoAgendamento:
      type: object
      additionalProperties: false      # campo extra = erro
      required: [pacienteId, slotId]
      properties:
        pacienteId: { type: string, format: uuid }
        slotId:     { type: string, format: uuid }
        observacao: { type: string, maxLength: 500 }

Mass assignment e BOPLA (API3)

Se o código copia o JSON do cliente direto para a entidade, o cliente escolhe campos que não deveria: "status":"CONFIRMADO", "valorCobrado":0, "papel":"admin". É o mass assignment, lado de escrita do BOPLA. O lado de leitura é a exposição excessiva de dados: a API serializa a entidade inteira e confia que o front esconda o que sobra.

app.patch("/pacientes/:id", requireAuth, async (req, res) => {
  // o cliente manda { "nome": "...", "convenioStatus": "ATIVO", "perfil": "admin" }

Defina DTOs por papel (visão da recepção, do médico, do paciente). Valide o formato de saída no teste de contrato: um campo novo na entidade não deve aparecer automaticamente na resposta.

Consumo irrestrito de recursos (API4)

Cada requisição custa CPU, memória, banco e, às vezes, dinheiro (SMS, e-mail, consulta paga à operadora). Sem limites, um cliente (ou um bug) esgota a capacidade ou a conta. Controles:

  • Tamanho máximo de página e de corpo; limit com teto no servidor (ex.: máximo 100).
  • Tempo máximo de execução, tamanho máximo de resposta e profundidade/complexidade em GraphQL.
  • Rate limit por cliente, por usuário, por IP e por endpoint sensível (detalhes no módulo 06).
  • Cotas e alertas de gasto para serviços pagos de terceiros.
  • Operações caras (exportações, relatórios) assíncronas, em fila, com limite por cliente.
GET /exames?limit=100000 HTTP/1.1

HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{"title":"Parâmetro inválido","detail":"limit deve ser no máximo 100","status":400}

Fluxos de negócio sensíveis (API6)

Algumas ações são legítimas uma a uma, mas abusivas em volume: reservar horários, aplicar cupom, validar carteirinha, solicitar segunda via de laudo, recuperar senha. Um robô pode "esvaziar" a agenda de um especialista ou enumerar números de carteirinha válidos, sem explorar nenhum bug técnico.

  • Identifique os fluxos de maior valor ou abuso no mapeamento de ameaças, por negócio, não só por endpoint.
  • Limites por identidade: máximo de reservas ativas por paciente, tempo mínimo entre ações, bloqueio de reserva sem confirmação.
  • Fricção proporcional ao risco: confirmação por código, CAPTCHA ou reautenticação (step-up) quando o comportamento foge do padrão.
  • Respostas que não confirmam existência (login, validação de carteirinha, recuperação de senha).
  • Detecção de padrão: dispositivo, ritmo, sequência de ids, múltiplas contas com o mesmo telefone.
Armadilha comum

Rate limit apenas por IP: atrás de NAT (um hospital inteiro) bloqueia gente legítima; um atacante com botnet contorna. Combine limites por conta/cliente, por IP e por fluxo.

Na entrevista

"O que é mass assignment e como evitar?" Copiar o corpo da requisição para o modelo permite ao cliente definir campos que não deveria. Evita-se com DTOs de entrada com allowlist, rejeição de campos desconhecidos e DTOs de saída explícitos; no OpenAPI, additionalProperties: false.

Para gestores

Torne o contrato OpenAPI a fonte de validação (gerar validação a partir dele) e inclua na definição de pronto: "campos de entrada e saída aprovados por revisão de dados pessoais". Para cada API com custo por chamada de terceiro, exija cota e alerta de gasto.

SSRF, CORS, segredos e consumo de APIs de terceiros

SSRF em webhooks e URLs fornecidas pelo cliente (API7)

Server Side Request Forgery: a API faz uma requisição para uma URL que o cliente escolheu, e o atacante a aponta para onde ele não alcança, mas o seu servidor sim: o serviço de metadados da nuvem (credenciais temporárias), a rede interna, bancos, painéis administrativos. Webhooks (módulo 04), importação por URL, "buscar imagem por link" e geração de PDF a partir de URL são os pontos clássicos.

POST /webhooks HTTP/1.1
Content-Type: application/json

{"url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/"}

Defesas, em camadas:

  • Allowlist de domínios/hosts aprovados quando possível; senão, exigir HTTPS e validar o IP resolvido (bloqueando loopback, link-local, redes privadas e IPv6 equivalentes).
  • Proteção contra DNS rebinding: resolver uma vez, conectar ao IP validado, e não resolver de novo.
  • Não seguir redirecionamentos automáticos (ou revalidar cada salto); permitir só http/https, sem file:, gopher: etc.
  • Egress controlado na rede: o worker de webhooks roda em uma sub-rede sem rota para a rede interna e sem acesso ao serviço de metadados (use a versão com sessão obrigatória do serviço de metadados do seu provedor).
  • Não devolver ao cliente o corpo da resposta recebida; limitar tempo e tamanho; assinar os webhooks enviados (HMAC) para que o parceiro verifique a origem.
// busca a URL que o cliente mandou, sem checar nada
const r = await fetch(req.body.url);
res.send(await r.text());
import { lookup } from "node:dns/promises";
import ipaddr from "ipaddr.js";

export async function urlSegura(texto) {
  const u = new URL(texto);
  if (u.protocol !== "https:") throw new Error("somente https");
  if (!HOSTS_PERMITIDOS.has(u.hostname)) throw new Error("host não aprovado");
  const { address } = await lookup(u.hostname);
  if (ipaddr.parse(address).range() !== "unicast")      // bloqueia privado, loopback, link-local
    throw new Error("destino não público");
  return { url: u, ip: address };                       // conectar neste IP, redirect: "error"
}

CORS correto para APIs

CORS controla quais origens de navegador podem ler respostas da sua API. Não protege a API de curl nem de servidores: é uma regra do navegador (visto na trilha web). Erros comuns de API8:

ConfiguraçãoProblema
Access-Control-Allow-Origin: * com dados autenticados por cookieNavegadores bloqueiam * com credenciais, e a "correção" de refletir qualquer Origin abre a API a qualquer site.
Refletir o Origin recebido sem allowlistEquivale a liberar tudo, inclusive com Allow-Credentials: true.
Regex frouxa (.*exemplo.com)Casa com exemplo.com.atacante.net.
Aceitar null como origemPáginas em iframe sandbox e arquivos locais enviam null.

Correto: allowlist exata de origens do seu front-end, Vary: Origin para os caches, métodos e cabeçalhos mínimos, Max-Age do preflight definido, e credenciais só quando necessário. APIs puramente máquina-a-máquina (sem navegador) não precisam de CORS.

Access-Control-Allow-Origin: https://portal.exemplo.com

Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 600
Vary: Origin

Gestão de segredos

  • Nada de segredo no repositório, imagem de contêiner, log ou front-end. Use varredura automática de segredos (pré-commit e CI) e trate qualquer vazamento como incidente: revogar e rotacionar.
  • Cofre de segredos (do provedor de nuvem ou HashiCorp Vault) com acesso por identidade da carga de trabalho, não por senha compartilhada.
  • Rotação automática e segredos de curta duração (credenciais dinâmicas de banco). Um segredo por ambiente e por consumidor.
  • Chaves de assinatura de JWT e de webhook em KMS/HSM quando possível; rotação com sobreposição (duas chaves válidas durante a transição, kid distingue).
  • Variáveis de ambiente são aceitáveis como veículo, mas não como armazenamento; cuidado com dumps de configuração e endpoints de diagnóstico.

Consumo inseguro de APIs de terceiros (API10)

As integrações com operadora, laboratório e gateway de pagamento costumam receber menos desconfiança que o usuário final. Mas a resposta delas é entrada externa: pode vir malformada, enorme, comprometida ou trazer redirecionamentos.

  • Valide a resposta contra um esquema antes de usar ou gravar; descarte campos desconhecidos.
  • Defina timeouts, limite de tamanho, número máximo de redirecionamentos e TLS verificado.
  • Nunca interpole dados da resposta em consultas, comandos ou URLs sem tratamento.
  • Isole a integração: se a operadora cair ou responder lixo, o resto do sistema segue (módulo 06).
  • Contrato (DPA/LGPD) e requisitos de segurança com o fornecedor; revise as credenciais que ele tem sobre você.
Armadilha comum

Validar a URL do webhook só na hora do cadastro. O DNS pode mudar depois (um nome que hoje aponta para um IP público passa a apontar para 10.x). Valide o IP no momento de cada envio.

Na entrevista

"Como protege um recurso de webhook contra SSRF?" Allowlist e HTTPS, validar o IP depois do DNS, sem redirecionamentos, saída por proxy/egress controlado sem rota para a rede interna nem para os metadados da nuvem, limite de tempo e tamanho, e não devolver o corpo ao cliente.

Para gestores

Pergunte em revisão de design: "este serviço faz requisições para URLs que não controlamos? Para onde ele consegue chegar na rede?". Cobre: política de egress por serviço, varredura de segredos bloqueando o merge, e inventário de integrações com dono e nível de dado trafegado.

Inventário de APIs e gateway como ponto de controle

Não se protege o que não se conhece. API9 (Improper Inventory Management) descreve o problema: versões antigas, ambientes de teste e endpoints internos esquecidos continuam acessíveis, muitas vezes sem as proteções que a versão atual recebeu.

Shadow e zombie APIs

  • Shadow API: existe e responde, mas ninguém a registrou (criada por um time para uma integração rápida, sem passar por revisão).
  • Zombie API: foi "desativada" na documentação, mas o endpoint segue vivo (a /v1 depois do lançamento da /v2).
  • Ambientes paralelos: homologação ou "teste" com dados reais copiados da produção e sem autenticação forte.
  • Documentação de depuração aberta em produção (/swagger, /actuator, /graphql com introspecção).

O que manter no inventário

Mantenha o inventário vivo, alimentado por fontes reais: contratos OpenAPI no repositório, rotas observadas no gateway, DNS e certificados, tráfego e logs. A diferença entre "o que está registrado" e "o que recebe tráfego" é a lista de shadow APIs.

Gateway como ponto de controle

O que o gateway faz bem: terminar TLS/mTLS, validar token (assinatura, iss, aud, escopo), aplicar rate limit e cota por consumidor, validar o corpo contra o OpenAPI, bloquear rotas não registradas, padronizar cabeçalhos de segurança e centralizar logs e métricas. É também o lugar natural para um catálogo e um portal de desenvolvedores (módulo 10).

  • Não fazer: tratar o gateway como a única defesa. Se alguém alcançar o serviço pela rede interna, tudo é contornado: autentique também entre serviços (mTLS interno, tokens com aud do serviço) e restrinja a rede para que o serviço aceite tráfego apenas do gateway.
  • Rotas não registradas devem responder 404, nunca atravessar para o backend por padrão.
  • Gateway é ponto único de falha e de custo: dimensione, replique e monitore como o resto da produção.
Regra de bolso

Se uma API não está no inventário, não deveria estar no ar. Se está no ar e não passa pelo gateway, é achado de auditoria.

Na entrevista

"O que é uma shadow API e como encontra?" Endpoint em produção que não está no inventário. Encontra-se comparando o catálogo (OpenAPI) com o tráfego real (gateway, logs, DNS, scanners de superfície externa), e fecha-se com processo: nada sobe sem registro e dono.

Para gestores

Meta objetiva: 100% das APIs expostas com dono, contrato e classificação de dados; data de desativação para toda versão depreciada. Trimestralmente, compare o inventário com o tráfego e investigue a diferença. Pergunta de revisão: "qual a versão mais antiga ainda recebendo tráfego e quem a usa?".

Logs, LGPD, testes de segurança e checklist de revisão

Logs e auditoria sem PII

Logs precisam responder "quem fez o quê, em qual objeto, quando e com qual resultado", e ao mesmo tempo não podem virar um segundo banco de dados pessoais sem controle. Em saúde, log com prontuário, CPF ou corpo da requisição é um vazamento esperando acontecer.

{"msg":"GET /pacientes/124/prontuario","authorization":"Bearer eyJ...",
 "resposta":{"nome":"Maria Exemplo","cpf":"000.000.000-00","diagnostico":"E11"}}
{"ts":"2026-11-25T14:03:11Z","traceId":"3f9a1c2e","cliente":"app-portal",
 "ator":"u_8841","acao":"prontuario.ler","objeto":"paciente:p_4f2a",
 "resultado":"negado","motivo":"sem_vinculo","ip":"203.0.113.9","status":404}
  • Nunca registrar: senhas, tokens, chaves, corpo clínico, CPF, cartão. Aplique redação (masking) automática por campo conhecido.
  • Registrar identificadores indiretos (id interno ou pseudônimo) e correlacionar por traceId.
  • Trilha de auditoria separada do log operacional, imutável (append-only), com acesso restrito e retenção definida. Acesso a prontuário, negações e mudanças de permissão são eventos obrigatórios.
  • Alertas sobre padrões: muitas negações 403/404 do mesmo cliente (enumeração), picos de leitura por profissional, acesso fora do horário.
  • Sincronize relógios e proteja a integridade (hash encadeado, envio a armazenamento WORM) se a auditoria for requisito.

LGPD e dado de saúde

Dado de saúde é dado pessoal sensível (LGPD, Lei 13.709/2018, art. 5º, II) e o tratamento tem bases legais específicas no art. 11 (por exemplo, consentimento específico e destacado, tutela da saúde em procedimento por profissionais de saúde, cumprimento de obrigação legal, proteção da vida). A segurança é um dever do controlador e do operador (art. 46) e incidentes com risco ou dano relevante devem ser comunicados à ANPD e aos titulares (art. 48).

Consequências de engenharia para a API:

  • Minimização: devolva e registre só o necessário; paginação e DTOs por papel reduzem o volume exposto.
  • Finalidade e acesso: o acesso do profissional deve estar ligado a um vínculo assistencial; a trilha comprova isso.
  • Retenção e descarte definidos por tipo de dado (e a lei de prontuário tem prazos próprios, tema para validar com o jurídico).
  • Direitos do titular (acesso, correção, eliminação quando cabível) precisam ter caminho técnico: API e logs devem permitir localizar os dados de uma pessoa.
  • Transferência a terceiros (operadoras, laboratórios): contrato com o operador, finalidade e controles equivalentes; cuidado com serviços fora do país.
Saiba mais

Este módulo trata do lado técnico. Interpretação de bases legais, prazos de guarda do prontuário e comunicação de incidentes devem ser validados com o encarregado (DPO) e o jurídico.

Checklist de revisão de segurança para o gestor

  1. Todos os endpoints têm autenticação e escopo declarados e negam por padrão?
  2. Cada acesso por identificador passa por checagem de objeto? Há teste automatizado "A não lê B"?
  3. Entradas validadas por esquema (campos extras rejeitados) e saídas por DTO explícito?
  4. Limites de página, corpo, tempo e rate limit por cliente; fluxos sensíveis protegidos?
  5. JWT validado com algoritmo, iss, aud, exp fixos; tokens curtos e escopos mínimos?
  6. Segredos em cofre, rotacionáveis e com varredura no CI; plano de rotação testado?
  7. Chamadas a URLs externas (webhooks, importação) com allowlist e egress controlado?
  8. CORS por allowlist; erros sem detalhes internos; documentação de depuração desligada em produção?
  9. API no inventário, com dono, contrato, classificação de dados e plano de desativação?
  10. Logs sem PII, auditoria de acessos a dado de saúde, alertas e plano de resposta a incidente (art. 48)?
  11. Integrações de terceiros tratadas como entrada não confiável (validação, timeout, isolamento)?
  12. Pentest/DAST/fuzzing com cadência definida e achados rastreados até o fechamento?
Na entrevista

"Como incluiria segurança no ciclo de desenvolvimento de APIs?" Modelagem de ameaças no design, contrato OpenAPI como fonte de validação, testes automatizados de autorização e fuzzing na pipeline, varredura de segredos e dependências, gateway e inventário em produção, e pentest periódico. Dê ao final métricas, não só ferramentas.

Para gestores

Defina o "mínimo inegociável" para uma API que toca dado de paciente (autorização por objeto testada, logs sem PII, inventário, dono) e transforme em critério de pronto. Acompanhe: tempo médio de correção de achados críticos, achados reincidentes por categoria e percentual de APIs com teste de autorização automatizado.

Cenários práticos

Cenário 1: a paciente que viu o exame do vizinho

Uma paciente relata ao SAC que, ao abrir o laudo no app, a URL tinha /exames/50231 e, por curiosidade, trocou para 50232 e viu o laudo de outra pessoa.

O que fazer
  • Tratar como incidente: acionar o encarregado e o jurídico; preservar logs; avaliar se houve acesso por terceiros (consulta aos logs por padrão de ids sequenciais).
  • Contenção imediata: bloquear a rota ou adicionar a checagem de dono no serviço de exames; só depois pensar em refatorar.
  • Corrigir a causa: autorização por objeto em todos os endpoints de exame (inclusive PDFs e URLs assinadas), com teste automatizado.
  • Rever outros endpoints com o mesmo padrão (id sequencial + sem checagem). Avaliar a comunicação à ANPD e aos titulares conforme o risco (art. 48).

Cenário 2: pentest aponta JWT aceito com alg: none

O relatório mostra que um token forjado, sem assinatura, é aceito pelo serviço de agenda.

O que fazer
  • Corrigir a validação para algoritmos fixos e emissor/audiência obrigatórios; atualizar a biblioteca; revisar todos os serviços que validam tokens.
  • Criar um teste de regressão (token none, token com aud errado, expirado, kid desconhecido).
  • Procurar nos logs evidência de uso de tokens forjados; considerar rotação de chaves se houver suspeita.
  • Padronizar a validação em uma biblioteca/gateway comum, para não depender de cada time.

Cenário 3: parceiro pede "uma chave que nunca expire"

O laboratório parceiro quer integrar resultados e diz que não consegue renovar tokens.

O que fazer
  • Explicar o risco e oferecer alternativa: client credentials com tokens de 10 a 15 minutos (é só uma chamada a mais) com escopo resultados.escrever.
  • Se o parceiro realmente não puder, usar mTLS e/ou API key com expiração anual, IP de origem permitido, cota e alerta de uso fora do padrão; registrar a exceção com dono e data de revisão.
  • Nunca criar uma chave com acesso a toda a API: escopo mínimo e um consumidor por chave.

Cenário 4: cadastro de webhook para operadoras

O time quer deixar cada operadora cadastrar a URL de callback pelo portal.

O que fazer
  • Exigir HTTPS e domínio previamente aprovado no contrato; validar o IP a cada envio; egress controlado.
  • Assinar as chamadas (HMAC com segredo por operadora, rotacionável) e documentar o replay window.
  • Timeout e limite de tamanho, sem redirecionamentos, e fila com dead letter para falhas (módulos 04 e 06).
  • Logar o envio (destino, status, latência), sem o corpo clínico.

Cenário 5: ambiente de homologação com dados reais

Descobre-se que a homologação foi populada com um dump de produção e tem uma API sem autenticação forte, exposta à internet.

O que fazer
  • Tirar do ar ou restringir imediatamente (VPN/IP); avaliar acesso indevido nos logs e acionar o processo de incidente se houver risco.
  • Substituir por dados sintéticos ou anonimizados; proibir cópia de produção sem aprovação do encarregado.
  • Incluir ambientes não produtivos no inventário e na varredura de superfície externa.

Perguntas de entrevista

01Qual a diferença entre autenticação e autorização em uma API?

Autenticação estabelece quem é o chamador (token válido, certificado). Autorização decide se ele pode executar aquela ação naquele objeto. A maior parte das falhas graves em APIs (BOLA, BFLA) é de autorização: o chamador estava autenticado.

02O que é BOLA e por que é o item número 1 do OWASP API Top 10?

É acessar objeto de outro usuário trocando um identificador, porque o servidor não verifica o relacionamento com o objeto. É o primeiro por ser muito frequente, de alto impacto e invisível para scanners genéricos, já que depende da regra de negócio.

03Usar UUID em vez de id sequencial resolve IDOR?

Não. Dificulta a enumeração, mas ids vazam por logs, links e respostas. O controle real é a checagem de autorização por objeto; o UUID é defesa extra.

04Devolver 403 ou 404 quando o usuário não pode ver um recurso?

Para dados sensíveis, 404 evita confirmar a existência do recurso. 403 é válido quando a existência não é segredo e ajuda o consumidor. Padronize e registre a tentativa na auditoria.

05Quando usar API key, OAuth client credentials ou mTLS?

API key para identificar consumidor e aplicar cota em baixo risco. Client credentials para serviço a serviço com escopo e expiração curta. mTLS (idealmente com tokens vinculados ao certificado) para parceiros regulados ou risco alto, aceitando o custo de gerir certificados.

06Quais verificações são obrigatórias ao validar um JWT?

Algoritmo fixo no servidor (nunca o do cabeçalho), assinatura pela chave do JWKS (pelo kid), iss, aud desta API, exp/nbf com pouca tolerância e os escopos exigidos pela rota.

07Como tratar rotação de chaves de assinatura de JWT?

O emissor publica as chaves no JWKS com kid; durante a rotação, a nova e a antiga ficam publicadas. O validador faz cache do JWKS e re-busca ao ver kid desconhecido, com limite de frequência. Tokens curtos tornam a transição simples.

08JWT ou token opaco com introspecção?

JWT valida offline e escala, mas não se revoga antes do exp; mitigue com vida curta. Opaco com introspecção permite revogação imediata ao custo de latência e dependência (com cache curto). A escolha depende do requisito de revogação e do perfil de tráfego.

09Qual a diferença entre escopo, papel e atributo?

Escopo limita o que o token/cliente pode; papel agrupa permissões por função; atributo (ou relação) avalia o contexto concreto: este médico, este paciente, esta unidade. Uma decisão completa combina os três.

10O que é mass assignment e como se defende?

É copiar o corpo da requisição diretamente na entidade, deixando o cliente definir campos como status ou perfil. Defesa: DTOs de entrada com allowlist, rejeição de campos extras (additionalProperties: false) e DTOs de saída explícitos.

11Como evitar que a API vaze campos na resposta?

Nunca serializar a entidade do banco; usar DTOs de saída por papel, testes de contrato que falham se aparecer campo novo e revisão de dados pessoais no design. Em consultas, selecionar só as colunas necessárias.

12O que é SSRF e onde aparece em APIs?

O servidor faz requisição a uma URL controlada pelo atacante e alcança recursos internos (metadados da nuvem, bancos). Aparece em webhooks, importação por URL, geração de PDF e pré-visualização de links. Defesa: allowlist, validar IP após DNS, sem redirecionamento, egress controlado.

13CORS protege a minha API contra acessos indevidos?

Não. É uma política do navegador sobre quais origens podem ler respostas; curl e servidores ignoram. Serve para limitar sites terceiros em chamadas de navegador, com allowlist exata, Vary: Origin e sem refletir qualquer origem com credenciais.

14Como proteger fluxos de negócio como reserva de consulta contra robôs?

Identificar os fluxos de valor, limitar por identidade (reservas ativas, intervalo), aplicar fricção proporcional ao risco (código, CAPTCHA, step-up), não confirmar existência em respostas e detectar padrões. Rate limit por IP sozinho não basta.

15O que são shadow e zombie APIs e como combatê-las?

Shadow: em produção sem registro. Zombie: depreciada que continua no ar. Combate-se com inventário vivo (contratos, gateway, DNS), comparação com tráfego real, dono e data de desativação para cada versão, e bloqueio de rotas não registradas no gateway.

16O que não pode estar em logs de uma API de saúde e o que deve estar na auditoria?

Não: tokens, senhas, CPF, corpo clínico. Sim: ator, ação, objeto (id interno), resultado, motivo da negação, traceId, origem e horário, em trilha imutável com acesso restrito. Dado de saúde é sensível (LGPD, art. 11) e o log precisa respeitar minimização.

17Como o gateway ajuda na segurança e quais são os seus limites?

Centraliza TLS, validação de token, rate limit, validação de esquema, logs e bloqueio de rotas não registradas. Não conhece regras de objeto e não protege contra acesso direto ao serviço pela rede interna: a autorização por objeto e a autenticação entre serviços continuam necessárias.

18Como você, como gestora, garantiria segurança consistente em vários times de API?

Padrões e bibliotecas comuns (validação de token, autorização, logs), um mínimo inegociável como critério de pronto, testes de segurança automatizados na pipeline, inventário com dono, revisão de design com checklist e métricas (cobertura de testes de autorização, tempo de correção, achados reincidentes). Mais incentivo a reportar falhas sem culpa.
