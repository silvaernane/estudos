MÓDULO 07 · Avançado

Compose avançado e projeto

O módulo 06 ensinou a descrever uma aplicação em um arquivo. Aqui o mesmo arquivo passa a servir desenvolvimento, teste e CI, sobe na ordem certa, guarda segredos fora do ambiente e escala o que pode escalar. Fechamos com um projeto completo de sete serviços e com o critério para saber quando o Compose deixou de ser suficiente.

Ao final você saberá
  • Combinar vários arquivos com merge, include, extends, âncoras YAML e extension fields, prevendo o resultado com docker compose config.
  • Ordenar a subida com healthchecks e depends_on, incluindo job de migração que roda e termina (service_completed_successfully).
  • Escolher entre variável de ambiente, secret e config, e saber o que cada um expõe.
  • Usar profiles, develop.watch, --scale, limites de recursos e logging, sabendo o que é respeitado fora do Swarm.
  • Montar, subir, testar e defender o projeto "agenda" (proxy, web, api, worker, migrate, db, redis) e dizer quando migrar para outro orquestrador.
1Intermediário

Compor arquivos: merge, include, extends e âncoras

Um projeto real tem mais de um contexto: o desenvolvedor quer bind mount e debugger, o CI quer um job de teste, o servidor quer versão fixa e nenhuma porta de debug. Duplicar o compose.yaml três vezes garante que eles divirjam. O Compose oferece quatro mecanismos de reaproveitamento, cada um resolvido em um momento diferente. Saber qual é qual evita a maior parte das confusões.

Nota de versão

Tudo aqui é Compose v2 (o plugin docker compose, não o antigo docker-compose em Python). O campo version: no topo do arquivo é obsoleto e só gera aviso: não use. O nome preferido do arquivo é compose.yaml; docker-compose.yml ainda é aceito.

Vários arquivos e o override automático

Sem a opção -f, o Compose procura compose.yaml e mescla compose.override.yaml automaticamente, se existir. Com -f, só os arquivos listados entram, na ordem dada, e o override automático deixa de ser lido. Os arquivos posteriores vencem os anteriores.

docker compose up -d                                   # compose.yaml + compose.override.yaml
docker compose -f compose.yaml up -d                   # só o base (produção)
docker compose -f compose.yaml -f compose.ci.yaml up   # base + CI (o override NÃO entra)
COMPOSE_FILE=compose.yaml:compose.ci.yaml docker compose up   # o mesmo, por variável (separador ":" no Linux, ";" no Windows)

docker compose config            # mostra o resultado final, já mesclado e interpolado
docker compose config --services # só os nomes dos serviços
Armadilha comum

Rodar docker compose -f compose.yaml -f compose.ci.yaml up no CI e esperar que os bind mounts do override de desenvolvimento estejam lá (ou, ao contrário, que não estejam). Com -f, o override automático some. Sempre confira o que vai rodar com docker compose ... config.

    ports: !override                  # em vez de concatenar, SUBSTITUI a lista do base
      - "127.0.0.1:3000:3000"
  db:
    ports: !reset []                  # remove o que o arquivo anterior definiu

include: compor projetos

include (a partir do Compose 2.20) importa outro arquivo Compose inteiro, com seus próprios caminhos relativos e variáveis. Serve para um time de plataforma publicar "o banco" ou "a observabilidade" e vários projetos reutilizarem.

include:
  - path: ../plataforma/observabilidade.yaml
  - path: ./db/compose.yaml
    project_directory: ./db           # caminhos relativos resolvidos aqui
    env_file: ./db/.env               # variáveis só para o arquivo incluído

services:
  api:
    depends_on: [postgres]            # "postgres" vem do arquivo incluído

Diferença essencial em relação ao merge: o conteúdo incluído é autocontido e conflito de nome de recurso (dois arquivos definindo o mesmo serviço) é erro, não mescla. Para customizar um serviço incluído, liste mais de um caminho em path (o primeiro é o base, os seguintes mesclam como overrides) ou use um arquivo de override à parte.

extends: herdar de um serviço

services:
  app-base:
    build: ./api
    restart: unless-stopped
    environment:
      LOG_LEVEL: info
services:
  worker:
    extends:
      file: common.yaml
      service: app-base
    command: ["node", "dist/worker.js"]

extends copia a definição de um serviço (de outro arquivo ou do mesmo) e aplica as mesmas regras de merge por cima. Os campos que ligam serviços entre si (depends_on, links, volumes_from) não são herdados, justamente porque dependem do conjunto de serviços de cada projeto.

Âncoras YAML e extension fields

Âncoras (&nome), aliases (*nome) e a chave de merge (<<) são recursos do YAML, não do Compose: resolvem-se ao ler o arquivo, antes de o Compose enxergar qualquer coisa. Chaves de topo começando com x- (extension fields) são ignoradas pelo Compose e servem de depósito para blocos reutilizáveis.

x-api-base: &api-base           # bloco reutilizável (ignorado pelo Compose)
  build:
    context: ./api
    target: prod
  restart: unless-stopped
  environment: &api-env
    DATABASE_HOST: db
    REDIS_URL: redis://redis:6379

x-logging: &default-logging
  driver: json-file
  options: { max-size: "10m", max-file: "3" }

services:
  api:
    <<: *api-base                  # traz build, restart e environment
    logging: *default-logging
    environment:                  # TROCA o environment inteiro (merge é raso)
      <<: *api-env                # truque: reimporta o mapa e acrescenta
      PORT: "3000"
  worker:
    <<: [*api-base]               # lista de âncoras também é aceita
    command: ["node", "dist/worker.js"]

Armadilha comum

A chave de merge << é rasa. Se o serviço define environment: próprio, ele substitui o mapa da âncora em vez de somá-lo (por isso o truque <<: *api-env acima). E uma âncora não existe fora do arquivo onde foi declarada: não dá para usar *api-base no compose.override.yaml.

Na entrevista

"Override e -f mesclam por tipo de campo: valores substituem, mapas se fundem, ports concatena e command substitui. include compõe projetos sem mesclar, extends herda um serviço e âncoras são só YAML, dentro de um arquivo. Eu confiro tudo com docker compose config."

Para gestores

Defina uma convenção única para o time: o base descreve o que roda em produção; o override automático é só conveniência de desenvolvimento; CI e produção sempre com -f explícito. Cobre que o docker compose config do ambiente de produção seja revisado em pull request, como código.

Ordem de subida: healthchecks, depends_on e jobs de migração

A forma curta depends_on: [db] só garante a ordem de início: o processo do banco foi iniciado, não que aceita conexões. Subir a API contra um Postgres ainda recuperando o WAL dá erro de conexão na primeira tentativa. A solução é medir "pronto" com um healthcheck e depender dessa condição.

Anatomia do healthcheck

db:
  image: postgres:17-alpine
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U app -d agenda"]   # exit 0 = saudável
    interval: 5s        # de quanto em quanto tempo testa
    timeout: 3s         # o teste que passar disso conta como falha
    retries: 10         # falhas seguidas até virar "unhealthy"
    start_period: 10s   # falhas no início não contam (tempo de aquecimento)
  • test aceita ["CMD", ...] (executa o binário direto), ["CMD-SHELL", "..."] (passa pelo /bin/sh -c) ou ["NONE"] (desliga um healthcheck herdado da imagem).
  • Estados: starting (no start_period), healthy e unhealthy. Aparecem em docker ps e docker compose ps.
  • Há ainda start_interval, um intervalo mais curto usado só durante o start_period, em versões recentes do Engine. Confirme na sua versão antes de depender dele.
  • O teste roda dentro do container: a ferramenta (wget, curl, pg_isready) precisa existir na imagem. Em imagem distroless, faça o próprio binário da aplicação oferecer um modo --healthcheck.
Armadilha comum

Fora do Swarm e do Kubernetes, um container unhealthy não é reiniciado. O healthcheck só informa (e libera ou bloqueia o depends_on). restart: unless-stopped reage a processo que morre, não a processo que trava. Para auto-cura por saúde no Docker puro, é preciso uma ferramenta externa ou um orquestrador.

depends_on na forma longa

api:
  depends_on:
    db:
      condition: service_healthy                  # espera o healthcheck passar
    migrate:
      condition: service_completed_successfully   # espera TERMINAR com exit 0
    redis:
      condition: service_started                  # o padrão da forma curta
      restart: true                               # se redis for reiniciado pelo Compose, reinicia a api
    adminer:
      condition: service_started
      required: false                             # se o serviço estiver desligado (profile), não é erro
CondiçãoLibera o dependente quandoUso típico
service_startedo container foi iniciadoserviços sem healthcheck, ordem simples
service_healthyo healthcheck ficou healthybanco, cache, broker, API da qual outro depende
service_completed_successfullyo container terminou com código 0migrations, seed, geração de assets, init jobs

Migração como job separado

Se cada réplica da API rodasse a migração ao iniciar, duas réplicas subindo juntas disputariam o mesmo ALTER TABLE. Um serviço migrate com a mesma imagem da API, outro command, restart: "no" e service_completed_successfully nos dependentes resolve a corrida e dá um ponto único de falha visível:

$ docker compose up -d
 ✘ Container agenda-migrate-1  service "migrate" didn't complete successfully: exit 1
dependency failed to start: container agenda-migrate-1 exited (1)

$ docker compose logs migrate
migrate-1  | ERROR: relation "paciente" already exists
  • A migração deve ser idempotente (ferramentas como Flyway, Liquibase e as migrations de ORMs guardam uma tabela de controle) e usar lock (advisory lock no PostgreSQL), para o caso de duas execuções simultâneas.
  • O job termina e o container fica em Exited (0). Ele não aparece em docker compose ps sem -a, e isso é normal.
  • Migração que mexe em tabelas grandes (como atendimento) deve ser compatível com a versão anterior da aplicação (padrão expandir/contrair): adiciona-se a coluna, depois muda-se o código, depois remove-se a antiga. Isso importa quando duas versões coexistem durante o deploy.
Regra de bolso

A aplicação sempre faz retry com espera ao conectar. O depends_on é um otimizador de subida no Compose, não uma garantia: o banco pode reiniciar depois, e o Kubernetes não oferece ordem nenhuma.

Saiba mais

Healthcheck não é liveness probe nem readiness probe do Kubernetes, embora se pareçam. Um /health que consulta o banco é útil para ordenar a subida no Compose, mas, num orquestrador que reinicia por saúde, uma falha momentânea do banco pode derrubar todas as APIs em cascata. Separe "estou vivo" de "estou pronto para receber tráfego". O assunto continua no módulo 10 e na trilha de APIs (confiabilidade).

Na entrevista

"depends_on simples só ordena o início. Eu uso service_healthy para banco e cache e service_completed_successfully para o job de migração, que roda uma vez e termina. Mesmo assim a aplicação reconecta sozinha, porque a ordem de subida não resolve o banco que cai depois."

Para gestores

Pergunte ao time onde a migração roda hoje. "No startup de cada instância" é risco de deploy quebrado em horário de pico. Peça migração versionada, idempotente, com job próprio no pipeline e plano de reversão (em geral, migração para frente compatível, não "rollback de schema").

Variáveis, secrets e configs

Credenciais em variável de ambiente aparecem em docker inspect, em /proc/<pid>/environ, em dumps de erro e são herdadas por todo processo filho. Secrets e configs resolvem isso levando o dado como arquivo. Antes, vale separar as três fontes de variáveis, que a maioria mistura.

Quem lê o quê: .env, env_file e environment

    image: registry.exemplo.com/api:${TAG:-dev}        # do shell/.env, ou "dev"
    env_file:
      - path: ./api.env
        required: false                                  # não falha se o arquivo não existir
    environment:
      LOG_LEVEL: ${LOG_LEVEL:-info}

Formas de interpolação: ${VAR:-padrao} (padrão se não definida ou vazia), ${VAR-padrao} (só se não definida), ${VAR:?mensagem} (erro se não definida ou vazia). A precedência para o valor final dentro do container é: docker compose run -e, depois environment, depois env_file, depois o ENV do Dockerfile.

Armadilha comum

docker compose config imprime o YAML já interpolado, com senhas vindas do .env em texto puro. Não cole essa saída em chamado nem a deixe em log de CI sem mascarar.

Secrets

No Compose (fora do Swarm), um secret declarado com file: é montado como arquivo somente leitura em /run/secrets/<nome> no container que o referencia. Só os serviços listados em secrets: o enxergam.

services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password   # convenção *_FILE das imagens oficiais
    secrets: [db_password]
  api:
    environment:
      DATABASE_PASSWORD_FILE: /run/secrets/db_password
      INTEGRACAO_TOKEN_FILE: /run/secrets/integracao_token
    secrets:
      - db_password
      - integracao_token

secrets:
  db_password:
    file: ./secrets/db_password.txt        # arquivo no host, fora do git
  integracao_token:
    environment: INTEGRACAO_TOKEN          # lê de uma variável do host ou do CI
import { readFileSync } from "node:fs";

// aceita VAR_FILE (secret) ou VAR (desenvolvimento rápido)
export function secret(name: string): string {
  const file = process.env[`${name}_FILE`];
  return file ? readFileSync(file, "utf8").trim() : process.env[name] ?? "";
}
  • Ganho real: o valor não aparece em docker inspect nem no ambiente do processo e de seus filhos.
  • Limite real: fora do Swarm o secret é um bind mount do arquivo do host. Quem lê o disco do host lê o segredo, e as permissões do arquivo no host valem. Não é cofre nem tem rotação automática.
  • Aplicações que só leem variável: um entrypoint que faz export DB_PASSWORD="$(cat /run/secrets/db_password)" e depois exec "$@" funciona, mas recoloca o valor no ambiente daquele processo. Prefira ensinar a aplicação a ler o arquivo.
  • Segredo de build (token de registry privado no npm ci) é outro mecanismo: build.secrets e RUN --mount=type=secret (módulos 03 e 09). Nunca ARG/ENV, que ficam nas camadas.

Configs

configs têm a mesma mecânica dos secrets, mas para configuração não sensível que você quer declarar em vez de montar na mão: nginx.conf, prometheus.yml. Podem vir de file:, de content: (inline no YAML) ou de environment:.

services:
  proxy:
    image: nginx:1.27-alpine
    configs:
      - source: proxy_conf
        target: /etc/nginx/conf.d/default.conf   # sem target, o padrão é /<nome>

configs:
  proxy_conf:
    file: ./proxy/nginx.conf
  banner:
    content: |
      ambiente=${AMBIENTE:-dev}

Regra de bolso

No .gitignore: .env, secrets/. No repositório: .env.example com nomes e valores fictícios. Em produção real, o Compose lê o secret de um arquivo que o pipeline de deploy criou a partir do cofre (Vault, AWS Secrets Manager, GitHub Secrets), nunca de algo versionado.

Na entrevista

"Variável de ambiente vaza em docker inspect e em processos filhos. Com secret do Compose a senha vira arquivo em /run/secrets, visível só ao serviço que o declara, e a aplicação lê pela convenção *_FILE. Não substitui um cofre: em produção o arquivo vem de um gerenciador de segredos."

Para gestores

Dados de saúde e credenciais de integração (convênios, laboratórios) exigem trilha de quem acessou e rotação. Compose secrets não oferecem nenhum dos dois. Garanta que há rotação definida, que nenhum segredo está no repositório (varredura com gitleaks ou similar no CI) e que quem tem acesso ao host de produção é um grupo pequeno e auditado.

Profiles e ambientes: dev, teste e CI com o mesmo arquivo

O objetivo é um só desenho da aplicação, com variações pequenas e explícitas por ambiente. Duas ferramentas fazem isso: profiles ligam e desligam serviços; arquivos de override mudam como os serviços são configurados.

Profiles

Serviço sem profiles sobe sempre. Serviço com profiles: [x] só sobe se o profile for ativado.

services:
  adminer:
    image: adminer
    profiles: [debug]
  tests:
    build: { context: ./api, target: dev }
    profiles: [test]
    command: ["npm", "test"]
docker compose --profile debug up -d          # sobe tudo + adminer
docker compose --profile debug --profile test up -d
COMPOSE_PROFILES=debug,test docker compose up -d
docker compose run --rm tests                 # citar o serviço pelo nome ativa o profile dele
docker compose --profile "*" config --services   # todos os profiles (útil para listar)
  • Serviço sem profile que depende de serviço com profile dá erro de configuração. O contrário é comum: tests (profile test) depende de api.
  • docker compose down também só remove os serviços dos profiles ativos. Rode com os mesmos profiles ou use --profile "*".
  • Profiles não são ambientes. Misturar "profile = produção" com "profile = dev" no mesmo arquivo cria exatamente o problema que se queria evitar: ninguém consegue ler o que roda em cada lugar.

Armadilha comum

Esquecer o down -v no CI. Runners reutilizados acumulam volumes e redes de execuções antigas, e o banco da execução seguinte começa com dados da anterior. O COMPOSE_PROJECT_NAME único evita colisão de nomes, mas não limpa nada.

Regra de bolso

O teste de integração acessa o sistema pelo mesmo caminho do usuário (o proxy), dentro da rede do Compose. Se só funciona com porta publicada no host, o teste depende do ambiente do runner.

Na entrevista

"Mesmo compose.yaml para todos os ambientes; o override automático dá o conforto de desenvolvimento, o CI usa -f com um arquivo próprio e profile test, e a produção usa só o base com a tag fixada. Cada execução de CI tem um project name único e termina com down -v."

Para gestores

"Funciona na minha máquina" costuma ser diferença de ambiente. Ter o CI subindo o mesmo arquivo que o desenvolvedor usa corta essa classe de problema. O custo é tempo de pipeline: acompanhe a duração do job e use cache de build (módulo 08).

Armadilha comum

migrate, api e worker têm build e image idênticos, então o Compose "constrói" três vezes. O cache do BuildKit torna as duas últimas instantâneas e o resultado é a mesma imagem (mesmo ID). Por que image: agenda/api-dev no override

As três peças migrate, api e worker compartilham o nome agenda/api:${TAG}. Se o override só trocasse o target da API para dev, o Compose construiria a imagem dev com o mesmo nome e tag da imagem prod usada por worker e migrate: a última construção vence e o worker passaria a rodar a imagem de desenvolvimento (ou vice-versa), de forma silenciosa. Dar à API de dev um nome próprio elimina a colisão. Na mesma linha, o build.target do override mescla com o build do base (mapa com mapa): o context continua o mesmo.

Pontos para defender numa entrevista
  • Segmentação de rede: o proxy não alcança o banco; um comprometimento do proxy não dá caminho direto ao Postgres.
  • Uma porta publicada em produção (a do proxy).
  • Migração como serviço separado, que roda uma vez, em vez de rodar dentro de cada réplica da API.
  • Mesma imagem, processos diferentes (api, worker, migrate): um build, um artefato versionado.
  • Healthchecks + depends_on com condição para a ordem de subida, e aplicação que reconecta sozinha.
  • Senha em secret, não em variável de ambiente nem no git.
  • Limites de recurso e rotação de log definidos, para um serviço não consumir o host inteiro.

Roteiro de subida e de testes do projeto

Ter os arquivos não basta: um projeto só "existe" quando você sabe subi-lo do zero, provar que funciona e provar que falha do jeito esperado. Este é o roteiro que serve também como checklist de revisão.

Subir do zero

  1. Preparar o que não está no git. cp .env.example .env; criar secrets/db_password.txt com uma senha de desenvolvimento (mkdir -p secrets && printf 'dev-senha-fraca' > secrets/db_password.txt). Sem esse arquivo o Compose recusa subir: o erro cita o caminho do secret.
  2. Validar a configuração. docker compose config -q (silencioso, só erra se houver problema). Em produção, o mesmo com -f compose.yaml.
  3. Subir. docker compose up -d --build --wait. O --wait bloqueia até os serviços ficarem prontos e devolve erro se algum falhar.
  4. Conferir o estado. Todos healthy ou Up; migrate terminou com 0.
  5. Rodar os testes de fumaça (abaixo) e, em desenvolvimento, docker compose watch.

O que o Compose faz no up, em ordem:

  1. Constrói web e api. migrate, api e worker usam o mesmo contexto e alvo; o cache do BuildKit faz a imagem ser construída uma vez.
  2. Cria as redes agenda_frontend e agenda_backend e os volumes agenda_pgdata e agenda_redisdata (o prefixo é o name: do projeto).
  3. Sobe db e redis e espera os healthchecks.
  4. Roda migrate; se sair com 0, libera api e worker.
  5. Quando api e web ficam healthy, sobe o proxy.

Testes de fumaça: provar o desenho

Cada decisão do projeto vira uma verificação executável. Um script curto no repositório (e no CI) impede que alguém desfaça a segmentação de rede sem perceber.

#!/bin/sh

FAILED=0

  if sh -c "$2" >/dev/null 2>&1; then echo "OK     $1"; else echo "FALHA  $1"; FAILED=1; fi
}

check "front-end responde 200 pelo proxy"   "curl -fsS $BASE/ -o /dev/null"
check "API responde via /api (contrato /health)" "curl -fsS $BASE/api/health"
check "proxy NÃO alcança o banco"           "! docker compose exec -T proxy nc -z -w2 db 5432"
check "senha NÃO está no ambiente da api"   "! docker compose exec -T api printenv | grep -q '^DATABASE_PASSWORD='"

Limites de recursos: o que o Compose respeita

Sem limite, um container pode consumir toda a memória do host e o OOM killer do kernel escolher a vítima (às vezes o banco). Limites são cgroups do kernel: valem em qualquer Docker, não dependem do Swarm.

services:
  api:
    deploy:
      resources:
        limits:   { cpus: "1.0", memory: 512M }    # teto rígido
        reservations: { memory: 256M }              # reserva "macia" (preferência de agendamento)
    pids_limit: 200                                 # contra fork bomb / vazamento de threads
  worker:
    mem_limit: 512m                                 # forma curta, equivalente ao limits.memory
    cpus: 0.5
ChaveNo Compose v2 fora do Swarm
deploy.resources.limits (cpus, memory)respeitado (o mesmo que cpus e mem_limit)
deploy.resources.reservationsmemória: reserva "macia" (mem_reservation); não garante nada se o host está sem memória
deploy.replicasrespeitado no up (equivale ao --scale)
deploy.placement, update_config, rollback_config, modesem efeito: são do Swarm; use restart: para política de reinício
pids_limit, ulimits, shm_sizerespeitados; úteis (o Postgres pode precisar de shm_size maior)

  • Memória estoura = o processo morre (código 137). CPU estoura = o processo é estrangulado (throttling por cota): ninguém morre, mas a latência sobe de forma enganosa, com uso médio de CPU "baixo".
  • Runtimes precisam conhecer o limite: a JVM é container-aware; no Node, ajuste o heap (NODE_OPTIONS=--max-old-space-size, em torno de 70-75% do limite) para não ser morto antes de o coletor agir.
  • O limite do banco merece cuidado: o Postgres usa a memória para shared_buffers e para o cache do sistema; um limite apertado causa OOM em consultas grandes. Dimensione com o DBA.

Logging no Compose

A regra de ouro: o aplicativo escreve em stdout/stderr, de preferência em JSON, e o Docker coleta. O driver padrão, json-file, não faz rotação: um serviço verboso enche o disco do host.

x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"        # rotaciona a cada 10 MB
    max-file: "3"          # mantém 3 arquivos (30 MB por container)

services:
  api:
    logging: *default-logging
  proxy:
    logging:
      driver: local        # alternativa com rotação por padrão, formato interno compacto
  worker:
    logging:
      driver: fluentd      # envia a um coletor remoto
      options: { fluentd-address: "logs.interno:24224", tag: "agenda.worker" }
docker compose logs -f --tail 100 api worker      # últimas 100 linhas e acompanha
docker compose logs --since 10m -t api            # últimos 10 minutos, com horário
docker compose logs --no-color > logs.txt         # para anexar a um chamado
  • Com driver remoto (fluentd, gelf, awslogs, splunk), o docker logs local continua funcionando em Engines recentes (dual logging); em versões antigas, não.
  • Padrão global do host: /etc/docker/daemon.json com "log-driver" e "log-opts". Vale só para containers criados depois da mudança e do restart do daemon.
  • Log não é para segredo nem dado de paciente: registre identificadores, não conteúdo clínico (LGPD).
Armadilha comum

Servidor com disco 100% cheio por causa de /var/lib/docker/containers/*/*-json.log de alguns GB. A correção (max-size/max-file) só vale ao recriar o container.

Na entrevista

"deploy.resources.limits é respeitado pelo Compose v2 mesmo sem Swarm, equivalente a mem_limit e cpus. Memória acima do limite mata o processo com 137; CPU acima é throttling. --scale serve bem para worker, mas não resolve balanceamento, autoscaling nem rolling update."

Para gestores

Limites e rotação de log são o seguro mais barato contra um serviço derrubar o host inteiro. Exija-os na revisão de qualquer novo serviço, e peça métricas (memória, CPU, reinícios) para dimensionar com dado, não com palpite.

Quando o Compose deixa de ser suficiente

O Compose é excelente para desenvolvimento, CI e produção de host único com poucos serviços. Ele não foi desenhado para o resto. Reconhecer o ponto de virada evita dois erros opostos: sofrer com Compose onde se precisa de orquestrador, e adotar Kubernetes onde uma VM com Compose bastava.

Compose em produção de host único: como fazer direito

ssh app01 'cd /opt/agenda && \
  TAG=1.4.2 REGISTRY=ghcr.io/equipe docker compose -f compose.yaml pull && \
  TAG=1.4.2 REGISTRY=ghcr.io/equipe docker compose -f compose.yaml up -d --remove-orphans --wait'
# rollback: o mesmo comando com TAG=1.4.1
  • O servidor não constrói: puxa a imagem já testada pela tag (melhor, pelo digest; módulo 08).
  • up -d só recria os serviços cujo YAML ou imagem mudaram.
  • Defina o que o host precisa: backup dos volumes (pgdata) testado com restauração, atualização do SO, monitoramento do Docker e do disco, e quem é chamado quando cai.
Regra de bolso

Migre quando a conta do tempo dos humanos virar: você passa mais horas compensando o que o Compose não faz (deploy fora do horário, restart manual, plano para o host cair) do que custaria adotar uma plataforma gerenciada. Antes de Kubernetes, considere um serviço de containers gerenciado.

Na entrevista

"Compose é ótimo para dev, CI e produção em host único. Passo para um orquestrador quando preciso de alta disponibilidade entre hosts, rolling update, autoscaling ou políticas de acesso. Mas é decisão de custo: Kubernetes só se compensar o time para operá-lo; muitas vezes um serviço gerenciado resolve."

Para gestores

Em saúde, a pergunta é o impacto da indisponibilidade (agenda parada, laudo inacessível) e quem opera o plantão. Defina o RTO (quanto tempo pode ficar fora) e o RPO (quantos dados pode perder). Um host único com Compose só serve se esses números forem compatíveis com a pior falha de uma máquina.

Laboratórios graduados. Faça no projeto da agenda (ou num compose.yaml mínimo equivalente), confira cada resposta com docker compose config e abra a resolução só depois de tentar.

E1Merge: dado o base e o override abaixo, escreva o que docker compose config mostra para api e confira.
# compose.yaml
services:
  api:
    image: agenda/api:1.0
    command: ["node", "dist/server.js"]
    environment: { LOG_LEVEL: info, TZ: America/Sao_Paulo }
    ports: ["3000:3000"]
    volumes: ["./cfg:/app/cfg:ro"]

# compose.override.yaml
services:
  api:
    command: ["npm", "run", "dev"]
    environment: { LOG_LEVEL: debug }
    ports: ["9229:9229"]
    volumes: ["./cfg-dev:/app/cfg:ro"]

Resposta. image permanece agenda/api:1.0. command vira ["npm","run","dev"] (lista de comando é substituída). environment fica com LOG_LEVEL=debug e TZ=America/Sao_Paulo (mapa mesclado por chave). ports tem as duas: 3000 e 9229 (concatenadas). volumes tem uma entrada só: as duas montam em /app/cfg, e volumes mesclam pelo destino, então vence ./cfg-dev. Verifique com docker compose config.

Extra. Faça ports: !override ["3000:3000"] no override e veja a lista deixar de ser concatenada.

E2Job de migração: faça o migrate falhar de propósito (ex.: command: ["sh","-c","echo erro; exit 1"]). Observe o up -d, o estado dos serviços e como se recupera.

Resposta. O up -d falha com dependency failed to start: container agenda-migrate-1 exited (1). db e redis estão de pé; api, worker e proxy não foram iniciados (nem ficam em loop), o que é o comportamento desejado: não se sobe aplicação com schema pela metade. O erro está em docker compose logs migrate.

docker compose up -d                    # falha
docker compose ps -a --format 'table {{.Service}}\t{{.Status}}'
docker compose logs migrate             # a causa
# corrija o command/migration e rode de novo:
docker compose up -d                    # recria o migrate; se sair 0, o resto sobe

Reexecutar up -d recria o job (a configuração mudou) e o grafo segue. Se fosse só uma falha transitória sem mudança de configuração, docker compose up -d --force-recreate migrate reexecutaria.

E3Secrets: hoje a senha do banco está em environment: POSTGRES_PASSWORD: .... Migre para secret e prove, com comandos, que melhorou.
mkdir -p secrets && printf 'dev-senha-fraca' > secrets/db_password.txt
echo "secrets/" >> .gitignore
# no compose.yaml: troque POSTGRES_PASSWORD por POSTGRES_PASSWORD_FILE=/run/secrets/db_password,
# adicione "secrets: [db_password]" ao serviço e o bloco secrets: no topo (file: ./secrets/db_password.txt)
docker compose up -d --force-recreate db

# provas
docker inspect -f '{{json .Config.Env}}' agenda-db-1 | grep -c dev-senha-fraca   # 0: fora do ambiente
docker compose exec db ls -l /run/secrets/db_password                            # existe, somente leitura
git check-ignore -v secrets/db_password.txt                                      # ignorado pelo git

Cuidado: o Postgres só lê a senha na primeira inicialização do volume. Com um volume pgdata já criado, trocar a variável não altera a senha do usuário. Para o laboratório, rode docker compose down -v antes (apaga os dados de desenvolvimento) ou altere a senha com ALTER USER. O ganho real: a senha saiu do docker inspect e do ambiente do processo; o limite continua sendo o arquivo no host.

E4Profiles e escala: coloque o adminer num profile, suba o worker com 3 réplicas e depois tente escalar a api (que publica a porta 3000 no override). Explique o que aconteceu.
docker compose up -d                          # sem adminer
docker compose --profile debug up -d          # com adminer
docker compose up -d --scale worker=3
docker compose ps worker                      # três instâncias
docker compose up -d --scale api=2            # erro de porta

Resposta. O adminer só aparece com --profile debug. O worker escala sem problema: não publica porta e várias instâncias consomem da mesma fila. A api falha na segunda réplica com port is already allocated porque o override publica 3000:3000. Saídas: escalar a API atrás do proxy sem publicar porta (em produção o base já não publica), usar faixa de portas ou, em desenvolvimento, simplesmente não escalar. Para o proxy enxergar as novas réplicas, use a variante com resolver 127.0.0.11 da seção 7.

E5CI: escreva o passo de CI que sobe o projeto com compose.ci.yaml, roda o serviço tests, devolve o código de saída correto e limpa tudo mesmo com falha. Simule um teste falhando e comprove a limpeza.
export COMPOSE_PROJECT_NAME="agenda-ci-$RANDOM"
C="docker compose -f compose.yaml -f compose.ci.yaml"
trap '$C down -v --remove-orphans' EXIT      # limpa em qualquer saída, inclusive erro

$C up -d --build --wait
$C run --rm tests                            # o código de saída do script é o do npm test
# fim do script: o trap limpa

Prova. Altere um teste para falhar e rode: o script sai com código diferente de 0. Depois confira docker ps -a --filter "name=agenda-ci", docker volume ls e docker network ls: nada com o prefixo do projeto deve ter ficado. O trap ... EXIT faz o papel do if: always() de um passo de CI. Alternativa de uma linha: up --abort-on-container-exit --exit-code-from tests, que também propaga o código do serviço escolhido.

E6Limites: limite a memória da API a 64 MB, provoque estouro (alocando memória no processo ou rodando docker compose exec api node -e "...") e leia a evidência. Depois explique como dimensionar de verdade.
# mem_limit: 64m no serviço api (ou deploy.resources.limits.memory: 64M)
docker compose up -d api
docker compose exec api node -e "const a=[];while(true)a.push(Buffer.alloc(10*1024*1024,1))"
# o exec morre; para o container principal, provoque o estouro na própria aplicação
docker inspect -f '{{.State.OOMKilled}} {{.State.ExitCode}}' agenda-api-1    # true 137
docker stats --no-stream agenda-api-1                                        # uso vs limite
dmesg | grep -i 'killed process'                                             # no host Linux

Resposta. O container principal morre com OOMKilled=true e código 137, e a política restart o recria (se houver loop de mortes, aparece como Restarting). Dimensionar: meça o pico real em carga representativa (docker stats, métricas), dê folga de 20 a 30% sobre o pico, ajuste o heap da runtime (--max-old-space-size no Node) abaixo do limite e revise quando o consumo crescer. Um limite derivado de palpite é tão perigoso quanto nenhum.

10Prática

Cenários práticos de trabalho

Cenário 1: "A API sobe, mas reclama que o banco recusou conexão"

O que fazer. Veja se o depends_on do serviço usa condition: service_healthy e se o db tem healthcheck (docker compose ps mostra (healthy)). Se a ordem está certa e o erro acontece só depois de o banco reiniciar, o problema é a aplicação: o pool de conexões não reconecta. Corrija com retry e backoff na conexão, e teste com docker compose restart db. Lembre que a ordem de subida do Compose não existe no Kubernetes: a correção durável é a resiliência da aplicação.

Cenário 2: "Dois pipelines de CI no mesmo runner se atropelam"

O que fazer. Sintoma: port is already allocated, nomes de container em conflito ou testes vendo dados da execução anterior. Causa: mesmo project name, portas fixas e falta de limpeza. Corrija: COMPOSE_PROJECT_NAME único por execução (inclua o ID do run), nenhuma porta fixa no host (ports: !reset [] no compose.ci.yaml ou porta por variável), testes acessando o proxy dentro da rede e down -v --remove-orphans garantido (trap ou if: always()). Limpe o runner uma vez com docker system prune (com cuidado em runner compartilhado).

Cenário 3: "O worker em desenvolvimento está rodando o código errado"

O que fazer. Verifique docker compose images e docker compose config: se api (alvo dev) e worker (alvo prod) compartilham o mesmo image: agenda/api:dev, o último build sobrescreve a tag. Dê à API de dev um nome próprio (image: agenda/api-dev), como no override do projeto, reconstrua com docker compose build --no-cache api worker e confirme com docker inspect -f '{{.Image}}' agenda-worker-1. Lição: duas variantes de build nunca devem dividir nome e tag.

Cenário 4: "Achamos a senha do banco no repositório e no log do CI"

O que fazer. Trate como incidente. (1) Rotacione a credencial agora: remover do git não desfaz o vazamento. (2) Reescreva o histórico apenas se necessário e tenha em mente que clones e caches já têm o valor. (3) Migre o uso para secret (*_FILE), secrets/ e .env no .gitignore, .env.example versionado. (4) Ative varredura de segredos no CI (gitleaks ou o recurso da plataforma) e mascare variáveis nos logs; revise quem roda docker compose config em pipeline. (5) Se o banco guarda dados de pacientes, acione o fluxo de incidente de segurança da empresa e avalie o encarregado de proteção de dados (LGPD).

Cenário 5: "O container da API morre toda tarde com código 137"

O que fazer. Confirme com docker inspect -f '{{.State.OOMKilled}}' e docker stats. Se foi OOM por limite baixo, o consumo cresce com a carga do pico da tarde: meça, aumente o limite com folga e ajuste o heap. Se a memória sobe sem parar até estourar, é vazamento: capture um heap snapshot, compare e corrija; o limite só contém o dano. Enquanto isso, restart: unless-stopped mascara o problema, então alerte em reinícios (métrica de restart count) e escale o worker/API de forma que um reinício não derrube o serviço. Em último caso, discuta migrar para plataforma com autoscaling.

12Entrevista

Perguntas de entrevista

Responda em voz alta antes de abrir. A resposta ideal tem uma frase de definição e um exemplo prático.

01Para que serve o compose.override.yaml?

É mesclado automaticamente ao compose.yaml quando se roda docker compose up sem -f. Convenção: o base descreve produção; o override acrescenta só o de desenvolvimento (bind mounts, portas de debug, alvo dev). Com -f, ele deixa de ser lido.

02Como o Compose mescla dois arquivos? O que acontece com ports, environment e command?

Por tipo: valores simples e command/entrypoint são substituídos; mapas como environment são mesclados por chave; ports é concatenado; volumes mescla pelo ponto de montagem. As tags !override e !reset mudam isso. Confirmo o resultado com docker compose config.

03Diferença entre include, extends e âncoras YAML.

Âncoras são YAML puro, resolvidas no parse e restritas ao arquivo. extends herda a definição de um serviço (de outro arquivo também), sem trazer depends_on. include importa um projeto Compose inteiro, autocontido, e conflito de nome é erro, não merge.

04Por que depends_on simples não basta? Como garantir que o banco está pronto?

Só ordena o início dos containers. Defino um healthcheck no banco (pg_isready) e uso condition: service_healthy no dependente. Mesmo assim a aplicação precisa de retry, porque o banco pode cair depois.

05Como rodar migrations no Compose sem que cada réplica da API as execute?

Um serviço migrate com a mesma imagem e outro command, restart: "no", e depends_on com service_completed_successfully nos dependentes. Roda uma vez e termina; se falhar, a API nem sobe. A migração deve ser idempotente e com lock.

06Um container unhealthy é reiniciado pelo Docker?

No Docker puro e no Compose, não: o healthcheck só informa o estado e controla o depends_on. restart reage a processo que morre. Reiniciar por saúde exige Swarm, Kubernetes ou uma ferramenta externa.

07Variável de ambiente ou secret para uma senha? Por quê?

Secret. A variável aparece em docker inspect, em /proc/<pid>/environ e é herdada por processos filhos. O secret do Compose é um arquivo em /run/secrets, lido pela aplicação (convenção *_FILE). Em produção o arquivo deve ser provido por um cofre; o Compose não rotaciona nem audita.

08Qual a diferença entre .env, env_file e environment?

.env alimenta a interpolação do YAML (${TAG}) e não chega ao container por si só. env_file carrega um arquivo de variáveis para dentro do container. environment define variáveis direto no YAML e vence o env_file.

09O que são profiles e quando usá-los?

Rótulos que tornam serviços opcionais: sobem só com --profile x ou COMPOSE_PROFILES. Uso para ferramentas auxiliares (adminer, mailhog) e para o job de testes. Não são "ambientes": variações de configuração por ambiente ficam em arquivos de override.

10Como usar o mesmo arquivo em desenvolvimento, CI e produção?

Base = produção; override automático para dev; -f compose.yaml -f compose.ci.yaml para CI, com profile test e COMPOSE_PROJECT_NAME único; produção só com o base e TAG fixa. O CI valida com docker compose config e termina com down -v.

11Que ações o compose watch oferece e em que versão ficou estável?

sync, rebuild, sync+restart e sync+exec. Ficou estável (GA) no Compose 2.22, que veio no Docker Desktop 4.24, em outubro de 2023. É para desenvolvimento, alternativa a bind mount sem os problemas de desempenho e permissão no Windows e no macOS.

12O que o --scale resolve e quais são seus limites?

Sobe N instâncias de um serviço, bom para workers. Limites: não funciona com porta fixa no host nem container_name; não há balanceador de verdade (DNS round robin, e o Nginx cacheia a resolução); réplica unhealthy não sai de rotação; sem autoscaling nem rolling update.

13deploy.resources funciona fora do Swarm?

No Compose v2, sim: limits (cpus, memory) é aplicado como cgroup, equivalente a cpus e mem_limit. Chaves de orquestração (placement, update_config, rollback_config) não têm efeito. Memória estourada mata com 137; CPU estourada gera throttling.

14Como evitar que os logs encham o disco do servidor?

O json-file padrão não rotaciona. Configuro max-size e max-file no serviço (ou o driver local), ou um padrão em daemon.json (vale só para containers novos). Para centralizar, envio a um coletor (fluentd, gelf, awslogs) e mantenho a aplicação escrevendo em stdout.

15Desenhe a arquitetura de uma aplicação web com API, worker, banco e fila e explique as redes.

Proxy na rede frontend com a única porta publicada; web e API no frontend; API, worker, migrate, banco e Redis na backend. O proxy não alcança o banco. Mesma imagem para API, worker e migrate, com comandos diferentes; migração como job; segredo em secret; healthchecks guiando a subida.

16Por que a API de desenvolvimento tem image: agenda/api-dev no override?

Porque migrate, api e worker usam o mesmo nome e tag. Se a API só trocasse o target para dev, o build sobrescreveria a tag usada pelos outros e o worker rodaria a imagem errada, em silêncio. Nome próprio evita colisão.

17Quando você tiraria um sistema do Compose? Que critérios usa?

Quando preciso de alta disponibilidade entre hosts, deploy sem indisponibilidade, autoscaling, políticas de acesso por equipe ou segredos com rotação e auditoria. Primeiro considero um serviço gerenciado de containers; Kubernetes só se o número de serviços e times justificar o time de plataforma. O critério é RTO/RPO e o custo humano de compensar o que o Compose não faz.

18Como você, como gestora, avalia se um serviço novo está pronto para produção em Compose?

Checklist: imagem versionada e escaneada; ordem de subida com healthcheck e migração como job; segredos fora do git e do ambiente; limites de CPU/memória e rotação de logs; só uma porta exposta; teste de fumaça no pipeline; backup restaurado de verdade; monitoramento e plantão definidos; RTO/RPO compatíveis com o host único.
