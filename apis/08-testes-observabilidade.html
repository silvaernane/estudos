Testes e observabilidade

Como testar APIs com confiança (integração real, contrato, carga) e como enxergar o que acontece em produção com logs, traces, métricas e SLOs.

Ao final você saberá
  • Montar uma estratégia de testes para APIs (pirâmide/troféu) e testar com dependências reais usando Testcontainers
  • Escolher entre contrato por schema (OpenAPI) e consumer-driven (Pact), e explicar o fluxo com o can-i-deploy
  • Usar mocks, stubs e sandboxes para parceiros, e conhecer Postman/Newman, Bruno, Hurl e REST Client
  • Planejar e ler testes de carga com k6 (smoke, load, stress, soak, spike) com metas em p95
  • Instrumentar uma API com logs JSON, correlation id, W3C Trace Context e OpenTelemetry
  • Definir SLIs, SLOs e error budget, alertas que acordam e monitoramento sintético, sem logar dados sensíveis
  • Conduzir a investigação de "a API está lenta" com método
1Intermediário

Pirâmide de testes e dependências reais

Testes existem para dar confiança para mudar. Uma API de agendamento que ninguém ousa tocar porque "pode quebrar o parceiro" é uma API sem testes úteis, mesmo que tenha 90 % de cobertura. A pergunta certa não é "quanto cobrimos?" e sim "o que acontece com o paciente e com o parceiro se isto falhar, e qual teste pegaria?".

A pirâmide e o troféu

Para APIs, o troféu costuma servir melhor: a maior parte do risco está nas fronteiras (HTTP, serialização, SQL, autenticação, filas), e não em funções puras. Regra de negócio complexa (cálculo de coparticipação, regras de elegibilidade) continua pedindo muitos unitários rápidos; mas o endpoint como um todo é testado de verdade, chamando HTTP e gravando no banco.

CamadaO que validaVelocidadeQuando falha
UnitárioRegra de negócio isolada (calcular valor, validar CPF, regra de remarcação)msLógica errada
Integração (componente)Endpoint HTTP + serialização + validação + SQL + migração em banco realsMapeamento, consulta, constraint, transação, índice
ContratoQue provedor e consumidor concordam sobre o formatosBreaking change acidental
E2E / sistemaFluxo completo entre vários serviços (ex.: agendar, notificar, cobrar)minIntegração entre times, configuração de ambiente

Unitário vs integração com dependências reais

O erro clássico é testar o repositório contra um banco em memória diferente do de produção (H2 no lugar de PostgreSQL, SQLite no lugar de Oracle). Passa no teste e falha em produção porque dialeto SQL, tipos, JSONB, índices parciais, locks e funções de data se comportam de outro jeito. A resposta moderna é o Testcontainers: biblioteca que sobe contêineres Docker descartáveis (PostgreSQL, Kafka, Redis, etc.) durante o teste e os remove ao fim.

@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
@Testcontainers
class AgendamentoApiIT {

  @Container
  @ServiceConnection                       // injeta URL/usuário/senha no datasource
  static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16");

  @Autowired TestRestTemplate http;

  @Test
  void naoPermiteDoisAgendamentosNoMesmoHorarioParaOMesmoMedico() {
    var req = new NovoAgendamento("pac_1", "med_204", "2026-04-02T14:30:00-03:00");

    var primeira = http.postForEntity("/v2/agendamentos", req, Agendamento.class);
    var segunda  = http.postForEntity("/v2/agendamentos", req, Problem.class);

    assertThat(primeira.getStatusCode()).isEqualTo(HttpStatus.CREATED);
    assertThat(segunda.getStatusCode()).isEqualTo(HttpStatus.CONFLICT);   // 409 vindo da constraint única
  }
}

O teste acima falharia com um mock de repositório e passaria "por engano" se a constraint única não existisse na migração. Só o banco real prova que a regra está garantida também no banco. As migrações (Flyway ou Liquibase) rodam no mesmo teste, então você testa o schema de verdade.

  • Vantagens: fidelidade, sem "funciona na minha máquina", qualquer pessoa roda com Docker, versão do banco fixada no código.
  • Custos: mais lento (segundos para subir o contêiner), exige Docker no CI. Reutilize o contêiner entre classes de teste (um contêiner estático por suíte) e deixe os dados limpos entre testes (transação com rollback ou truncate).
  • Oracle: existe módulo do Testcontainers para Oracle, mas as imagens são pesadas e o licenciamento exige atenção. Se a produção é Oracle, teste as consultas críticas nele; se o ambiente permitir só PostgreSQL, não finja que o resultado vale para Oracle.
Armadilha comum

Mockar o repositório e declarar "testamos o endpoint". Mocks provam que você chamou o método, não que a query funciona. Teste de API com mock total do banco é teste do mock.

Regra de bolso

Unitário para decisões (lógica), integração para conexões (HTTP, SQL, filas), contrato para acordos (entre times), e2e só para os poucos fluxos que não podem falhar.

Na entrevista

"Como você testa uma API?" Resposta sênior: unitários para regra de negócio; testes de integração da API contra PostgreSQL real com Testcontainers (migrações incluídas); testes de contrato para proteger os consumidores; e2e mínimos. Explique que H2 ou SQLite escondem bugs de dialeto.

Para gestores

Cobertura de linhas é métrica fraca. Cobre do time: testes que falham quando o comportamento muda, suíte de integração abaixo de 10 minutos no CI, e zero testes ignorados ("flaky") por mais de uma semana. Um teste instável ensina o time a ignorar o vermelho.

2Avançado

Testes de contrato

O problema: o time do provedor muda a API e todos os testes dele passam; o aplicativo do consumidor quebra em produção. O teste de contrato fecha essa lacuna verificando o acordo entre as duas pontas. Há duas famílias.

1. Contrato baseado em schema (OpenAPI)

O contrato é o próprio OpenAPI (módulo 02). Valida-se que a implementação real responde conforme o schema e que a mudança no schema não é breaking (diff, módulo 07). Ferramentas: validadores em testes de integração (por exemplo, validar cada resposta contra o schema), Schemathesis e Dredd (geram requisições a partir do OpenAPI e checam respostas), Spectral para lint.

schemathesis run openapi/agendamentos.yaml \
  --url http://localhost:8080 \
  --checks all \
  --header "Authorization: Bearer $TOKEN_TESTE"

2. Contrato dirigido pelo consumidor (consumer-driven, Pact)

Cada consumidor escreve o que realmente usa da API, como exemplos de requisição e resposta. Esses exemplos formam o "pact" (arquivo JSON). O provedor os executa contra a implementação real no seu CI. Se alguma expectativa de consumidor quebrar, o provedor sabe quem será afetado antes do deploy.

{
  "consumer": { "name": "app-paciente" },
  "provider": { "name": "api-agendamentos" },
  "interactions": [
    {
      "description": "consulta de agendamento existente",
      "providerStates": [{ "name": "agendamento ag_7731 existe" }],
      "request": { "method": "GET", "path": "/v2/agendamentos/ag_7731" },
      "response": {
        "status": 200,
        "headers": { "Content-Type": "application/json" },
        "body": { "id": "ag_7731", "status": "AGENDADO", "inicio": "2026-04-02T14:30:00-03:00" },
        "matchingRules": {
          "body": { "$.status": { "match": "type" }, "$.inicio": { "match": "regex", "regex": "^\\d{4}-\\d{2}-\\d{2}T.*$" } }
        }
      }
    }
  ]
}
# consumidor: publica o contrato gerado pelos testes
pact-broker publish ./pacts --consumer-app-version "$GIT_SHA" --branch "$GIT_BRANCH"

# antes de promover a versão para produção
pact-broker can-i-deploy --pacticipant app-paciente --version "$GIT_SHA" --to-environment production

Quando cada um vale a pena

Baseado em schema (OpenAPI)Consumer-driven (Pact)
Quem define o contratoProvedorConsumidores, pelo que realmente usam
DetectaImplementação fora do schema; breaking change em relação ao OpenAPI publicadoQuebra de um consumidor específico, inclusive uso de campo que o provedor julgava pouco importante
EsforçoBaixo: um arquivo e ferramentasMaior: cada consumidor escreve testes, há Broker, provider states, versionamento de pacts
Escala bem comAPI pública com muitos consumidores desconhecidosPoucos consumidores conhecidos e sob o mesmo guarda-chuva organizacional (times internos, parceiros próximos)
LimitaçãoNão sabe como cada consumidor usa a APINão funciona se você não consegue fazer o consumidor escrever e publicar pacts
Boa escolha quandoContrato design-first, API pública ou de parceiros externosMicrosserviços internos, app móvel próprio, BFF
Regra de bolso

Comece pelo schema: é barato e dá 80 % do valor. Adote Pact onde houver consumidores conhecidos e acessíveis cuja quebra custa caro, como o app do paciente ou o sistema de faturamento interno.

Armadilha comum

Pact com asserção de valores exatos ("status == AGENDADO e id == ag_7731"). O contrato deve validar formato e tipo (matching rules), não dados de exemplo. Senão o teste quebra a cada mudança de massa de dados e ninguém confia nele.

Na entrevista

"Contract testing: o que é e por que Pact?" Resposta: acordo verificável entre as pontas. Por schema, o provedor valida que cumpre o OpenAPI; consumer-driven, cada consumidor declara o que usa e o provedor verifica antes do deploy, com can-i-deploy bloqueando o que quebraria alguém. Cite que é indicado quando os consumidores são conhecidos.

Para gestores

Contrato consumer-driven exige acordo entre times: quem escreve o pact, quem corrige quando quebra, qual o SLA para verificar. Sem isso, o Broker vira cemitério de contratos vermelhos. Comece com um par de times e um fluxo crítico; meça quantos incidentes de integração o contrato evitou.

3Intermediário

Mocks, stubs, sandboxes e ferramentas

Dublês de teste

TermoO que éExemplo em API de saúde
StubResposta pronta, sem lógicaServiço de elegibilidade do convênio sempre devolve {"elegivel": true}
MockDublê que também verifica as chamadas recebidasGarante que o envio de SMS foi chamado 1 vez com o telefone certo
FakeImplementação simplificada que funcionaFila em memória no lugar do broker real
Servidor simulado (mock server)Processo HTTP que imita uma API externa, configurávelWireMock, MockServer ou Prism simulando o laboratório parceiro

Use dublês para o que você não controla (APIs de terceiros, gateways de pagamento, convênios) e para simular falha: latência, 500, 429, timeout, resposta malformada. Para o que você controla (seu banco, sua fila), prefira o real com Testcontainers.

{
  "request": {
    "method": "GET",
    "urlPath": "/convenios/elegibilidade",
    "queryParameters": { "carteirinha": { "equalTo": "000111" } }
  },
  "response": {
    "status": 200,
    "jsonBody": { "elegivel": true, "plano": "ENFERMARIA" },
    "fixedDelay": 3000
  }
}

Esse stub devolve a resposta após 3 segundos: serve para provar que o seu código aplica timeout, circuit breaker e fallback (módulo 06) em vez de pendurar a thread.

Armadilha comum

Mock que diverge da API real. O parceiro mudou, o mock não, e os testes ficam verdes enquanto produção quebra. Gere ou valide o mock a partir do contrato (OpenAPI no Prism, contratos gravados) e rode periodicamente testes contra o ambiente real do parceiro.

Sandbox para parceiros

Se você oferece API, forneça um sandbox: ambiente separado, com o mesmo contrato da produção, dados fictícios e chaves próprias. É o que permite onboarding rápido (time to first hello world, módulo 07) e testes automatizados do parceiro sem tocar em dado real.

  • Mesmo contrato, mesma autenticação, URL e credenciais diferentes. Se o sandbox é "quase igual", o parceiro descobre a diferença em produção.
  • Dados 100 % fictícios. Nunca copie produção, mesmo "anonimizada", sem análise formal de reidentificação (LGPD: dado de saúde é sensível).
  • Gatilhos de cenário previsíveis: carteirinha terminada em 999 devolve convênio inativo; CPF de teste devolve conflito de horário; assim o parceiro testa erros sem depender de sorte.
  • Reset e limites: dados redefinidos periodicamente, rate limit generoso, mas existente.
  • Mesmo ciclo de vida: o sandbox recebe a versão nova antes da produção, para o parceiro testar migrações (módulo 07).

Regra de bolso

Ferramenta boa é a que o time versiona, revisa e roda no CI. Teste manual numa GUI que ninguém guarda é conhecimento perdido; escolha formato em texto, no repositório, ao lado do código.

Na entrevista

"Mock, stub e fake?" Stub devolve resposta fixa; mock verifica interações; fake é implementação simples que funciona. E acrescente o critério sênior: dublê para o que é de terceiros e para simular falha; dependências próprias, reais com Testcontainers.

Para gestores

Sandbox bom é o investimento de maior retorno no onboarding de parceiros: reduz chamados de suporte e acelera integrações. Cobre: paridade de contrato com produção, dados fictícios, reset automático e monitoramento do próprio sandbox.

4Avançado

Testes de carga com k6

Testes funcionais respondem "funciona?". Testes de carga respondem "funciona com 500 pacientes abrindo o app ao mesmo tempo na segunda às 8h?". O k6 (open source, scripts em JavaScript, motor em Go) é uma escolha comum: código versionável, metas como thresholds que falham o build e saída padronizada.

Tipos de teste

TipoPerfil de cargaPergunta que responde
Smoke1 a 3 usuários virtuais, 1 a 2 minO script e a API funcionam? (rode a cada deploy)
LoadCarga esperada de pico, sustentada (10 a 60 min)Atende o SLO com o tráfego normal?
StressSubir além do pico até degradarOnde está o limite? Como falha (graciosamente ou em cascata)?
Soak (resistência)Carga moderada por horasHá vazamento de memória, conexões ou disco? A latência deriva?
SpikeSalto súbito (ex.: 10x em segundos) e quedaAguenta rajadas? Como o autoscaling, o pool e a fila reagem?
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 50 },    // sobe até 50 usuários virtuais
    { duration: '10m', target: 50 },   // mantém (carga normal de pico)
    { duration: '1m', target: 0 },     // desce
  ],
  thresholds: {
    http_req_failed: ['rate<0.01'],                       // < 1 % de erros
    http_req_duration: ['p(95)<400', 'p(99)<1000'],       // metas em p95 e p99
    'http_req_duration{endpoint:listar}': ['p(95)<300'],  // meta por endpoint
  },
};

const BASE = __ENV.BASE_URL;
const params = { headers: { Authorization: `Bearer ${__ENV.TOKEN}` } };

export default function () {
  const lista = http.get(`${BASE}/v2/pacientes/pac_teste_1/agendamentos`, { ...params, tags: { endpoint: 'listar' } });
  check(lista, { 'listar 200': (r) => r.status === 200 });
  sleep(1);                           // tempo de "pensar" do usuário

  const novo = http.post(`${BASE}/v2/agendamentos`,
    JSON.stringify({ paciente_id: 'pac_teste_1', medico_id: 'med_204', inicio: '2026-04-02T14:30:00-03:00' }),
    { headers: { ...params.headers, 'Content-Type': 'application/json', 'Idempotency-Key': `${__VU}-${__ITER}` }, tags: { endpoint: 'criar' } });
  check(novo, { 'criar 201 ou 409': (r) => r.status === 201 || r.status === 409 });
  sleep(1);
}
k6 run -e BASE_URL=https://staging.clinica.example -e TOKEN=$TOKEN_TESTE agendamentos-load.js

Como ler os resultados

     http_req_duration..............: avg=182ms min=21ms med=140ms max=2.9s p(90)=320ms p(95)=410ms
       { endpoint:listar }..........: avg=95ms  p(95)=180ms
     http_req_failed................: 0.42%  ✓ 123      ✗ 29112
     http_reqs......................: 29235  48.7/s
     iterations.....................: 14617  24.3/s
     vus............................: 50     min=1  max=50

   ✗ http_req_duration p(95)<400   (p(95)=410ms)
  • Percentis, não média. A média (182 ms) esconde a cauda: o p95 (410 ms) diz que 5 % dos pacientes esperam mais que isso. Metas se escrevem em p95 e p99.
  • Threshold vermelho acima: p95 de 410 ms estourou a meta de 400 ms. O teste falha mesmo com 99,6 % de sucesso. Isso é o objetivo.
  • Erros: http_req_failed 0,42 %: dentro da meta de 1 %, mas investigue quais (timeouts? 5xx? 429 do rate limit?).
  • Vazão (http_reqs/s) e a curva ao longo do tempo: a latência cresce linearmente com a carga ou "dobra" de repente (saturação de pool de conexões)?
  • Correlacione com o servidor: o k6 mostra o sintoma; CPU, pool do banco, filas e traces mostram a causa (seções 7 e 8).
Armadilha comum

Testar contra um ambiente muito menor que o de produção (1 réplica, banco minúsculo) e extrapolar. Carga mede o ambiente testado. Garanta paridade de configuração e volume de dados; um índice ausente só aparece com milhões de linhas. E nunca rode carga contra produção ou contra sistema de terceiros sem autorização.

Cuidado com "coordinated omission"

Geradores de carga "closed model" (cada usuário só faz a próxima requisição após a resposta) diminuem a pressão justamente quando o sistema está lento, subestimando a latência. Para medir sistemas abertos ao público, use executores com taxa de chegada constante (no k6, constant-arrival-rate).

export const options = {
  scenarios: {
    pico: {
      executor: 'constant-arrival-rate',
      rate: 100, timeUnit: '1s',     // 100 requisições por segundo, independentemente da resposta
      duration: '10m',
      preAllocatedVUs: 50, maxVUs: 400,
    },
  },
};
Na entrevista

"Como você planeja um teste de carga?" Defina a meta em p95/p99 e erro (vinda do SLO); modele o tráfego real (mix de endpoints, pico); use ambiente equivalente; rode smoke, load, stress, soak e spike conforme o risco; falhe o build por thresholds; e correlacione com métricas do servidor. Cite que média engana.

Para gestores

Exija teste de carga antes de eventos previsíveis (campanha de vacinação, abertura de agenda, virada de ano) e depois de mudança de arquitetura relevante. Pergunta de revisão: "qual a capacidade medida, não estimada, e o que acontece 20 % acima dela?".

5Avançado

Testes no CI/CD e ambientes efêmeros

Testes que ninguém roda não protegem nada. A ordem do pipeline segue o princípio de falhar cedo e barato: o que é rápido e pega muito vem primeiro.

  1. Lint e análise estática (código, Spectral no OpenAPI, diff de breaking change, scanners de dependências e de segredos). Segundos.
  2. Unitários. Segundos a poucos minutos.
  3. Integração com Testcontainers e contrato (verificação do provedor, publicação de pacts, can-i-deploy). Poucos minutos.
  4. Build da imagem e scan de vulnerabilidades.
  5. Deploy em ambiente efêmero, smoke/e2e mínimos e k6 smoke contra ele.
  6. Promoção a staging/produção por canary ou blue/green, com verificação automática (SLI) e rollback automático.
  7. Pós-deploy: monitoramento sintético e alertas de burn rate (seção 8).
name: api
on: [pull_request]
jobs:
  verificacao:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx @stoplight/spectral-cli lint openapi/agendamentos.yaml
      - run: ./mvnw -B verify            # unitários + integração (Testcontainers precisa de Docker)
      - run: ./mvnw -B pact:publish      # publica contratos do consumidor
      - run: |
          pact-broker can-i-deploy --pacticipant api-agendamentos \
            --version "${{ github.sha }}" --to-environment staging
  ambiente-efemero:
    needs: verificacao
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/deploy-preview.sh "pr-${{ github.event.number }}"
      - run: k6 run -e BASE_URL="https://pr-${{ github.event.number }}.preview.clinica.example" smoke.js
      - if: always()
        run: ./scripts/destroy-preview.sh "pr-${{ github.event.number }}"

Ambientes efêmeros

Um ambiente efêmero (ou preview environment) é uma cópia completa e isolada da aplicação criada por PR e destruída ao fechar. Em Kubernetes, um namespace por PR com a imagem do commit, um PostgreSQL próprio com dados sintéticos e as dependências externas substituídas por mocks ou sandboxes.

GanhoCusto / cuidado
Fim da disputa por "o ambiente de homologação" compartilhado e sempre quebradoInfra extra: defina TTL (ex.: destruir após 24 h sem uso) e cotas de recursos
Cada PR é testado isolado, com dados controladosDados sintéticos e semente de banco precisam ser mantidos como código
Parceiros e QA podem validar uma mudança antes do mergeNunca copie dados de produção (LGPD); proteja o acesso ao ambiente
Armadilha comum

Testes e2e longos e instáveis como porta de entrada para todo PR. O pipeline passa a levar 40 minutos, o time re-executa até ficar verde e ignora o sinal. Mantenha a suíte de PR enxuta e mova os cenários pesados para execuções agendadas (noturnas), com dono para corrigir as falhas.

Regra de bolso

Pipeline de PR: menos de 15 minutos. Um teste instável é um bug a ser corrigido hoje, não um re-run. Quarentene-o com prazo, ou apague-o.

Na entrevista

"O que roda no pipeline de uma API?" Lint do contrato e diff de breaking change, unitários, integração com Testcontainers, contrato (can-i-deploy), build e scan da imagem, deploy em ambiente efêmero com smoke e k6 smoke, depois canary com verificação automática por SLI e rollback.

Para gestores

Meça o pipeline: duração média, taxa de testes instáveis, tempo entre merge e produção, taxa de falha de mudança (DORA). Pipeline lento e instável é o maior imposto escondido sobre a produtividade do time.

Observabilidade: logs estruturados, correlation id e Trace Context

Monitorar é saber se algo está errado (você definiu antes o que olhar). Observabilidade é conseguir perguntar por que está errado, inclusive perguntas que você não previu, a partir dos sinais que o sistema emite: logs, métricas e traces. A trilha web (06-backend-infra.html) apresentou os conceitos; aqui o foco é em APIs.

Logs estruturados em JSON

Log em texto livre ("Erro ao agendar paciente 123") é impossível de consultar em escala. Emita um evento JSON por linha, com campos consistentes, para poder filtrar e agregar.

{"ts":"2026-04-02T14:30:00.412Z","level":"info","service":"api-agendamentos","env":"prod",
 "msg":"request completed","method":"POST","route":"/v2/agendamentos","status":201,
 "duration_ms":187,"client_id":"parceiro_lab_01","api_version":"v2",
 "trace_id":"0af7651916cd43dd8448eb211c80319c","span_id":"b7ad6b7169203331","request_id":"req_9f31c2"}
  • Use a rota (/v2/agendamentos/{id}), não a URL com ID, para agregar. O ID vai em campo à parte, se necessário (e se não for dado pessoal identificável; veja abaixo).
  • Níveis com critério: error exige ação; warn é anomalia tratada; info é fluxo normal (um por requisição, não dez); debug desligado em produção.
  • Mesmos nomes de campo em todos os serviços (um esquema de log da empresa), para que uma consulta funcione em qualquer um.
  • Amostragem e custo: logs custam armazenamento e consulta. Logue o necessário, com retenção definida.

Correlation id e W3C Trace Context

Uma requisição passa por gateway, API, banco e fila. Para juntar o que cada componente registrou, ela precisa carregar um identificador que viaja junto. A forma antiga: um correlation id (ex.: X-Request-Id) gerado na borda e repassado. A forma padronizada: o W3C Trace Context, com o cabeçalho traceparent.

O que NÃO logar

Log é cópia de dado, normalmente com retenção longa, muita gente com acesso e fora das proteções do banco. Em saúde, o risco é alto: dado pessoal e dado de saúde são dados sensíveis pela LGPD. Um log que vaza expõe pacientes.

  // allowlist: só entra o que foi explicitamente aprovado
  return Object.fromEntries(Object.entries(obj).filter(([k]) => CAMPOS_PERMITIDOS.includes(k)));
}

Armadilha comum

Logar o corpo completo "só para depurar" e esquecer ligado. Ou o logger da biblioteca HTTP registrando cabeçalhos (inclusive Authorization) em nível debug. Revise a configuração dos loggers de terceiros e teste: faça uma requisição com dado fictício reconhecível e procure-o nos logs.

Na entrevista

"Como você rastreia uma requisição entre serviços?" Gero o traceparent (W3C Trace Context) na borda, cada serviço propaga o trace-id e põe-no em todos os logs estruturados; devolvo o trace id ao cliente. Complemento: não logo PII, tokens nem dado de saúde.

Para gestores

Logs de produção são ativo de risco LGPD. Defina: política de retenção, quem acessa, mascaramento por padrão e um teste automatizado que falha se campos proibidos aparecerem. Pergunte: "se este log vazar, o que está nele?". Incidente de log com dado de paciente é incidente de segurança.

OpenTelemetry e traces distribuídos

OpenTelemetry (OTel) é o padrão aberto (projeto da CNCF) para gerar e exportar traces, métricas e logs, independente de fornecedor. Ele define APIs e SDKs por linguagem, convenções semânticas (nomes padronizados de atributos), o protocolo OTLP e o Collector, um processo que recebe, processa (filtra, amostra, mascara) e encaminha os dados para o backend de sua escolha (Jaeger, Tempo, Prometheus, Datadog, etc.). Você instrumenta uma vez e troca de backend sem mexer no código.

Os três sinais

SinalO que éBoa para
TracesO caminho de uma requisição, como árvore de spansDescobrir onde o tempo foi gasto e qual dependência falhou
MétricasNúmeros agregados ao longo do tempo (contadores, medidores, histogramas)Painéis, alertas e tendências baratas
LogsEventos discretos com contextoDetalhe de um caso; ligados ao trace via trace_id

Spans e traces

Um trace é a história de uma requisição; um span é uma etapa dela, com início, duração, atributos e status, ligada ao span-pai. Chamadas HTTP, consultas SQL e publicações em fila viram spans (a maioria automaticamente, via instrumentação automática). Spans de mensageria usam links ou contexto na mensagem para ligar o produtor ao consumidor, já que o processamento assíncrono acontece depois.

Instrumentando uma API (Node.js)

const { NodeSDK } = require('@opentelemetry/sdk-node');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-http');
const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');

const sdk = new NodeSDK({
  serviceName: 'api-agendamentos',
  traceExporter: new OTLPTraceExporter({ url: 'http://otel-collector:4318/v1/traces' }),
  instrumentations: [getNodeAutoInstrumentations()],   // HTTP, Express, pg, etc.
});
sdk.start();
const { trace, SpanStatusCode } = require('@opentelemetry/api');
const tracer = trace.getTracer('agendamentos');

async function reservarHorario(medicoId, inicio) {
  return tracer.startActiveSpan('reservar-horario', async (span) => {
    span.setAttribute('medico.id', medicoId);        // atributos úteis, sem PII
    try {
      return await repo.reservar(medicoId, inicio);
    } catch (e) {
      span.recordException(e);
      span.setStatus({ code: SpanStatusCode.ERROR });
      throw e;
    } finally {
      span.end();
    }
  });
}

Amostragem

Guardar 100 % dos traces é caro. Estratégias: head sampling (decide no início: 5 % ao acaso) é simples, mas pode perder o trace raro que interessa; tail sampling (no Collector, decide ao fim do trace) guarda todos os traces com erro ou lentos e uma fração dos normais. Combine com o bit de amostragem do traceparent para o caminho todo respeitar a mesma decisão.

Armadilha comum

Perder o contexto no meio do caminho: uma chamada assíncrona, uma fila ou uma biblioteca HTTP não instrumentada. O trace quebra em dois pedaços e ninguém liga os pontos. Teste a propagação explicitamente (um teste de integração que verifica que o trace-id chega ao serviço seguinte e à mensagem na fila).

Atributos e cardinalidade

Não ponha dado pessoal em atributos de span (CPF, nome) nem valores de alta cardinalidade em métricas (ID do paciente como label): explode o custo do backend de métricas e expõe dados. Em traces, atributos com ID são aceitáveis só se opacos.

Na entrevista

"O que é OpenTelemetry?" Padrão aberto para instrumentar traces, métricas e logs, com SDKs, convenções semânticas, protocolo OTLP e Collector; desacopla instrumentação do backend. Explique trace, span e como o traceparent liga serviços. Comente que tail sampling guarda erros e lentidão.

Para gestores

Observabilidade tem custo (ingestão, armazenamento, licenças). Decida amostragem, retenção e o que é essencial; e padronize instrumentação (bibliotecas e convenções comuns) para não ter cada time com seu jeito. Cobre: todo serviço novo nasce com trace, métricas RED e logs correlacionados no checklist de go-live.

Métricas, SLOs, alertas e monitoramento sintético

RED e USE

Duas listas curtas para não se perder em centenas de métricas:

MétodoParaMedeExemplo em API de agendamento
REDServiços (o que o usuário sente)Rate (requisições/s), Errors (taxa de erro), Duration (latência, em histograma)Por rota e versão: 120 req/s, 0,3 % de 5xx, p95 = 240 ms
USERecursos (o que sustenta o serviço)Utilization (% ocupado), Saturation (fila de espera), ErrorsPool de conexões do banco: 90 % em uso, 35 requisições esperando, 12 timeouts. CPU, disco, fila

RED responde "o usuário está sofrendo?"; USE responde "qual recurso está no limite?". Use RED para painéis de serviço e alertas, USE para diagnóstico. Latência sempre em histograma (permite p95/p99) e nunca só média.

SLI, SLO e error budget

  • SLI (indicador): uma medida do que o usuário sente, como razão "bons / total". Ex.: requisições com status diferente de 5xx / total.
  • SLO (objetivo): a meta para o SLI numa janela. Ex.: 99,9 % em 30 dias.
  • SLA: compromisso contratual (com consequência), normalmente mais frouxo que o SLO interno.
  • Error budget: o que você pode errar sem violar o SLO: 100 % menos o SLO.
SLIComo medirSLO de exemplo (30 dias)
Disponibilidaderequisições sem 5xx / total, medido no gateway99,9 %
Latênciarequisições respondidas em até 400 ms / total95 % em ≤ 400 ms (equivale a p95 ≤ 400 ms)
Frescor (assíncrono)eventos entregues em até 60 s / total99 %

Exemplo numérico

A API de agendamentos tem SLO de disponibilidade de 99,9 % em 30 dias e recebe cerca de 10 milhões de requisições por mês.

  • Error budget = 0,1 % = 10.000 requisições com falha no mês.
  • Em tempo, se fosse indisponibilidade total: 30 dias × 24 h × 60 min × 0,001 = 43,2 minutos por mês.
  • Um deploy ruim que, por 20 minutos, faz 5 % das requisições falharem (tráfego de ~230 req/min, cerca de 4.600 requisições): são ~230 falhas, ou 2,3 % do budget. Já uma queda total de 20 minutos, com o mesmo tráfego, perde 4.600 requisições: 46 % do budget do mês.
  • Se o budget do mês já foi 80 % consumido na segunda semana, o time congela mudanças arriscadas e prioriza confiabilidade até a janela renovar. Com budget sobrando, pode correr mais riscos e lançar mais rápido.
Regra de bolso

100 % não é meta: custa infinitamente mais e ninguém precisa. O SLO é uma negociação entre produto e engenharia sobre o que o usuário percebe como "bom o bastante". O budget transforma discussões de opinião ("está estável?") em números.

Alerte em sintomas (taxa de erro, latência, burn rate), não em causas ("CPU a 85 %" pode ser perfeitamente saudável). Um alerta que acorda alguém deve ter dono, runbook e ser acionável; se não é, vira ruído e as pessoas passam a ignorar os alertas (fadiga).

Alerta por taxa de consumo do budget (burn rate)

Burn rate 1 significa consumir o budget exatamente ao longo da janela. Um burn rate de 14,4 durante 1 hora consome 2 % do budget mensal (14,4 ÷ 720 h). Usa-se uma janela longa e uma curta juntas, para ser rápido ao detectar e rápido ao silenciar.

groups:
  - name: slo-agendamentos
    rules:
      - alert: AgendamentosBurnRateAlto
        expr: |
          (
            sum(rate(http_server_requests_total{service="api-agendamentos",status=~"5.."}[1h]))
            / sum(rate(http_server_requests_total{service="api-agendamentos"}[1h]))
          ) > (14.4 * 0.001)
          and
          (
            sum(rate(http_server_requests_total{service="api-agendamentos",status=~"5.."}[5m]))
            / sum(rate(http_server_requests_total{service="api-agendamentos"}[5m]))
          ) > (14.4 * 0.001)
        for: 2m
        labels: { severity: page }
        annotations:
          summary: "Consumindo o error budget 14x mais rápido que o normal"
          runbook: "https://runbooks.clinica.example/agendamentos-5xx"

Monitoramento sintético

Métricas reais só existem se há tráfego. Às 3h da manhã, ou numa região sem usuários, uma API pode estar quebrada sem ninguém saber. Monitoramento sintético executa, de fora e continuamente (a cada minuto ou poucos minutos), transações de teste contra a API como um cliente faria: autentica, lista, cria e cancela um agendamento de um paciente fictício.

  • Rode de fora da sua rede e de mais de um ponto: pega falha de DNS, certificado expirado e rota de internet que as métricas internas não veem.
  • Cubra jornadas críticas (agendar, consultar resultado), não só /health. Um health check que devolve 200 com o banco fora é mentira.
  • Use dados de teste isolados (paciente e agenda fictícios) e limpe depois, para não poluir relatórios nem tocar em dado real.
  • Alerte pela falha de N execuções consecutivas, para não acordar por um soluço de rede. Verifique também a validade do certificado TLS e do token do usuário sintético.
  • Ferramentas: scripts k6 agendados, blackbox exporter do Prometheus, serviços de monitoramento sintético dos provedores de nuvem e de observabilidade.
Armadilha comum

Alertas demais e sem dono: 200 alertas por semana, 190 inúteis. Revise toda semana os alertas que acordaram alguém: tinha ação? Era sintoma? Se não, mude, rebaixe a ticket ou apague. Quem recebe plantão deve poder dormir.

Na entrevista

"Como você define a confiabilidade de uma API?" SLI como razão bons/total (disponibilidade e latência), SLO acordado com produto (99,9 % em 30 dias, por exemplo), error budget como moeda de decisão, alerta por burn rate em sintoma. Complemente com RED para serviços, USE para recursos e checks sintéticos de jornadas.

Para gestores

O SLO transforma conversa de "estabilidade vs velocidade" em decisão: budget sobrando, acelera; budget esgotado, congela e investe em confiabilidade. Cobre: SLO por API crítica publicado, revisão trimestral, post-mortem sem culpados quando o budget estoura e carga de plantão sob controle (número de páginas por semana).

Cenários práticos

Cenário 1: "a API está lenta" (roteiro de investigação)

Situação: o suporte avisa que parceiros e o app do paciente reclamam de lentidão no agendamento. Nenhum alerta disparou.

O que fazer: método, não palpite. Do sintoma para a causa:

  1. Delimite o problema. Quando começou? Para quem (um parceiro, todos)? Quais rotas? Em que percentil (só p99 ou também p50)? Um deploy, configuração ou aumento de tráfego coincide com o início? Mudou alguma coisa? é a pergunta de maior retorno.
  2. Olhe o painel RED. Taxa, erros e latência por rota e por versão. Lentidão em uma rota aponta para código ou consulta; em todas, para recurso compartilhado (banco, rede, CPU, dependência comum).
  3. Use um trace lento. Pegue o trace_id de uma requisição lenta (do log, do parceiro, do tail sampling) e veja onde está o tempo: espera no banco, chamada externa, fila, GC?
  4. Confira o USE dos recursos suspeitos. Pool de conexões saturado? CPU em throttling? Bloqueios e consultas lentas no PostgreSQL (pg_stat_statements, pg_locks) ou no Oracle (relatórios de execução)? Fila acumulando? Réplicas insuficientes?
  5. Verifique dependências externas. O convênio ou o laboratório parceiro ficou lento? Timeouts, circuit breaker e fallbacks estão configurados (módulo 06)? A sua API herda a lentidão deles?
  6. Mitigue primeiro, entenda depois. Reverter o deploy, escalar réplicas, desligar feature flag, aplicar rate limit a um consumidor abusivo, aumentar o timeout curto demais. Comunique o status.
  7. Corrija a causa e feche o ciclo. Post-mortem sem culpados, teste de carga que reproduz, alerta de SLO que teria avisado antes (aqui, nenhum disparou: por quê?).
SELECT pid, now() - query_start AS duracao, state, wait_event_type, left(query, 120) AS consulta
FROM   pg_stat_activity
WHERE  state <> 'idle' AND now() - query_start > interval '2 seconds'
ORDER  BY duracao DESC;
Regra de bolso

Dado antes de hipótese. "Deve ser o banco" sem trace é achismo caro. E mitigue (reverta, escale) antes de investigar a fundo, quando há paciente esperando.

Cenário 2: o pipeline demora 45 minutos e ninguém confia nos testes

Situação: a suíte e2e tem testes instáveis; o time reexecuta até ficar verde.

O que fazer: meça quais testes falham de modo intermitente; quarentene-os com prazo e dono; mova e2e pesados para o pipeline noturno; troque e2e por testes de integração com Testcontainers e contrato onde possível; paralelize; meta: PR em menos de 15 minutos. Trate a instabilidade como defeito prioritário.

Cenário 3: o parceiro diz "vocês mudaram a API e quebraram a gente"

Situação: o laboratório parceiro afirma que parou de funcionar ontem à noite.

O que fazer: peça o trace-id ou o horário e o client_id; ache as requisições deles nos logs e compare as respostas antes e depois do deploy; veja se foi mudança de contrato (o diff do OpenAPI deveria ter acusado). Se a mudança era "compatível" mas o parceiro tinha dependência implícita (lei de Hyrum), reverta, converse e inclua o caso na suíte de contrato. Para o futuro: Pact com esse parceiro, ou sandbox que receba a versão antes.

Cenário 4: SLO violado três meses seguidos e o produto quer lançar funcionalidade nova

Situação: o error budget de 99,9 % estourou em três meses; a diretoria de produto pressiona por novidades.

O que fazer: mostre o dado: quantos incidentes, quanto tempo de indisponibilidade, impacto em atendimento. Proponha a política de budget já acordada: com budget esgotado, congela-se funcionalidade nova até recuperar, ou aloca-se parte da capacidade a confiabilidade (causas dos três principais incidentes). Se o SLO é mais agressivo do que o negócio precisa, renegocie o SLO com números, não relaxe em silêncio.

Cenário 5: alerta de madrugada por "CPU alta" que não era nada

Situação: o plantonista foi acordado três vezes na semana por CPU acima de 85 % sem impacto ao usuário.

O que fazer: troque o alerta de causa por alerta de sintoma (burn rate de erro/latência); a CPU vira painel e alerta de ticket em caso de tendência. Registre num post-mortem curto de "alerta ruim" e revise todos os alertas que acordaram alguém no mês. Tempo de sono é parte da confiabilidade da equipe.

11Avançado

Perguntas de entrevista

01Pirâmide de testes: como você aplica a uma API?

Muitos unitários para regra de negócio; testes de integração do endpoint contra banco real (Testcontainers), que é onde está o maior risco; contratos para proteger consumidores; poucos e2e. Na prática, o "troféu" descreve melhor APIs, porque o risco mora nas fronteiras.

02Por que não usar H2 ou SQLite para testar uma API que roda em PostgreSQL ou Oracle?

Dialeto, tipos, funções, índices e locks diferem; o teste passa e produção falha. Com Testcontainers subo o mesmo banco e rodo as migrações no teste. Em Oracle, as imagens são pesadas, então reservo para as consultas críticas.

03Diferença entre mock, stub e fake?

Stub devolve respostas fixas; mock também verifica as chamadas recebidas; fake é uma implementação simplificada que funciona (fila em memória). Uso dublês para sistemas de terceiros e para simular falhas; para o que é meu, uso o real.

04O que é teste de contrato e por que importa?

Verifica o acordo entre provedor e consumidor para que mudanças em um lado não quebrem o outro de forma silenciosa. Evita o cenário em que todos os testes do provedor passam e o consumidor quebra em produção.

05Contrato por schema vs consumer-driven: quando usar cada um?

Schema (OpenAPI): barato, o provedor valida que cumpre o contrato publicado; serve para APIs públicas e muitos consumidores desconhecidos. Consumer-driven (Pact): cada consumidor declara o que usa e o provedor verifica; vale com consumidores conhecidos e acessíveis, como app próprio e serviços internos.

06Descreva o fluxo do Pact.

O consumidor escreve testes contra um mock do provedor, o que gera o pact; publica no Broker. O CI do provedor baixa os pacts e os verifica contra a API real, publicando o resultado. Antes do deploy, can-i-deploy consulta a matriz de versões verificadas e bloqueia combinações não verificadas.

07Como é um bom sandbox para parceiros?

Mesmo contrato e autenticação da produção, dados 100 % fictícios, gatilhos previsíveis de cenário (erros), reset periódico, limites razoáveis e recebendo versões novas antes da produção. Reduz o time to first hello world e o suporte.

08Quais os tipos de teste de carga?

Smoke (funciona com carga mínima), load (carga esperada sustentada), stress (além do pico até degradar), soak (horas, atrás de vazamentos e deriva) e spike (salto súbito). Cada um responde a uma pergunta diferente sobre capacidade e comportamento sob pressão.

09Por que usar p95/p99 em vez de média?

A média esconde a cauda: poucas requisições muito lentas somem num número bonito. O p95 diz que 95 % respondem abaixo daquele valor; o p99 pega os piores casos, que são os usuários insatisfeitos. SLOs e thresholds se escrevem em percentis.

10Como evitar que testes de carga enganem?

Ambiente e volume de dados equivalentes aos de produção, mix real de endpoints, modelo de chegada aberto (constant-arrival-rate) para evitar coordinated omission, metas vindas do SLO, e correlacionar com métricas do servidor (CPU, pool, filas) para achar a causa.

11O que é um correlation id e como o W3C Trace Context o padroniza?

Correlation id é um identificador que viaja com a requisição para juntar logs entre serviços. O W3C Trace Context padroniza isso no cabeçalho traceparent: versão, trace-id (32 hex), parent-id (16 hex) e flags. Cada serviço propaga o trace-id e gera seu próprio span-id.

12O que é OpenTelemetry e o que é o Collector?

OTel é o padrão aberto para traces, métricas e logs, com APIs/SDKs, convenções semânticas e o protocolo OTLP. O Collector recebe os dados, processa (amostra, filtra, mascara) e exporta para o backend; isso desacopla a instrumentação do fornecedor.

13Como a lentidão aparece num trace distribuído?

Como o span mais largo na cascata: se o gateway mostra 500 ms e o span do banco 320 ms, o tempo está na consulta. O trace também mostra dependências externas lentas e chamadas sequenciais que poderiam ser paralelas.

14Explique RED e USE.

RED para serviços: taxa de requisições, taxa de erros e duração (histograma). USE para recursos: utilização, saturação e erros (CPU, pool de conexões, filas). RED diz se o usuário sofre; USE diz qual recurso está no limite.

15Calcule o error budget de um SLO de 99,9 % em 30 dias com 10 milhões de requisições.

0,1 % de 10 milhões = 10.000 requisições com falha. Em tempo, equivale a cerca de 43 minutos de indisponibilidade total por mês. Budget consumido pela metade em duas semanas indica que é hora de reduzir risco de mudanças.

16Que alertas devem acordar alguém e quais não?

Acordam os que indicam sintoma real ao usuário e têm ação possível: burn rate alto do error budget, indisponibilidade. Tendências e causas (CPU, disco 80 %) viram ticket ou painel. Todo alerta tem dono e runbook; revisão semanal elimina ruído.

17O que NÃO logar numa API de saúde e por quê?

Tokens e credenciais, CPF e demais identificadores pessoais, diagnósticos, exames e conteúdo de prontuário, corpos completos de requisição, dados financeiros. Log tem retenção longa e acesso amplo, e dado de saúde é sensível pela LGPD. Logue IDs opacos e campos em allowlist, e teste o mascaramento.

18"A API está lenta." Como você investiga?

Delimito (quando, quem, quais rotas, o que mudou), olho RED por rota, abro um trace lento para ver onde está o tempo, confiro USE dos recursos suspeitos (pool, CPU, locks, fila) e dependências externas. Mitigo cedo (rollback, escala, flag) e depois corrijo a causa, com post-mortem e alerta que teria avisado.
