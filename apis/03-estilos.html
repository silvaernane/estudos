MÓDULO 03 · Intermediário

GraphQL, gRPC e outros estilos

REST resolve a maior parte dos casos, mas não todos. Este módulo mostra o que GraphQL, gRPC, SOAP e companhia realmente fazem, onde cada um brilha, onde machuca e como decidir sem cair em modismo.

Ao final você saberá
  • Explicar por que existem vários estilos de API e qual problema cada um atacou
  • Modelar e proteger uma API GraphQL (N+1, DataLoader, cache, limites de custo, introspecção)
  • Ler um arquivo .proto, escolher o tipo de chamada gRPC e evoluir o contrato sem quebrar clientes
  • Integrar com serviços SOAP legados (convênios, governo) sem sofrer
  • Comparar REST, GraphQL, gRPC e SOAP por critério e defender uma escolha numa revisão de design
1Básico

Panorama: por que existem vários estilos

Todo estilo de API nasceu para resolver uma dor concreta de uma época e de um tipo de cliente. Entender a dor original é a forma mais rápida de saber quando o estilo serve e quando vira peso.

EstiloDor que atacouIdeia centralTransporte típico
SOAPIntegração corporativa com contrato formal, segurança e transações entre empresasEnvelope XML + contrato WSDL + extensões WS-*HTTP (também SMTP, filas)
RESTComplexidade do SOAP; web como plataformaRecursos com URL, verbos HTTP, cache da webHTTP/1.1, HTTP/2
GraphQLApps móveis pedindo dados diferentes em telas diferentes; muitas viagens de redeCliente descreve o formato da resposta num endpoint únicoHTTP POST (WebSocket/SSE em subscriptions)
gRPCChamadas entre microsserviços: latência, contrato forte, streamingContrato em Protocol Buffers, binário, funções remotas tipadasHTTP/2
JSON-RPC / tRPC / ODataChamar procedimentos de forma simples; consultar dados com padrão abertoMétodo + parâmetros; tipos compartilhados; query string padronizadaHTTP

Repare que nenhum substituiu o anterior. Hoje convivem na mesma empresa: um convênio fala SOAP com você, seu portal fala REST ou GraphQL com o backend, e os serviços internos falam gRPC ou eventos. Estilo de API é ferramenta por contexto, não religião.

As três perguntas que organizam a escolha

  1. Quem é o cliente? Navegador, app móvel, outro serviço seu, parceiro externo, sistema legado de operadora.
  2. Quem controla os dois lados? Se você controla cliente e servidor, pode adotar contrato binário e evolução coordenada. Se não controla, o menor denominador comum (HTTP + JSON) vence.
  3. O gargalo é rede, CPU, número de viagens ou coordenação entre times? Cada estilo otimiza uma coisa diferente.
Na entrevista

Quando perguntarem "REST ou GraphQL ou gRPC?", não escolha de cara. Diga: "depende de quem consome e de quem controla os dois lados. Para parceiros externos eu partiria de REST; para telas com dados muito variáveis, GraphQL, normalmente atrás de um BFF; entre serviços internos com latência crítica, gRPC". Em seguida cite o custo operacional de cada um. Isso é a resposta sênior: critérios, não preferência.

Para gestores

Cada estilo novo custa: ferramentas de teste, observabilidade, gateway, segurança e curva de aprendizado do time. Antes de aprovar um estilo novo, pergunte "qual dor mensurável isto resolve que o REST atual não resolve?" e "quem vai operar isto às três da manhã?". Estilo sem dor medida é modismo.

Saiba mais

O módulo 08 da trilha web (08-apis.html) já apresentou os estilos em alto nível. Aqui o foco é o funcionamento interno, os problemas de produção e a decisão.

2Intermediário

GraphQL: schema, operações e resolvers

GraphQL é uma linguagem de consulta para APIs e um runtime que a executa. O servidor publica um schema tipado; o cliente envia um documento dizendo exatamente quais campos quer; a resposta tem o mesmo formato da pergunta. Há normalmente um único endpoint (por exemplo POST /graphql).

Schema e tipos (SDL)

# Escalares: Int, Float, String, Boolean, ID (e os que você definir)
scalar DateTime

enum StatusAgendamento { AGENDADO CONFIRMADO CANCELADO REALIZADO }

type Paciente {
  id: ID!
  nome: String!
  convenio: Convenio          # nullable: paciente particular não tem
  agendamentos(status: StatusAgendamento, first: Int = 20, after: String): AgendamentoConnection!
}

type Convenio { id: ID!  nome: String!  plano: String }

type Agendamento {
  id: ID!
  inicio: DateTime!
  status: StatusAgendamento!
  paciente: Paciente!
  medico: Medico!
}

type Medico { id: ID!  nome: String!  especialidade: String! }

# Paginação estilo Relay (cursor)
type AgendamentoConnection { edges: [AgendamentoEdge!]!  pageInfo: PageInfo! }
type AgendamentoEdge { node: Agendamento!  cursor: String! }
type PageInfo { hasNextPage: Boolean!  endCursor: String }

input NovoAgendamento { pacienteId: ID!  medicoId: ID!  inicio: DateTime! }

type Query {
  paciente(id: ID!): Paciente
  agendamentos(medicoId: ID!, dia: String!): [Agendamento!]!
}
type Mutation {
  agendar(input: NovoAgendamento!): Agendamento!
  cancelarAgendamento(id: ID!, motivo: String): Agendamento!
}
type Subscription {
  agendamentoAtualizado(medicoId: ID!): Agendamento!
}
  • ! significa não nulo; sem ! o campo pode ser null. Decidir nulabilidade é decisão de contrato: String! que vira null por falha de um serviço faz o erro "subir" e anular o objeto pai.
  • input é um tipo só para entrada; type só para saída. Não se misturam.
  • interface e union permitem retornos polimórficos (ex.: um resultado de busca que pode ser Paciente ou Medico).
  • Descontinuação é por campo: campoAntigo: String @deprecated(reason: "use novoCampo"). Não existe "versão da API" no GraphQL; a evolução é aditiva.

Query, mutation e subscription

OperaçãoPara quêDetalhe que importa
queryLer dadosOs campos de um mesmo nível podem ser resolvidos em paralelo. Deve ser livre de efeitos colaterais.
mutationAlterar dadosOs campos da raiz executam em série, na ordem escrita. Retorne o objeto alterado para o cliente atualizar a tela sem nova consulta.
subscriptionReceber eventos em tempo realConexão longa, em geral WebSocket (às vezes SSE). Dá estado no servidor e complica escala (ver módulo 04).

Uma consulta e a resposta correspondente. O cliente de uma tela de agenda pede só o que a tela mostra:

Host: api.clinica.exemplo
Content-Type: application/json
Authorization: Bearer eyJ...

{
  "query": "query Agenda($medico: ID!, $dia: String!) { agendamentos(medicoId: $medico, dia: $dia) { id inicio status paciente { nome convenio { nome } } } }",
  "variables": { "medico": "m-77", "dia": "2026-03-10" },
  "operationName": "Agenda"
}
{
  "data": {
    "agendamentos": [
      { "id": "a-1", "inicio": "2026-03-10T09:00:00-03:00", "status": "CONFIRMADO",
        "paciente": { "nome": "Paciente Exemplo A", "convenio": { "nome": "Convênio Alfa" } } },
      { "id": "a-2", "inicio": "2026-03-10T09:30:00-03:00", "status": "AGENDADO",

    ]
  }
}

Sempre use variáveis ($medico) em vez de montar a string da consulta com valores concatenados: evita injeção e permite cache e persisted queries (seção 3).

Resolvers: onde a lógica realmente roda

Cada campo do schema tem um resolver: uma função que sabe buscar aquele campo. O runtime percorre a consulta de cima para baixo e chama o resolver de cada campo pedido, passando o objeto pai.

const resolvers = {
  Query: {
    agendamentos: (_, { medicoId, dia }, ctx) =>
      ctx.db.agendamentos.porMedicoEDia(medicoId, dia),
  },
  Agendamento: {
    // chamado UMA VEZ PARA CADA agendamento retornado acima
    paciente: (ag, _, ctx) => ctx.db.pacientes.porId(ag.pacienteId),
  },
  Paciente: {
    convenio: (p, _, ctx) => p.convenioId ? ctx.db.convenios.porId(p.convenioId) : null,
  },
};

Esse comentário no resolver de paciente é o germe do problema da próxima seção.

Na entrevista

"GraphQL substitui REST?" Não: troca quem decide o formato da resposta (do servidor para o cliente) ao custo de mover complexidade para o servidor (resolvers, custo de consulta, cache). Mostre que você sabe o lado ruim: N+1, cache HTTP perdido e superfície de ataque maior.

Para gestores

O schema é um contrato vivo compartilhado entre times de frontend e backend. Cobre: dono do schema definido, revisão de mudanças no schema como em qualquer API pública (aditivo, depreciar antes de remover) e verificação automática de quebra no CI (ferramentas de schema diff e checagem contra as consultas reais em uso).

3Intermediário

GraphQL: overfetching, N+1, DataLoader e cache

Overfetching e underfetching: o que o GraphQL realmente resolve

  • Overfetching: o endpoint REST devolve 40 campos e a tela usa 4. Em redes móveis ruins, bytes e parsing contam.
  • Underfetching: uma tela precisa de agendamento, paciente, convênio e médico; em REST puro são 4 chamadas encadeadas, cada uma esperando a anterior.

Mas REST bem desenhado já mitiga: campos selecionáveis (?fields=), expansão (?include=paciente) e endpoints de composição. Se o único motivo para GraphQL é "evitar duas chamadas", provavelmente um BFF (seção 9) resolve mais barato.

O problema N+1

No resolver da seção anterior, buscar 20 agendamentos custa 1 consulta; depois, para cada um, paciente dispara outra consulta. Total: 1 + N idas ao banco. Com o campo medico também, vira 1 + 2N. A consulta GraphQL parece inocente; o custo está escondido nos resolvers.

DataLoader: batching e cache por requisição

O padrão DataLoader (criado no ecossistema JavaScript, com equivalentes em Java, Python, C#, Go) faz duas coisas: agrupa (batch) todas as chaves pedidas no mesmo ciclo em uma única busca, e memoiza o resultado durante aquela requisição para não buscar a mesma chave duas vezes.

import DataLoader from 'dataloader';

// uma instância POR REQUISIÇÃO (nunca global: vazaria dados entre usuários)
export function criarLoaders(db) {
  return {
    pacientePorId: new DataLoader(async (ids) => {
      const rows = await db.query('SELECT * FROM paciente WHERE id = ANY($1)', [ids]);
      const porId = new Map(rows.map(r => [r.id, r]));
      // contrato: devolver na MESMA ORDEM das chaves, com null/erro onde faltar
      return ids.map(id => porId.get(id) ?? null);
    }),
  };
}

// resolver
paciente: (ag, _, ctx) => ctx.loaders.pacientePorId.load(ag.pacienteId),
Armadilha comum

Três erros clássicos: (1) loader global em vez de por requisição, vazando cache e autorização entre usuários; (2) esquecer de devolver o array na mesma ordem e com o mesmo tamanho das chaves; (3) "resolver" N+1 só no resolver raiz e esquecer os campos aninhados. Meça sempre o número de queries por operação em teste automatizado.

Outra saída é olhar o que a consulta pediu e montar um JOIN único (look-ahead). É mais eficiente, porém mais acoplado ao banco. Para dados que vêm de outros serviços, o DataLoader costuma ser o caminho.

Cache: por que é mais difícil que em REST

Em REST, GET /pacientes/42 é uma URL: navegador, CDN e proxy cacheiam de graça com Cache-Control e ETag (visto no módulo 06 da trilha web). Em GraphQL, por padrão tudo é POST /graphql: a URL é a mesma para qualquer consulta, e o POST não é cacheado por padrão. Consequências:

  • Sem cache HTTP/CDN automático; o cache passa a ser do cliente (caches normalizados por id e __typename) e do servidor (por resolver, via DataLoader, Redis, hints de TTL por campo).
  • Cada tela tem uma consulta diferente, então a taxa de acerto de um cache de resposta inteira é baixa.
  • Invalidação: o cache normalizado do cliente só atualiza o que a mutation retornar. Mutation que devolve pouco deixa a tela velha.

Persisted queries: cache, segurança e banda

Na persisted query, o texto da consulta é registrado antes (em build ou no primeiro uso) e o cliente envia só um identificador/hash. Ganhos:

  • Pode-se usar GET /graphql?id=abc123&variables=..., cacheável por CDN.
  • Menos bytes por requisição.
  • Segurança: o servidor pode aceitar somente consultas previamente registradas (allowlist). Um atacante não consegue enviar consultas arbitrárias e caras.
GET /graphql?extensions={"persistedQuery":{"version":1,"sha256Hash":"ecf4..."}}&variables={"medico":"m-77","dia":"2026-03-10"} HTTP/1.1
Host: api.clinica.exemplo
Accept: application/json
Regra de bolso

API GraphQL consumida só pelos seus próprios apps: use persisted queries com allowlist em produção. API GraphQL aberta a terceiros: não dá para allowlist, então os limites de custo (próxima seção) viram obrigatórios.

Na entrevista

"O que é o problema N+1 em GraphQL e como resolve?" Resposta curta: "cada item da lista dispara um resolver filho que consulta o banco; corrijo com DataLoader (batching + cache por requisição) ou JOIN planejado, e protejo com teste que conta queries". Citar "uma instância por requisição" mostra experiência.

Para gestores

GraphQL desloca o custo do cliente para o servidor. Monitore por operação nomeada (operationName), não por URL: todas as requisições têm a mesma rota. Exija nome de operação em todo cliente, latência p95 por operação e número médio de queries por operação. Sem isso, o time fica cego.

4Avançado

GraphQL em produção: segurança, erros e federação

Limites de profundidade e complexidade

Como o cliente escreve a consulta, ele também pode escrever uma consulta maliciosa (ou só ingênua) que custa uma fortuna. Com relações circulares no schema, a consulta pode se aninhar sem fim:

query {
  paciente(id: "42") {
    agendamentos(first: 1000) { edges { node {
      medico { agendamentos(first: 1000) { edges { node {
        paciente { agendamentos(first: 1000) { edges { node { id } } } }
      } } } }
    } } }
  }
}

Defesas em camadas (todas, não uma):

  • Profundidade máxima (ex.: 8 a 12 níveis) rejeitando antes de executar.
  • Análise de custo/complexidade: cada campo tem um custo; listas multiplicam pelo argumento first; rejeitar acima de um orçamento por requisição.
  • Limite de paginação: first com teto (ex.: 100). Nunca aceitar listas sem limite.
  • Timeout de execução e cancelamento quando o cliente desiste.
  • Rate limit por custo, não por número de requisições: 1 requisição pode valer 1 ou 10 mil unidades.
  • Limite de tamanho do documento e de aliases/batching (um atacante pode repetir a mesma operação cara com 500 aliases numa só requisição, contornando o rate limit por requisição e tentando força bruta de login).
  • Persisted queries com allowlist quando possível.
Armadilha comum

Autorização feita só na camada de rota ("o usuário tem acesso ao /graphql"). Em GraphQL a autorização precisa ser por campo/objeto, na regra de negócio: um paciente que consegue navegar de agendamento para paciente para outro agendamento vê dados que não são dele (BOLA/IDOR, visto no OWASP do módulo 09 da trilha web). Centralize a checagem em uma camada de domínio, não em cada resolver.

Introspecção em produção

A introspecção permite que o cliente pergunte ao servidor "quais tipos e campos você tem?" (__schema). É o que alimenta GraphiQL, geração de código e autocompletar. Em produção, para APIs que não são públicas, ela entrega o mapa completo da superfície de ataque, incluindo campos internos esquecidos.

  • API privada/interna: desligue a introspecção em produção; use o schema versionado no repositório/registro de schemas para ferramentas.
  • API pública documentada: pode manter, mas então a segurança não pode depender de "ninguém conhece esse campo" (segurança por obscuridade).
  • Desligar introspecção não protege sozinho: muitos servidores sugerem nomes de campo parecidos nas mensagens de erro ("Did you mean ..."), vazando o schema. Desligue as sugestões também.

Erros que voltam com HTTP 200

No GraphQL, a resposta pode ter data e errors ao mesmo tempo (resposta parcial), e o HTTP costuma ser 200 mesmo com erro de negócio, porque a requisição HTTP em si deu certo. Isso quebra hábitos: o monitor que olha só status 5xx não vê nada, e o retry automático do cliente HTTP não dispara.

{
  "data": { "paciente": { "nome": "Paciente Exemplo A", "convenio": null } },
  "errors": [
    {
      "message": "Serviço de convênios indisponível",
      "path": ["paciente", "convenio"],
      "extensions": { "code": "UPSTREAM_UNAVAILABLE", "retryable": true }
    }
  ]
}
  • Padronize extensions.code (equivalente ao type/code do problem details do REST) e nunca vaze stack trace.
  • Distinga erros de sistema (vão em errors) de erros esperados de negócio. Para estes, muitos times modelam no próprio schema: a mutation retorna uma union como AgendarResultado = Agendamento | HorarioIndisponivel | ConvenioNaoCobre, tipada e explícita.
  • Métricas e alertas precisam ler o corpo (errors não vazio), não só o status HTTP.
  • Erros em campo ! propagam: o nulo "sobe" até o primeiro ancestral anulável. Um campo obrigatório que falha pode apagar um objeto inteiro da resposta.

Federação, em alto nível

Quando há muitos times, um schema único mantido por um time vira gargalo. Federação (a mais conhecida é a do Apollo; há outras implementações) divide o schema em subgrafos, cada um pertencente a um time/serviço (pacientes, agenda, faturamento). Um gateway/router compõe tudo num supergrafo único para o cliente e planeja a consulta: decide quais subgrafos chamar e junta o resultado.

# o subgrafo de faturamento ESTENDE o tipo Paciente, que pertence ao subgrafo de pacientes
extend type Paciente @key(fields: "id") {
  id: ID! @external
  guias: [GuiaTiss!]!        # campo que só o faturamento sabe resolver
}
  • Ganho: autonomia de times, schema único para o cliente, evolução independente.
  • Custo: operar um router, gestão de composição/CI de schemas, consultas distribuídas difíceis de depurar (tracing distribuído é obrigatório), latência somada, e N+1 entre serviços.
  • Só compensa com vários times e vários domínios. Para um time único, um monólito GraphQL ou um BFF é muito mais simples.
Na entrevista

"Como protege uma API GraphQL?" Liste em ordem: autenticação e autorização por campo; profundidade e custo máximos; teto de paginação; timeouts; rate limit por custo; persisted queries; introspecção desligada se privada; erros sem detalhes internos; logs por operação.

Para gestores

Antes de aprovar GraphQL público, pergunte: "qual o orçamento de custo por requisição e quem é paginado?", "como o monitoramento enxerga erros se tudo é 200?", "quem é dono de cada campo do schema?". Se não há resposta, o time ainda não está pronto para operar isso fora de casa.

5Intermediário

gRPC: Protocol Buffers, HTTP/2 e tipos de chamada

gRPC é um framework de RPC (chamada de procedimento remoto) originado no Google. O cliente chama um método de um serviço remoto como se fosse uma função local, com tipos gerados a partir de um contrato único escrito em Protocol Buffers (protobuf). Dois pilares: o contrato (.proto) e o transporte (HTTP/2).

Protocol Buffers e o arquivo .proto

Protobuf é uma linguagem de definição de contrato e um formato binário compacto. Você escreve o .proto, roda o compilador (protoc ou buf) e ganha código cliente e servidor tipados em Java, Go, C#, Python, JS e outras.

syntax = "proto3";

package clinica.agenda.v1;

import "google/protobuf/timestamp.proto";

service AgendaService {
  // Unária: 1 pedido, 1 resposta
  rpc ObterAgendamento(ObterAgendamentoRequest) returns (Agendamento);

  // Server streaming: 1 pedido, N respostas ao longo do tempo
  rpc ListarAgendamentos(ListarRequest) returns (stream Agendamento);

  // Client streaming: N pedidos, 1 resposta (ex.: importar lote)
  rpc ImportarAgendamentos(stream Agendamento) returns (ResumoImportacao);

  // Bidirecional: os dois lados enviam streams independentes
  rpc Acompanhar(stream FiltroEvento) returns (stream EventoAgenda);
}

enum Status {
  STATUS_UNSPECIFIED = 0;   // sempre um zero "não informado"
  STATUS_AGENDADO = 1;
  STATUS_CONFIRMADO = 2;
  STATUS_CANCELADO = 3;
}

message Agendamento {
  string id = 1;
  string paciente_id = 2;
  string medico_id = 3;
  google.protobuf.Timestamp inicio = 4;
  Status status = 5;
  reserved 6;               // campo removido: o número nunca mais pode ser reutilizado
  reserved "observacao_antiga";
  optional string motivo_cancelamento = 7;
}

message ObterAgendamentoRequest { string id = 1; }
message ListarRequest { string medico_id = 1; string dia = 2; }
message FiltroEvento { string medico_id = 1; }
message EventoAgenda { string tipo = 1; Agendamento agendamento = 2; }
message ResumoImportacao { int32 importados = 1; int32 rejeitados = 2; }
  • Cada campo tem um número (= 1, = 2). No fio, o que viaja é o número, não o nome. Por isso o payload é pequeno.
  • Números de 1 a 15 ocupam menos bytes no fio: reserve-os para os campos mais usados.
  • No proto3, campo ausente assume o valor padrão (0, string vazia, falso). Para distinguir "ausente" de "zero", use optional ou tipos wrapper.
  • Timestamp, Duration e outros tipos conhecidos já vêm prontos na biblioteca padrão.

Por que HTTP/2 importa

  • Multiplexação: muitas chamadas concorrentes numa única conexão TCP, sem bloqueio entre elas no nível HTTP.
  • Frames binários e compressão de cabeçalhos (HPACK): menos overhead por chamada.
  • Streams bidirecionais sobre a mesma conexão: base do streaming do gRPC.
  • Trailers: o status final do gRPC viaja nos trailers, depois do corpo. É um dos motivos de o gRPC não funcionar direto em navegadores (seção 6).

Cada chamada vira um POST /clinica.agenda.v1.AgendaService/ObterAgendamento com content-type: application/grpc. Na prática você não escreve isso à mão; o stub gerado cuida.

Os quatro tipos de chamada

TipoFormaExemplo em saúde
Unária1 requisição, 1 respostaObter um agendamento; calcular cobertura de um procedimento
Server streaming1 requisição, fluxo de respostasListar milhares de exames sem carregar tudo em memória; acompanhar a fila de atendimento
Client streamingFluxo de requisições, 1 respostaEnviar um lote grande de resultados de laboratório e receber o resumo ao final
BidirecionalFluxos independentes nos dois sentidosCanal de eventos de uma central de monitoramento; chat entre serviços

Cliente em pseudocódigo JavaScript (stub gerado) para o streaming de servidor:

const stream = client.listarAgendamentos({ medicoId: 'm-77', dia: '2026-03-10' });
stream.on('data', (ag) => console.log(ag.id, ag.status));
stream.on('error', (err) => console.error(err.code, err.details));
stream.on('end', () => console.log('fim'));
Na entrevista

"Por que gRPC é mais rápido que REST/JSON?" Três razões: serialização binária compacta e barata de ler (protobuf), HTTP/2 com multiplexação numa conexão persistente e código gerado sem parsing manual. Mas diga: "o ganho aparece em volume alto e payload grande entre serviços; para um CRUD simples, a diferença some perto de uma consulta ao banco".

Para gestores

gRPC exige um fluxo de contrato: repositório central de .proto, versionamento por pacote (v1, v2), geração de código no CI e linter de compatibilidade (ex.: buf breaking). Sem essa disciplina, o time perde a vantagem do contrato forte e acumula clientes quebrando em silêncio.

6Avançado

gRPC em produção: deadlines, status, compatibilidade e navegador

Deadlines: o timeout que se propaga

No gRPC, o cliente define um deadline (prazo absoluto) por chamada. O servidor recebe esse prazo, e ao chamar um terceiro serviço propaga o que sobrou. Se o prazo estoura, todos na cadeia cancelam o trabalho. Sem deadline, uma chamada pode ficar pendurada indefinidamente e esgotar threads e conexões (cascata de falhas; assunto do módulo 06 desta trilha).

const deadline = new Date(Date.now() + 800); // 800 ms para a chamada inteira
client.obterAgendamento({ id: 'a-1' }, { deadline }, (err, resp) => {
  if (err) return tratar(err); // err.code === 4 (DEADLINE_EXCEEDED) se estourar
  usar(resp);
});
Regra de bolso

Toda chamada gRPC sai com deadline. Defina um padrão na biblioteca do cliente para ninguém esquecer, e o servidor deve respeitar o cancelamento (parar de consultar o banco quando o cliente já desistiu).

Códigos de status gRPC

O gRPC tem seu próprio conjunto de códigos (não são status HTTP). Os mais usados:

Para detalhes além do código, o gRPC permite anexar mensagens de erro estruturadas (o modelo de erro "rich" do Google) com campos violados, informações de retry e mais.

Compatibilidade: números de campo são o contrato

Protobuf foi pensado para que cliente e servidor em versões diferentes continuem se entendendo. Isso vale se você respeitar regras, e elas são mais duras do que parecem:

Apagar um campo do .proto "porque ninguém usa" e, meses depois, outro dev reaproveitar o número. Dados gravados em fila, cache ou banco com o formato antigo passam a ser interpretados errado. Sempre reserved, e rode checagem automática de quebra no CI.

gRPC-Web, transcoding e o navegador

O navegador não permite controlar frames HTTP/2 nem ler trailers via fetch, então não consegue falar gRPC nativo. Soluções:

  • gRPC-Web: variante do protocolo feita para navegadores, que usa um proxy (como o Envoy ou um middleware) para traduzir para gRPC puro. Suporta só unária e streaming de servidor, sem client streaming nem bidirecional.
  • Transcoding (gRPC-JSON): o gateway expõe uma API REST/JSON gerada a partir do .proto (anotações google.api.http, grpc-gateway, Envoy). Parceiros e frontends falam REST; os serviços internos falam gRPC.
  • Protocolos alternativos compatíveis (como o Connect, da Buf) funcionam em navegador e falam também com servidores gRPC.

Por que é ótimo entre serviços e ruim direto no navegador

Ótimo entre serviçosRuim para clientes externos/web
Contrato forte e código gerado; erro de tipo vira erro de compilaçãoBinário: não dá para testar com curl e olhar na aba Network sem ferramentas
Baixa latência e boa vazão, streaming nativoNavegador exige proxy; sem client streaming
Deadlines e cancelamento propagadosCache HTTP e CDN não se aplicam
Vários idiomas com o mesmo contratoParceiros esperam REST/JSON e OpenAPI; menos ferramentas para eles

Detalhe operacional: o balanceamento de carga em gRPC é diferente. Como a conexão HTTP/2 é longa e multiplexada, um balanceador de camada 4 distribui conexões, não chamadas, e pode deixar uma instância sobrecarregada. Use balanceamento por chamada (camada 7 ciente de gRPC, service mesh ou balanceamento no cliente).

Na entrevista

"Posso expor gRPC para o frontend web?" Resposta sênior: "diretamente não; só com gRPC-Web via proxy, e sem alguns tipos de streaming. Em geral mantenho gRPC entre serviços e exponho REST/JSON ou GraphQL na borda, com transcoding ou um BFF".

Para gestores

Cobre três coisas do time que adota gRPC: deadline padrão em todo cliente, checagem de compatibilidade do .proto no CI e tracing distribuído (a depuração de binário é mais difícil). Pergunte também como os testes manuais serão feitos: sem ferramentas como grpcurl ou um cliente gráfico, o suporte sofre.

7Intermediário

SOAP, WSDL e XML: o legado que ainda manda

SOAP (Simple Object Access Protocol) é um protocolo de mensagens baseado em XML, descrito por um contrato WSDL (Web Services Description Language). Parece coisa do passado, mas continua presente em saúde suplementar, governo e operadoras. Integrações com convênios (troca de guias, verificação de elegibilidade), serviços fiscais e sistemas de órgãos públicos muitas vezes ainda são SOAP, e você não escolhe: o lado de lá dita. Vale confirmar no manual de integração de cada parceiro (no Brasil, o padrão TISS da ANS é um caso em que serviços web SOAP são comuns).

Anatomia de uma mensagem

POST /ws/elegibilidade HTTP/1.1
Host: servicos.convenio-alfa.exemplo
Content-Type: text/xml; charset=utf-8
SOAPAction: "urn:verificarElegibilidade"

<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"
                  xmlns:el="urn:convenio-alfa:elegibilidade:v2">
  <soapenv:Header>
    <!-- credenciais, assinatura, timestamp (WS-Security) -->
  </soapenv:Header>
  <soapenv:Body>
    <el:VerificarElegibilidadeRequest>
      <el:carteirinha>0001234567890</el:carteirinha>
      <el:procedimento>10101012</el:procedimento>
    </el:VerificarElegibilidadeRequest>
  </soapenv:Body>
</soapenv:Envelope>
HTTP/1.1 500 Internal Server Error
Content-Type: text/xml; charset=utf-8

<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/">
  <soapenv:Body>
    <soapenv:Fault>
      <faultcode>soapenv:Client</faultcode>
      <faultstring>Carteirinha inválida</faultstring>
      <detail><codigo>E102</codigo></detail>
    </soapenv:Fault>
  </soapenv:Body>
</soapenv:Envelope>
  • Envelope (raiz), Header (metadados: segurança, roteamento) e Body (a mensagem). Falhas vêm como Fault dentro do Body.
  • Quase tudo é POST para um único endpoint; a operação vai no Body (e no cabeçalho SOAPAction no SOAP 1.1). Por isso o cache HTTP e as semânticas de verbo não se aplicam.
  • O WSDL descreve operações, mensagens, tipos (via XSD), endpoints e bindings. Dele se geram os clientes.
  • Há duas versões, SOAP 1.1 e 1.2, que diferem em content type e detalhes de Fault. Confirme qual o parceiro usa.
  • O status HTTP pode ser 200 com Fault no corpo em alguns serviços; leia o corpo, como no GraphQL.

WS-Security e a família WS-*

SOAP tem um conjunto de extensões padronizadas. A mais comum é a WS-Security, que coloca segurança dentro da mensagem (no Header), não só no transporte: UsernameToken (usuário e senha, às vezes com hash e nonce), assinatura XML (integridade e autoria), criptografia de partes do XML e Timestamp (anti-replay). Isso permite que a mensagem atravesse intermediários e continue protegida, mas é complexo: erros de canonicalização do XML ou deslocamento de relógio causam falhas confusas.

Como integrar com legado sem sofrer

  1. Gere o cliente a partir do WSDL. Não monte o XML à mão. Ferramentas: wsimport/Apache CXF (Java), clientes de serviço do .NET, zeep (Python). Versione o WSDL no repositório.
  2. Isole atrás de um adaptador (anti-corruption layer). Um módulo ou serviço próprio fala SOAP e expõe ao resto do sistema uma interface limpa em REST/JSON ou um contrato interno. Os nomes do legado não vazam para o domínio.
  3. Trate timeouts, retries e idempotência. Serviços legados são lentos e instáveis. Defina timeouts curtos, retry só para operações idempotentes e circuit breaker. Muitos não têm chave de idempotência: você precisa consultar antes de reenviar.
  4. Valide e registre as mensagens. Guarde (com mascaramento de dados pessoais) o XML enviado e recebido: é a prova em disputas com a operadora. Valide contra o XSD antes de enviar.
  5. Gerencie certificados e relógio. Certificados de cliente vencem; renovação sem alerta derruba a integração num feriado. Sincronize NTP: WS-Security rejeita timestamps fora da janela.
  6. Teste com um stub. Use SoapUI ou um mock a partir do WSDL para testes automatizados sem depender do homologador do parceiro, que vive fora do ar.
GET /elegibilidade?carteirinha=0001234567890&procedimento=10101012 HTTP/1.1
Host: api.clinica.exemplo

HTTP/1.1 200 OK
Content-Type: application/json

{ "elegivel": true, "coparticipacao": 25.00, "origem": "convenio-alfa" }
Armadilha comum

Cuidado com XML: use um parser com entidades externas desabilitadas (ataque XXE, que aparece no OWASP) e com limites de tamanho. SOAP aceita XML de fora; parser configurado por padrão em algumas bibliotecas é vulnerável.

Na entrevista

"Já integrou com SOAP?" Mesmo sem experiência, mostre o método: gero cliente do WSDL, isolo num adaptador, trato Fault e timeouts, valido contra o XSD e monitoro certificados. Demonstra maturidade tratar legado como realidade de saúde, não como desprezo.

Para gestores

Integração SOAP vira dívida de operação: poucos devs conhecem, o homologador é instável e o contrato muda por ofício. Mapeie quem é o dono de cada integração, onde ficam os certificados e as datas de vencimento, e meça disponibilidade e taxa de falha por parceiro. Não migre o parceiro: você não controla o lado dele.

8Intermediário

JSON-RPC, tRPC e OData em resumo

JSON-RPC

Especificação minúscula (versão 2.0) para chamar métodos remotos com JSON. A requisição tem jsonrpc, method, params e id; sem id é uma notificação (não espera resposta). Suporta lote (array de chamadas). Códigos de erro padrão: -32700 (parse), -32600 (requisição inválida), -32601 (método inexistente), -32602 (parâmetros inválidos) e -32603 (erro interno).

{ "jsonrpc": "2.0", "method": "agenda.cancelar", "params": { "id": "a-1", "motivo": "paciente" }, "id": 7 }

{ "jsonrpc": "2.0", "result": { "status": "CANCELADO" }, "id": 7 }

{ "jsonrpc": "2.0", "error": { "code": -32602, "message": "Parâmetros inválidos" }, "id": 7 }

Onde aparece: nós de blockchain, o Language Server Protocol dos editores e protocolos de agentes de IA. Bom para ações ("cancelar", "recalcular") que não encaixam em recurso. Ruim para cache e para descoberta (sem contrato padrão como OpenAPI).

tRPC

Biblioteca TypeScript para chamar funções do servidor no cliente com tipos inferidos, sem schema separado nem geração de código. Mudou o tipo no servidor, o cliente quebra na compilação. Excelente quando servidor e cliente são TypeScript no mesmo repositório (monorepo) e o mesmo time os mantém. Não serve como API pública nem para clientes em outras linguagens, porque o contrato é o código TypeScript.

OData

Padrão aberto (OASIS) para APIs de dados em cima de REST, com convenções de consulta na URL: $filter, $select, $expand, $orderby, $top/$skip, $count, além de um $metadata que descreve o modelo. Popular no ecossistema Microsoft, SAP e em ferramentas de BI.

GET /odata/Agendamentos?$filter=status eq 'CONFIRMADO' and inicio ge 2026-03-10T00:00:00Z&$select=id,inicio&$expand=Paciente($select=nome)&$orderby=inicio&$top=20 HTTP/1.1
Host: api.clinica.exemplo

Dá "um GraphQL limitado" sobre REST, com ferramentas prontas (Excel, Power BI leem OData). O risco é parecido: o cliente escreve filtros arbitrários que podem não ter índice. Limite campos filtráveis e ordenáveis, como no módulo de paginação e índices da trilha de SQL.

JSON-RPCProtocolo simples orientado a ações; ferramentas e agentesPrecisa de cache HTTP, descoberta e documentação padrão
tRPCFull-stack TypeScript, um time, monorepoClientes em outras linguagens ou parceiros externos

Na entrevista

Se perguntarem por estilos menos comuns, basta uma frase de cada com o trade-off: "JSON-RPC é chamada de método leve sem contrato forte; tRPC dá tipos ponta a ponta só dentro do TypeScript; OData padroniza consulta em REST, útil para BI". Admitir que não usa em produção e explicar quando usaria é melhor do que fingir.

Para gestores

Quanto mais estilos no portfólio, maior o custo de gateway, segurança e treinamento. Mantenha uma lista curta e aprovada: por exemplo REST para externos, gRPC ou eventos entre serviços, GraphQL só atrás de BFF. Exceções entram por revisão de design, com dono e justificativa.

Regra de bolso

Default: REST com OpenAPI. Troque quando houver dor concreta: telas com dados muito variáveis (GraphQL, atrás de BFF), latência e vazão entre serviços ou streaming (gRPC), ou parceiro que só fala outro dialeto (SOAP, via adaptador).

BFF: Backend for Frontend

O BFF é uma camada de API feita sob medida para um tipo de cliente (app móvel, portal web, portal do convênio), de propriedade do time desse cliente. Ele compõe várias chamadas aos serviços internos, formata a resposta exatamente como a tela precisa e esconde a topologia interna. O problema que resolve: um backend genérico serve mal a todos e vira campo de disputa entre times.

  • Quando usar: vários canais com necessidades diferentes; telas que juntam dados de vários serviços; necessidade de reduzir viagens no móvel; esconder serviços internos (gRPC, SOAP) do cliente.
  • Dentro do BFF você escolhe o estilo: pode ser REST, ou GraphQL só para o frontend, enquanto fala gRPC para trás. Esse arranjo concentra o risco de GraphQL num lugar controlado.
  • Armadilhas: regra de negócio vazando para o BFF (duplicada entre BFFs); BFF virando monólito "faz-tudo"; muitas camadas somando latência; time de BFF diferente do time do frontend, trazendo de volta a fila de pedidos.
  • Regra: BFF compõe e adapta; regra de negócio fica nos serviços de domínio.

Erros comuns de escolha por modismo

  • "GraphQL porque o time de frontend pediu", sem ter medido overfetching: troca simplicidade por N+1, cache complexo e segurança nova.
  • "gRPC em tudo", inclusive na API pública: parceiros não conseguem integrar e o suporte fica cego.
  • "Microsserviços com gRPC" para um sistema que cabia num monólito: o custo é distribuição, não protocolo.
  • Querer "modernizar" a integração SOAP do convênio: você não controla o outro lado. Isole com adaptador.
  • Federação GraphQL com um time só.
  • Escolher estilo pelo currículo ("resume-driven development") em vez de pelo problema.
  • Duas APIs (REST e GraphQL) para o mesmo domínio sem dono e sem plano de desligar uma: dobra o custo e a superfície de ataque.
Armadilha comum

Comparar estilos só por velocidade de benchmark. Em saúde, o gargalo real quase sempre é banco, sistema de terceiros ou rede de unidades remotas, não a serialização. Meça antes de trocar de protocolo.

Na entrevista

Monte a resposta como um mini ADR: contexto, opções, critério, decisão, consequências. Por exemplo: "portal do paciente e app, com telas ricas em dados de vários serviços: BFF com GraphQL falando gRPC com os serviços; API de parceiros em REST/OpenAPI; integração com operadora via adaptador SOAP".

Para gestores

Registre a decisão (ADR) com a dor que motivou e a condição para revisar. Pergunta de revisão de design: "o que acontece se o time que fez isso sair?". Estilos exóticos aumentam o fator de risco de pessoas-chave.

Cenários práticos e glossário

Cenários

Cenário 1: a tela de agenda ficou lenta depois de migrar para GraphQL

A latência da operação Agenda subiu de 200 ms para 2 s. O que fazer: habilitar tracing por resolver e contar queries por operação; provavelmente 1 + N em paciente e convenio. Introduzir DataLoader por requisição, adicionar teste que falha se a operação passar de X queries e criar alerta de p95 por operationName.

Cenário 2: parceiro quer consultar seus agendamentos por API

O time sugere expor o GraphQL interno. O que fazer: não expor. Parceiro externo pede estabilidade, quotas e documentação clássica. Oferecer REST com OpenAPI, escopos OAuth e rate limit; reutilizar os serviços internos por baixo. GraphQL público só com limite de custo, sem introspecção e com monitoramento de abuso.

Cenário 3: integração com a operadora é SOAP e cai toda semana

Falhas esporádicas, timeouts e um certificado que venceu no domingo. O que fazer: adaptador isolado com timeout, circuit breaker e retry só em leitura; alerta de vencimento de certificado com 30 dias de antecedência; log do XML (mascarado) para disputa; painel de disponibilidade por parceiro; abrir chamado formal com evidências.

Cenário 4: um dev removeu um campo do .proto e o serviço de faturamento começou a gravar lixo

O número do campo foi reaproveitado. O que fazer: reverter, reservar o número e o nome, incluir buf breaking no CI e revisar dados gravados no período. Na retrospectiva, tornar o linter obrigatório no pipeline.

Cenário 5: o time quer gRPC para o portal do paciente

Argumento: "é mais rápido". O que fazer: perguntar qual métrica será melhorada e se foi medida; apontar que o navegador exige gRPC-Web com proxy e limita streaming; propor REST/GraphQL via BFF para o portal e gRPC só entre serviços, onde há ganho real.

Perguntas de entrevista

01Qual a diferença fundamental entre REST e GraphQL?

Em REST o servidor define o formato de cada recurso/endpoint; em GraphQL o cliente descreve, num endpoint único, exatamente os campos que quer, com base num schema tipado. GraphQL reduz overfetching e viagens de rede, mas move complexidade para o servidor e perde o cache HTTP padrão.

02O que são query, mutation e subscription?

Query lê dados; mutation altera (campos da raiz executam em série); subscription entrega eventos ao longo do tempo, normalmente por WebSocket ou SSE. As duas primeiras são requisição/resposta.

03O que é overfetching e underfetching? GraphQL é a única solução?

Overfetching é receber mais campos do que a tela usa; underfetching é precisar de várias chamadas para montar uma tela. GraphQL resolve os dois, mas não é a única: campos selecionáveis, expansão de relações e um BFF também resolvem, com menos custo operacional.

04Explique o problema N+1 e como o DataLoader ajuda.

Um resolver de lista dispara um resolver filho por item, que consulta o banco: 1 + N queries. O DataLoader agrupa as chaves pedidas no mesmo ciclo em uma busca em lote e memoiza por requisição. Deve haver uma instância por requisição, e a função de lote devolve resultados na mesma ordem das chaves.

05Por que é mais difícil fazer cache em GraphQL?

Porque tudo é um POST para a mesma URL, com consultas diferentes por tela; o cache HTTP/CDN não se aplica. O cache fica no cliente (normalizado por id e tipo), no servidor (por resolver) ou via persisted queries com GET, que permitem cache de borda.

06Como proteger uma API GraphQL contra consultas abusivas?

Limites de profundidade e de custo por consulta, teto de paginação, timeout, rate limit por custo, limite de aliases e tamanho, persisted queries com allowlist, autorização por campo e introspecção desligada se a API é privada.

07Por que o monitoramento de uma API GraphQL pode "não ver" erros?

Porque erros de execução costumam voltar com HTTP 200 e um array errors no corpo, possivelmente com dados parciais. É preciso instrumentar pelo corpo e por operação nomeada, padronizar extensions.code e usar union types para erros de negócio esperados.

08Quando faz sentido federação GraphQL?

Quando muitos times são donos de partes diferentes do domínio e um schema central virou gargalo. Cada time mantém um subgrafo e um router compõe o supergrafo. Custo: operar o router, governança de schema, tracing distribuído e latência somada. Para um time só é exagero.

09O que é gRPC e o que o diferencia de REST?

É um framework de RPC com contrato em Protocol Buffers, serialização binária e HTTP/2. Dá código gerado tipado, multiplexação, streaming e deadlines, e brilha entre serviços internos. Perde em transparência (binário), cache e facilidade para parceiros e navegadores.

10Quais os quatro tipos de chamada do gRPC? Dê um exemplo de uso.

Unária (obter um agendamento), server streaming (listar muitos exames em fluxo), client streaming (enviar lote de resultados e receber um resumo) e bidirecional (canal contínuo de eventos entre serviços).

11Como evoluir um .proto sem quebrar clientes antigos?

Só adicionar campos com números novos; nunca reutilizar um número nem mudar o tipo; ao remover, usar reserved para número e nome; tratar valores de enum desconhecidos; para mudança incompatível, criar nova versão do pacote/serviço. Automatizar com um linter de quebra (por exemplo buf breaking) no CI.

12O que é um deadline em gRPC e por que não usar apenas timeout?

É um prazo absoluto definido pelo cliente e propagado pelos serviços da cadeia, que repassam o tempo restante. Ao estourar, todos cancelam o trabalho. Timeouts independentes por serviço não se coordenam e podem manter trabalho inútil rodando depois que o cliente já desistiu.

13Por que o navegador não fala gRPC nativo e o que se faz?

As APIs do navegador não dão controle dos frames HTTP/2 nem acesso a trailers, onde viaja o status do gRPC. Usa-se gRPC-Web com um proxy (por exemplo Envoy), ciente de que não há client streaming nem bidirecional, ou transcoding para REST/JSON, ou um BFF.

14O que é um BFF e quando não usar?

Uma camada de API sob medida para um tipo de cliente, que agrega serviços e adapta o formato. Não use quando há um só cliente simples ou quando o BFF viraria monólito com regra de negócio duplicada. Mantenha a regra de negócio nos serviços de domínio e o BFF no time dono do cliente.

15Você precisa integrar com um serviço SOAP de uma operadora. Como começa?

Pego o WSDL e os XSDs, gero o cliente, isolo tudo num adaptador que expõe uma interface limpa ao resto do sistema, valido o XML contra o XSD, trato Fault e timeouts, aplico retry só em operações idempotentes, registro mensagens mascaradas e monitoro certificados e relógio por causa do WS-Security. Testo com um mock gerado do WSDL.

16Que riscos de segurança são específicos de SOAP/XML?

XXE (entidades externas no parser), expansão de entidades (billion laughs), documentos gigantes, e erros de validação de assinatura XML (por exemplo assinar uma parte do documento e processar outra). Mitigo com parser endurecido, limites de tamanho, validação de schema e bibliotecas de WS-Security mantidas.

17Montou uma tabela REST vs GraphQL vs gRPC. Qual você recomenda para uma API de parceiros?

REST com OpenAPI: é o denominador comum, cacheável, testável com curl, com ferramentas e gateways maduros e mais fácil de versionar e limitar. GraphQL público exige controle de custo e perde o cache; gRPC dificulta a adoção por terceiros.

18Como você evita que o time escolha o estilo de API por modismo?

Exijo um registro de decisão (ADR) com a dor medida, as alternativas, o custo operacional (ferramentas, observabilidade, segurança, treinamento) e a condição de revisão. Mantenho uma lista curta de estilos aprovados e aceito exceções por revisão de design com dono definido.
