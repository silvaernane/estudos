MÓDULO 05 · Intermediário

Navegador e front-end

O que acontece entre a chegada do HTML e os pixels na tela, por que o JavaScript roda numa única thread, onde guardar dados no cliente e como escolher modelo de renderização, framework e metas de desempenho e acessibilidade.

Ao final você saberá
  • Explicar o pipeline de renderização e o caminho crítico, e usar async/defer com critério.
  • Prever a ordem de execução de tarefas e microtarefas no event loop.
  • Escolher o armazenamento certo no navegador e saber o que nunca guardar ali.
  • Comparar MPA, SPA, SSR, SSG e ISR e defender uma escolha de framework para o contexto do time.
  • Ler Core Web Vitals, cobrar acessibilidade (WCAG e LBI) e entender o build moderno.
1Básico

O papel do navegador e de HTML, CSS e JS

O navegador é um programa que busca recursos pela rede, interpreta esses recursos e desenha o resultado na tela. Ele também isola sites uns dos outros, guarda dados locais e executa código de terceiros com permissões limitadas. Na prática ele é quase um sistema operacional: tem processos separados por site, gerenciador de memória, rede, armazenamento e um motor de JavaScript.

A busca do HTML em si usa o que você viu nos módulos anteriores: resolução de nome (módulo 2), conexão TCP ou QUIC (módulo 1), TLS (módulo 4) e uma requisição HTTP (módulo 3). Este módulo começa quando os bytes do HTML chegam.

As três linguagens e o que cada uma faz

CamadaResponsabilidadeErro típico
HTMLEstrutura e significado do conteúdo: títulos, listas, formulários, links, botões.Usar <div> para tudo e perder semântica e acessibilidade.
CSSApresentação: layout, cores, tipografia, responsividade, animações.CSS gigante e global que bloqueia a primeira pintura.
JavaScriptComportamento: reagir a eventos, buscar dados, alterar o DOM.Recriar em JS o que HTML já faz de graça (links, botões, formulários).

Os motores de renderização mais comuns são o Blink (Chrome, Edge, Opera), o WebKit (Safari, e todos os navegadores no iOS por regra da Apple em boa parte do mundo) e o Gecko (Firefox). Os motores de JavaScript correspondentes são V8, JavaScriptCore e SpiderMonkey. O Node.js usa o V8 fora do navegador, sem DOM.

Regra de bolso

Use o elemento HTML que já faz o que você precisa. Um <button> já recebe foco, responde a Enter e Espaço e é anunciado por leitores de tela. Um <div onclick> não faz nada disso sem trabalho extra.

Na entrevista

"O HTML dá estrutura e significado, o CSS dá apresentação e o JS dá comportamento. O navegador baixa esses recursos, monta o DOM e o CSSOM, calcula layout, pinta e compõe a tela."

Para gestores

O front-end roda em aparelhos que você não controla, com redes ruins, e é onde o usuário percebe lentidão e erro. Num portal de paciente, boa parte dos acessos vem de celulares intermediários em rede móvel. Peça ao time que teste nesse cenário, não só no notebook de desenvolvimento.

2Básico

Do HTML aos pixels

O navegador transforma texto em imagem por um pipeline de etapas. Entender essas etapas explica quase todo problema de desempenho visual.

  1. Parsing do HTML. O parser lê os bytes, decodifica os caracteres, gera tokens e monta o DOM (Document Object Model), uma árvore de nós. O parser é tolerante a erros: HTML malformado ainda vira uma árvore.
  2. CSSOM. Cada folha de estilo vira o CSSOM, a árvore de regras de estilo. O navegador precisa dele completo para saber como algo aparece, por isso CSS bloqueia a renderização.
  3. Render tree. DOM e CSSOM se combinam numa árvore só com o que será desenhado. Elementos com display: none ficam de fora; <head> também.
  4. Layout (ou reflow). O navegador calcula posição e tamanho de cada caixa a partir da largura da janela. Uma mudança no topo da árvore pode refazer o layout de tudo abaixo.
  5. Paint. Gera as instruções de desenho: texto, cores, bordas, sombras, imagens, separadas em camadas.
  6. Composite. Junta as camadas na ordem certa, em geral com ajuda da GPU, e manda o quadro para a tela.

Por que isso importa no dia a dia

Ler uma propriedade de geometria (como offsetHeight) logo depois de alterar o estilo obriga o navegador a calcular layout na hora. Repetir isso num laço causa layout thrashing (layout forçado repetidas vezes) e trava a página.

// ruim: alterna escrita e leitura, força layout a cada volta
for (const el of itens) {
  el.style.width = (el.offsetWidth + 10) + 'px';
}

// melhor: lê tudo, depois escreve tudo
const larguras = itens.map(el => el.offsetWidth);
itens.forEach((el, i) => { el.style.width = (larguras[i] + 10) + 'px'; });
Regra de bolso

Para animar, prefira transform e opacity. Animar top, left, width ou height refaz layout a cada quadro.

Na entrevista

"O navegador faz parsing do HTML para o DOM e do CSS para o CSSOM, combina os dois na render tree, calcula layout, pinta e compõe as camadas. Alterar geometria refaz layout; animar transform e opacity costuma ficar só no composite."

3Intermediário

Caminho crítico e recursos que bloqueiam

O caminho crítico de renderização (critical rendering path) é a sequência mínima de recursos e etapas até a primeira pintura útil. Quanto menos coisa estiver nesse caminho, mais cedo o usuário vê conteúdo.

Quem bloqueia o quê

RecursoBloqueiaObservação
CSS em <link rel="stylesheet">RenderizaçãoTambém atrasa scripts síncronos que vêm depois dele, porque o script pode consultar estilos.
<script> sem atributoParsing do HTMLO parser para, baixa, executa e só então continua.
<script async>Parsing só durante a execuçãoBaixa em paralelo e executa assim que chega. Sem ordem garantida entre scripts.
<script defer>Nada durante o parsingBaixa em paralelo e executa depois do parsing, antes do evento DOMContentLoaded, na ordem do documento.
<script type="module">Como deferMódulos são adiados por padrão; com async passam a executar quando prontos.
ImagensNão bloqueiamMas sem dimensões declaradas causam deslocamento de layout ao chegar.
Fontes webTexto, conforme font-displayPodem esconder o texto por um tempo; font-display: swap mostra a fonte do sistema antes.
<head>
  <!-- CSS crítico pequeno, o resto carregado depois -->
  <link rel="stylesheet" href="/css/base.css">
  <!-- avisa cedo sobre a imagem principal -->
  <link rel="preload" as="image" href="/img/banner.avif" fetchpriority="high">
  <!-- código da aplicação: não bloqueia o parser -->
  <script src="/js/app.js" defer></script>
  <!-- analytics independente: ordem não importa -->
  <script src="/js/analytics.js" async></script>
</head>
Regra de bolso

defer para o código da aplicação, que depende do DOM e da ordem. async para scripts independentes, como analytics. Script síncrono no <head> só com justificativa.

Armadilha comum

Scripts de terceiros (chat, analytics, testes A/B, tag managers) entram sem revisão e viram os maiores bloqueadores da página. Eles também executam com o mesmo poder do seu código. O risco de segurança disso está no módulo 9.

Na entrevista

"CSS bloqueia a renderização e script síncrono bloqueia o parser. async executa quando chega, sem ordem; defer executa na ordem depois do parsing. Para encurtar o caminho crítico eu reduzo e adio o que não é necessário na primeira tela."

Para gestores

Crie uma regra de entrada para scripts de terceiros: quem pede, qual o ganho, qual o custo em desempenho e privacidade, quem revisa. Num contexto de saúde, um pixel de marketing numa página de resultado de exame pode expor dado sensível. Dono e revisão periódica evitam o acúmulo.

4Intermediário

Event loop e a thread única do JavaScript

O JavaScript de uma página roda na main thread (thread principal), a mesma que trata cliques, calcula estilo e layout e pinta. A linguagem foi desenhada para isso: um modelo de execução sem concorrência no acesso ao DOM evita locks e condições de corrida em toda manipulação de interface. O preço é que código demorado trava tudo: rolagem, cliques, animações.

A concorrência vem do event loop. Operações lentas (timers, rede, eventos do usuário) são tratadas pelo navegador fora da thread do JS. Quando terminam, o callback entra numa fila e espera a pilha de chamadas esvaziar.

Prevendo a ordem

console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');
// saída: A, D, C, B

A e D rodam no código síncrono atual. C é microtarefa e roda assim que a pilha esvazia. B é uma nova tarefa e só roda numa volta seguinte do loop, mesmo com atraso zero.

Como não travar a interface

  • Quebrar trabalho longo em pedaços e devolver o controle ao navegador entre eles (por exemplo com setTimeout ou, onde houver suporte, scheduler.yield()). O navegador chama de long task qualquer tarefa acima de 50 ms.
  • Web Workers rodam JS em outra thread, sem acesso ao DOM, conversando com a página por mensagens (postMessage). Servem para cálculo pesado, parsing de arquivos grandes, compressão.
  • Evitar microtarefas infinitas: como a fila de microtarefas é esvaziada inteira antes de renderizar, um laço de promessas que sempre agenda outra trava a página do mesmo jeito.
// página
const w = new Worker('/js/processa-planilha.js');
w.postMessage(arquivo);
w.onmessage = (e) => mostrarResumo(e.data);
Armadilha comum

async/await não cria thread. Uma função async com um laço pesado continua travando a main thread. await só cede o controle quando espera algo que de fato é assíncrono.

Na entrevista

"JS no navegador roda numa thread só, junto com a renderização. O event loop executa uma tarefa, esvazia todas as microtarefas e então pode renderizar. Por isso uma promessa resolvida roda antes de um setTimeout de zero. Para trabalho pesado uso Web Workers ou quebro o trabalho em pedaços."

Armazenamento no navegador e same-origin policy

O que não guardar no navegador

  • Tokens de acesso em localStorage: qualquer script que rode na página, incluindo um injetado por XSS ou uma biblioteca comprometida, lê esse valor. Cookies HttpOnly, Secure e com SameSite adequado reduzem essa exposição. O desenho completo de sessões e tokens está no módulo 7.
  • Dados pessoais sensíveis (diagnósticos, resultados de exames, CPF) em armazenamento persistente: o computador pode ser compartilhado, como numa recepção de clínica, e o dado fica lá depois do logout.
  • Segredos da aplicação (chaves de API privadas): tudo que vai para o navegador é público, inclusive variáveis "de ambiente" embutidas no bundle.
  • Regras de autorização: esconder um botão no front não impede a chamada à API. A verificação real é sempre no servidor.

Same-origin policy

A same-origin policy (política de mesma origem) é a regra que impede um site de ler dados de outro dentro do navegador. Uma origem é a combinação de esquema, host e porta.

Comparado com https://app.clinica.com.brMesma origem?Motivo
https://app.clinica.com.br/examesSimSó o caminho muda
http://app.clinica.com.brNãoEsquema diferente
https://api.clinica.com.brNãoHost diferente (subdomínio conta)
https://app.clinica.com.br:8443NãoPorta diferente

A política restringe principalmente a leitura: o script de uma origem não lê a resposta de um fetch para outra origem, não acessa o DOM de um iframe de outra origem e não lê o localStorage dela. Carregar imagens, scripts e folhas de estilo de outras origens continua permitido, e formulários podem enviar dados para outra origem. Essa última brecha é a base do CSRF. Como liberar leituras entre origens de forma controlada (CORS) e como se defender de CSRF e XSS fica no módulo 9.

Armadilha comum

Achar que CORS protege o servidor. CORS é o servidor dizendo ao navegador quem pode ler a resposta. Um curl ou um script fora do navegador ignora tudo isso.

Na entrevista

"Origem é esquema, host e porta. A same-origin policy impede que um site leia dados de outro no navegador. Para sessão eu prefiro cookie HttpOnly e Secure; localStorage fica exposto a qualquer script da página."

Para gestores

Inclua no checklist de revisão: nada de token ou dado de saúde em localStorage, logout limpa armazenamento local, nenhum segredo no bundle. Isso conversa com a LGPD, que trata dado de saúde como dado pessoal sensível (veja o módulo 10).

6Intermediário

Modelos de renderização: MPA, SPA, SSR, SSG e híbridos

A pergunta central é: onde e quando o HTML final é gerado? No servidor a cada requisição, no servidor no momento do build, ou no navegador pelo JavaScript.

ModeloOnde o HTML nascePontos fortesCustos
MPA (multi-page application)Servidor, a cada páginaSimples, rápido no primeiro acesso, bom para SEO, pouco JSRecarrega a página inteira na navegação; interatividade rica exige JS extra
SPA (single-page application)Navegador, a partir de um HTML quase vazioNavegação fluida, sensação de aplicativo, front e back bem separadosBundle grande, tela branca até o JS rodar, SEO e acessibilidade exigem cuidado, roteamento e foco feitos à mão
SSR (server-side rendering)Servidor, a cada requisição, com o mesmo framework do clienteConteúdo visível cedo, bom para SEO, dados sempre atuaisServidor Node (ou similar) para manter, custo por requisição, hidratação
SSG (static site generation)Servidor, no buildMuito rápido, barato, servido direto da CDNConteúdo muda só no próximo build; ruim para dados por usuário
ISR e híbridosBuild, com regeneração periódica ou sob demandaEquilíbrio entre estático e atual; escolha por rotaMais complexidade de cache e invalidação; depende do framework e da hospedagem

Hidratação

No SSR e no SSG o usuário recebe HTML pronto, mas os botões ainda não respondem. Hidratação (hydration) é o passo em que o JS do framework roda no navegador, reconstrói a árvore de componentes e liga os eventos ao HTML existente. Até terminar, a página parece pronta e não reage, o que prejudica a métrica INP (seção 9). Abordagens recentes tentam reduzir isso: hidratação parcial ou em "ilhas" (só os componentes interativos recebem JS, como no Astro), streaming de HTML e componentes que rodam só no servidor (React Server Components).

Regra de bolso

Site de conteúdo público (institucional, blog, páginas de serviço): SSG ou MPA. Sistema interno autenticado com muita interação (prontuário, agenda): SPA atende bem e simplifica a infraestrutura. Conteúdo público com dados que mudam e SEO importante: SSR ou híbrido.

Na entrevista

"A diferença é onde o HTML é gerado. SPA gera no navegador e paga com bundle e tela inicial vazia; SSR gera no servidor a cada requisição e paga com infraestrutura e hidratação; SSG gera no build e é o mais rápido, mas fica desatualizado até o próximo build. Escolho por rota, conforme SEO, frequência de mudança e interatividade."

Para gestores

SSR significa um servidor a mais para operar, monitorar e escalar, com sua própria superfície de ataque. Antes de aprovar uma migração "para SSR", pergunte qual métrica vai melhorar, quanto e para qual público. Para um sistema interno usado em desktop por equipe treinada, o ganho costuma ser pequeno.

7Intermediário

Frameworks: como decidir

React, Angular e Vue resolvem o mesmo problema: manter a interface em sincronia com o estado da aplicação por meio de componentes. As diferenças relevantes para decisão estão em escopo, convenções e ecossistema, mais do que em desempenho bruto.

CritérioReactAngularVue
EscopoBiblioteca de interface; roteamento, formulários e dados vêm de outras bibliotecasFramework completo: roteador, formulários, HTTP, injeção de dependência, testesNúcleo progressivo, com roteador e gerenciador de estado oficiais
LinguagemJS ou TypeScript, com JSXTypeScript como padrãoJS ou TypeScript, templates em arquivos .vue
ConvençõesPoucas; cada projeto monta sua pilhaFortes; projetos se parecem entre siIntermediárias
Meta-framework comum para SSRNext.js, React Router (antigo Remix)SSR integrado ao próprio AngularNuxt
MantenedorMeta e comunidadeGoogleComunidade, liderada pelo criador
Quando brilhaMercado de contratação amplo, ecossistema enormeTimes grandes, sistemas corporativos longos, padronizaçãoCurva de entrada suave, adoção gradual em páginas existentes

Perguntas que decidem de verdade

  • O que o time já domina e o que o mercado local oferece para contratar?
  • Quanto de convenção você quer imposta pela ferramenta e quanto quer decidir e documentar?
  • Qual o horizonte de vida do sistema? Sistemas de saúde costumam viver uma década ou mais; peso de atualização entre versões importa.
  • Precisa de SSR? Então avalie o meta-framework junto, não só a biblioteca.
  • Precisa mesmo de framework? Formulários e páginas de conteúdo funcionam bem com HTML renderizado no servidor e um pouco de JS.
Armadilha comum

Trocar de framework para resolver problema de processo. Reescrever um front funcionando custa meses e devolve, no melhor caso, o mesmo produto. Migração incremental (rota por rota, ou micro-frontends quando há times independentes) reduz risco, mas também tem custo.

Na entrevista

"Os três resolvem componentes e reatividade. Angular traz tudo e impõe convenções, bom para times grandes; React é uma biblioteca com ecossistema enorme e mais decisões a tomar; Vue tem entrada suave. Eu decido pelo time, pelo tempo de vida do sistema e pela necessidade de SSR."

Para gestores

Registre a escolha numa ADR (Architecture Decision Record, registro de decisão de arquitetura) com contexto, alternativas e consequências. Defina também política de atualização de dependências: um front parado três versões atrás vira dívida que bloqueia correções de segurança.

8Intermediário

Acessibilidade

Acessibilidade (a11y) é garantir que pessoas com deficiência visual, auditiva, motora ou cognitiva consigam usar o sistema, com ou sem tecnologia assistiva: leitores de tela, navegação só por teclado, ampliação, comando de voz. Num sistema de saúde, o público inclui idosos e pessoas em tratamento, que dependem disso com frequência.

WCAG

As WCAG (Web Content Accessibility Guidelines) do W3C são a referência internacional. A versão 2.2 é a recomendação mais recente. Os critérios se organizam em quatro princípios (perceptível, operável, compreensível e robusto) e três níveis de conformidade: A, AA e AAA. O nível AA é a meta usual de empresas e governos.

PráticaO que fazer
SemânticaUsar <button>, <a>, <nav>, <main>, <label>, títulos em ordem. ARIA só quando não existir elemento nativo.
TecladoTudo que se faz com mouse precisa ser possível com Tab, Enter, Espaço e setas. Foco sempre visível. Nada de armadilha de foco em modais.
ContrasteNo nível AA, 4,5:1 para texto normal e 3:1 para texto grande.
Texto alternativoalt descritivo em imagens informativas; alt="" em imagens decorativas.
FormuláriosRótulo associado a cada campo; mensagens de erro em texto, perto do campo e anunciadas.
CorNão usar só cor para transmitir informação (por exemplo, resultado alterado só em vermelho).
SPAAo trocar de rota, mover o foco e atualizar o título da página; leitores de tela não percebem a troca sozinhos.
<!-- ruim -->
<div class="btn" onclick="agendar()">Agendar</div>

<!-- bom -->
<label for="data">Data da consulta</label>
<input id="data" type="date" required>
<button type="submit">Agendar</button>

Obrigação legal no Brasil

A Lei Brasileira de Inclusão da Pessoa com Deficiência (Lei 13.146/2015, também chamada Estatuto da Pessoa com Deficiência) torna obrigatória a acessibilidade em sites mantidos por empresas com sede ou representação comercial no país e por órgãos de governo. Para o setor público existe ainda o eMAG (Modelo de Acessibilidade em Governo Eletrônico). Na prática, empresas usam as WCAG nível AA como forma de demonstrar conformidade. Para detalhes jurídicos, consulte o jurídico da empresa.

Armadilha comum

Confiar só em ferramenta automática. Lighthouse e axe encontram uma parte dos problemas (contraste, alt ausente, rótulos). Navegar o fluxo principal só com teclado e com um leitor de tela (NVDA no Windows, VoiceOver no macOS e iOS) encontra o resto.

Na entrevista

"Sigo WCAG nível AA: HTML semântico, tudo acessível por teclado com foco visível, contraste mínimo de 4,5:1, rótulos nos campos e texto alternativo. No Brasil a Lei Brasileira de Inclusão exige acessibilidade em sites, então trato como requisito desde o início."

Para gestores

Coloque acessibilidade na definição de pronto: componente novo só entra com teste de teclado e verificação automática no CI. Corrigir depois custa muito mais do que fazer certo no design system. Acompanhe o número de problemas por tela crítica e trate acessibilidade como risco legal e reputacional, além de qualidade.

9Avançado

Desempenho e Core Web Vitals

Os Core Web Vitals são três métricas do Google para experiência real de carregamento, resposta e estabilidade visual. São medidas em usuários reais e avaliadas no percentil 75: a página passa se 75% das visitas ficam dentro do limite "bom".

MétricaMedeBomCausas comuns de nota ruim
LCP (Largest Contentful Paint)Quando o maior elemento visível (imagem ou bloco de texto) aparece≤ 2,5 sServidor lento, CSS e JS bloqueantes, imagem principal pesada ou descoberta tarde, SPA que renderiza tudo no cliente
INP (Interaction to Next Paint)Tempo entre uma interação (clique, toque, tecla) e o próximo quadro pintado, considerando as interações da visita≤ 200 msTarefas longas na main thread, hidratação pesada, handlers que fazem trabalho demais
CLS (Cumulative Layout Shift)Quanto o conteúdo pula de lugar sem o usuário pedir≤ 0,1Imagens e anúncios sem dimensão reservada, fontes trocando, banners inseridos no topo

O INP substituiu o FID (First Input Delay) como Core Web Vital em 2024. Outras métricas úteis para diagnóstico: TTFB (Time to First Byte, tempo até o primeiro byte da resposta) e FCP (First Contentful Paint, primeira pintura com conteúdo).

Dados de campo e de laboratório

Dados de campo (RUM, real user monitoring) vêm de usuários reais, em aparelhos e redes reais; o relatório CrUX do Chrome é um exemplo público. Dados de laboratório vêm de uma execução controlada, como o Lighthouse. O laboratório ajuda a reproduzir e comparar; o campo diz o que o usuário vive. Na auditoria padrão de carregamento, o Lighthouse não mede INP porque não há usuário interagindo; ele usa o TBT (Total Blocking Time) como indicador aproximado.

O que acontece no build

O código que o time escreve (TypeScript, JSX, módulos, CSS moderno) passa por um processo de build antes de ir para o navegador.

O webpack dominou por anos e ainda está em muitos projetos legados. O Vite virou padrão em projetos novos: em desenvolvimento serve módulos ES nativos ao navegador, o que dá partida rápida, e em produção gera um bundle otimizado.

Armadilha comum

Publicar source maps abertos em produção expõe o código-fonte completo, incluindo comentários. A prática comum é gerar os mapas e enviá-los só para a ferramenta de monitoramento de erros, sem servir publicamente.

Compatibilidade

O time define quais navegadores suporta (por exemplo, com uma configuração browserslist) e o build usa isso para decidir quanto transpilar. Para saber se uma API existe em determinado navegador, consulte o MDN ou o caniuse.com. Polyfills implementam em JS uma API ausente; aumentam o bundle, então inclua só os necessários. Para recursos novos, prefira melhoria progressiva (progressive enhancement): a base funciona em todos, o recurso novo melhora onde existir.

PWA e service workers

Uma PWA (Progressive Web App) é um site que se comporta como aplicativo: pode ser instalado na tela inicial, abrir em janela própria e funcionar com rede ruim ou sem rede. As peças são um manifesto (JSON com nome, ícones, cores) e um service worker.

O service worker é um script que roda em segundo plano, separado da página, e intercepta as requisições de rede da origem dele. Com isso ele decide responder do cache, da rede ou de uma combinação, e pode receber notificações push. Ele só funciona em HTTPS (com exceção de localhost) porque um intermediário que injetasse um service worker controlaria o site de forma persistente.

if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js');
}
Armadilha comum

Um service worker com cache mal planejado continua servindo a versão antiga do site depois do deploy. Defina desde o início a estratégia de atualização e de versão do cache, e como forçar a atualização em caso de bug.

DevTools e Lighthouse

  • Elements: DOM e estilos computados ao vivo.
  • Console: erros e execução de JS.
  • Network: cada requisição, cabeçalhos, tempos, tamanho, cache; simula rede lenta.
  • Performance: grava a linha do tempo da main thread e mostra tarefas longas, layout e paint.
  • Application: cookies, localStorage, IndexedDB, service workers, cache.
  • Lighthouse: auditoria de laboratório de desempenho, acessibilidade, boas práticas e SEO. Pode rodar no CI.

12Avançado

Cenários práticos e troubleshooting

"O portal ficou lento depois do deploy"

  1. Confirme com dados. Compare LCP e INP de campo antes e depois, por tipo de aparelho. Reclamação isolada pode ser rede do usuário.
  2. Compare os builds. O bundle cresceu? Uma dependência nova entrou? Um analisador de bundle mostra o que pesa.
  3. Reproduza no DevTools. Network com rede lenta e CPU reduzida; Performance para achar tarefas longas.
  4. Olhe o servidor. TTFB subiu? Então o problema pode estar na API ou no SSR, não no front.
  5. Decida. Se o impacto é grande, reverta primeiro e investigue depois.

"Usuários veem a versão antiga mesmo depois do deploy"

Suspeitos, em ordem: HTML com cache longo na CDN ou no navegador (o HTML deve ter cache curto ou revalidação; os assets com hash podem ter cache longo), service worker servindo cache antigo, e CDN sem invalidação. A correção estrutural é HTML sempre revalidado e assets imutáveis com hash.

"A tela pula quando a página carrega"

CLS alto. Procure imagens sem width/height, banners de aviso inseridos no topo depois da carga, fontes que mudam de tamanho ao trocar. Reserve espaço com dimensões ou aspect-ratio.

"O botão de salvar demora a responder"

INP alto. Grave no painel Performance e procure tarefas longas no handler do clique: validação pesada, re-renderização de uma lista enorme, chamada síncrona. Mostre o retorno visual primeiro (botão desabilitado, indicador) e faça o resto depois ou em Worker.

"O time quer reescrever o front em outro framework"

Peça o problema concreto e a métrica: lentidão, dificuldade de contratar, versão sem suporte, produtividade. Muitos desses problemas se resolvem com atualização de versão, limpeza de dependências ou refatoração por partes. Se a migração for justificada, prefira incremental, por rota, com critério de saída e prazo.

"Auditoria apontou que o sistema não é acessível"

Priorize os fluxos críticos (login, agendamento, resultado de exame). Corrija primeiro o que bloqueia uso: teclado, rótulos, contraste. Leve as correções para os componentes do design system, para que a correção se propague. Inclua verificação automática no CI para não regredir.

Para gestores

Em todos esses cenários a pergunta de gestão é a mesma: temos medição para saber se piorou e um caminho rápido para voltar atrás? Painel de Core Web Vitals de campo, monitoramento de erros de front-end com source maps privados e rollback simples respondem às duas.

13Avançado

Perguntas de entrevista

01O que acontece entre o navegador receber o HTML e mostrar a página?

O parser monta o DOM a partir do HTML e o CSSOM a partir do CSS. Os dois formam a render tree, que passa por layout (geometria), paint (pixels em camadas) e composite (junção das camadas). Scripts síncronos pausam o parser e CSS bloqueia a renderização.

02Qual a diferença entre async e defer?

Os dois baixam o script sem parar o parser. async executa assim que o download termina, pausando o parser naquele momento e sem ordem garantida. defer executa depois do parsing, antes do DOMContentLoaded, na ordem em que aparecem.

03O que é reflow e como evitá-lo?

É o recálculo de layout. Acontece ao mudar geometria ou conteúdo. Evito alternar leituras e escritas de geometria em laço, agrupo alterações e animo com transform e opacity.

04Explique o event loop. Em que ordem saem A, D, C, B no exemplo com setTimeout e Promise?

O código síncrono roda primeiro (A, D). Ao esvaziar a pilha, todas as microtarefas rodam (C, da Promise). Só então o loop pega a próxima tarefa (B, do setTimeout). A ordem é sempre: uma tarefa, todas as microtarefas, renderização se for a hora.

05Se o JavaScript é single-thread, como fazer cálculo pesado sem travar a tela?

Movendo o cálculo para um Web Worker, que roda em outra thread e troca mensagens com a página, ou quebrando o trabalho em pedaços que devolvem o controle ao navegador entre si. async/await sozinho não resolve.

06Onde guardar o token de sessão no navegador?

De preferência num cookie HttpOnly, Secure e com SameSite, que o JS não consegue ler. localStorage fica exposto a qualquer script da página, incluindo um injetado por XSS. A escolha final depende do desenho de autenticação.

07O que é a same-origin policy?

É a regra que impede uma origem (esquema, host e porta) de ler dados de outra no navegador: respostas de fetch, DOM de iframes, armazenamento. Carregar recursos e enviar formulários entre origens continua permitido. CORS é o mecanismo para o servidor liberar leituras específicas.

08SPA, SSR ou SSG: como você escolhe?

Pelo tipo de conteúdo. Público e pouco mutável: SSG. Público, dinâmico e com SEO: SSR ou híbrido. Sistema autenticado e muito interativo: SPA. Considero também custo de operar servidor de SSR e o efeito da hidratação na interatividade.

09O que é hidratação e qual o problema dela?

É o JS do framework rodando no cliente para ligar eventos ao HTML que veio do servidor. Enquanto não termina, a página parece pronta e não responde, o que prejudica o INP. Ilhas, hidratação parcial e componentes só de servidor reduzem esse custo.

10Quais são os Core Web Vitals e os limites bons?

LCP ≤ 2,5 s (carregamento do maior elemento), INP ≤ 200 ms (resposta a interações) e CLS ≤ 0,1 (estabilidade visual), avaliados no percentil 75 de usuários reais.

11Como você melhoraria um LCP ruim?

Identifico o elemento de LCP e o que o atrasa. Reduzo TTFB (servidor, CDN), removo CSS e JS bloqueantes, faço a imagem principal ser descoberta cedo com fetchpriority="high" ou preload, uso formato e tamanho adequados e não aplico lazy loading nela.

12O que é code splitting?

Dividir o bundle em partes carregadas sob demanda, por rota ou funcionalidade, com import() dinâmico. A primeira tela baixa e executa menos JS.

13Para que servem source maps e qual o cuidado em produção?

Ligam o código minificado ao original, para depuração e para stack traces legíveis. Em produção eu os envio para a ferramenta de monitoramento de erros sem servi-los publicamente, para não expor o código-fonte.

14O que é um service worker e por que exige HTTPS?

É um script em segundo plano que intercepta requisições da origem e permite cache offline e push. Exige HTTPS porque controla a origem de forma persistente; um atacante na rede que injetasse um service worker manteria o controle mesmo depois.

15Como garantir acessibilidade num time que nunca se preocupou com isso?

Adoto WCAG nível AA como meta, começo pelos fluxos críticos, corrijo no design system, coloco verificação automática no CI e teste manual de teclado na definição de pronto. Explico que no Brasil a Lei Brasileira de Inclusão torna isso obrigação, além de qualidade.

16Como gestor, como você evitaria que o desempenho do front piore com o tempo?

Com orçamento de desempenho verificado no CI (tamanho de bundle e métricas de laboratório), painel de Core Web Vitals de campo revisado após cada release, regra de entrada para scripts de terceiros e responsável definido para cada métrica.

17O time quer trocar Angular por React. O que você pergunta antes de aprovar?

Qual problema concreto a troca resolve e como vamos medir. Quanto custa, quanto tempo o produto fica sem evolução, se uma atualização ou refatoração resolveria, como fica a contratação e qual o plano incremental com critério de saída. Registro a decisão numa ADR.
