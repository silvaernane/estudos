MÓDULO 08 · Avançado

Registry, CI/CD e supply chain

A imagem só vale o que o caminho entre o commit e o servidor garante. Este módulo cobre onde as imagens vivem (registries), como se nomeia e promove cada versão, um pipeline completo no GitHub Actions e a cadeia de suprimentos: SBOM, proveniência, assinatura, verificação no deploy e tratamento de vulnerabilidades.

Ao final você saberá
  • Escolher um registry (Docker Hub, GHCR, ECR, ACR, Artifact Registry, Harbor), autenticar com segurança e reduzir dependência do Docker Hub com mirror e pull-through cache.
  • Definir estratégia de tags, usar digest no deploy e promover a mesma imagem entre ambientes (build once, deploy many).
  • Montar um pipeline no GitHub Actions com buildx, cache gha, multi-arch, varredura antes do push, SBOM, proveniência e assinatura.
  • Assinar com cosign (Sigstore) e verificar a assinatura e a identidade na hora do deploy.
  • Tratar CVEs com critério (severidade, exploitabilidade, correção disponível), manter imagens base atualizadas, e definir retenção, limpeza e custos do registry.
1Intermediário

Registries: onde as imagens vivem

Um registry é um servidor HTTP que guarda e serve imagens segundo a especificação de distribuição da OCI. O docker push e o docker pull falam com ele. Entender o que ele guarda explica tags, digests, assinaturas e limpeza adiante.

ghcr.io/equipe/agenda/api:1.4.2
└─ host ─┘└─── repositório ──┘└tag┘

ghcr.io/equipe/agenda/api@sha256:9f2c4e…        ← pelo digest (imutável)
123456789012.dkr.ecr.sa-east-1.amazonaws.com/agenda-api:sha-3f9c2e1   ← ECR
southamerica-east1-docker.pkg.dev/meu-projeto/agenda/api:1.4.2                   ← Artifact Registry
  • Um repositório agrupa as versões de uma imagem. Uma tag é um ponteiro móvel para um manifesto. O digest (sha256:…) é o hash do conteúdo do manifesto: identifica exatamente uma imagem, para sempre.
  • O registry guarda blobs (camadas e config) endereçados por digest, e manifestos que listam esses blobs. Camadas iguais são guardadas uma vez, mesmo entre repositórios.
  • Uma imagem multi-arch é um índice (image index) que aponta para um manifesto por plataforma. A mesma tag serve amd64 e arm64.
  • Assinaturas, SBOM e atestados também ficam no registry, como manifestos ou artefatos associados (seções 5 e 6).

Regra de bolso

Escolha o registry mais perto de onde a imagem roda e do sistema de identidade que você já usa: ECR para AWS, ACR para Azure, Artifact Registry para GCP, GHCR para código no GitHub. Harbor quando há exigência de controle total, ambiente isolado ou vários provedores. Evite o Docker Hub como única fonte de produção.

Docker Hub e os limites de pull

O Docker Hub limita os pulls para proteger o serviço. Valores publicados na documentação oficial (confirmados na redação deste módulo, mas sujeitos a revisão do Docker, então verifique a página de uso antes de dimensionar):

Quem puxaLimite por janela de 6 horas
Sem autenticação100 pulls por endereço IPv4 ou sub-rede IPv6 /64
Conta Personal autenticada200 pulls
Pro, Team, Businesssem limite de pulls, sujeito a uso justo (fair use)
  • O que conta é o pull (a verificação de versão sozinha não conta). Uma imagem multi-arch conta um pull por arquitetura baixada. Ao estourar, vem HTTP 429 e a mensagem toomanyrequests: You have reached your unauthenticated pull rate limit.
  • Sem autenticação, o contador é por IP. Runners de CI e saídas NAT compartilhadas somam o tráfego de muita gente e estouram rápido, como se fosse um incidente "aleatório".
  • Soluções, em ordem de custo: autenticar o CI; usar uma conta paga para o time; colocar um pull-through cache (seção 2); ou copiar as imagens base para o seu registry e referenciá-las de lá.
Armadilha comum

Tratar um build que falhou com 429 como "instabilidade do Docker Hub" e dar retry. É um problema estrutural: cada reexecução consome mais cota. Autentique ou use cache.

Na entrevista

"Uma tag é um ponteiro móvel e o digest identifica o conteúdo. O registry guarda blobs por digest e manifestos que os listam. No Docker Hub há limite de pulls (100 por 6 h sem autenticação, 200 autenticado no plano gratuito), então CI precisa autenticar ou usar cache/mirror."

Para gestores

O registry é infraestrutura crítica: se ele cai, nenhum deploy novo acontece e nenhum nó recupera uma imagem. Pergunte: onde fica, quem tem permissão de push em produção, há réplica ou cache, o time depende de imagens públicas sem cópia interna? Dependência única do Docker Hub é risco de disponibilidade e de cadeia de suprimentos.

2Intermediário

Login, credenciais e mirrors

Autenticação no dia a dia

echo "$TOKEN" | docker login ghcr.io -u meu-usuario --password-stdin   # nunca -p na linha de comando
docker logout ghcr.io

# ECR: o token dura cerca de 12 horas
aws ecr get-login-password --region sa-east-1 \
  | docker login --username AWS --password-stdin 123456789012.dkr.ecr.sa-east-1.amazonaws.com

az acr login --name meuacr                              # Azure
gcloud auth configure-docker southamerica-east1-docker.pkg.dev    # Google Artifact Registry

--password-stdin evita que a senha apareça no histórico do shell e na lista de processos (ps).

Onde as credenciais ficam: credential helpers

O docker login grava em ~/.docker/config.json. Sem um credential helper, a credencial fica ali apenas codificada em base64, que não é criptografia: qualquer um que leia o arquivo a obtém. Com um helper, o segredo vai para o cofre do sistema (Keychain, Credential Manager, pass) ou é gerado sob demanda.

{
  "credsStore": "desktop",
  "credHelpers": {
    "123456789012.dkr.ecr.sa-east-1.amazonaws.com": "ecr-login",
    "southamerica-east1-docker.pkg.dev": "gcloud"
  }
}
  • credsStore: helper padrão para todos os registries (desktop, osxkeychain, wincred, pass, secretservice).
  • credHelpers: helper por registry. O docker-credential-ecr-login (Amazon ECR Credential Helper) obtém tokens do ECR a partir das credenciais AWS, sem docker login periódico.

Credenciais em CI: curtas e mínimas

DestinoRecomendadoEvite
GHCR no GitHub ActionsGITHUB_TOKEN com permissions: packages: writePAT pessoal de alguém que sai da empresa
ECROIDC do GitHub assumindo um papel IAM de menor privilégio (sem chave de acesso guardada)chaves IAM de longa duração em secret

Separe quem publica de quem consome: o servidor de produção precisa de pull, nunca de push. Em ambientes de produção, o nó puxa com uma credencial somente leitura.

Mirrors e pull-through cache

Um pull-through cache é um registry que, ao receber um pull de uma imagem que não tem, busca no upstream (Docker Hub, GHCR...), guarda a cópia e passa a servir dela. Ganhos: reduz a contagem de pulls no Hub, acelera builds, e mantém imagens base disponíveis se o upstream cair.

OpçãoComo funciona
registry-mirrors no Docker daemon/etc/docker/daemon.json com "registry-mirrors": ["https://mirror.interno"]. Só vale para o Docker Hub e cai no upstream se o mirror falhar.
ECR pull-through cacheregra que mapeia um prefixo do ECR a um upstream (Docker Hub, GHCR, Quay, ECR público...). As imagens são puxadas como <conta>.dkr.ecr...amazonaws.com/<prefixo>/library/nginx; o ECR as atualiza periodicamente. Para o Docker Hub é preciso configurar credenciais no upstream.
Harbor (projeto proxy cache)um projeto Harbor aponta para um registry de origem; as imagens são servidas pelo Harbor, com scan e política próprias.
Artifact Registry (repositório remoto)repositório que faz cache de um upstream.
registry:2 com proxy.remoteurlo registry de referência da OCI em modo proxy; simples, sem UI e sem permissões finas.
Artifactory, Nexusrepositórios universais com proxy de containers e de pacotes (npm, Maven).
Saiba mais

O cache também é controle de supply chain: você decide o que entra (listas permitidas), faz o scan antes de liberar e deixa de depender de um repositório público. Uma imagem copiada para o seu registry com a tag original pode ficar defasada: defina quem a atualiza (Renovate/Dependabot e rebuild periódico, seção 7).

Na entrevista

"Credencial em CI deve ser de curta duração e menor privilégio: OIDC para ECR/ACR/GAR, GITHUB_TOKEN para GHCR. No cliente uso credential helper em vez de base64 em config.json. Para os limites do Docker Hub, autentico e uso pull-through cache."

Para gestores

Audite quem tem permissão de push e quais chaves de longa duração existem em CI. Troque por federação OIDC: não há segredo para vazar nem para rotacionar. Pergunte também se o servidor de produção consegue baixar imagens se o Docker Hub estiver indisponível.

3Avançado

Tags, digest e promoção: build once, deploy many

Uma tag aponta hoje para uma imagem e amanhã pode apontar para outra. Para operar com segurança é preciso decidir o que cada tag promete e quando o deploy deve se amarrar ao digest.

docker build -t ghcr.io/equipe/api:1.4.2 -t ghcr.io/equipe/api:sha-3f9c2e1 .
docker push ghcr.io/equipe/api:1.4.2
docker push ghcr.io/equipe/api:sha-3f9c2e1
docker tag api:dev ghcr.io/equipe/api:1.4.2     # dá outro nome à MESMA imagem local

Estratégia de tags

TagPromessaMutável?Uso
sha-3f9c2e1 (commit)este commit, este buildnão (por convenção)rastreio e deploy em homologação/produção
1.4.2 (semver completo)release exatanão (regra de ouro)release; pode ser o que a equipe lê e o deploy referencia (idealmente com digest)
1.4, 1"o último patch/minor"sim, segue os lançamentosconsumo por terceiros que aceitam atualização automática
main, edgeo último build do branchsimambientes de teste contínuo
latest"o que alguém publicou por último"sim, sem regrasó em demonstração; evite em produção
prod, stg (ambiente)o que está em cada ambientesim, é o ponteiro de promoçãoopcional, como atalho legível; o deploy real usa digest
Armadilha comum

latest não significa "mais recente" nem "estável": é só o nome da tag quando nenhuma é informada. Dois servidores que fizeram pull em momentos diferentes têm "latest" diferentes, e um rollback para "a versão anterior" é impossível porque ela não tem nome. Em Compose, image: agenda/api sem tag é latest.

  • Imutabilidade. Nunca republique uma tag de versão. Se algo estiver errado em 1.4.2, publique 1.4.3. Ative tag imutável no registry onde existir (ECR e Harbor oferecem; confira no seu): ele recusa o push sobre uma tag já usada.
  • Rollback é subir a tag (ou o digest) anterior: por isso as imagens antigas precisam existir (retenção, seção 8).

Digest no deploy

Mesmo com tags "imutáveis por convenção", só o digest é uma garantia técnica: o conteúdo foi hasheado. Quando o deploy referencia @sha256:…, o que se testou e o que roda são bit a bit a mesma coisa, e uma tag adulterada no registry não muda nada.

docker buildx imagetools inspect ghcr.io/equipe/api:1.4.2
docker inspect --format '{{index .RepoDigests 0}}' ghcr.io/equipe/api:1.4.2   # imagem já puxada
crane digest ghcr.io/equipe/api:1.4.2                                          # sem baixar a imagem
Name:      ghcr.io/equipe/api:1.4.2
MediaType: application/vnd.oci.image.index.v1+json
Digest:    sha256:9f2c4e1ab7d3c85e0f6a1b2c3d4e5f60718293a4b5c6d7e8f9012a3b4c5d6e7f

Manifests:
  Name:      ghcr.io/equipe/api:1.4.2@sha256:1a2b3c…
  Platform:  linux/amd64
  Name:      ghcr.io/equipe/api:1.4.2@sha256:4d5e6f…
  Platform:  linux/arm64
services:
  api:
    # tag para humanos + digest para a máquina: se o digest não bater, o pull falha
    image: ghcr.io/equipe/api:1.4.2@sha256:9f2c4e1ab7d3c85e0f6a1b2c3d4e5f60718293a4b5c6d7e8f9012a3b4c5d6e7f

Para imagem multi-arch, referencie o digest do índice (o que o imagetools inspect mostra no topo): cada arquitetura resolve o seu manifesto. Digests ficam ilegíveis, então o pipeline os gera e o Renovate (seção 7) os atualiza.

Promoção: construa uma vez, implante muitas

# promoção dentro do mesmo registry: cria a tag "prod" apontando para o digest já testado
docker buildx imagetools create \
  --tag ghcr.io/equipe/api:1.4.2 \
  ghcr.io/equipe/api@sha256:9f2c4e1ab7d3c85e0f6a1b2c3d4e5f60718293a4b5c6d7e8f9012a3b4c5d6e7f

crane tag ghcr.io/equipe/api@sha256:9f2c4e1ab7d3… 1.4.2           # alternativa com crane
skopeo copy --all docker://hml.registry/api@sha256:9f2c4e1ab7d3… \
                  docker://prod.registry/api:1.4.2                # entre registries (todas as plataformas)
  • As cópias entre registries preservam o digest quando o manifesto não é convertido: confirme comparando com imagetools inspect dos dois lados.
  • A diferença entre ambientes fica na configuração (variáveis, secrets, arquivos de config) e nunca na imagem. É o mesmo princípio de "12 factors": configuração separada do artefato.
  • Aprovação em produção pode virar um gate no pipeline (aprovação manual do ambiente), com o digest registrado no ticket de mudança: o que auditoria pergunta é "qual versão exatamente estava rodando em tal data".
Regra de bolso

CI publica sha-<commit> em todo build. Release cria X.Y.Z apontando para o mesmo digest. O deploy usa tag@digest. Ninguém sobrescreve tag. latest não existe em produção.

Na entrevista

"Build once, deploy many: o artefato é construído uma vez, testado, e a promoção só move uma referência para o mesmo digest. Reconstruir por ambiente quebra a garantia de que o testado é o implantado. No deploy uso o digest, porque tag é mutável."

Para gestores

Registre em cada deploy o digest implantado (changelog, ticket). Em um incidente, a primeira pergunta é "o que mudou?"; com tags móveis ninguém consegue responder com certeza. Em saúde, isso também é rastreabilidade para auditoria e validação de sistemas.

4Avançado

Pipeline completo no GitHub Actions

Um bom pipeline de imagem faz sempre a mesma sequência: constrói com cache, varre antes de publicar, publica para as plataformas necessárias, anexa SBOM e proveniência e assina o resultado. O fluxo abaixo faz isso, e o resto da seção explica cada decisão.

name: imagem

on:
  push:
    branches: [main]
    tags: ["v*.*.*"]
  pull_request:

permissions:
  contents: read                # padrão mínimo; cada job pede o que precisa

concurrency:
  group: imagem-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write           # push no GHCR
      id-token: write           # token OIDC para assinatura sem chave (cosign)
    steps:
      - uses: actions/checkout@v6

      - name: Nome da imagem em minúsculas (GHCR exige)
        run: echo "IMAGE=ghcr.io/${GITHUB_REPOSITORY,,}/api" >> "$GITHUB_ENV"

      - uses: docker/setup-qemu-action@v4          # emulação para arm64
      - uses: docker/setup-buildx-action@v4

      - uses: docker/login-action@v4
        if: github.event_name != 'pull_request'
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta
        uses: docker/metadata-action@v6
        with:
          images: ${{ env.IMAGE }}
          flavor: latest=false                      # nunca gera "latest"
          tags: |
            type=sha,prefix=sha-
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}

      - name: Build (amd64) para varredura
        uses: docker/build-push-action@v7
        with:
          context: ./api
          target: prod
          load: true                                # fica no daemon local, sem push
          tags: scan-local:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Varredura de vulnerabilidades (Trivy)
        uses: aquasecurity/trivy-action@v0.36.0
        with:
          image-ref: scan-local:${{ github.sha }}
          severity: CRITICAL,HIGH
          ignore-unfixed: true                      # só falha se há correção disponível
          exit-code: "1"

      - name: Build e push (multi-arch, com SBOM e proveniência)
        id: push
        uses: docker/build-push-action@v7
        with:
          context: ./api
          target: prod
          platforms: linux/amd64,linux/arm64
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          sbom: true
          provenance: mode=max

      - uses: sigstore/cosign-installer@v4
        if: github.event_name != 'pull_request'

      - name: Assinar pelo digest
        if: github.event_name != 'pull_request'
        env:
          DIGEST: ${{ steps.push.outputs.digest }}
        run: cosign sign --yes "${IMAGE}@${DIGEST}"

Notas de versão: os números de versão das actions mudam. Os usados aqui eram os mais recentes na redação deste módulo (docker/build-push-action v7, docker/setup-buildx-action v4, docker/login-action v4, docker/metadata-action v6, docker/setup-qemu-action v4, sigstore/cosign-installer v4, aquasecurity/trivy-action v0.36.0). Confira a página de releases de cada uma e deixe o Dependabot ou o Renovate mantê-las (seção 7). Para segurança máxima, fixe por SHA do commit (uses: org/acao@<sha> com a versão em comentário), porque tags de actions também são móveis.

O que cada decisão resolve

TrechoPor quê
permissions mínimaso GITHUB_TOKEN nasce com o mínimo e cada job eleva só o necessário. id-token: write permite o OIDC da assinatura sem chave.
concurrencycancela execuções antigas do mesmo ref: poupa minutos e evita publicar um build mais velho depois de um mais novo.
metadata-actiongera tags e labels OCI (inclui org.opencontainers.image.source, que liga o pacote ao repositório no GHCR). Com flavor: latest=false, nunca produz latest.
load: true + scancom load, o resultado vai para o daemon local e o Trivy o escaneia sem que nada tenha sido publicado. load só funciona para uma plataforma; por isso o build de scan é amd64.
ignore-unfixedfalha apenas quando há versão corrigida. Falhar por CVE sem correção deixa o pipeline vermelho sem ação possível (seção 7).
cache-to type=gha,mode=maxmode=max guarda as camadas de todos os estágios, não só do estágio final. Em multi-stage, é o que faz o cache de deps e build funcionar.
push: ${{ ... != 'pull_request' }}PRs (inclusive de forks, sem acesso a secrets) constroem e escaneiam, mas não publicam.
sbom e provenanceanexam atestados à imagem (seção 5). mode=max traz mais detalhe, inclusive argumentos de build: não use com segredo em ARG (nem deveria existir).
assinar pelo digestassinar uma tag é assinar um ponteiro móvel. O digest vem de steps.push.outputs.digest.

Multi-arch: custos e alternativas

Com platforms: linux/amd64,linux/arm64, o BuildKit gera um manifesto por plataforma e um índice. No runner amd64, o arm64 roda por emulação QEMU, que pode ser de 5 a 10 vezes mais lenta em passos pesados de CPU (npm ci com módulos nativos, compilação). Três saídas:

  • Cross-compilation no Dockerfile: o estágio de build roda na arquitetura do runner e só o resultado muda de alvo (linguagens que suportam, como Go, Rust e .NET).
  • Runners nativos arm64 (disponíveis no GitHub e em outros provedores; confira o plano), com um build por arquitetura e imagetools create para juntá-las num índice.
  • Publicar só a arquitetura em que o ambiente roda, se ninguém executa arm64.
# syntax=docker/dockerfile:1
FROM --platform=$BUILDPLATFORM golang:1.23 AS build
ARG TARGETOS TARGETARCH
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /out/api ./cmd/api

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/api /api
ENTRYPOINT ["/api"]
Armadilha comum

pull_request_target e workflows que rodam código de PR com acesso a secrets. Um fork malicioso pode exfiltrar tokens. Use pull_request (sem secrets) para build e scan, e publique só em push para branches e tags protegidos.

Na entrevista

"Checkout, buildx, login, metadata para tags e labels, build com cache gha, scan antes do push, push multi-arch com SBOM e proveniência, e assinatura pelo digest com cosign sem chave. Permissões mínimas por job, nada publicado em PR, e latest desligado."

Para gestores

O pipeline é o único caminho para produção: ninguém publica da própria máquina. Proteja o branch main e as tags v*, exija revisão para mexer em .github/workflows (CODEOWNERS) e acompanhe o tempo do pipeline: cache e multi-arch bem feitos fazem a diferença entre 3 e 25 minutos.

5Avançado

SBOM e proveniência: provar o que há dentro e como foi feito

Duas perguntas aparecem em toda auditoria e em todo incidente de segurança: "o que tem dentro desta imagem?" e "quem a construiu, a partir de quê?". O SBOM responde à primeira; a proveniência, à segunda.

SBOM: lista de ingredientes

O Software Bill of Materials lista pacotes do sistema operacional e bibliotecas da aplicação com versões. Formatos: SPDX (Linux Foundation) e CycloneDX (OWASP). Quando sai uma CVE nova, o SBOM guardado permite responder "quais das minhas imagens usam essa biblioteca?" sem baixar e reescanear tudo.

# 1) pelo BuildKit, no build (anexa como atestado à imagem)
docker buildx build --sbom=true --provenance=mode=max \
  --platform linux/amd64,linux/arm64 -t ghcr.io/equipe/api:1.4.2 --push ./api

# ler o que ficou anexado
docker buildx imagetools inspect ghcr.io/equipe/api:1.4.2 --format '{{ json .SBOM }}'
docker buildx imagetools inspect ghcr.io/equipe/api:1.4.2 --format '{{ json .Provenance }}'

# 2) com o Syft, sobre uma imagem pronta
syft ghcr.io/equipe/api@sha256:9f2c… -o spdx-json=sbom.spdx.json -o cyclonedx-json=sbom.cdx.json

# 3) varrer o SBOM depois, sem a imagem
grype sbom:sbom.spdx.json --fail-on high

No caso 1, o BuildKit usa um scanner (baseado no Syft) como parte do build. No Docker Desktop e no Docker Scout também é possível consultar o SBOM de uma imagem (docker scout sbom).

Proveniência e SLSA

A proveniência é um atestado, no formato in-toto, descrevendo como o artefato foi produzido: repositório e commit de origem, workflow e plataforma de build, imagens base usadas (com digest), parâmetros e horário. SLSA (Supply-chain Levels for Software Artifacts, "salsa") é o modelo que gradua essa garantia. Em resumo, na trilha de build:

NívelGarantiaNa prática
L1a proveniência existepipeline emite o atestado, mesmo sem assinatura robusta
L2proveniência gerada e assinada por uma plataforma de build hospedadaGitHub Actions emitindo e assinando; difícil de forjar a partir do seu código
L3build isolado e endurecido; a proveniência não pode ser forjada pelo código do projetoworkflows reutilizáveis e runners isolados; exige disciplina de pipeline

O provenance: mode=max do buildx gera o atestado com bastante detalhe (mode=min traz o essencial). Existe ainda o caminho nativo do GitHub, com a action actions/attest-build-provenance e a verificação por gh attestation verify. Confira a documentação para a versão atual.

Onde os atestados ficam

  • As entradas unknown/unknown não são lixo: aparecem assim em algumas UIs de registry porque não são imagens executáveis.
  • Outra via, a do cosign: cosign attest --type spdxjson --predicate sbom.spdx.json IMAGE@DIGEST assina e guarda o SBOM como atestado, verificável com cosign verify-attestation.
  • Políticas de limpeza que apagam "manifestos sem tag" podem destruir atestados e assinaturas. Revise a política depois de ligar sbom e provenance (seção 8).
  • SBOM não é um relatório de vulnerabilidades: é o inventário. As vulnerabilidades mudam todo dia; o inventário não. Reavalie o SBOM contra bases novas.
Armadilha comum

Gerar SBOM e guardar em um bucket que ninguém consulta. O valor está em poder buscar: "quais imagens em produção contêm log4j-core 2.14?". Decida onde o SBOM vive, quem consulta e com que ferramenta (Dependency-Track, Grype, Scout) antes de gerar milhares deles.

Na entrevista

"SBOM é o inventário de componentes da imagem (SPDX ou CycloneDX); proveniência é o atestado de como e onde foi construída, no modelo SLSA. Gero ambos no build com buildx, e assino o digest do índice para que a assinatura cubra os atestados."

Para gestores

Regulação e contratos já exigem SBOM em vários setores. Para sistemas que tratam dados de saúde, a pergunta de auditoria "o que roda e a partir de que código" é rotina. Tenha uma resposta que não dependa de alguém lembrar: SBOM e proveniência guardados por versão, com retenção igual à da imagem.

6Avançado

Assinatura com cosign e verificação no deploy

Hash garante integridade, não autoria. Quem escreve no registry pode publicar uma imagem com o digest dele. A assinatura liga a imagem a uma identidade ("este workflow deste repositório"), e a verificação, feita no momento do deploy, recusa o que não vier dela.

Sigstore e o modo sem chave (keyless)

Assinar com chave privada exige guardá-la, protegê-la e rotacioná-la, e é aí que a maioria das iniciativas morre. O Sigstore propõe assinar sem chave de longa duração:

  • Cosign: a ferramenta de linha de comando que assina e verifica imagens (e atestados).
  • Fulcio: autoridade certificadora que troca um token de identidade OIDC (o do GitHub Actions, por exemplo) por um certificado de vida curta (minutos) que carrega a identidade do workflow.
  • Rekor: log de transparência público e imutável, onde fica registrado que a assinatura aconteceu enquanto o certificado era válido.

Assinar e verificar

# no pipeline (com id-token: write); assinar o DIGEST, nunca a tag
cosign sign --yes ghcr.io/equipe/agenda/api@sha256:9f2c4e1ab7d3…

# no deploy: exigir QUEM assinou e por qual emissor de identidade
cosign verify ghcr.io/equipe/agenda/api@sha256:9f2c4e1ab7d3… \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp '^https://github.com/equipe/agenda/\.github/workflows/imagem\.yml@refs/(heads/main|tags/v.*)$'

# atestados (SBOM, proveniência) assinados à parte
cosign attest --yes --type spdxjson --predicate sbom.spdx.json ghcr.io/equipe/agenda/api@sha256:9f2c…
cosign verify-attestation --type spdxjson \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp '^https://github.com/equipe/agenda/' \
  ghcr.io/equipe/agenda/api@sha256:9f2c…

  - Existence of the claims in the transparency log was verified offline

  • Verificar sem --certificate-identity e --certificate-oidc-issuer aceitaria a assinatura de qualquer pessoa com uma conta no GitHub. A identidade esperada é parte da política.
  • O cosign 3.x (instalado pela action cosign-installer v4) mudou formatos e padrões em relação ao 2.x. A sintaxe dos exemplos é a de uso corrente; confirme com cosign sign --help na sua versão.
  • Alternativa com chave: cosign generate-key-pair, ou chaves em KMS (--key awskms://…, gcpkms://…, azurekms://…), útil em ambientes isolados sem OIDC. O custo é gerir a chave.
  • Outras ferramentas: Notation (projeto Notary v2, usado no ecossistema Azure/AWS) e o antigo Docker Content Trust (Notary v1, DOCKER_CONTENT_TRUST=1), hoje pouco adotado.

AmbienteComo impor

IMAGE="ghcr.io/equipe/agenda/api"
DIGEST="$1"      # sha256:... vindo do pipeline/aprovação

  --certificate-oidc-issuer https://token.actions.githubusercontent.com \

Regra de bolso

Assinar sem verificar é teatro. O ciclo só fecha quando algo bloqueia a execução de imagem sem assinatura válida da identidade esperada.

Na entrevista

"Cosign com Sigstore assina sem chave: o pipeline troca o token OIDC por um certificado curto no Fulcio, a assinatura vai ao registry e o evento ao log Rekor. No deploy verifico a assinatura, o emissor e a identidade do workflow, e o admission controller ou o script de deploy bloqueia o que não passar."

Para gestores

Assinatura responde a ameaças reais: credencial de registry vazada, pipeline comprometido, imagem trocada. Mas só protege se a verificação for obrigatória. Comece em modo de auditoria (registra o que não estaria assinado), depois imponha, ambiente por ambiente.

7Avançado

Varredura de vulnerabilidades e tratamento de CVEs

Um scanner compara os pacotes da imagem (do SO e das bibliotecas da aplicação) com bases de vulnerabilidades conhecidas. Toda imagem tem CVEs listadas; o trabalho é separar as que importam, corrigir o que é corrigível e não parar o time por ruído.

Como priorizar: severidade não é risco

A severidade (CVSS: baixa, média, alta, crítica) mede o impacto potencial da falha em abstrato. O risco para o seu sistema depende de outros fatores:

  • VEX (Vulnerability Exploitability eXchange): documento que declara, por CVE e produto, se está not_affected, affected, fixed ou under_investigation, com justificativa. Scanners como Trivy e Grype aceitam VEX para suprimir achados já avaliados.
  • Exceções (.trivyignore, .grype.yaml) devem ter justificativa, dono e data de validade (o Trivy aceita validade na própria linha em versões recentes; confira). Exceção sem validade vira dívida invisível.
  • O resultado do scan muda sem que o código mude: uma imagem "limpa" ontem pode ter uma CVE crítica hoje. Escaneie também o que já está no registry e em produção, em agenda (varredura contínua).

Atualizando imagens base

A maior parte das CVEs de uma imagem vem da camada base (distribuição, OpenSSL, glibc/musl, runtime). Três práticas resolvem a maioria:

  • Imagem mínima: -slim, alpine ou distroless reduzem a quantidade de pacotes e, portanto, de achados (módulo 04).
  • Rebuild periódico mesmo sem mudança de código, com --pull (e sem cache para a camada base). Um workflow agendado reconstrói semanalmente e publica uma nova versão (patch) que atravessa o pipeline normal, com scan e assinatura.
  • Atualização automática da referência da base por bot (Renovate ou Dependabot), com a base fixada por digest: o bot abre um PR a cada nova versão, o CI valida e a revisão aprova.

Armadilha comum

Fixar a base por digest e nunca atualizar. A imagem fica reproduzível e cheia de CVEs antigas. O digest é para controle, não para esquecimento: sempre acompanhado de um bot que propõe a atualização.

Na entrevista

"Severidade CVSS não é risco. Priorizo por exploitabilidade (KEV, EPSS), existência de correção, se o código é alcançável e se o serviço está exposto. O gate falha em HIGH/CRITICAL com correção; o resto vira backlog com dono e prazo. Mantenho as bases atualizadas com Renovate e rebuild semanal."

Para gestores

Defina uma política escrita com prazos por classe de risco e um dono para exceções. "Zero vulnerabilidades" é uma meta que gera maquiagem; "nenhuma explorada ativamente em produção e correções críticas em X dias" é uma meta que se mede. Acompanhe tempo médio de correção, não contagem bruta de CVEs.

8Intermediário

Retenção, limpeza e custos do registry

Todo build cria imagem nova; sem limpeza, o registry cresce para sempre e a conta junto. Apagar demais, porém, quebra rollback e auditoria. A política equilibra os dois.

Um exemplo de ordem de grandeza: numa imagem de 400 MB implantada em 50 nós, cada deploy move cerca de 20 GB de dados (400 MB × 50). Os valores de preço por GB variam por provedor, região e plano e mudam com o tempo: use a calculadora do provedor e meça seu consumo real antes de decidir.

Regra de bolso

Reduza o tamanho da imagem antes de mexer no plano do registry: ele reduz armazenamento, tempo de deploy, egress e superfície de ataque ao mesmo tempo (módulos 03 e 04).

Na entrevista

"Retenção por categoria: releases e digests em produção protegidos; sha- por contagem; PR curto. Cuido para a limpeza não apagar atestados e assinaturas. O custo vem de armazenamento e, mais, de egress; o remédio é imagem menor e registry na mesma região."

Para gestores

Peça o custo do registry por serviço (tags de custo no provedor) e o tempo de deploy. Imagens de 1 GB por serviço são sinal de dívida técnica que custa dinheiro e velocidade. Defina a retenção junto com compliance: quanto tempo precisamos conseguir reproduzir o que rodou em produção?

Exercícios

Laboratórios graduados. Nos primeiros, use um registry local; os demais podem ser feitos num repositório de teste do GitHub.

E1Registry local: suba um registry, publique uma imagem, liste o catálogo e puxe a imagem pelo digest.
docker run -d --name registry -p 5000:5000 registry:2

docker pull alpine:3.20
docker tag alpine:3.20 localhost:5000/lab/alpine:1.0
docker push localhost:5000/lab/alpine:1.0

curl -s http://localhost:5000/v2/_catalog                    # {"repositories":["lab/alpine"]}
curl -s http://localhost:5000/v2/lab/alpine/tags/list        # {"name":"lab/alpine","tags":["1.0"]}

docker rmi localhost:5000/lab/alpine:1.0
docker buildx imagetools inspect localhost:5000/lab/alpine:1.0    # pega o Digest: sha256:...
docker pull localhost:5000/lab/alpine@sha256:<digest>            # pull pelo digest

O que observar. O registry guarda o repositório lab/alpine com a tag 1.0; o pull por digest funciona sem tag nenhuma, e é a referência estável. localhost é tratado como registry sem TLS pelo Docker; outros hosts HTTP exigem configuração de insecure registry.

E2Tags e promoção: construa uma imagem, publique com sha-<n>, promova para 1.0.0 e depois para prod sem rebuild, provando que o digest é o mesmo. Depois mostre o que acontece se alguém republicar 1.0.0 com outro conteúdo.
printf 'FROM alpine:3.20\nRUN echo v1 > /versao\n' > Dockerfile
docker build -t localhost:5000/lab/app:sha-aaa111 . && docker push localhost:5000/lab/app:sha-aaa111
D=$(docker buildx imagetools inspect localhost:5000/lab/app:sha-aaa111 | awk '/^Digest:/ {print $2}')

docker buildx imagetools create --tag localhost:5000/lab/app:1.0.0 localhost:5000/lab/app@$D
docker buildx imagetools create --tag localhost:5000/lab/app:prod  localhost:5000/lab/app@$D
for t in sha-aaa111 1.0.0 prod; do docker buildx imagetools inspect localhost:5000/lab/app:$t | grep ^Digest; done
# os três imprimem o MESMO digest

# sobrescrita (o anti-padrão)
printf 'FROM alpine:3.20\nRUN echo v2 > /versao\n' > Dockerfile
docker build -t localhost:5000/lab/app:1.0.0 . && docker push localhost:5000/lab/app:1.0.0
docker buildx imagetools inspect localhost:5000/lab/app:1.0.0 | grep ^Digest   # digest DIFERENTE

Conclusão. O registry aceitou a sobrescrita e a tag 1.0.0 agora aponta para outro conteúdo, enquanto prod e sha-aaa111 continuam no digest antigo. Quem implantou "1.0.0" ontem e hoje roda coisas diferentes. Tag imutável no registry (ECR, Harbor) recusaria o push, e o deploy por tag@digest falharia no pull.

        with: { push: true, tags: "ghcr.io/Equipe/api:latest" }

  1. pull_request_target com checkout do código do PR executa código não confiável com acesso a secrets. Use pull_request.
  2. permissions: write-all: dê o mínimo (contents: read, packages: write só no job que publica).
  3. Senha na linha de comando (-p) e PAT pessoal: use docker/login-action com GITHUB_TOKEN.
  4. Nome com maiúscula (Equipe): o GHCR exige minúsculas.
  5. Só a tag latest: sem rastreio nem rollback. Use metadata-action com sha- e semver.
  6. Publica antes de escanear, e o Trivy roda sem --exit-code 1, então nunca falha: o scan é decorativo. Escaneie antes do push e falhe em HIGH/CRITICAL com correção.
  7. Publica em todo PR (inclusive de fork): push: ${{ github.event_name != 'pull_request' }}.
  8. Sem setup-buildx, cache (type=gha), SBOM, proveniência e assinatura; sem usar o digest. Sem concurrency.
E4SBOM e scan: gere o SBOM de node:22-alpine com o Syft, escaneie o SBOM com o Grype e defina um critério de falha para o CI.
syft node:22-alpine -o spdx-json=sbom.spdx.json
jq '.packages | length' sbom.spdx.json                       # quantos componentes

grype sbom:sbom.spdx.json                                     # tudo
grype sbom:sbom.spdx.json --only-fixed                        # só o que tem correção
grype sbom:sbom.spdx.json --fail-on high --only-fixed; echo "saída: $?"   # critério do CI

O que observar. O SBOM lista pacotes do Alpine e do Node (e módulos globais do npm); o Grype consegue trabalhar só com ele, sem a imagem. Com --only-fixed a lista encolhe bastante, e a saída é diferente de zero apenas se houver achado HIGH ou pior com correção. Esse é o critério defensável para quebrar o pipeline; o resto vai para o backlog. Resultados variam com a base de vulnerabilidades do dia.

E5Assinatura: com um registry local e um par de chaves, assine uma imagem pelo digest, verifique, e mostre que a verificação falha para uma imagem diferente.
cosign generate-key-pair                                   # cosign.key e cosign.pub (peça uma senha)

D=$(docker buildx imagetools inspect localhost:5000/lab/app:1.0.0 | awk '/^Digest:/ {print $2}')
cosign sign --key cosign.key localhost:5000/lab/app@$D     # assina o digest
cosign verify --key cosign.pub localhost:5000/lab/app@$D   # passa

# outra imagem, sem assinatura (a do E1)
D2=$(docker buildx imagetools inspect localhost:5000/lab/alpine:1.0 | awk '/^Digest:/ {print $2}')
cosign verify --key cosign.pub localhost:5000/lab/alpine@$D2   # falha: no signatures found

Observações. Com chave, o cosign pode tentar registrar a assinatura no log público Rekor; num laboratório local, desative esse envio com a opção da sua versão (por exemplo, --tlog-upload=false) e ajuste a verificação de acordo. As flags mudaram entre o cosign 2.x e o 3.x: confira cosign sign --help. A assinatura fica no registry, em uma tag/artefato ligado ao digest (veja com crane ls); no modo sem chave, a verificação usaria --certificate-identity e --certificate-oidc-issuer em vez de --key.

E6Retenção: escreva a política do ECR para: manter as 20 imagens sha- mais recentes, apagar sem tag com mais de 7 dias, e nunca tocar nas tags de release. Aponte o risco da regra de "sem tag".
{
  "rules": [
    { "rulePriority": 1, "description": "20 mais recentes com prefixo sha-",
      "selection": { "tagStatus": "tagged", "tagPrefixList": ["sha-"],
                     "countType": "imageCountMoreThan", "countNumber": 20 },
      "action": { "type": "expire" } },
    { "rulePriority": 2, "description": "sem tag há mais de 7 dias",
      "selection": { "tagStatus": "untagged", "countType": "sinceImagePushed",
                     "countUnit": "days", "countNumber": 7 },
      "action": { "type": "expire" } }
  ]
}

Tags de release (1.4.2) não casam com nenhuma regra, então não expiram. Risco: manifestos de assinatura e atestados de SBOM/proveniência que fiquem sem tag podem ser tratados como "sem tag" e apagados, quebrando a verificação do deploy. Mitigue testando em um repositório de teste, validando com cosign verify depois da limpeza e, se necessário, aumentando o prazo da regra 2. Teste primeiro em modo de pré-visualização.

10Prática

Cenários práticos de trabalho

Cenário 1: "O CI está quebrando com toomanyrequests"

O que fazer. Confirme na mensagem de erro que é o limite de pulls do Docker Hub (HTTP 429). Verifique se o pipeline está autenticado (docker/login-action com token do Hub): sem login, o limite é por IP e o runner compartilhado estoura rápido. Depois, reduza a dependência: espelhe as imagens base (ECR pull-through cache, Harbor proxy ou cópia para o registry interno) e referencie-as de lá; use cache de build para não rebaixar bases a cada execução. Não faça retry em loop: gasta mais cota. Avalie conta paga para o time se o uso for legítimo e alto.

Cenário 2: "Subiu a versão errada em produção depois de um reinício"

O que fazer. Veja se o Compose/manifesto usa latest ou uma tag móvel: o pull no reinício trouxe uma imagem nova. Descubra o que roda agora (docker inspect → digest) e volte para o digest anterior conhecido (do registro de deploy). Correção estrutural: tags semânticas imutáveis, deploy por tag@digest, latest desligado no metadata-action, política de "sem latest" revisada no PR (um lint como hadolint ou uma regra de política no CI). Anote o digest implantado em cada deploy.

Cenário 3: "Saiu uma CVE crítica em uma biblioteca amplamente usada. Estamos afetados?"

O que fazer. (1) Consulte os SBOMs guardados por versão: "quais imagens contêm a biblioteca na versão afetada?" (Grype sobre os SBOMs, Dependency-Track ou busca no Scout), sem baixar tudo. (2) Cruze com o que roda em produção (digests implantados) e com a exposição (internet, dados de pacientes). (3) Verifique exploração ativa (KEV, avisos do fornecedor). (4) Corrija: atualize a dependência/base, rode o pipeline completo (scan, assinatura) e implante por digest, na ordem de risco. (5) Mitigações temporárias (WAF, flag, regra de rede) enquanto o deploy não chega. (6) Registre o incidente, o tempo até a correção e o que melhorar (inventário ausente? bases desatualizadas?).

Cenário 4: "Alguém republicou a tag 1.4.2 com outro conteúdo"

O que fazer. Contenha: bloqueie o push no repositório (permissões) e avalie credenciais usadas (token vazado? pipeline comprometido?); rotacione. Descubra qual digest cada ambiente roda e compare com o digest legítimo do registro de deploy e com a assinatura (cosign verify): se o deploy é por digest e verifica a assinatura, o impacto tende a ser nulo. Restaure a tag legítima ou, melhor, abandone-a e publique 1.4.3. Corrija o que permitiu: tag imutável no registry, push só pelo pipeline (a identidade do pipeline é a única com permissão), verificação obrigatória no deploy.

Cenário 5: "A fatura do registry triplicou"

O que fazer. Separe armazenamento de transferência. No armazenamento, liste repositórios por tamanho e idade e aplique retenção (sha- por contagem, PR curto, sem tag cuidadoso). Na transferência, descubra quem faz pull: nós em outra região, CI baixando base repetidamente, deploys frequentes em muitos nós. Ações: registry e cache na região do consumo, endpoint privado, pull-through cache para as bases, imagens menores, cache nos nós. Meça antes e depois, e documente a política de retenção com compliance para não apagar o que a auditoria exige.

11Referência

Glossário

Registry
Servidor que guarda e serve imagens (API de distribuição da OCI).
Digest
Hash sha256:… do manifesto: identifica uma imagem de forma imutável.
Image index
Manifesto que aponta para um manifesto por plataforma (multi-arch) e para atestados.
Pull-through cache
Registry que busca no upstream no primeiro pull e serve a cópia depois.
Credential helper
Programa que guarda ou gera credenciais de registry fora do config.json.
Build once, deploy many
Construir o artefato uma vez e promover o mesmo digest entre ambientes.
SBOM
Inventário de componentes de uma imagem, em SPDX ou CycloneDX.
Proveniência
Atestado de como e onde um artefato foi construído (in-toto).
SLSA
Modelo de níveis de garantia da cadeia de build (L1 a L3 na trilha de build).
Cosign / Sigstore
Ferramenta e projeto para assinar e verificar artefatos, com modo sem chave.
Fulcio / Rekor
CA de certificados de vida curta e log público de transparência do Sigstore.
CVE / CVSS
Identificador de uma vulnerabilidade conhecida e a nota de severidade padronizada.
KEV / EPSS
Catálogo da CISA de vulnerabilidades exploradas de fato e probabilidade estimada de exploração.
VEX
Declaração de que uma CVE afeta ou não um produto, com justificativa.
Lifecycle policy
Regra declarativa que expira imagens por tag, idade ou contagem.
Egress
Tráfego de saída cobrado pelo provedor (por exemplo, pulls entre regiões).
12Entrevista

Perguntas de entrevista

Responda em voz alta antes de abrir. A resposta ideal tem uma frase de definição e um exemplo prático.

01Qual a diferença entre tag e digest?

Tag é um ponteiro móvel e legível (api:1.4.2); pode ser reapontada. Digest é o hash do manifesto (@sha256:…): identifica um conteúdo exato e nunca muda. Por isso o deploy deve usar o digest, ou tag@digest.

02Por que usar latest em produção é perigoso?

É só o nome da tag quando nenhuma é indicada, sem garantia de ser a mais recente nem a estável. Servidores que puxam em momentos diferentes ficam com versões diferentes, reinícios trazem versão nova sem ninguém decidir, e não há como dar rollback porque a versão anterior não tem nome.

03Que estratégia de tags você adota?

sha-<commit> em todo build (rastreio), X.Y.Z em release (imutável, apontando para o mesmo digest), X.Y e X opcionais para consumidores externos, e nunca latest em produção. Tag imutável habilitada no registry, e o deploy por digest.

04O que é "build once, deploy many" e por que importa?

Constrói-se a imagem uma vez no CI, testa-se e promove-se o mesmo digest para homologação e produção; as diferenças ficam na configuração. Reconstruir por ambiente pode trazer outra base ou dependência, e o que foi testado deixa de ser o que roda.

05Quais são os limites de pull do Docker Hub e como lidar com eles?

Pela documentação oficial: 100 pulls por 6 horas por IP (ou /64 de IPv6) sem autenticação, 200 com conta gratuita autenticada, e sem limite (uso justo) em planos pagos. Multi-arch conta por arquitetura. Soluções: autenticar o CI, usar conta paga, pull-through cache ou espelhar as bases no registry próprio. Confirmo os números na documentação, pois podem mudar.

06O que é um pull-through cache e para que serve?

Um registry intermediário que busca no upstream no primeiro pull e serve a cópia nos seguintes. Reduz a contagem de pulls no Hub, acelera builds, dá resiliência se o upstream cair e permite aplicar scan e política antes de liberar. ECR, Harbor e Artifact Registry têm o recurso; o registry-mirrors do daemon vale só para o Docker Hub.

07Onde o docker login guarda a credencial e como melhorar isso?

Em ~/.docker/config.json; sem credential helper fica em base64, que não é criptografia. Com credsStore ou credHelpers usa o cofre do sistema ou gera o token sob demanda (ECR credential helper). No login, --password-stdin para a senha não ir para o histórico.

08Como autenticar o CI no registry de forma segura?

Credenciais de curta duração e mínimo privilégio: GITHUB_TOKEN com packages: write para o GHCR e federação OIDC com papel de menor privilégio para ECR, ACR e GAR, sem chaves de longa duração em secrets. Quem faz pull em produção só tem permissão de leitura.

09Descreva um pipeline de imagem no GitHub Actions.

Checkout, setup-qemu e setup-buildx, login (fora de PR), metadata-action para tags e labels, build local com cache gha, scan (falha em HIGH/CRITICAL com correção), build e push multi-arch com SBOM e proveniência, assinatura com cosign pelo digest. Permissões mínimas por job, concurrency, e nada publicado em pull request.

10Por que escanear antes do push?

Para que uma imagem vulnerável nunca chegue ao registry nem a um ambiente. Faz-se um build de uma plataforma com load: true (fica no daemon local), escaneia-se, e só depois o build multi-arch com push, que reaproveita o cache. Complementa-se com varredura contínua do que já está publicado, porque CVEs novas surgem depois.

11O que faz cache-to: type=gha,mode=max?

Exporta as camadas de todos os estágios do build para o cache do GitHub Actions, não só do estágio final. Em multi-stage, sem mode=max os estágios deps e build não são reaproveitados. Para CI sem o cache do GitHub, a alternativa é type=registry.

12Como publicar imagem multi-arch e quais os custos?

platforms: linux/amd64,linux/arm64 no buildx, que publica um índice com um manifesto por plataforma. A emulação QEMU torna o arm64 bem mais lento; alternativas: cross-compilation no Dockerfile (--platform=$BUILDPLATFORM, TARGETARCH) ou runners arm64 nativos e imagetools create para juntar. Sem multi-arch, uma imagem feita em Mac M1 falha em servidor amd64 com "exec format error".

13Qual a diferença entre SBOM e proveniência?

SBOM é o inventário do que há na imagem (pacotes e versões, em SPDX ou CycloneDX) e serve para saber se uma CVE nova me afeta. Proveniência é o atestado de como, onde e a partir de que foi construída (repo, commit, builder, bases), no modelo SLSA. Ambos se anexam à imagem como atestados.

14Como funciona a assinatura sem chave com cosign e como se verifica no deploy?

O pipeline obtém um token OIDC, o Fulcio emite um certificado de poucos minutos com a identidade do workflow, o cosign assina o digest e o evento fica no log Rekor. No deploy, cosign verify exige o emissor OIDC e a identidade esperada (o workflow do repositório), e um script de deploy ou admission controller bloqueia imagens sem isso.

15Um scanner acusou 200 CVEs. O que você faz?

Não trato como lista plana. Filtro as que têm correção, priorizo por exploração ativa (KEV, EPSS), alcançabilidade e exposição, e vejo se vêm da base (atualizo a imagem) ou da aplicação (atualizo a dependência). As sem correção ou não alcançáveis viram exceção documentada, com dono e validade (VEX). O gate do CI bloqueia só o que é crítico/alto e corrigível.

16Como manter as imagens base atualizadas sem quebrar tudo?

Base fixada por digest para reprodutibilidade e um bot (Renovate ou Dependabot) abrindo PRs a cada atualização, validados pelo CI. Mais um rebuild agendado semanal para pegar correções de pacotes. Imagem mínima (slim, distroless) reduz a superfície.

17Como definir retenção e limpeza do registry sem comprometer rollback e auditoria?

Por categoria: releases e digests em produção protegidos pelo prazo de auditoria; sha- por contagem; PR/branch curto; sem tag com prazo e cuidado para não apagar assinaturas e atestados. Regras declarativas (lifecycle) testadas em pré-visualização, e validação com cosign verify depois da limpeza.

18Como gestora, como você garante que só imagens confiáveis chegam à produção, e como controla o custo?

Um único caminho: pipeline protegido, com scan, SBOM, proveniência e assinatura; push só pela identidade do pipeline; verificação obrigatória no deploy (admission controller ou script); tags imutáveis e deploy por digest com registro por versão. Política escrita de CVEs com prazos. No custo: retenção por categoria, imagens menores, registry próximo do consumo e cache para as bases; acompanho tempo de correção e custo por serviço.
