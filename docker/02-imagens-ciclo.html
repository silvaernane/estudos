Imagens e ciclo de vida

A imagem é o artefato imutável; o container é a execução dela, com vida própria. Este módulo explica como a imagem é construída por dentro (camadas, manifest, digest, multi-arquitetura), como um container nasce, vive e morre (estados, sinais, códigos de saída, restart) e os comandos e hábitos do dia a dia, incluindo limpeza de disco sem estragos.

Ao final você saberá
  • Explicar camadas, overlay2 e copy-on-write, e por que apagar arquivos numa camada posterior não reduz a imagem.
  • Ler manifest, config e digest; diferenciar tag de digest; inspecionar imagens multi-arquitetura.
  • Descrever os estados do container e usar com segurança run, exec, logs, inspect --format, stats, top e cp.
  • Explicar docker stop (SIGTERM, prazo, SIGKILL), PID 1, zumbis e --init, e interpretar os códigos de saída 0, 1, 125, 126, 127, 137, 139 e 143.
  • Escolher política de restart, prever o efeito de ENTRYPOINT e CMD em tempo de execução e limpar disco com system df e prune sem perder dados.
1Básico

Imagem, container e camadas

Uma imagem é um modelo somente leitura: um sistema de arquivos em camadas mais metadados (comando padrão, variáveis de ambiente, usuário, portas expostas). Um container é uma instância em execução (ou parada) dessa imagem, com uma camada gravável por cima e configuração própria (nome, rede, volumes, limites). A analogia é classe e objeto: uma imagem, vários containers, e mexer em um container não altera a imagem.

Camadas e overlay2

Cada instrução do Dockerfile que altera arquivos (RUN, COPY, ADD) produz uma camada: um tar com as diferenças em relação à anterior. Instruções que só mudam metadados (ENV, CMD, WORKDIR, EXPOSE) entram no config, sem camada de arquivos (aparecem com 0B no history). Na execução, o overlay2 (OverlayFS do kernel) monta as camadas da imagem como lowerdir (somente leitura), cria um upperdir vazio para o container e entrega o resultado unificado (merged) como a raiz /.

  • Copy-on-write (copy-up): ao modificar um arquivo que mora numa camada inferior, o overlay2 copia o arquivo inteiro para o upperdir e altera a cópia. Arquivos grandes alterados com frequência (bancos, logs) sofrem; por isso dados vão para volumes.
  • Remoção: apagar um arquivo da imagem cria um marcador (whiteout) na camada de cima; os bytes continuam na camada de baixo.
  • Compartilhamento: dez containers da mesma imagem usam o espaço das camadas da imagem uma vez, mais dez upperdir pequenos. Imagens que partem da mesma base compartilham as camadas da base em disco e na rede (o pull só baixa as que faltam).
  • Apagar em camada posterior não encolhe a imagem: se um RUN baixa 500 MB e o seguinte os remove, a imagem continua com 500 MB. Limpe na mesma instrução que gerou os arquivos ou use multi-stage (módulos 03 e 04).
Saiba mais: o armazenamento mudou?

Além do storage driver clássico (overlay2), o Docker oferece o containerd image store, que guarda imagens no containerd e dá suporte a imagens multi-arquitetura e novos formatos. Em instalações recentes ele vem sendo adotado como padrão. O conceito de camadas é o mesmo; o que muda são caminhos em /var/lib/docker e alguns campos do inspect. Confira com docker info (campo Storage Driver / driver-type).

Na entrevista

"A imagem é um modelo imutável em camadas; o container é a instância com uma camada gravável por cima, via overlay2 e copy-on-write. As camadas são compartilhadas entre containers e imagens. Remover um arquivo em uma camada posterior só o esconde, então não reduz o tamanho."

Para gestores

Camadas explicam três custos que o time sente: tamanho (pull lento, disco e banda do registry), tempo de build (cache por camada) e superfície de vulnerabilidades (tudo o que está nas camadas é escaneado, mesmo o que foi "apagado"). Peça uma regra simples: nenhum segredo entra em camada alguma, porque ele fica no histórico mesmo se for removido depois.

Manifest, digest, tags, multi-arquitetura e inspeção

Por baixo do nome nginx:1.27 há um conjunto de arquivos JSON e tarballs endereçados pelo hash do próprio conteúdo (content-addressable). Entender isso responde a perguntas práticas: "essa é a mesma imagem?", "por que a tag mudou?", "por que deu exec format error?".

Imagens multi-arquitetura

Um mesmo nome pode servir arquiteturas diferentes (linux/amd64, linux/arm64...) por meio de um index (manifest list): uma lista de manifests, cada um com sua platform. O docker pull escolhe a variante da máquina. Em Mac com Apple Silicon ou em servidores Graviton, isso decide se a imagem roda nativa ou emulada.

docker buildx imagetools inspect nginx:1.27        # lista as plataformas e digests
docker pull --platform linux/arm64 nginx:1.27      # força outra plataforma
docker image inspect nginx:1.27 --format '{{.Os}}/{{.Architecture}}'
docker run --rm --platform linux/amd64 alpine uname -m   # emulado em máquina arm64
Name:      docker.io/library/nginx:1.27
MediaType: application/vnd.oci.image.index.v1+json

Manifests:

  ...

Se uma imagem não tem a variante da sua arquitetura, o Docker avisa ("requested image's platform does not match the detected host platform") e, ao rodar, pode falhar com exec format error (binário de outra CPU). Como construir multi-arquitetura é assunto do módulo 08.

Imagens dangling e remoção

Uma imagem dangling aparece como <none>:<none>: perdeu sua tag (normalmente ao reconstruir api:dev, a imagem antiga fica sem nome) e nenhuma outra imagem depende dela. Acumulam-se rápido em máquinas de desenvolvimento e de CI.

docker image prune                  # remove só as dangling
docker image prune -a               # remove TODAS as sem uso (sem container, mesmo parado)
docker image prune -a --filter "until=168h"   # só as criadas há mais de 7 dias
docker rmi api:1.4.2                # remove a tag; as camadas só saem se nada mais as usa
Armadilha comum: tag não é imagem

docker rmi nome:tag remove o nome; se houver outro nome para a mesma imagem, ela continua. E uma imagem em uso por um container (mesmo parado) não pode ser removida sem -f. Para comparar "é a mesma imagem?", compare digests, nunca tags.

Na entrevista

"Tag é um ponteiro mutável; digest é o hash do manifest e é imutável. O manifest aponta para o config e para as camadas, todos por sha256. Para imagens multi-arquitetura, a tag aponta para um index que lista um manifest por plataforma. Em produção, uso tag de versão e registro o digest do que foi implantado."

Para gestores

Defina a política de tags do time: latest proibido em produção; versão ou SHA do commit como tag; deploys registram o digest (rastreabilidade para auditoria e para o "o que estava rodando às 14h?"). Defina também a retenção no registry e quem pode sobrescrever uma tag (idealmente ninguém: tags imutáveis). Isso é o que torna o rollback uma operação de segundos.

Ciclo de vida do container

Um container existe independentemente de estar rodando. Ele nasce created, roda enquanto seu processo principal (PID 1) estiver vivo e vira exited quando esse processo termina. Parado, ele continua em disco (com a camada gravável, os logs e o código de saída) até ser removido.

EstadoSignificaComo entra / sai
createdcontainer criado (camada gravável, rede, config), processo ainda não iniciadodocker create; sai com start
runningprocesso principal em execuçãostart, run, restart, unpause
pausedprocessos congelados (cgroup freezer); o processo não sabe, nada é sinalizadodocker pause / unpause
restartingDocker reiniciando por causa da política de restartautomático após o processo sair
exitedprocesso terminou; guarda o código de saídafim do processo, stop, kill; sai com start ou rm
 
docker create --name c1 alpine sleep 300    # created
docker start c1                              # running
docker pause c1 && docker ps --filter name=c1 --format '{{.Names}} {{.Status}}'
docker unpause c1 && docker stop c1          # exited
docker ps -a --filter status=exited          # parados
docker rm c1                                 # removido
c1 Up 5 seconds (Paused)
  • docker start reinicia o mesmo container (mesma camada gravável, mesmos arquivos). docker run cria sempre um novo.
  • docker restart = stop + start. docker events mostra a sequência (create, start, die, stop, destroy...) em tempo real.
  • Um container sem processo principal de longa duração (docker run alpine sem comando) sai imediatamente: não há nada para manter vivo. Isso não é erro.
Armadilha comum: "o container reiniciou, perdi os arquivos"

Reiniciar (stop/start, restart, política de restart) preserva a camada gravável. Perde-se tudo no recriar (rm e run de novo, compose up com imagem ou configuração nova, deploy). Quem depende de dados gravados dentro do container tem um bug esperando para acontecer: use volumes.

Na entrevista

"Estados: created, running, paused, restarting, exited e removido. O container vive enquanto o PID 1 vive; ao terminar vira exited, mantendo logs e código de saída até o rm. run é create mais start e sempre cria um novo; start reinicia um existente."

Para gestores

Containers são descartáveis por desenho: a regra é tratá-los como gado, não como animais de estimação. Se o time precisa "entrar no container para consertar", isso é sinal de processo falho (imagem, configuração, dados fora de volume). Reforce: sem ajuste manual em produção; correção vira nova imagem e novo deploy.

Armadilha comum: run x exec, stop x kill
  • docker run cria um container novo. docker exec roda um comando extra em um container existente: se o processo principal morrer, o exec some junto.
  • Variáveis passadas no exec -e valem só para aquele comando; as do run -e valem para o processo principal. Mudar variável de um container existente exige recriá-lo.
  • stop pede para encerrar e dá um prazo; kill mata na hora. Seção 5.
Regra de bolso

Tag fixa, --name para o que fica, --rm para o que é descartável, -p 127.0.0.1:... em desenvolvimento, --memory em produção.

Na entrevista

"run faz create e start de um container novo; exec executa um comando dentro de um existente; logs lê o stdout/stderr do processo principal; inspect -f extrai estado e configuração; stats mostra uso contra os limites."

Para gestores

Padronize como o time sobe containers em vez de cada um lembrar flags: em desenvolvimento e produção pequena, Compose (módulo 06) versiona as flags em arquivo revisável. Comando docker run colado em wiki é configuração sem revisão nem histórico. E cobre limites de memória e CPU em tudo que vai para servidor compartilhado.

5Intermediário

docker stop, sinais, PID 1 e zumbis

Encerrar bem um container é um problema de sinais. O docker stop envia SIGTERM ao processo principal (um pedido: "termine de forma limpa"), espera um prazo (padrão 10 s, ajustável com -t) e, se o container ainda estiver vivo, envia SIGKILL, que o processo não pode tratar nem ignorar (o kernel o encerra). O docker kill envia SIGKILL direto (ou outro sinal com -s).

Por que o PID 1 é especial

Dentro do container, o processo principal é o PID 1 do namespace. No Linux, o PID 1 tem dois comportamentos próprios:

  • Sinais sem tratador são ignorados. Para qualquer outro processo, SIGTERM sem handler mata o processo (ação padrão). Para o PID 1, se ele não instalou um handler, o kernel descarta o sinal vindo de fora do namespace (só SIGKILL e SIGSTOP passam). Resultado: docker stop "não faz nada" e cai no SIGKILL.
  • Deve recolher órfãos. Quando um processo filho termina e o pai não chama wait(), ele vira zumbi (Z, <defunct>) e ocupa uma entrada na tabela de processos. Processos cujo pai morreu são adotados pelo PID 1, que precisa recolhê-los. Um PID 1 que não faz isso (um app qualquer) acumula zumbis.

Na prática, isso significa:

  • Use a forma exec (CMD ["node","server.js"]) para a aplicação ser o PID 1. Na forma shell, o PID 1 é um /bin/sh -c que normalmente não repassa o sinal ao filho.
  • Trate SIGTERM na aplicação: parar de aceitar novas requisições, concluir as em andamento, fechar conexões e sair (graceful shutdown). Node.js e Python não têm handler por padrão (precisam registrar process.on('SIGTERM') ou signal.signal); a JVM trata SIGTERM e executa shutdown hooks; Go exige signal.Notify.
  • Use --init (ou init: true no Compose) quando a aplicação cria subprocessos ou não trata sinais: o Docker coloca o tini como PID 1, que repassa sinais ao filho e recolhe zumbis.
  • Em scripts de entrypoint, termine com exec "$@" para o script ser substituído pela aplicação, que assume o PID 1.
  • Sinal diferente por imagem: algumas imagens declaram STOPSIGNAL próprio (a do nginx usa SIGQUIT, desligamento gracioso; a do postgres usa SIGINT, desligamento "rápido"). Dá para definir com --stop-signal e o prazo com --stop-timeout (ou docker stop -t).
# PID 1 = sleep, sem handler de SIGTERM: o stop espera os 10 s inteiros
docker run -d --name t1 alpine sleep 300
time docker stop t1
docker inspect -f '{{.State.ExitCode}}' t1          # 137

# com --init: o tini repassa SIGTERM e o sleep morre na hora
docker run -d --init --name t2 alpine sleep 300
time docker stop t2
docker inspect -f '{{.State.ExitCode}}' t2          # 143
docker rm t1 t2
t1  ...  real  0m10.2s   (exit 137)
t2  ...  real  0m0.4s    (exit 143)

(Tempos ilustrativos.) O que um zumbi parece em ps dentro do container, quando o PID 1 não recolhe:

PID   USER   STAT COMMAND
  1   app    S    node server.js

Armadilha comum: CMD npm start e scripts de shell

Com npm start (ou um .sh que chama o app sem exec), a cadeia é sh → npm → node, e o SIGTERM costuma não chegar ao node. Prefira CMD ["node","server.js"]. Se precisar de um script, termine-o com exec node server.js.

Na entrevista

"docker stop envia SIGTERM, espera o prazo (10 s) e envia SIGKILL. O PID 1 não tem ação padrão para sinais: sem handler, ignora SIGTERM, e por isso usamos forma exec, tratamos o sinal e usamos --init (tini) quando há subprocessos ou zumbis."

Para gestores

Desligamento mal tratado aparece como erros no deploy: requisições cortadas, 502 no balanceador, jobs pela metade, transações abertas. Cobre do time o graceful shutdown em todo serviço, testado (envie SIGTERM durante carga). Em orquestradores o prazo se chama terminationGracePeriod (Kubernetes) ou stop_grace_period (Compose): ele precisa ser maior que o pior tempo de drenagem, e o balanceador deve tirar a instância do rodízio antes.

6Intermediário

Códigos de saída e políticas de restart

Quando o processo principal termina, o shim registra o código de saída. Por convenção do Unix, 0 é sucesso, de 1 a 125 são erros definidos pela aplicação e 128 + n significa "morto pelo sinal n". O diagnóstico de container que parou começa por ele.

docker ps -a --filter status=exited --format 'table {{.Names}}\t{{.Status}}'
docker inspect -f 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}} erro={{.State.Error}}' api
CódigoSignificadoCausas e o que olhar
0terminou com sucessonormal para tarefas. Para um serviço, o processo principal acabou: CMD errado (comando que vai para segundo plano, service x start), ou o programa só imprime e sai

Políticas de restart

PolíticaComportamentoQuando usar
no (padrão)nunca reinicia sozinhotarefas, desenvolvimento
on-failure[:N]reinicia se sair com código diferente de 0, até N vezesjobs que podem falhar de forma transitória
alwayssempre reinicia; um container parado à mão só volta quando o daemon reiniciaserviços que devem estar sempre no ar
unless-stoppedcomo always, mas um container parado à mão continua parado mesmo depois de o daemon reiniciarserviços em host único (a escolha comum)
  • A política só passa a valer depois que o container fica de pé por um tempo mínimo (a documentação fala em 10 segundos); entre tentativas há um intervalo crescente (backoff). Um container que cai logo ao iniciar entra em Restarting (1) em loop.
  • Mudar sem recriar: docker update --restart unless-stopped api. Ver: docker inspect -f '{{.HostConfig.RestartPolicy.Name}} {{.RestartCount}}' api.
  • --rm e --restart não combinam. Reiniciar o processo não conserta uma causa persistente (configuração errada, banco fora): vira loop silencioso. Combine com logs, alertas e healthcheck (módulo 03).
  • Restart policy cobre falha do processo e reboot do host. Não cobre nó inteiro fora do ar nem rolling update: isso é papel do orquestrador (módulo 10).
Armadilha comum: always que esconde o problema

Com --restart always um serviço que falha ao subir fica reiniciando sem parar, e o painel mostra "Up 3 seconds" repetidamente. Verifique RestartCount e docker logs; alerte quando a contagem passa de um limite, em vez de contar que "está de pé".

Na entrevista

"137 é SIGKILL: costuma ser OOM (confirmo com OOMKilled) ou stop que estourou o prazo. 143 é SIGTERM tratado. 127 é comando não encontrado, 126 sem permissão, 125 falha do próprio docker run, 139 segfault. Em restart uso unless-stopped em host único e on-failure para jobs."

Para gestores

Restart automático é rede de proteção, não estratégia de confiabilidade. Pergunte ao time: o que alerta quando um serviço reinicia mais de N vezes? Quem vê o OOMKilled? Qual o limite de memória definido e com base em quê? Incidentes repetidos com 137 normalmente pedem ajuste de limite e investigação de vazamento, não só "aumentar a memória".

ENTRYPOINT e CMD em tempo de execução

Como escrever Dockerfiles é assunto do módulo 03. Aqui interessa o efeito ao executar: o comando final do container é a combinação de ENTRYPOINT, CMD da imagem e o que você passou no docker run.

Imagem defineSem argumentos no runCom docker run img X Y
só CMD ["a","b"]a bX Y (substitui o comando inteiro)
só ENTRYPOINT ["e"]ee X Y
ENTRYPOINT ["e"] + CMD ["a"]e ae X Y (substitui o CMD)
forma shell: CMD a b/bin/sh -c "a b"X Y
forma shell: ENTRYPOINT e (+ qualquer CMD)/bin/sh -c "e" (CMD ignorado)/bin/sh -c "e" (argumentos ignorados)

Forma exec x forma shell

  • Exec (["node","server.js"], JSON): o programa é executado direto. É o PID 1 e recebe os sinais. Não há expansão de variáveis nem pipes ($HOME vira texto; para isso chame ["sh","-c","..."] explicitamente).
  • Shell (node server.js): vira /bin/sh -c "node server.js". Há expansão e pipes, mas o PID 1 é o shell (seção 5). Em ENTRYPOINT, a forma shell ainda descarta o CMD e os argumentos.

Ver e sobrescrever

docker image inspect -f 'ENTRYPOINT={{json .Config.Entrypoint}} CMD={{json .Config.Cmd}}' nginx:1.27
docker run --rm alpine echo oi                       # substitui o CMD
docker run --rm --entrypoint cat nginx:1.27 /etc/os-release   # troca o ENTRYPOINT
docker run --rm -it --entrypoint sh nginx:1.27       # shell para investigar a imagem
docker run --rm --entrypoint "" alpine ls /          # remove o ENTRYPOINT da imagem
ENTRYPOINT=["/docker-entrypoint.sh"] CMD=["nginx","-g","daemon off;"]

Esse é o padrão do entrypoint de preparação, muito comum em imagens oficiais (nginx, postgres, mysql): o ENTRYPOINT é um script que prepara o ambiente (gera configuração, inicializa o banco, ajusta permissões) e termina com exec "$@", que executa o CMD como PID 1. Por isso docker run postgres:17 postgres -c max_connections=200 funciona: o argumento substitui o CMD e o script o repassa.

Armadilha comum: "passei um comando e a imagem ignorou"

Se a imagem tem ENTRYPOINT, o que vem depois do nome da imagem são argumentos dele, não um comando. Para rodar outro programa na mesma imagem (um shell de diagnóstico, por exemplo), use --entrypoint. E se um ENTRYPOINT em forma shell parece "comer" os argumentos, é porque ele descarta mesmo.

Na entrevista

"ENTRYPOINT define o executável; CMD, os argumentos padrão (ou o comando, se não há ENTRYPOINT). Argumentos no docker run substituem o CMD; o ENTRYPOINT só muda com --entrypoint. Uso forma exec para o processo ser o PID 1 e receber sinais."

Para gestores

Imagens "executáveis" (ENTRYPOINT definido, CMD com padrão) e entrypoints de preparação dão ao time um contrato claro de uso, e facilitam a reutilização: a mesma imagem como API, worker ou job de migração, mudando só os argumentos. Combine uma convenção e documente no README da imagem.

Boas práticas do dia a dia e limpeza de disco

Hábitos que evitam dor

  • Tags fixas (postgres:17, nginx:1.27-alpine), nunca latest em ambientes compartilhados.
  • Nome e rótulos: --name para o que fica; --label (ex.: equipe=pagamentos) permite filtrar e limpar com precisão (--filter label=...).
  • --rm em containers descartáveis; -it só quando há terminal.
  • Logs na saída padrão: a aplicação escreve em stdout/stderr, e o driver de log cuida do resto. Arquivo de log dentro do container some e enche a camada gravável.
  • Um processo principal por container; dados em volumes; configuração por variáveis ou arquivos montados; segredos nunca na imagem.
  • Limites de memória e CPU, e --pids-limit quando fizer sentido, em qualquer servidor compartilhado.
  • Não corrija dentro do container: exec é para investigar; a correção vai para a imagem ou a configuração.

Um container de banco parado para manutenção deixa seu volume "sem uso", e o --volumes (ou o volume prune -a) o apaga, com dados reais dentro. Não existe lixeira. Em produção, rotule volumes importantes, faça backup antes de qualquer limpeza em massa e prefira remover itens por nome ou filtro.

Regra de bolso

Antes de apagar, veja: system df -v, ps -a, volume ls. Em desenvolvimento, pode ser agressivo; em produção, só com filtro de idade, backup dos volumes e uma janela combinada.

Na entrevista

"Disco cheio: docker system df -v para achar o culpado (imagens antigas, cache de build, volumes, logs sem rotação), prune com filtros e cuidado com volumes, e rotação de logs no daemon ou por container."

Para gestores

Servidor Docker sem política de limpeza e de rotação de logs enche o disco e cai, quase sempre de madrugada. Defina: rotação de logs padrão no daemon.json, rotina de limpeza para runners de CI, alerta de uso de disco em /var/lib/docker e retenção de imagens no registry. É manutenção barata contra um incidente caro.

Exercícios

Laboratórios para um host Linux (ou WSL 2) com Docker. Tente antes de abrir a resolução.

E1Prove que apagar arquivos em uma camada posterior não diminui a imagem. Monte um Dockerfile de três instruções, compare os tamanhos e descubra qual camada pesa.
FROM alpine:3.20
RUN dd if=/dev/zero of=/grande.bin bs=1M count=50
RUN rm /grande.bin
docker build -t lab-camadas .
docker image ls lab-camadas
docker image history lab-camadas

O history mostra a camada do dd com cerca de 52 MB e a do rm com 0B: o tamanho da imagem continua perto de 60 MB (7-8 MB da base + 50 MB). O arquivo está escondido, não ausente. Correção: gerar e apagar na mesma instrução (RUN dd ... && rm ...), caso em que a camada não guarda os 50 MB. Limpeza: docker rmi lab-camadas.

E2Mostre o copy-on-write: altere um arquivo da imagem dentro de um container, veja o que mudou com docker diff, localize a alteração no UpperDir e confirme que a imagem não mudou.
docker run -d --name cow nginx:1.27
docker exec cow sh -c 'echo "# alterado" >> /etc/nginx/nginx.conf; touch /novo'
docker diff cow
sudo ls "$(docker inspect -f '{{.GraphDriver.Data.UpperDir}}' cow)/etc/nginx"
docker run --rm nginx:1.27 tail -1 /etc/nginx/nginx.conf    # container novo: sem a alteração
docker rm -f cow

O diff lista C /etc/nginx, C /etc/nginx/nginx.conf e A /novo, além de arquivos que o próprio nginx criou. O arquivo inteiro foi copiado para o UpperDir (copy-up). O container novo, criado da mesma imagem, não tem a alteração, e ao remover o cow a camada gravável desaparece. (O UpperDir só existe com o storage driver clássico; com o containerd image store, use apenas o diff.)

E3Descubra o digest de nginx:1.27, as plataformas disponíveis e rode a imagem por digest. Explique por que o "ID" local difere do digest.
docker pull nginx:1.27
docker image inspect -f '{{index .RepoDigests 0}}' nginx:1.27      # nginx@sha256:...
docker image inspect -f '{{.Id}}' nginx:1.27                       # sha256 do CONFIG (outro número)
docker buildx imagetools inspect nginx:1.27 | grep -E 'Digest|Platform'
D=$(docker image inspect -f '{{index .RepoDigests 0}}' nginx:1.27)
docker run --rm "$D" nginx -v

O RepoDigests traz o digest do manifest/index no registry; o Id é o hash do config da imagem. São objetos diferentes, daí números diferentes. O imagetools lista uma linha Platform por arquitetura. Rodar pelo digest garante o conteúdo exato, mesmo que a tag 1.27 seja movida depois.

E4Meça o efeito do PID 1: compare o tempo e o código de saída de docker stop em um sleep sem e com --init, e repita com -t 2. Depois envie SIGTERM com docker kill -s TERM.
docker run -d --name a alpine sleep 300
time docker stop a; docker inspect -f '{{.State.ExitCode}}' a             # ~10 s, 137
docker run -d --name b alpine sleep 300
time docker stop -t 2 b; docker inspect -f '{{.State.ExitCode}}' b        # ~2 s, 137
docker run -d --init --name c alpine sleep 300
time docker stop c; docker inspect -f '{{.State.ExitCode}}' c             # <1 s, 143
docker run -d --name d alpine sleep 300
docker kill -s TERM d; sleep 2; docker ps --filter name=d --format '{{.Names}} {{.Status}}'   # continua Up
docker rm -f a b c d

Sem handler, o sleep (PID 1) ignora o SIGTERM: o stop espera o prazo inteiro e termina com SIGKILL (137); -t 2 só encurta a espera. Com --init, o tini repassa o sinal ao sleep, que morre pela ação padrão, e o tini sai com 143. O kill -s TERM direto no PID 1 sem handler não tem efeito: o container segue Up.

E5Reproduza os códigos de saída 3, 125, 126, 127 e 137 (com OOMKilled), e depois observe uma política on-failure:3.
docker run --rm alpine sh -c 'exit 3'; echo $?                 # 3  (código da aplicação)
docker run --rm --opcao-inexistente alpine; echo $?           # 125 (erro do docker run)
docker run --rm alpine /etc/passwd; echo $?                   # 126 (não executável)
docker run --rm alpine comando-que-nao-existe; echo $?        # 127 (não encontrado)

docker run --name oom --memory 20m alpine sh -c 'tail /dev/zero'; echo $?   # 137
docker inspect -f 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' oom   # oom=true
docker rm oom

docker run -d --name falha --restart on-failure:3 alpine sh -c 'echo tentei; exit 1'
sleep 15; docker inspect -f '{{.State.Status}} exit={{.State.ExitCode}} restarts={{.RestartCount}}' falha
docker logs falha | wc -l ; docker rm -f falha

O tail /dev/zero lê zeros sem quebra de linha e acumula em memória até o cgroup de 20 MB estourar: o OOM killer envia SIGKILL e o container sai com 137 e OOMKilled=true. O container da política termina em exited exit=1 restarts=3 (quatro execuções no total, com intervalos crescentes: logs mostra "tentei" quatro vezes).

E6Descubra o ENTRYPOINT e o CMD de nginx:1.27 e de postgres:17, execute outro programa dentro da imagem do nginx e passe um argumento ao entrypoint do postgres.
for i in nginx:1.27 postgres:17; do
  docker image inspect -f "$i  ENTRYPOINT={{json .Config.Entrypoint}} CMD={{json .Config.Cmd}} STOPSIGNAL={{.Config.StopSignal}}" $i
done
docker run --rm --entrypoint nginx nginx:1.27 -v        # versão do nginx, sem subir o servidor
docker run --rm --entrypoint "" nginx:1.27 cat /etc/os-release

Ambas usam um script de entrypoint (/docker-entrypoint.sh) e um CMD que roda o servidor; o nginx declara SIGQUIT e o postgres SIGINT como sinal de parada. O argumento postgres -c max_connections=50 substitui o CMD e o script o repassa ao servidor (show retorna 50). Com --rm -d, o stop final já remove o container.

Cenários práticos de trabalho

Cenário 1: o disco do servidor de homologação chegou a 95%

O alerta dispara em /var/lib/docker e os deploys começam a falhar com "no space left on device".

O que fazer: docker system df -v para achar a categoria; se são logs, olhe *-json.log dos containers e configure rotação (daemon.json) e recrie os serviços; se são imagens, image prune -a --filter until=...; se for cache de build, builder prune; se forem volumes, veja volume ls e de quem são antes de apagar qualquer coisa. Não rode system prune --volumes às cegas. Depois, deixe uma rotina de limpeza e um alerta em 80%, e registre o aprendizado.

Cenário 2: o serviço "está Up" mas ninguém consegue usá-lo

O docker ps mostra Up 4 seconds, e na próxima olhada Up 2 seconds. Clientes recebem erro.

O que fazer: o tempo de "Up" nunca passa de alguns segundos: loop de reinício. docker inspect -f '{{.RestartCount}} {{.State.ExitCode}} {{.State.OOMKilled}}' api e docker logs --tail 50 api. Se o código é 1, o log dirá a causa (variável faltando, banco inacessível); se 137 com OOMKilled=true, o limite de memória é baixo ou há vazamento; se 127/126, a imagem ou o entrypoint estão errados. Corrija a causa em vez de depender do always; crie alerta para contagem de restarts.

Cenário 3: cada deploy derruba requisições e leva 10 segundos por container

No deploy, usuários veem 502 por alguns segundos e a troca de cada container demora exatamente 10 s.

O que fazer: é o padrão "SIGTERM ignorado": o stop espera o prazo e mata (137), cortando requisições em voo. Verifique o CMD (forma shell? npm start?), mude para a forma exec ou exec no script, implemente o graceful shutdown no app, use --init se houver subprocessos e ajuste o prazo (--stop-timeout / stop_grace_period) para o tempo real de drenagem. No balanceador, tire a instância do rodízio antes de enviar o sinal. Teste com carga e SIGTERM.

Cenário 4: a nova versão quebrou e ninguém sabe voltar

Produção roda minha-api:latest. Após um deploy, o sistema falha. Querem "voltar para a anterior", mas a tag foi sobrescrita.

O que fazer: no curto prazo, localize a imagem antiga: docker image ls --digests no servidor, imagens dangling ainda no host (docker image ls -a) ou o histórico do registry/CI; recrie o container com o digest anterior. Em seguida, mude o processo: tags de versão imutáveis (1.4.2 ou SHA do commit), deploy registrando o digest, e o rollback passa a ser "implantar a tag anterior". Proíba sobrescrever tags no registry e defina retenção das últimas N versões.

12Intermediário

Perguntas de entrevista

Responda em voz alta antes de abrir. Boa resposta: definição, mecanismo e uma consequência prática.

01Qual a diferença entre imagem e container?

A imagem é um modelo imutável em camadas, com metadados. O container é uma instância dela com uma camada gravável própria e configuração de execução. Uma imagem gera vários containers; remover o container descarta a camada gravável, não a imagem.

02O que são camadas e como o overlay2 as usa?

Cada instrução que altera arquivos gera uma camada somente leitura. O overlay2 as monta como lowerdirs, acrescenta um upperdir gravável e apresenta a união como a raiz do container. As camadas são compartilhadas entre imagens e containers e cacheadas no build e no pull.

03Explique copy-on-write no Docker.

Ao alterar um arquivo que vem de uma camada da imagem, o overlay2 copia o arquivo inteiro para o upperdir do container e altera a cópia; a camada original permanece intacta. Escritas pesadas em arquivos grandes ficam caras, por isso bancos e dados volumosos usam volumes.

04Por que apagar um arquivo em um RUN posterior não reduz o tamanho da imagem?

Camadas são imutáveis e aditivas: o rm grava um whiteout na camada nova, mas a camada que criou o arquivo continua com os bytes. A solução é criar e apagar na mesma instrução ou usar multi-stage, copiando só o necessário para a imagem final.

05Tag x digest? Por que evitar latest em produção?

Tag é um ponteiro mutável; digest é o sha256 do manifest e identifica o conteúdo exato. latest é só a tag padrão, não "a mais recente": não diz qual versão roda, pode mudar sem aviso e inviabiliza rollback confiável. Use tag de versão ou SHA do commit e registre o digest do que foi implantado.

06O que são manifest, config e digest?

O manifest é o JSON que aponta, por digest, para o config e para as camadas. O config traz os metadados (CMD, ENV, usuário, histórico, diff_ids). Digest é o sha256 do conteúdo. O ID local da imagem é o hash do config; o digest do registry é o do manifest, por isso são diferentes.

07Como funcionam as imagens multi-arquitetura?

A tag aponta para um index (manifest list) com um manifest por plataforma. O runtime escolhe a variante da sua CPU e baixa só as camadas dela. Se não existir a plataforma, há aviso ou exec format error. Em Apple Silicon x servidor amd64, constrói-se com buildx --platform.

08O que são imagens dangling e como limpar o disco com segurança?

Dangling são imagens sem tag e sem dependentes. docker image prune as remove; -a remove também as sem container. Para disco cheio: docker system df -v para ver imagens, cache, volumes e logs; prune com --filter until; cuidado com volumes (apagam dados); rotação de logs no daemon.

09Quais são os estados de um container e as transições?

created, running, paused, restarting e exited (mais removing/dead, raros). create leva a created; start a running; pause/unpause congelam e retomam por cgroup freezer; o fim do processo, stop ou kill levam a exited; a política de restart passa por restarting; rm remove. O container vive enquanto o PID 1 vive.

10run x start x exec?

run = create + start de um container novo. start reinicia um existente, com a mesma camada gravável. exec executa um comando adicional dentro de um container em execução e termina junto com ele se o principal morrer.

11O que faz docker stop e como ele difere de kill?

stop envia SIGTERM (ou o STOPSIGNAL da imagem), espera o prazo (10 s, -t) e envia SIGKILL. kill envia SIGKILL na hora ou outro sinal com -s. Para o stop ser limpo, a aplicação precisa tratar SIGTERM e ser o PID 1 (forma exec) ou ter um init que repasse o sinal.

12Por que o PID 1 é especial e para que serve --init?

O PID 1 não tem ação padrão para sinais: sem handler, SIGTERM é ignorado. Também precisa recolher processos órfãos; senão viram zumbis. --init coloca o tini como PID 1: ele repassa sinais ao filho e recolhe zumbis. Em scripts de entrypoint, exec "$@" entrega o PID 1 à aplicação.

13O que significam os exit codes 0, 1, 125, 126, 127, 137, 139 e 143?

0 sucesso; 1 erro da aplicação; 125 falha do próprio docker run (flag, porta ocupada); 126 comando sem permissão de execução; 127 comando não encontrado; 137 SIGKILL (OOM, kill ou stop sem tratar SIGTERM); 139 SIGSEGV; 143 SIGTERM tratado. Acima de 128, é 128 mais o número do sinal. Confirmo OOM com docker inspect e OOMKilled.

14Quais políticas de restart existem e qual você escolhe?

no, on-failure[:N], always e unless-stopped. Em host único uso unless-stopped para serviços (respeita parada manual após reboot) e on-failure para jobs. A política só vale após o container subir por alguns segundos, e não substitui alerta, healthcheck nem orquestrador: reiniciar não conserta causa persistente.

15ENTRYPOINT x CMD em tempo de execução? Forma exec x shell?

ENTRYPOINT é o executável; CMD, os argumentos padrão. Argumentos do docker run substituem o CMD; --entrypoint troca o ENTRYPOINT e zera o CMD. Na forma exec o programa é o PID 1 e recebe sinais; na forma shell (/bin/sh -c) o shell fica como PID 1 e, em ENTRYPOINT, o CMD e os argumentos são ignorados. Entrypoints de preparação terminam com exec "$@".

16O container reinicia sozinho em loop. Como você investiga?

Vejo docker ps (Restarting ou Up de poucos segundos), depois docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.RestartCount}}' e docker logs --tail. O código orienta: 1 aplicação/configuração, 137 com OOM é memória, 127/126 é imagem ou entrypoint, 0 é processo principal que termina. Reproduzo com docker run --rm -it --entrypoint sh se faltar contexto. Corrijo a causa e deixo um alerta de restarts.

17Como você definiria, para uma equipe, a política de imagens e de limpeza de containers?

Imagens identificadas por versão imutável ou SHA do commit, latest proibido em produção, digest registrado em cada deploy, retenção definida no registry e imagens construídas uma vez e promovidas entre ambientes. No host: rotação de logs no daemon, limites de memória e CPU, rotina de limpeza com filtros de idade para runners e desenvolvimento, e nenhuma limpeza de volumes em produção sem backup e revisão. Alertas de disco, de reinícios e de OOM completam a política.
