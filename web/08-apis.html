MÓDULO 08 · Intermediário

APIs: fundamentos

APIs ligam o front-end ao back-end, os sistemas internos entre si e a empresa aos parceiros. Este módulo apresenta os conceitos que aparecem em toda entrevista e em toda reunião de integração, e prepara o terreno para a trilha dedicada a APIs.

Ao final você saberá
  • Explicar o que é uma API, o que é contrato e o que torna uma API REST.
  • Aplicar boas práticas de nomes, filtros, paginação, ordenação e erros padronizados.
  • Usar idempotência, versionamento, timeouts e retries com segurança.
  • Comparar REST, GraphQL, gRPC, WebSocket e SSE e saber quando usar webhooks.
  • Tratar uma API como produto: documentação, governança e depreciação.
1Básico

O que é uma API e o que é um contrato

API (application programming interface, interface de programação de aplicações) é a forma combinada pela qual um software pede algo a outro. Neste módulo, "API" quase sempre significa API web: um sistema expõe operações via HTTP (módulo 3) e outros sistemas as chamam.

O ponto central é o contrato: o acordo sobre o que o consumidor envia e o que recebe de volta. Ele inclui:

  • Endereços e métodos disponíveis.
  • Formato dos dados de entrada e saída, campos obrigatórios e tipos.
  • Códigos de status e formato dos erros.
  • Como se autenticar, limites de uso e garantias de disponibilidade.

Enquanto o contrato se mantém, o provedor pode reescrever tudo por dentro: trocar o banco, a linguagem, a nuvem. É isso que permite que equipes diferentes evoluam sem se travar.

Tipo de APIQuem consomeExemplo
Privada (interna)Equipes da própria empresaAPI de agenda usada pelo app da recepção
De parceirosEmpresas com contratoLaboratório enviando resultados de exames
PúblicaQualquer desenvolvedor cadastradoAPI de CEP, de pagamentos, de mapas
Na entrevista

"API é a interface pela qual sistemas conversam. O contrato define requisições, respostas, erros e regras de uso; enquanto ele se mantém, cada lado evolui de forma independente."

Para gestores

Toda API tem consumidores, mesmo que sejam só outras equipes. Quebrar o contrato gera retrabalho em quem consome e desgaste entre times. Exija que cada API tenha um dono identificado e um contrato escrito antes da implementação.

2Básico

REST na prática

REST (representational state transfer) é um estilo de arquitetura, descrito por Roy Fielding em 2000. Na prática do mercado, uma "API REST" segue algumas ideias:

  • Recursos: tudo é uma coisa com identificador. Paciente, consulta, exame.
  • URIs identificam recursos: /pacientes/p-30551.
  • Métodos HTTP dizem a ação: GET lê, POST cria, PUT substitui, PATCH altera parte, DELETE remove.
  • Status HTTP dizem o resultado: 200, 201, 204, 400, 404, 409, 500 (detalhes no módulo 3).
  • Stateless (sem estado de sessão no servidor entre chamadas): cada requisição carrega tudo o que precisa, inclusive a credencial. Isso facilita escalar horizontalmente.
  • Representações: o recurso viaja num formato, quase sempre JSON, negociado pelos cabeçalhos Accept e Content-Type.

Fielding também previa HATEOAS: respostas trazem links para as próximas ações possíveis, e o cliente navega por eles. Pouquíssimas APIs de mercado seguem isso à risca; vale saber o nome.

Na entrevista

"REST organiza a API em recursos identificados por URI, manipulados por métodos HTTP com semântica padrão, sem estado de sessão no servidor e com representações, em geral JSON. HATEOAS é o nível mais estrito e raramente aplicado."

Para gestores

"REST" virou rótulo genérico. Na revisão de design, pergunte se a API usa métodos e status de forma consistente. Uma API que responde 200 com {"erro": true} obriga cada consumidor a tratar erros de forma especial, e isso vira custo em todos os times que a usam.

Design de recursos: nomes, filtros, paginação e ordenação

Nomes

Minúsculas, hífen entre palavras/planos-de-saude/PlanosDeSaude, /planos_de_saude

Campos com um padrão únicodataNascimento em todo lugardata_nasc numa rota e birthDate em outra

Datas em ISO 8601 com fuso (2026-12-03T14:00:00-03:00) e identificadores como string evitam muitos bugs de integração.

Filtros e ordenação

GET /v1/consultas?status=agendada&unidade=u-12&inicio_de=2026-12-01&sort=-inicio,especialidade&limit=20 HTTP/1.1

Convenção comum: o sinal de menos em sort indica ordem decrescente. Escolha uma convenção, documente e aplique em todas as rotas. Não coloque dados sensíveis em query string: URLs acabam em logs de proxy, de servidor e no histórico do navegador.

Paginação: offset x cursor

Toda listagem precisa de limite, senão um dia alguém pede um milhão de registros de uma vez.

Offset (?offset=40&limit=20)Cursor (?cursor=eyJpZCI6...&limit=20)
Como funcionaPula N registrosContinua a partir de uma posição codificada (ex.: último ID visto)
Pular para a página 37FácilNão suporta
Desempenho em páginas altasPiora: o banco lê e descarta as linhas puladasEstável, usa índice
Inserções durante a leituraItens repetidos ou puladosConsistente
Bom paraTelas administrativas pequenasFeeds, sincronização, integrações, grandes volumes

  "data": [

Na entrevista

"Recursos no plural, filtros e ordenação por query string, sempre com limite. Offset é simples e permite pular páginas, mas fica lento e inconsistente em volume grande; cursor é estável e indicado para integrações e feeds."

Para gestores

Um guia de estilo de API de duas páginas economiza meses de discussões repetidas: nomes, datas, paginação, erros, versionamento. Ferramentas de lint de OpenAPI, como o Spectral, aplicam o guia automaticamente no pipeline e tiram o tema da revisão manual.

4Intermediário

Erros padronizados e idempotência

Problem Details (RFC 9457)

Cada API inventar seu formato de erro obriga o consumidor a escrever um tratamento por fornecedor. A RFC 9457, que substituiu a RFC 7807, define um formato padrão com o tipo de mídia application/problem+json.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.exemplo-saude.com.br/erros/horario-indisponivel",
  "title": "Horário indisponível",
  "status": 422,
  "detail": "Não há agenda de cardiologia em 03/12/2026 às 14:00 na unidade u-12.",
  "instance": "/v1/consultas",
  "trace_id": "4bf92f3577b34da6"
}
CampoUso
typeURI que identifica o tipo de erro; pode apontar para documentação
titleResumo legível do tipo, igual para todas as ocorrências
statusO código HTTP, repetido no corpo
detailExplicação desta ocorrência
instanceIdentifica esta ocorrência específica
extensõesCampos próprios, como trace_id ou lista de erros de validação
Armadilha comum

Devolver stack trace, SQL ou nome de tabela no detail. Ajuda o atacante e pode expor dados. Mostre uma mensagem útil e um trace_id; o detalhe técnico fica no log interno.

Idempotência

Uma operação é idempotente quando repeti-la produz o mesmo efeito no servidor que executá-la uma vez. Isso importa porque redes falham: o cliente envia, o servidor processa, a resposta se perde, e o cliente não sabe se deu certo.

MétodoIdempotente pela especificação?Comentário
GET, HEADSim (e seguros: não alteram estado)Pode repetir à vontade
PUTSimSubstituir pelo mesmo conteúdo duas vezes dá o mesmo resultado
DELETESimO efeito é o mesmo; o status da segunda chamada pode ser 404
POSTNãoRepetir pode criar dois agendamentos ou duas cobranças
PATCHNão garantidoDepende da operação: "somar 1" não é idempotente

Chave de idempotência

Para tornar um POST seguro de repetir, o cliente gera um identificador único por operação e envia num cabeçalho. O padrão foi popularizado por APIs de pagamento e está em padronização na IETF como cabeçalho Idempotency-Key (ainda rascunho).

POST /v1/cobrancas HTTP/1.1
Idempotency-Key: 6f1c2a9e-3b7d-4e21-9a55-0c8f2d1b7e40
Content-Type: application/json

{"paciente": "p-30551", "valor_centavos": 25000}
  1. Primeira chamada. O servidor grava a chave junto com o resultado da operação, de forma atômica.
  2. Repetição com a mesma chave. O servidor devolve o resultado guardado, sem executar de novo.
  3. Mesma chave com corpo diferente. Erro, pois indica bug no cliente.
  4. Expiração. As chaves ficam guardadas por um período definido e documentado.
Na entrevista

"Erros no formato Problem Details, RFC 9457. GET, PUT e DELETE são idempotentes, POST não; para POST com efeito financeiro ou clínico uso chave de idempotência, que permite retry sem duplicar a operação."

Para gestores

Cobrança duplicada e agendamento duplicado são incidentes caros e visíveis para o paciente. Exija chave de idempotência em toda operação que cria algo com efeito financeiro ou clínico, e um teste automatizado que repete a chamada e confirma que nada duplicou.

Versionamento, compatibilidade e documentação

O que quebra e o que não quebra

Compatível (não quebra)Incompatível (breaking change)
Adicionar campo opcional na respostaRemover ou renomear campo
Adicionar endpoint novoMudar tipo de um campo (número para string)
Adicionar parâmetro opcionalTornar obrigatório um parâmetro que era opcional
Aceitar novos valores de entradaMudar o significado de um status ou de um campo
Adicionar valor novo num enum que o cliente trata de forma fechada (depende do cliente: documente que enums podem crescer)

Do lado do consumidor vale o princípio do leitor tolerante (tolerant reader): ignorar campos desconhecidos em vez de falhar. Isso permite ao provedor evoluir sem nova versão.

Onde colocar a versão

EstratégiaExemploPrósContras
Na URL/v1/consultasVisível, fácil de rotear e testar com curlA versão vale para a API inteira
Em cabeçalho próprioApi-Version: 2026-11-01URL estável; permite versão por dataMenos visível; precisa de padrão no gateway
No tipo de mídiaAccept: application/vnd.exemplo.v2+jsonAlinhado à negociação de conteúdo do HTTPMais difícil de usar e de documentar

A versão na URL é a mais comum e a mais simples de explicar. O mais importante é escolher uma estratégia e manter. Nova versão maior só para breaking change; o resto evolui de forma compatível.

Documentação com OpenAPI

OpenAPI é uma especificação para descrever APIs HTTP em YAML ou JSON: rotas, parâmetros, esquemas, respostas e autenticação. Swagger é o nome antigo da especificação e hoje designa um conjunto de ferramentas em torno dela, como o Swagger UI, que gera a página interativa de documentação.

openapi: 3.1.0
info:
  title: API de Agenda
  version: 1.4.0
paths:
  /v1/consultas/{id}:
    get:
      summary: Busca uma consulta
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: string }
      responses:
        '200':
          description: Consulta encontrada
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Consulta' }
        '404':
          description: Não encontrada
          content:
            application/problem+json:
              schema: { $ref: '#/components/schemas/Problema' }

Há duas abordagens: design first, em que o contrato é escrito e revisado antes do código, e code first, em que o documento é gerado a partir de anotações no código. Design first favorece a conversa com consumidores; code first reduz divergência entre documento e implementação. Com OpenAPI se geram também clientes (SDKs), mocks e validações.

Testes de contrato

Testes de contrato verificam se provedor e consumidor continuam de acordo. Duas formas comuns: validar automaticamente as respostas reais contra o documento OpenAPI, e testes orientados pelo consumidor (consumer-driven), em que cada consumidor registra o que espera e o pipeline do provedor falha se uma mudança quebrar alguma dessas expectativas. Pact é a ferramenta mais conhecida desse segundo tipo.

Na entrevista

"Adicionar é compatível, remover ou mudar tipo quebra. Versiono na URL por simplicidade e só subo versão maior em breaking change. Documento em OpenAPI e uso testes de contrato para detectar quebras no pipeline, antes do consumidor."

Para gestores

Manter duas versões em paralelo custa: código, testes, monitoramento e suporte em dobro. Exija justificativa para cada versão maior nova e defina na política quanto tempo uma versão antiga é mantida. Documentação desatualizada gera chamado de suporte; ponha a validação do OpenAPI no pipeline para que ela não envelheça.

JWT, OAuth, escopos e contas de serviço estão no módulo 7; mTLS no módulo 4. Autenticação diz quem chama; a API ainda precisa checar se aquele cliente pode acessar aquele registro.

Rate limiting e 429

Rate limiting (limitação de taxa) protege a API de abuso e de clientes com bug, e reparte capacidade de forma justa. Quando o limite estoura, a resposta é 429 Too Many Requests, de preferência com Retry-After.

HTTP/1.1 429 Too Many Requests
Retry-After: 30
Content-Type: application/problem+json

{"type": "https://api.exemplo-saude.com.br/erros/limite", "title": "Limite de requisições excedido", "status": 429}

Muitas APIs também informam o consumo em cabeçalhos como X-RateLimit-Limit e X-RateLimit-Remaining. Esses nomes são convenção de mercado; há um rascunho na IETF para padronizar cabeçalhos RateLimit. Algoritmos comuns: janela fixa, janela deslizante e token bucket (balde de fichas, que permite rajadas curtas dentro de uma média).

Timeouts

Toda chamada de rede precisa de timeout. Sem ele, uma dependência lenta prende threads e conexões até derrubar quem chama, e a falha se espalha em cascata. Defina timeout de conexão e de resposta, e um prazo total coerente com o que o seu próprio cliente espera.

Retries com backoff exponencial

  • Quando repetir: timeout, erro de conexão, 429, 502, 503, 504. Respeite Retry-After quando vier.
  • Quando não repetir: 400, 401, 403, 404, 422. Repetir não muda o resultado.
  • O que repetir: só operações idempotentes ou protegidas por chave de idempotência.
  • Limites: poucas tentativas, teto na espera e orçamento total de tempo. Retries em várias camadas se multiplicam: 3 tentativas em 3 camadas viram até 27 chamadas na ponta.
  • Circuit breaker (disjuntor): depois de muitas falhas seguidas, o cliente para de chamar por um tempo e falha rápido, dando fôlego à dependência.
async function comRetry(fn, { tentativas = 4, baseMs = 500, tetoMs = 8000 } = {}) {
  for (let i = 0; ; i++) {
    try {
      return await fn();
    } catch (err) {
      const repetivel = err.timeout || [429, 502, 503, 504].includes(err.status);
      if (!repetivel || i === tentativas - 1) throw err;
      const exp = Math.min(tetoMs, baseMs * 2 ** i);
      const espera = err.retryAfterMs ?? Math.random() * exp;   // "full jitter"
      await new Promise((r) => setTimeout(r, espera));
    }
  }
}
Na entrevista

"Toda chamada tem timeout. Retry só em falhas transitórias e operações idempotentes, com backoff exponencial, jitter, limite de tentativas e respeito ao Retry-After. Do lado do servidor, rate limiting com 429."

Para gestores

Muitos incidentes graves nascem de retries mal configurados: uma dependência fica lenta, todos repetem ao mesmo tempo e a sobrecarga impede a recuperação. Peça que timeouts e políticas de retry sejam configuração revisada, não valor padrão da biblioteca. Para parceiros externos, publique limites de uso no contrato e ofereça planos diferentes se necessário.

7Avançado

Webhooks e estilos de API

Webhooks

Em vez de o consumidor perguntar a cada minuto "tem novidade?" (polling), o provedor chama uma URL do consumidor quando algo acontece. Isso é um webhook: uma requisição HTTP, normalmente POST, enviada pelo provedor.

POST /webhooks/resultados HTTP/1.1
Host: integracao.exemplo-saude.com.br
Content-Type: application/json
X-Evento-Id: evt_01JD3K9W
X-Assinatura: t=1795600500,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd

{"tipo": "resultado.disponivel", "exame": "ex-55102", "ocorrido_em": "2026-11-25T09:55:00Z"}

Boas práticas para quem recebe:

  • Verificar a assinatura HMAC do corpo com o segredo compartilhado e rejeitar timestamps antigos, para impedir falsificação e reenvio.
  • Responder 2xx rápido e processar de forma assíncrona (fila).
  • Tratar duplicatas pelo ID do evento: provedores reenviam quando não recebem confirmação.
  • Não depender da ordem de chegada.
  • Preferir payload mínimo ("resultado disponível, ID tal") e buscar o detalhe pela API autenticada, o que reduz dado sensível trafegando.
import crypto from 'node:crypto';

function assinaturaValida(corpoBruto, cabecalho, segredo) {
  const { t, v1 } = Object.fromEntries(cabecalho.split(',').map((p) => p.split('=')));
  if (Math.abs(Date.now() / 1000 - Number(t)) > 300) return false;   // mais de 5 min: rejeita
  const esperado = crypto.createHmac('sha256', segredo).update(`${t}.${corpoBruto}`).digest('hex');
  const a = Buffer.from(esperado), b = Buffer.from(v1 || '');
  return a.length === b.length && crypto.timingSafeEqual(a, b);    // comparação em tempo constante
}

Quem envia precisa de retries com backoff, registro das entregas, forma de o consumidor reenviar eventos perdidos e rotação do segredo.

Regra de bolso

Parceiro externo: REST com webhooks. Entre microsserviços internos com alto volume: gRPC. Tela que agrega muitos dados: considere GraphQL ou um BFF. Servidor avisando o navegador: SSE; conversa nos dois sentidos: WebSocket.

Na entrevista

"Escolho pelo consumidor e pelo padrão de comunicação. REST para APIs públicas, gRPC entre serviços internos, GraphQL quando o front precisa compor dados variados, SSE ou WebSocket para tempo real. Para eventos entre empresas, webhooks assinados e idempotentes."

Para gestores

Cada estilo novo traz ferramentas, monitoramento, segurança e curva de aprendizado. Adotar GraphQL ou gRPC "porque é moderno" sem um problema concreto aumenta o custo de manutenção. Peça um registro de decisão de arquitetura (ADR) com o problema, as alternativas e o custo operacional.

8Avançado

API gateway, ferramentas e API como produto

API gateway

O API gateway é a porta de entrada única para as APIs. Ele concentra funções que se repetiriam em cada serviço:

  • Terminação TLS e roteamento para o serviço certo.
  • Validação de token e de chave de API.
  • Rate limiting e cotas por cliente.
  • Logs, métricas e rastreamento centralizados.
  • Transformações simples e publicação do portal do desenvolvedor.

Exemplos: Kong, Apigee, AWS API Gateway, Azure API Management. O gateway não substitui a autorização no serviço: ele sabe quem chama, mas não sabe se aquele médico pode ver aquele paciente.

Ferramentas

curl está em qualquer servidor e é o idioma comum para reproduzir problemas. Postman e Insomnia são clientes gráficos com coleções, variáveis por ambiente e testes automatizados.

# GET com token, mostrando cabeçalhos de resposta
curl -i https://api.exemplo-saude.com.br/v1/consultas?limit=5 \
  -H "Authorization: Bearer $TOKEN"

# POST com JSON e chave de idempotência
curl -X POST https://api.exemplo-saude.com.br/v1/consultas \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"especialidade": "cardiologia", "inicio": "2026-12-03T14:00:00-03:00"}'
Armadilha comum

Coleções do Postman compartilhadas com tokens e segredos reais salvos nas variáveis. Elas acabam em espaços públicos ou com ex-funcionários. Use variáveis locais e cofre de segredos.

API como produto

Tratar a API como produto significa pensar no consumidor como cliente: ele precisa descobrir, entender, testar, integrar e confiar.

  • Experiência do desenvolvedor: documentação com exemplos, ambiente de testes (sandbox), guia de início rápido, changelog.
  • Compromissos claros: SLA (acordo de nível de serviço), limites de uso, política de versões e de depreciação.
  • Métricas: quem usa cada endpoint e versão, latência, taxa de erro por consumidor, tempo até a primeira chamada bem-sucedida de um parceiro novo.

Governança

Governança de APIs é o conjunto de padrões e processos que mantém dezenas de APIs coerentes: guia de estilo, revisão de design antes da implementação, lint automático do OpenAPI, catálogo central de APIs com dono de cada uma, e critérios de segurança obrigatórios.

Depreciação e comunicação com consumidores

  1. Anunciar. Changelog, e-mail aos contatos técnicos, portal. Data de desligamento definida com antecedência combinada em contrato.
  2. Sinalizar na própria API. Cabeçalhos Deprecation (RFC 9745) e Sunset (RFC 8594) informam que o endpoint está depreciado e quando sai do ar.
  3. Medir. Acompanhar quem ainda chama a versão antiga, por cliente, e contatar diretamente.
  4. Desligar. Na data, com plano de reversão. Algumas empresas fazem indisponibilidades curtas programadas antes (brownouts) para revelar consumidores esquecidos.

Para gestores

Uma política de depreciação escrita evita a reclamação mais comum de parceiros: "mudou sem aviso". Defina prazo mínimo de aviso, canais de comunicação, quem aprova breaking changes e como medir quem ainda usa a versão antiga. Mantenha uma lista de contatos técnicos por consumidor; sem ela, não há como avisar ninguém.

Cenários práticos

1. Um parceiro reclama que a API mudou sem aviso

O laboratório parceiro parou de importar agendamentos: o campo data virou inicio num deploy da semana passada.

  • Agora: restaurar o campo antigo (devolvendo os dois por um período) para destravar o parceiro.
  • Causa: breaking change sem nova versão e sem teste de contrato.
  • Prevenção: validação do OpenAPI e testes de contrato no pipeline; detecção automática de breaking change comparando versões do documento; política de depreciação com prazo e canais.
  • Gestão: comunicar o parceiro com transparência, registrar post-mortem e criar lista de contatos técnicos por consumidor.

2. Pacientes cobrados em dobro

Num pico de lentidão, o app repetiu POSTs de pagamento que tinham dado timeout, e o servidor processou as duas chamadas.

  • Estornar e comunicar os afetados.
  • Implantar Idempotency-Key no endpoint de cobrança e gerar a chave no app uma vez por intenção de pagamento.
  • Revisar a política de retry do app: só com chave, com backoff e limite.

3. Um cliente derruba a API

Uma integração com bug chama a listagem em loop, milhares de vezes por segundo, e degrada o atendimento de todos.

  • Imediato: bloquear ou limitar aquele cliente no gateway.
  • Estrutural: rate limit por cliente com 429 e Retry-After, cotas no contrato, alertas de consumo anormal.

4. A listagem de atendimentos ficou lenta

A integração de faturamento lê todos os atendimentos do mês com offset, e as últimas páginas levam dezenas de segundos.

  • Migrar para paginação por cursor sobre uma coluna indexada.
  • Para sincronização, oferecer filtro por data de alteração (alterado_desde) e, se fizer sentido, webhooks de alteração.

5. O time quer trocar REST por GraphQL

  • Pergunta de gestor: qual problema concreto isso resolve? Excesso de chamadas no app? Campos demais nas respostas?
  • Alternativas mais baratas: um BFF para o app, ou endpoints compostos.
  • Se a decisão for adotar, registrar ADR, prever limites de custo de consulta, autorização por campo e monitoramento.

Perguntas de entrevista

01O que torna uma API "REST"?

Recursos identificados por URI, manipulados por métodos HTTP com semântica padrão, comunicação sem estado de sessão no servidor, representações negociadas (em geral JSON) e uso correto de status. HATEOAS é parte do estilo original, mas raramente aplicado no mercado.

02Qual a diferença entre PUT e PATCH?

PUT substitui o recurso inteiro pela representação enviada e é idempotente. PATCH aplica uma alteração parcial e não é garantidamente idempotente, porque depende da operação descrita.

03O que é idempotência e como tornar um POST seguro para retry?

Idempotência é repetir a operação e obter o mesmo efeito de uma execução. POST não é idempotente; o cliente envia uma chave única no cabeçalho Idempotency-Key, o servidor guarda a chave com o resultado e, numa repetição, devolve o resultado guardado sem executar de novo.

04Offset ou cursor para paginação?

Offset é simples e permite pular para qualquer página, mas fica lento em páginas altas e repete ou pula itens se houver inserções. Cursor usa índice, tem custo estável e é consistente; serve melhor para integrações, feeds e grandes volumes.

05Como você padroniza erros numa API?

Uso Problem Details (RFC 9457), com application/problem+json e os campos type, title, status, detail e instance, mais um trace_id para correlacionar com logs. Status HTTP corretos e nada de stack trace na resposta.

06O que é uma breaking change? Dê exemplos.

Uma mudança que quebra consumidores existentes: remover ou renomear campo, mudar tipo, tornar parâmetro obrigatório, mudar significado de um valor. Adicionar campo opcional ou endpoint novo é compatível, desde que os clientes ignorem campos desconhecidos.

07Como você versiona uma API?

Normalmente na URL (/v1), por ser explícito e fácil de rotear. Alternativas são cabeçalho próprio ou tipo de mídia. Só crio versão maior para breaking change, evoluo o resto de forma compatível e mantenho política de depreciação com prazos.

08Para que serve o OpenAPI?

Descreve a API de forma legível por máquina: rotas, parâmetros, esquemas, respostas e autenticação. A partir dele se gera documentação interativa, SDKs, mocks, validação de requisições e testes de contrato.

09Quando um cliente deve fazer retry e como?

Em falhas transitórias: timeout, erro de conexão, 429, 502, 503, 504. Só em operações idempotentes ou com chave de idempotência. Com backoff exponencial e jitter, limite de tentativas, respeito ao Retry-After e, se as falhas persistirem, circuit breaker.

10Como proteger um endpoint que recebe webhooks?

Verificar a assinatura HMAC do corpo com segredo compartilhado, comparando em tempo constante, e rejeitar timestamps antigos. Responder 2xx rápido, processar em fila, deduplicar pelo ID do evento e não depender da ordem de chegada.

11REST, GraphQL ou gRPC: quando usar cada um?

REST para APIs públicas e de parceiros, pela simplicidade e pelo cache HTTP. GraphQL quando clientes variados precisam compor dados de muitas fontes numa chamada. gRPC para comunicação interna entre serviços, com contrato tipado e eficiência. Para tempo real, SSE (só servidor para cliente) ou WebSocket (bidirecional).

12O que um API gateway faz e o que ele não deve fazer?

Centraliza TLS, roteamento, validação de credenciais, rate limiting, logs e métricas. Não deve concentrar regra de negócio nem substituir a autorização por registro, que depende de dados que só o serviço conhece.

13(Gestão) Como você evita que mudanças de API quebrem parceiros?

Contrato em OpenAPI revisado antes de implementar, testes de contrato e detecção automática de breaking change no pipeline, política escrita de versionamento e depreciação, cabeçalhos Deprecation e Sunset, métricas de uso por consumidor e lista de contatos técnicos para comunicação direta.

14(Gestão) O que significa tratar uma API como produto?

Ter dono, roadmap e consumidores tratados como clientes: documentação com exemplos, sandbox, SLA, limites claros, changelog, canal de suporte e métricas como adoção e tempo até a primeira integração bem-sucedida.

15(Gestão) Como você organizaria a governança de dezenas de APIs internas?

Guia de estilo curto, lint automático do OpenAPI no pipeline, catálogo central com dono de cada API, revisão de design para APIs novas ou breaking changes, requisitos mínimos de segurança e observabilidade, e revisão periódica das APIs sem uso para desligamento.

16Você conhece algum padrão de API específico da área de saúde?

O HL7 FHIR, que define recursos clínicos e administrativos como Patient e Observation expostos por uma API REST. No Brasil, a RNDS adota FHIR. Conhecer o padrão facilita integrações com laboratórios, operadoras e governo.
