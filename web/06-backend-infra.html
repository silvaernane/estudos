Back-end e infraestrutura web

As peças que ficam atrás da URL: proxies, balanceadores, cache, bancos, filas, deploy, nuvem e observabilidade. Para cada uma, o que ela resolve, o que custa e o que um gestor precisa cobrar do time.

Ao final você saberá
  • Desenhar uma arquitetura web típica com reverse proxy, load balancer, aplicação stateless, cache, banco e fila.
  • Escolher entre escalar vertical ou horizontalmente e explicar onde fica o estado.
  • Comparar monólito, monólito modular e microsserviços com honestidade.
  • Explicar CI/CD e estratégias de deploy (rolling, blue-green, canary, feature flags) e como fazer rollback.
  • Definir SLI, SLO e error budget, planejar RPO e RTO e conversar sobre custo de nuvem.
1Básico

Servidor web, servidor de aplicação e reverse proxy

Quando uma requisição HTTP (módulo 3) chega à sua infraestrutura, ela costuma passar por várias camadas antes de chegar ao código do time.

PeçaFunçãoExemplos
Servidor webFala HTTP, serve arquivos estáticos, termina TLS, comprime, encaminha requisiçõesNginx, Apache httpd, Caddy, IIS
Servidor de aplicaçãoExecuta o código da aplicação e gera respostas dinâmicasTomcat e WildFly (Java), Kestrel (.NET), Gunicorn e Uvicorn (Python), PHP-FPM, o próprio processo Node.js
Reverse proxyFica na frente dos servidores de aplicação e recebe as requisições em nome delesNginx, HAProxy, Envoy, Traefik

Um forward proxy age em nome do cliente (o proxy corporativo que controla o acesso dos funcionários à internet). Um reverse proxy age em nome do servidor: o cliente acha que fala com o site, mas fala com o proxy, que repassa ao servidor certo.

O que um reverse proxy resolve

  • Terminação TLS: os certificados (módulo 4) ficam num ponto só.
  • Roteamento: /api vai para um serviço, / para outro.
  • Estáticos e compressão: serve arquivos e comprime respostas sem ocupar a aplicação.
  • Proteção: limite de taxa (rate limiting), limites de tamanho de corpo, esconder a topologia interna.
  • Buffering: absorve clientes lentos para que a aplicação não fique presa esperando.
upstream app {
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
}
server {
    listen 443 ssl;
    server_name portal.clinica.com.br;
    location /static/ { root /srv; expires 30d; }
    location / {
        proxy_pass http://app;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
Armadilha comum

Atrás de um proxy, a aplicação vê o IP do proxy como cliente. O IP real vem em cabeçalhos como X-Forwarded-For, que o próprio cliente pode forjar. Configure a aplicação para confiar nesse cabeçalho só quando ele vier dos seus proxies.

Na entrevista

"O servidor web fala HTTP e serve estáticos; o servidor de aplicação executa o código. O reverse proxy fica na frente, termina TLS, roteia, comprime e protege, e o cliente não enxerga os servidores internos."

2Intermediário

Load balancer

Um load balancer (balanceador de carga) distribui requisições entre várias instâncias da aplicação. Ele permite crescer adicionando máquinas e tirar do caminho uma instância com problema.

Camada 4 x camada 7

Camada 4 (transporte)Camada 7 (aplicação)
EnxergaIP, porta, conexão TCP ou UDPHTTP completo: método, caminho, host, cabeçalhos, cookies
Decide porConexãoRequisição
Pode fazerEncaminhar com pouquíssima sobrecarga, qualquer protocoloRotear por caminho ou host, terminar TLS, reescrever cabeçalhos, retentar, aplicar regras de WAF
ExemplosAWS NLB, HAProxy em modo TCP, LVSAWS ALB, Nginx, HAProxy em modo HTTP, Envoy, Azure Application Gateway

As camadas aqui são as do modelo OSI, vistas no módulo 1.

Algoritmos

AlgoritmoComo escolheBom quando
Round robinUm de cada vez, em rodízioInstâncias iguais e requisições parecidas
Round robin ponderadoRodízio proporcional a pesosInstâncias de tamanhos diferentes
Menos conexões (least connections)A instância com menos conexões ativasRequisições de duração muito variável
Menor tempo de respostaA instância mais rápida recentementeDesempenho desigual entre instâncias

Health checks

O balanceador testa periodicamente cada instância (por exemplo, GET /health) e tira do rodízio as que falham. Em Kubernetes há dois conceitos separados: liveness (o processo está vivo ou precisa ser reiniciado?) e readiness (está pronto para receber tráfego agora?).

Armadilha comum

Um health check que consulta o banco parece completo, mas se o banco ficar lento todas as instâncias falham ao mesmo tempo e o balanceador tira todas do ar. O check de readiness deve refletir se a instância consegue atender; dependências compartilhadas merecem alerta próprio.

Sticky sessions e por que evitar

Sticky session (afinidade de sessão) prende cada usuário a uma instância, normalmente por um cookie do balanceador. Ela existe para aplicações que guardam a sessão na memória do servidor. Os problemas: a carga fica desigual, quando a instância cai os usuários dela perdem a sessão, e deploys e autoscaling ficam mais difíceis. A solução é tirar o estado da instância (próxima seção).

Na entrevista

"Balanceador de camada 4 decide por conexão olhando IP e porta; o de camada 7 entende HTTP e roteia por caminho, host ou cabeçalho. Uso health checks para tirar instâncias doentes e evito sticky session deixando a aplicação stateless."

Para gestores

O balanceador é ponto único de falha se houver um só. Em nuvem, balanceadores gerenciados já são distribuídos entre zonas; em data center próprio, pergunte como está a redundância dele. Pergunte também o que o health check verifica de fato.

3Intermediário

Aplicação stateless e escalabilidade

Uma aplicação stateless (sem estado) não guarda nada entre requisições na memória ou no disco local da instância. Qualquer instância atende qualquer requisição. O estado continua existindo, só que fora das instâncias:

  • Dados de negócio: no banco de dados.
  • Sessão: num armazenamento compartilhado (Redis, banco) ou no próprio cliente em token assinado (módulo 7).
  • Arquivos enviados: em armazenamento de objetos (S3, Azure Blob, GCS), não no disco da instância.
  • Trabalho em andamento: numa fila.

Vertical x horizontal

Vertical (scale up)Horizontal (scale out)
O que éMáquina maior: mais CPU, memória, discoMais máquinas iguais atrás de um balanceador
VantagemSimples, nenhuma mudança no códigoSem teto prático, tolera falha de instância, permite autoscaling
LimiteTamanho máximo da máquina; custo cresce rápido no topo; continua um ponto único de falhaExige aplicação stateless; complexidade de rede, deploy e observabilidade
Típico paraBancos relacionais, sistemas legadosCamada de aplicação web

Autoscaling ajusta o número de instâncias por métrica (CPU, requisições, tamanho de fila). Ele costuma levar minutos para reagir; picos muito bruscos pedem capacidade mínima já provisionada.

Regra de bolso

A camada de aplicação escala horizontalmente com facilidade. O gargalo costuma migrar para o banco, que é a parte difícil de escalar. Antes de multiplicar instâncias, olhe as consultas.

Na entrevista

"Stateless significa que a instância não guarda estado entre requisições: sessão vai para Redis ou token, arquivos para armazenamento de objetos, dados para o banco. Isso permite escalar horizontalmente e trocar instâncias sem perder nada."

Para gestores

Escalar vertical é a decisão mais barata em engenharia e a mais cara em infraestrutura no longo prazo. Ganhar tempo com uma máquina maior é legítimo, desde que exista um plano para o próximo limite. Peça teste de carga antes de eventos previsíveis de pico, como campanhas de vacinação ou abertura de agenda.

4Intermediário

Cache em camadas e CDN

Cache é guardar uma resposta pronta para não recalcular nem buscar de novo. Numa aplicação web ele aparece em várias camadas, cada uma mais perto do usuário que a seguinte.

CamadaO que guardaControlado porCuidado
NavegadorEstáticos, às vezes respostas de APICabeçalhos HTTP (módulo 3)Difícil de invalidar: você não alcança o disco do usuário
CDNEstáticos e páginas públicas, perto do usuárioCabeçalhos e regras da CDNNunca cachear resposta personalizada como se fosse pública
Reverse proxyRespostas inteirasConfiguração do proxyMesma regra da CDN
Aplicação (Redis, Memcached)Resultados de consultas, objetos calculados, sessõesCódigo da aplicaçãoInvalidação e consistência
BancoPáginas de dados em memória, planos de consultaO próprio bancoMemória insuficiente derruba o desempenho

Padrões e invalidação

  • Cache-aside: a aplicação procura no cache; se não acha, busca no banco e grava no cache. É o padrão mais comum.
  • TTL (time to live): o item expira depois de um tempo. Simples e tolera dado levemente desatualizado.
  • Invalidação explícita: ao alterar o dado, apaga ou atualiza a chave. Mais atual, mais fácil de esquecer um caminho.
  • Nomes versionados: para estáticos, um hash no nome do arquivo dispensa invalidação.
async function buscarAgenda(medicoId) {
  const chave = 'agenda:' + medicoId;
  const emCache = await redis.get(chave);
  if (emCache) return JSON.parse(emCache);
  const agenda = await db.agendaDoMedico(medicoId);
  await redis.set(chave, JSON.stringify(agenda), { EX: 60 }); // 60 s
  return agenda;
}
Armadilha comum

Cache stampede (efeito manada): uma chave popular expira e centenas de requisições vão ao banco ao mesmo tempo. Mitigações: TTL com variação aleatória, uma única requisição recalcula enquanto as outras esperam ou recebem o valor antigo, renovação antes de expirar.

CDN

Uma CDN (Content Delivery Network, rede de distribuição de conteúdo) mantém servidores em muitos pontos de presença pelo mundo. O usuário é direcionado ao ponto mais próximo, normalmente por DNS ou anycast (módulo 2), e recebe de lá o conteúdo em cache. Além de latência menor, a CDN absorve picos e ataques volumétricos antes que cheguem à origem. Exemplos: Cloudflare, Akamai, Amazon CloudFront, Azure Front Door, Fastly.

Na entrevista

"Cache existe em camadas: navegador, CDN, proxy, aplicação com Redis e o próprio banco. O difícil é invalidar. Uso TTL quando tolero dado um pouco velho, invalidação explícita quando não tolero, e hash no nome para estáticos."

Para gestores

Cache mal configurado em sistema de saúde pode mostrar dados de um paciente para outro. Exija revisão específica de qualquer regra de cache em CDN ou proxy que envolva rotas autenticadas. Pergunte também: se o cache cair, o banco aguenta a carga sozinho?

5Intermediário

Bancos de dados e filas

Relacional x NoSQL

Aqui o banco aparece no papel de arquitetura; SQL em detalhe está no guia de SQL.

TipoExemplosForte emAtenção
RelacionalPostgreSQL, Oracle, SQL Server, MySQLTransações ACID, integridade referencial, consultas flexíveis com junçõesEscala de escrita horizontal exige particionamento ou soluções específicas
DocumentoMongoDB, CouchbaseEsquema flexível, leitura de agregados inteirosJunções e transações entre documentos são mais limitadas ou caras
Chave-valorRedis, DynamoDBAcesso muito rápido por chave, cache, sessãoConsultas além da chave são pobres
Colunar largoCassandraGrande volume de escrita distribuídaModelagem guiada pelas consultas; consistência configurável
BuscaElasticsearch, OpenSearchTexto livre, filtros, agregaçõesNão deve ser a fonte da verdade

Réplicas de leitura aliviam o primário em sistemas com muita leitura, com a ressalva de que a réplica pode estar um pouco atrasada (replication lag). Em sistemas distribuídos, quando a rede se parte, o sistema precisa escolher entre responder com dado possivelmente desatualizado ou recusar a resposta; essa tensão é o que o teorema CAP descreve.

Regra de bolso

Comece com um banco relacional, a não ser que exista um padrão de acesso claro que ele atende mal. Dados clínicos, financeiros e de faturamento pedem transações e integridade.

Filas e processamento assíncrono

Uma fila desacopla quem produz trabalho de quem o executa. A requisição do usuário grava uma mensagem e responde logo; um worker processa depois.

  • Tempo de resposta: gerar PDF de laudo, enviar e-mail, integrar com operadora de saúde saem da requisição.
  • Absorção de picos: a fila cresce no pico e esvazia depois; os workers trabalham no próprio ritmo.
  • Resiliência: se o sistema de destino cair, as mensagens esperam em vez de se perder.
FerramentaModeloQuando faz sentido
RabbitMQBroker de mensagens com filas e roteamento flexível; a mensagem sai da fila ao ser confirmadaTarefas de trabalho, roteamento por tipo, integrações
Apache KafkaLog distribuído e particionado; mensagens ficam retidas por um período e podem ser relidasFluxos de eventos de alto volume, vários consumidores independentes, reprocessamento
Amazon SQSFila gerenciada; tipo padrão (entrega ao menos uma vez, ordem aproximada) ou FIFOQuem já está na AWS e quer zero operação
Armadilha comum

A maioria dos sistemas de fila entrega ao menos uma vez: a mesma mensagem pode chegar duas vezes. O consumidor precisa ser idempotente (processar duas vezes tem o mesmo efeito de processar uma), por exemplo registrando o ID da mensagem já processada. Mensagens que falham repetidamente vão para uma DLQ (dead-letter queue), que alguém precisa monitorar.

Na entrevista

"Uso relacional por padrão pela integridade e transações, e NoSQL quando o padrão de acesso pede. Uso fila para tirar trabalho lento da requisição e absorver picos; como a entrega costuma ser ao menos uma vez, o consumidor precisa ser idempotente e as falhas vão para uma DLQ monitorada."

Para gestores

Cada banco ou fila novo é mais uma coisa para operar, fazer backup, atualizar e proteger. Pergunte quem vai operar e se o time tem experiência. Exija alerta para tamanho de fila e idade da mensagem mais antiga: fila crescendo em silêncio é incidente adiado.

Monólito, monólito modular e microsserviços

MonólitoMonólito modularMicrosserviços
Unidade de deployUmaUmaVárias, independentes
Fronteiras internasMuitas vezes fracasMódulos com interfaces explícitas e dados separados por móduloRede entre serviços; cada um com seus dados
TransaçõesLocais, simplesLocais, simplesDistribuídas; exigem sagas, eventos, consistência eventual
OperaçãoSimplesSimplesExige plataforma madura: CI/CD por serviço, observabilidade distribuída, descoberta de serviços
Escala de timesTimes grandes se atrapalhamBom até muitos times com disciplinaTimes autônomos com deploy independente
FalhasUm bug pode derrubar tudoIdemFalhas parciais, latência de rede, versões incompatíveis entre serviços

Microsserviços resolvem principalmente um problema organizacional: permitir que muitos times entreguem de forma independente. Eles trazem custos técnicos reais: rede onde antes havia chamada de função, consistência eventual, depuração entre serviços, mais infraestrutura. Uma divisão ruim gera um monólito distribuído, com os acoplamentos do monólito e os custos dos microsserviços.

O monólito modular é um meio-termo muito usado: um só deploy, com módulos separados por domínio, que conversam por interfaces e não acessam as tabelas uns dos outros. Se um dia um módulo precisar virar serviço, a fronteira já existe.

Regra de bolso

Extraia um serviço quando houver motivo concreto: um time precisa de deploy independente, uma parte tem necessidade de escala ou de tecnologia muito diferente, ou um requisito de isolamento (por exemplo, dados sensíveis num perímetro menor).

Na entrevista

"Microsserviços trocam complexidade de código por complexidade de operação e de dados distribuídos. Valem quando vários times precisam entregar de forma independente e há plataforma para sustentar. Na maioria dos casos eu começaria com um monólito modular bem dividido."

Para gestores

A lei de Conway diz que a arquitetura tende a espelhar a estrutura de comunicação da organização. Com três desenvolvedores, vinte microsserviços significam que cada pessoa opera sete sistemas. Pergunte qual problema de entrega a mudança resolve e se o time tem CI/CD, observabilidade e plantão maduros. Sem isso, a migração piora a confiabilidade.

Armadilha comum

Copiar a base de produção para homologação com dados reais de pacientes. Isso espalha dado sensível para um ambiente com controles mais fracos e mais pessoas com acesso. Use dados sintéticos ou anonimizados.

CI/CD

Integração contínua (CI): a cada mudança, o código é compilado e testado automaticamente. Entrega contínua (continuous delivery): todo build aprovado está pronto para ir a produção com um clique. Implantação contínua (continuous deployment): vai sozinho, sem clique.

commit -> build -> testes unitários -> análise estática e de dependências
       -> imagem de container versionada -> deploy em homologação
       -> testes de integração e smoke -> aprovação -> deploy em produção
       -> verificação automática de métricas -> (rollback se piorar)

Estratégias de deploy

EstratégiaComo funcionaVantagemCusto
RecreateDerruba a versão antiga e sobe a novaSimplesIndisponibilidade durante a troca
RollingTroca as instâncias aos poucosSem indisponibilidade, sem infra extraDuas versões convivem; rollback também é gradual
Blue-greenSobe o ambiente novo inteiro ao lado do antigo e vira o tráfego de uma vezRollback instantâneo: volta o tráfegoDobro de infraestrutura durante a troca
CanaryManda uma fração pequena do tráfego para a versão nova e aumenta se as métricas forem boasProblema atinge poucos usuáriosExige métricas confiáveis e roteamento por porcentagem
Feature flagsO código novo vai a produção desligado e é ativado por configuração, para todos ou para um grupoSepara deploy de lançamento; desliga sem novo deployFlags acumuladas viram dívida e caminhos de código difíceis de testar

Rollback e banco de dados

O código volta fácil; o esquema do banco não. A técnica expand/contract (expandir e contrair) mantém as duas versões compatíveis: primeiro adiciona a coluna nova sem remover a antiga, faz o deploy do código que escreve nas duas, migra os dados e só num deploy posterior remove a antiga. Assim qualquer versão do código pode rodar com o esquema atual e o rollback não quebra.

Na entrevista

"Rolling troca instâncias aos poucos; blue-green sobe tudo ao lado e vira o tráfego, com rollback instantâneo; canary manda uma fração pequena para a versão nova e promove conforme as métricas; feature flags separam deploy de lançamento. Para o banco uso migrações compatíveis com as duas versões."

Para gestores

As métricas DORA são uma boa base para medir entrega: frequência de deploy, lead time de mudanças, taxa de falha de mudanças e tempo de recuperação. Deploy pequeno e frequente com rollback fácil é mais seguro do que um deploy grande por mês. Defina antes do deploy qual sinal dispara o rollback e quem decide, para não discutir isso no meio do incidente. Faça a limpeza periódica de feature flags entrar no planejamento.

8Intermediário

Cloud: modelos, regiões e responsabilidade

ModeloVocê gerenciaO provedor gerenciaExemplos
IaaSSistema operacional, runtime, aplicação, dadosHardware, rede física, virtualizaçãoMáquinas virtuais (EC2, Azure VM, Compute Engine)
PaaSAplicação e dadosTambém SO, runtime, escalaAzure App Service, Heroku, bancos gerenciados (RDS, Cloud SQL)
Serverless (FaaS)Código das funções e dadosTudo o mais, inclusive escalar a zeroAWS Lambda, Azure Functions, Cloud Run
SaaSConfiguração, usuários e dados que você colocaO software inteiroMicrosoft 365, Salesforce, sistemas de gestão hospitalar em nuvem

Serverless cobra por execução e escala sozinho, o que é ótimo para carga irregular. Os custos são partida a frio (cold start), limites de tempo de execução, dependência maior do provedor e custo que pode superar o de servidores fixos sob carga alta e constante.

Regiões e zonas de disponibilidade

Uma região é uma área geográfica (por exemplo, São Paulo) com vários data centers. Uma zona de disponibilidade (availability zone) é um ou mais data centers isolados dentro da região, com energia e rede independentes, ligados às outras zonas por conexões de baixa latência. Distribuir instâncias em várias zonas protege contra a queda de um data center; usar várias regiões protege contra a queda de uma região inteira, com custo e complexidade bem maiores.

Modelo de responsabilidade compartilhada

O provedor responde pela segurança da nuvem (instalações, hardware, virtualização). O cliente responde pela segurança na nuvem (configuração, identidades e permissões, dados, criptografia, aplicação). A fronteira se desloca conforme o modelo: em IaaS você corrige o sistema operacional; em SaaS, não. Em nenhum modelo o provedor configura por você quem tem acesso aos seus dados.

Armadilha comum

Boa parte dos vazamentos em nuvem vem de configuração do cliente: bucket público, chave de acesso em repositório, porta de banco aberta para a internet, permissões amplas demais. Ferramentas de postura de segurança (CSPM) e políticas automatizadas ajudam a pegar isso. Detalhes no módulo 10.

Na entrevista

"Em IaaS eu cuido do sistema operacional para cima; em PaaS, da aplicação e dos dados; em SaaS, da configuração e do acesso. O provedor protege a infraestrutura e eu protejo o que coloco nela. Para alta disponibilidade distribuo entre zonas de uma região."

Para gestores

A escolha de região tem efeito em latência, custo e requisitos legais. Para dados de saúde, envolva jurídico e encarregado de dados (DPO) antes de usar regiões fora do Brasil, por causa das regras de transferência internacional da LGPD. Prefira serviços gerenciados quando o time é pequeno: o custo da fatura costuma ser menor que o custo de operar.

9Avançado

Observabilidade, SLI, SLO e error budget

Observabilidade é a capacidade de entender o que acontece dentro do sistema a partir do que ele emite. Monitoramento responde "algo conhecido quebrou?"; observabilidade ajuda a responder "por que isso está acontecendo?", inclusive em falhas que ninguém previu.

SinalO que éRespondeExemplos de ferramenta
LogsRegistros de eventos com contexto, de preferência estruturados (JSON)O que aconteceu nesta requisição?ELK/OpenSearch, Loki, Splunk, CloudWatch Logs
MétricasNúmeros agregados ao longo do tempoComo o sistema está agora e qual a tendência?Prometheus, Grafana, Datadog, Azure Monitor
TracesO caminho de uma requisição entre serviços, com o tempo de cada trechoOnde o tempo foi gasto?Jaeger, Tempo, Zipkin, ferramentas de APM

O OpenTelemetry é o padrão aberto, mantido pela CNCF, para instrumentar aplicações e gerar logs, métricas e traces num formato comum. Instrumentar com ele reduz a dependência de um fornecedor específico de monitoramento.

 "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","rota":"POST /consultas",
 "status":500,"duracao_ms":1840,"erro":"timeout ao consultar convênio"}
Armadilha comum

Logar dado pessoal: CPF, nome de paciente, diagnóstico, token. Logs são copiados para muitos sistemas e ficam acessíveis a muita gente. Defina campos proibidos e mascare na origem.

Os sinais de ouro

O livro de SRE do Google propõe quatro sinais para monitorar qualquer serviço voltado ao usuário: latência (tempo de resposta, separando sucesso de erro), tráfego (demanda, como requisições por segundo), erros (taxa de falhas) e saturação (quão cheio está o recurso mais limitado). Para latência, use percentis (p95, p99); a média esconde os usuários que esperam muito.

SLI, SLO, SLA e error budget

TermoO que éExemplo
SLI (indicador)Medida da qualidade do serviço do ponto de vista do usuárioProporção de requisições de agendamento respondidas com sucesso em menos de 500 ms
SLO (objetivo)Meta interna para o SLI num período99,9% em janela de 30 dias
SLA (acordo)Compromisso contratual com cliente, com penalidade99,5% ao mês, com desconto se não cumprir
Error budgetO quanto se pode falhar sem violar o SLO: 100% menos o SLO0,1% de 30 dias, cerca de 43 minutos

Conta de referência: 30 dias têm 43.200 minutos. 99,9% deixa cerca de 43 minutos de orçamento; 99,95%, cerca de 22 minutos; 99,99%, cerca de 4 minutos. Cada nove a mais custa bem mais em arquitetura e operação.

Regra de bolso

O SLO interno fica mais apertado que o SLA, para haver margem. Alerte sobre a velocidade de consumo do error budget (burn rate), não sobre cada pico de CPU.

Na entrevista

"Logs dizem o que aconteceu, métricas mostram tendência e traces mostram onde o tempo foi gasto; instrumento com OpenTelemetry. Monitoro latência, tráfego, erros e saturação. O SLO é a meta interna sobre um SLI, o SLA é o contrato, e o error budget é a margem de falha que equilibra velocidade e estabilidade."

Para gestores

O error budget transforma a discussão "entregar features ou estabilizar" num acordo objetivo: com orçamento sobrando, o time arrisca mais; com o orçamento estourado, prioriza confiabilidade. Combine essa política com o produto antes de precisar dela. Exija que alertas sejam acionáveis (cada alerta tem um runbook e uma ação) e acompanhe o volume de alertas por plantão: excesso de alerta gera fadiga e o alerta importante passa despercebido.

Alta disponibilidade, recuperação de desastres e custos

Alta disponibilidade (HA) é continuar funcionando quando uma parte falha: várias instâncias, várias zonas, banco com réplica e failover automático, nenhum ponto único de falha. Recuperação de desastres (DR) é voltar a funcionar depois de uma falha grande: perda de região, corrupção de dados, ransomware, exclusão acidental.

Backups

  • Regra 3-2-1: três cópias dos dados, em dois tipos de mídia, uma fora do local principal. Contra ransomware, mantenha também uma cópia imutável ou isolada.
  • Backup que nunca foi restaurado não é confiável. Agende testes de restauração e meça o tempo real, que é o seu RTO de verdade.
  • Replicação não substitui backup: um DELETE errado é replicado em segundos.

Custos de nuvem e FinOps

FinOps é a prática de gerir custo de nuvem em conjunto entre engenharia, finanças e produto. A FinOps Foundation descreve um ciclo de três fases: informar (saber quem gasta o quê), otimizar (reduzir desperdício e negociar preço) e operar (tornar isso contínuo).

Na entrevista

"RPO é quanto dado posso perder; RTO é quanto tempo posso ficar fora. Eles definem a estratégia, de backup e restauração até ativo-ativo, e o custo. Backup só vale se a restauração for testada. Em custo de nuvem começo por tags, rightsizing e desligar o que está ocioso."

Para gestores

RPO e RTO são decisões de negócio: pergunte à área usuária quanto custa uma hora parada e quanto custa perder uma hora de registros clínicos, e mostre o preço de cada nível. Faça exercícios de DR pelo menos uma vez por ano, com cronômetro. Em custos, coloque orçamento e alertas por conta, revise a fatura mensalmente com o time e torne o custo de cada sistema visível para quem toma decisões de arquitetura.

Cenários práticos e troubleshooting

"O site ficou lento depois do deploy"

  1. Correlacione. A latência p95 e a taxa de erro subiram exatamente no horário do deploy? Marque deploys nos painéis para enxergar isso de imediato.
  2. Reverta se o impacto for alto. Restaurar o serviço vem antes de entender a causa.
  3. Siga um trace lento. O tempo está na aplicação, no banco, no cache ou numa API externa?
  4. Suspeitos comuns: consulta nova sem índice, N+1 consultas, cache desativado ou com chave errada, dependência nova lenta, pool de conexões pequeno.
  5. Corrija a causa e o processo. Que teste ou métrica de canary teria pego isso antes?

"O banco caiu no pico"

Contenha primeiro: limite a taxa de entrada, desligue funcionalidades não essenciais por feature flag, aumente o cache de leituras. Depois investigue: conexões esgotadas (cada instância nova abre mais conexões; um pooler como PgBouncer ou o pool do próprio banco ajuda), consultas pesadas no horário de pico, relatório rodando no primário em vez da réplica, falta de memória. No médio prazo: réplicas de leitura, filas para escritas que podem esperar, teste de carga antes do próximo pico.

"O time quer migrar para microsserviços"

Pergunte qual dor isso resolve: deploys travados por outro time, uma parte que precisa escalar diferente, base de código que ninguém entende. Muitas dessas dores se resolvem com monólito modular e melhor CI/CD. Se a extração for justificada, comece por um módulo de fronteira clara, com time dono, e só depois de ter observabilidade distribuída e pipeline por serviço. Use o padrão strangler fig: a nova parte cresce em volta da antiga e assume rota por rota.

"Usuários são deslogados aleatoriamente"

Clássico de sessão guardada em memória com várias instâncias e sem sticky session, ou de instâncias reiniciadas pelo autoscaling. Corrija levando a sessão para um armazenamento compartilhado ou para token, em vez de ligar sticky session.

"A fatura da nuvem dobrou"

Abra o relatório de custos por serviço e por tag. Suspeitos comuns: autoscaling que subiu e não desceu, ambiente de teste esquecido ligado, logs em volume excessivo, transferência de dados entre regiões, snapshots acumulados. Crie alerta de orçamento para detectar o próximo aumento em poucos dias, antes do fechamento do mês.

"Queremos 99,99% de disponibilidade"

São cerca de 4 minutos de indisponibilidade por mês, incluindo deploys e manutenção. Isso exige múltiplas zonas, deploy sem indisponibilidade, failover automático do banco e plantão rápido, e todas as dependências precisam ser mais disponíveis que isso. Mostre o custo e pergunte se 99,9% atende ao negócio.

Para gestores

Durante um incidente, defina um coordenador (incident commander) que não está digitando comandos, um canal único de comunicação e atualizações em intervalos fixos para as áreas afetadas. Depois, faça um postmortem sem culpados (blameless): linha do tempo, causa, o que ajudou, o que atrapalhou e ações com dono e prazo. O objetivo é melhorar o sistema e o processo; procurar culpado faz as pessoas esconderem informação na próxima vez.

13Avançado

Perguntas de entrevista

01Qual a diferença entre servidor web, servidor de aplicação e reverse proxy?

O servidor web fala HTTP e serve estáticos. O servidor de aplicação executa o código que gera respostas dinâmicas. O reverse proxy fica na frente, recebe as requisições em nome dos servidores internos, termina TLS, roteia, comprime e protege. O Nginx, por exemplo, pode fazer os papéis de servidor web e de reverse proxy.

02Load balancer de camada 4 ou de camada 7?

Camada 4 decide por conexão com base em IP e porta, com pouca sobrecarga e para qualquer protocolo. Camada 7 entende HTTP e pode rotear por caminho, host ou cabeçalho, terminar TLS e retentar. Para aplicações web costumo usar camada 7; camada 4 para protocolos não HTTP ou volume muito alto.

03Por que evitar sticky sessions?

Porque distribuem a carga de forma desigual, fazem o usuário perder a sessão quando a instância cai e atrapalham deploy e autoscaling. A alternativa é deixar a aplicação stateless, com sessão em armazenamento compartilhado ou em token.

04O que significa uma aplicação ser stateless e onde fica o estado?

A instância não guarda nada entre requisições. Dados ficam no banco, sessão no Redis ou em token, arquivos em armazenamento de objetos, trabalho pendente em fila. Assim qualquer instância atende qualquer requisição e posso escalar horizontalmente.

05Como você invalidaria cache?

Depende da tolerância a dado velho. Com tolerância, TTL curto. Sem tolerância, invalidação explícita ao gravar. Para estáticos, hash no nome do arquivo e cache longo. Também me protejo de stampede com TTL variável ou recálculo por uma única requisição.

06Quando usar NoSQL em vez de relacional?

Quando o padrão de acesso pede: chave-valor para cache e sessão, documento para agregados com esquema variável, colunar largo para escrita distribuída em grande volume, busca para texto livre. Para dados transacionais com integridade, como clínicos e financeiros, começo pelo relacional.

07Por que usar uma fila? Qual o cuidado principal?

Para tirar trabalho lento da requisição, absorver picos e não perder trabalho quando um destino cai. O cuidado principal é que a entrega costuma ser ao menos uma vez, então o consumidor precisa ser idempotente, e mensagens que falham vão para uma DLQ monitorada.

08Kafka ou RabbitMQ?

RabbitMQ é um broker de filas com roteamento flexível, bom para distribuir tarefas. Kafka é um log distribuído que retém eventos e permite que vários consumidores leiam e releiam no próprio ritmo, bom para fluxos de eventos de alto volume e reprocessamento. A escolha segue o padrão de uso e a experiência do time em operar cada um.

09Monólito ou microsserviços?

Microsserviços resolvem principalmente o problema de muitos times entregarem de forma independente, ao custo de rede, consistência eventual e operação complexa. Sem esse problema e sem plataforma madura, um monólito modular entrega mais. Extraio serviços quando há motivo concreto.

10Explique blue-green e canary.

Blue-green sobe a versão nova completa ao lado da antiga e vira todo o tráfego de uma vez, com rollback instantâneo e custo de infraestrutura dobrada na troca. Canary manda uma fração pequena do tráfego para a versão nova, compara métricas e aumenta em etapas, limitando o impacto de um problema.

11Como fazer rollback quando o deploy inclui migração de banco?

Com migrações expand/contract: cada mudança de esquema é compatível com a versão anterior do código. Adiciono antes de remover, migro dados em etapas e só removo o antigo num deploy posterior. Assim o código pode voltar sem quebrar o banco.

12O que é o modelo de responsabilidade compartilhada?

O provedor protege a infraestrutura da nuvem; o cliente protege o que coloca nela: configuração, identidades, dados, aplicação. A fronteira muda entre IaaS, PaaS e SaaS, mas o controle de acesso aos dados é sempre do cliente.

13Quais são os pilares da observabilidade e os sinais de ouro?

Logs, métricas e traces, de preferência instrumentados com OpenTelemetry e ligados por um trace ID. Os sinais de ouro são latência, tráfego, erros e saturação.

14Diferencie SLI, SLO e SLA. O que é error budget?

SLI é a medida (por exemplo, requisições bem-sucedidas abaixo de 500 ms). SLO é a meta interna para ela (99,9% em 30 dias). SLA é o contrato com cliente, com penalidade, normalmente menos exigente que o SLO. Error budget é 100% menos o SLO: cerca de 43 minutos em 30 dias para 99,9%. Ele decide quando acelerar e quando priorizar estabilidade.

15O que são RPO e RTO e como eles afetam a arquitetura?

RPO é a perda máxima de dados aceitável, medida em tempo; RTO é o tempo máximo para voltar. RPO baixo exige replicação contínua ou backups frequentes; RTO baixo exige ambiente de reserva pronto e failover automatizado. Quanto menores, maior o custo.

16Como gestor, como você conduz um incidente grave em produção?

Defino um coordenador, um canal único e atualizações periódicas para as áreas afetadas. A prioridade é restaurar o serviço, com rollback se possível, antes de buscar a causa. Depois faço um postmortem sem culpados, com ações que têm dono e prazo, e acompanho a conclusão delas.

17A fatura de nuvem está crescendo. O que você faz como gestor?

Garanto tags para saber quem gasta o quê, coloco orçamentos e alertas, reviso a fatura com o time todo mês e ataco o óbvio: recursos ociosos, máquinas superdimensionadas, ambientes de teste ligados à noite. Depois avalio compromissos de uso para a carga estável e torno o custo visível nas decisões de arquitetura.

18Que métricas você usaria para avaliar a entrega do seu time?

As métricas DORA: frequência de deploy, lead time de mudanças, taxa de falha de mudanças e tempo de recuperação, junto com o cumprimento dos SLOs. Uso para encontrar gargalos no processo, não para comparar pessoas.
