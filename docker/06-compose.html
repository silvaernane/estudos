MÓDULO 06 · Intermediário

Docker Compose essencial

Uma aplicação real tem API, banco, cache e ferramentas de apoio. O Compose descreve tudo isso num arquivo versionado e sobe o conjunto com um comando. Este módulo ensina a ler, escrever e depurar esse arquivo, e a evitar as armadilhas que fazem o ambiente funcionar só na máquina de quem o criou.

Ao final você saberá
  • Explicar por que usar o Compose, a diferença entre docker compose (v2) e docker-compose (v1) e por que o campo version é obsoleto.
  • Escrever e ler um compose.yaml com services, build, ports, volumes, networks, restart e command/entrypoint.
  • Entender o nome do projeto, a rede padrão e o DNS por nome de serviço.
  • Usar corretamente .env, env_file e environment, a precedência entre eles e a interpolação ${VAR:-padrao} e ${VAR:?erro}.
  • Controlar a ordem de inicialização com healthcheck e depends_on: condition: service_healthy.
  • Dominar os comandos do dia a dia, o ciclo de desenvolvimento com hot reload e montar uma stack completa API + PostgreSQL + Adminer.
  • Reconhecer e corrigir os erros comuns: localhost dentro do container, ordem de inicialização, porta em uso e volumes órfãos.
1Básico

Por que Compose, e qual Compose

Subir uma aplicação com docker run funciona para um container. Com três, já é ruim: cada um tem dezenas de flags (portas, variáveis, volumes, rede, restart) que vivem na cabeça de alguém ou numa nota de wiki desatualizada, a ordem importa e a rede precisa ser criada antes. O Docker Compose resolve isso descrevendo a aplicação inteira, declarativamente, num arquivo YAML que vai para o Git junto com o código: serviços, redes, volumes, variáveis e dependências. Um docker compose up cria o que falta e converge o ambiente para o que o arquivo diz.

# antes: três comandos longos, na ordem certa, lembrando de cada flag
docker network create loja
docker volume create pgdata
docker run -d --name db --network loja -e POSTGRES_PASSWORD=dev -v pgdata:/var/lib/postgresql/data postgres:17-alpine
docker run -d --name api --network loja -p 3000:3000 -e DATABASE_URL=postgres://postgres:dev@db:5432/postgres minha-api

# depois: o mesmo, versionado
docker compose up -d

O ganho vai além da conveniência: o arquivo é documentação executável da arquitetura da aplicação, reprodutível por qualquer pessoa do time e pelo CI. O novo desenvolvedor faz git clone, docker compose up e tem o ambiente completo.

Formato do arquivoCompose SpecificationFormatos "2.x" e "3.x" com campo version
 
docker compose version
# Docker Compose version v2.xx.x      (o número depende da instalação)
  • A Compose Specification é a especificação aberta do formato do arquivo (usada pelo Compose v2 e por outras ferramentas). É uma única especificação, sem as "versões" 2 e 3 do passado.
  • O campo version: "3.8" no topo é obsoleto: o Compose atual o ignora e emite um aviso (the attribute version is obsolete). Remova-o de arquivos novos e antigos. O que decide os recursos disponíveis é a versão do Compose instalada, não o arquivo.
  • O nome preferido do arquivo é compose.yaml (também compose.yml). docker-compose.yml e docker-compose.yaml continuam sendo reconhecidos. O Compose procura o arquivo no diretório atual e nos diretórios acima; use -f arquivo.yaml para apontar outro.
  • Se aparecer docker-compose: command not found ou um tutorial usar hífen, é material antigo: troque por docker compose.
Armadilha: Compose não é produção em escala

O Compose é excelente para desenvolvimento, testes, CI e para implantações simples em um único host. Ele não replica entre máquinas, não faz failover nem rolling update sofisticado. Quando a necessidade for multi-host e alta disponibilidade, o assunto é orquestração (módulo 10).

Na entrevista

"O que é o Docker Compose e por que usar?" Ferramenta que define e executa aplicações multi-container a partir de um arquivo YAML declarativo (serviços, redes, volumes). Dá reprodutibilidade, versionamento da infraestrutura local e um comando só para subir tudo. Mostre atualidade: "uso docker compose (v2, plugin); o docker-compose v1 está descontinuado e o campo version é obsoleto".

Para gestores

Um compose.yaml no repositório reduz o tempo de integração de novos membros de dias para minutos e torna o ambiente de desenvolvimento um artefato revisável em PR. Faça dele parte da definição de pronto de cada serviço: "sobe com um comando e tem um README de como usar".

2Básico

Anatomia do compose.yaml

O arquivo tem poucos blocos de topo: services (obrigatório), volumes, networks (e, nos módulos seguintes, configs, secrets e name). Cada serviço vira um ou mais containers a partir de uma imagem.

name: clinica                      # nome do projeto (opcional; padrão = nome da pasta)

services:
  api:
    build:                          # constrói a imagem a partir de um Dockerfile
      context: ./api                #   pasta de contexto
      dockerfile: Dockerfile        #   (opcional) nome do arquivo
      target: dev                   #   (opcional) estágio do multi-stage
      args:
        NODE_ENV: development       #   ARG do Dockerfile
    image: clinica-api:dev          # com build: nome/tag dados à imagem construída
    ports:
      - "127.0.0.1:3000:3000"       # host:container (sempre entre aspas)
    environment:
      DATABASE_URL: postgres://app:dev@db:5432/app
      LOG_LEVEL: debug
    env_file:
      - ./api/.env.dev              # variáveis lidas de arquivo
    volumes:
      - ./api/src:/app/src          # bind mount (código)
      - uploads:/app/uploads        # volume nomeado
    networks:
      - frontend
      - backend
    command: ["npm", "run", "dev"]  # substitui o CMD da imagem
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:17-alpine       # imagem pronta, sem build
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: dev
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - backend

volumes:
  pgdata:
  uploads:

networks:
  frontend:
  backend:

image versus build

  • image sozinho: o Compose baixa a imagem (como docker pull). Típico para infraestrutura: Postgres, Redis, Adminer.
  • build sozinho: o Compose constrói a imagem e a nomeia <projeto>-<servico>. Típico para o código da própria equipe.
  • Os dois: constrói e dá o nome indicado em image; útil para enviar a imagem a um registry depois (módulo 08).
  • Alterou o código ou o Dockerfile? docker compose up -d --build (ou docker compose build). O Compose não reconstrói sozinho: ele só constrói se a imagem ainda não existe.

command, entrypoint e restart

services:
  worker:
    image: minha-api
    entrypoint: ["node"]                    # troca o ENTRYPOINT da imagem
    command: ["dist/worker.js", "--fila", "agendamentos"]   # argumentos / CMD
    restart: on-failure:5                   # reinicia só se falhar, no máximo 5 vezes
restartComportamento
"no" (padrão)Nunca reinicia. Escreva entre aspas: sem aspas, o YAML entende no como o booleano falso.
alwaysSempre reinicia, inclusive quando o daemon sobe de novo, mesmo se você parou o container antes do reinício do daemon.
on-failure[:N]Reinicia só com código de saída diferente de zero, até N vezes.
unless-stoppedComo always, mas respeita um stop manual (não volta depois de reiniciar o daemon).
Armadilhas de YAML que o Compose herda
  • Indentação com espaços, nunca tabs. Dois espaços por nível é o padrão.
  • Portas sem aspas: - 22:22 pode ser lido como o número 1342 (notação sexagesimal do YAML 1.1). Sempre "22:22".
  • Valores que viram booleanos: yes, no, on, off sem aspas. Em environment, escreva "true"/"false" quando a aplicação espera texto.
  • Dois-pontos e # em valores (senhas, URLs): coloque o valor entre aspas.
  • Quando em dúvida sobre o que o Compose entendeu, rode docker compose config (seção 6): ele mostra o arquivo final já interpretado.
Regra de bolso

Imagem de terceiros: image com tag fixa. Código próprio: build. Porta que só você usa: 127.0.0.1:. Dados: volume nomeado declarado. Restart: unless-stopped em servidores, "no" em desenvolvimento.

Na entrevista

"Qual a diferença entre command e entrypoint?" O entrypoint é o executável fixo do container; o command são os argumentos padrão (ou o comando padrão, se a imagem não tiver entrypoint). No Compose, command substitui o CMD da imagem e entrypoint substitui o ENTRYPOINT (e descarta o CMD padrão). Relembre o módulo 03 sobre forma exec versus shell.

Para gestores

Padronize o esqueleto do compose.yaml da empresa (nomes de serviço, convenção de portas, volumes nomeados, tags fixas) e revise-o em PR como código. Divergências entre projetos custam tempo de onboarding e escondem problemas de segurança (portas abertas, tags latest).

3Intermediário

Projeto, rede padrão e DNS por nome de serviço

Tudo que o Compose cria pertence a um projeto, identificado por um nome. O nome vira prefixo de containers, redes e volumes, e é por ele que o Compose sabe o que é "seu". Isso permite rodar duas cópias da mesma aplicação lado a lado (por exemplo, duas branches) sem conflito, desde que os nomes de projeto sejam diferentes.

Como o nome do projeto é definido

Em ordem de precedência (do que vence ao que perde):

  1. a opção -p / --project-name na linha de comando;
  2. a variável de ambiente COMPOSE_PROJECT_NAME (pode estar no .env);
  3. o campo name: no compose.yaml;
  4. o nome da pasta do projeto (em minúsculas e normalizado).

O nome só pode ter letras minúsculas, números, hífen e sublinhado. Um name: explícito no arquivo evita a surpresa de o nome depender da pasta em que cada pessoa clonou o repositório (ou do nome temporário de uma pasta no CI).

RecursoNome gerado (projeto clinica)
Containerclinica-api-1, clinica-db-1 (serviço + índice da réplica)
Rede padrãoclinica_default
Rede declarada backendclinica_backend
Volume declarado pgdataclinica_pgdata
Imagem construída do serviço apiclinica-api

O comportamento é o das redes definidas pelo usuário do módulo 05: o resolvedor embutido responde pelo nome do serviço (db, api). O serviço é encontrado pela porta interna (a que a aplicação escuta), não pela porta publicada. Com réplicas (--scale), o nome do serviço resolve para o IP de todas elas, em rodízio.

docker compose up -d
docker compose exec api sh -c "getent hosts db"
# 172.19.0.2      db

docker network ls --filter name=clinica
# NETWORK ID     NAME              DRIVER    SCOPE
# 3c1f0b9d7a12   clinica_default   bridge    local

docker volume ls --filter name=clinica
# DRIVER    VOLUME NAME
# local     clinica_pgdata

Redes personalizadas

Sem a chave networks, todos os serviços ficam na default e se enxergam. Para segmentar (por exemplo, o proxy só alcança a API e só a API alcança o banco), declare redes e ligue cada serviço só às que precisa:

services:
  proxy:
    image: nginx:1.27-alpine
    ports: ["80:80"]
    networks: [frontend]
  api:
    build: ./api
    networks: [frontend, backend]          # ponte entre as duas
  db:
    image: postgres:17-alpine
    networks:
      backend:
        aliases: [banco-clinica]

networks:
  frontend:
  backend:
    internal: true                         # sem saída para a internet; só tráfego interno
  legado:
    external: true                         # rede que já existe (criada fora do Compose)
  • internal: true bloqueia a saída para fora da rede: bom para o banco. Cuidado: containers só nessa rede também não baixam pacotes nem falam com APIs externas.
  • external: true usa uma rede ou volume que o Compose não cria nem remove. É também a proteção de dados mais barata em produção: um volume external não é apagado por down -v.
  • Volumes e redes podem ter name: próprio para não receber o prefixo do projeto.
  • O Compose marca tudo com rótulos com.docker.compose.project; é assim que down encontra o que remover.
Armadilha: container_name fixo

Com container_name: db você perde o prefixo de projeto: duas cópias do projeto brigam pelo mesmo nome e o serviço não pode ser escalado (--scale db=2 falha). O DNS por nome de serviço já resolve o que o container_name costuma querer resolver. Só use em casos justificados.

Na entrevista

"Como o serviço A encontra o serviço B no Compose?" Pelo nome do serviço, resolvido pelo DNS embutido da rede do projeto (<projeto>_default), usando a porta interna do B. Sem precisar de links (legado), de IP, nem de ports: ports é só para acesso de fora do Docker.

Para gestores

Fixe o name: do projeto no arquivo e cobre o uso de redes separadas para o banco. Em máquinas de CI compartilhadas, exija nomes de projeto únicos por execução (-p com o ID do job) para que pipelines paralelos não derrubem o ambiente uns dos outros.

4Intermediário

Variáveis: .env, env_file, environment e interpolação

Há dois problemas diferentes que parecem um só: (1) preencher valores dentro do próprio compose.yaml (portas, tags, senhas), e (2) definir as variáveis de ambiente que o processo dentro do container enxerga. Misturar os dois é a maior fonte de confusão com variáveis no Compose.

MecanismoO que fazVai para dentro do container?
.env (na pasta do projeto)Fornece valores para a interpolação ${VAR} do compose.yaml, e para variáveis do próprio Compose (COMPOSE_PROJECT_NAME, COMPOSE_FILE, COMPOSE_PROFILES).Não, por si só. Só chega ao container se o compose.yaml o referenciar (em environment, por exemplo).
environmentDefine variáveis do container, direto no YAML.Sim.
env_fileCarrega variáveis de um ou mais arquivos para o container.Sim.
--env-file (CLI)Troca o arquivo usado na interpolação (no lugar do .env).Não, mesma lógica do .env.

Interpolação no compose.yaml

SintaxeSignificado
${VAR} ou $VARValor de VAR. Se não existir, o Compose avisa e usa texto vazio.
${VAR:-padrao}padrao se VAR não existir ou estiver vazia.
${VAR-padrao}padrao só se VAR não existir (vazia conta como definida).
${VAR:?mensagem}Erro e para, se VAR não existir ou estiver vazia. Exibe a mensagem.
${VAR?mensagem}Erro só se VAR não existir.
${VAR:+outro}outro se VAR estiver definida e não vazia; caso contrário, vazio.
$$Um $ literal (escape). Essencial em healthchecks com CMD-SHELL.
 
# NÃO versionar. Versione um .env.example sem segredos.
POSTGRES_USER=app
POSTGRES_PASSWORD=troque-isto
POSTGRES_DB=clinica
API_PORT=3000
services:
  db:
    image: postgres:${PG_VERSION:-17}-alpine                 # padrão 17 se PG_VERSION não existir
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-app}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?defina POSTGRES_PASSWORD no .env}   # falha cedo, com mensagem clara
      POSTGRES_DB: ${POSTGRES_DB:-app}
  api:
    build: ./api
    ports:
      - "127.0.0.1:${API_PORT:-3000}:3000"
$ docker compose config
error while interpolating services.db.environment.POSTGRES_PASSWORD: required variable POSTGRES_PASSWORD is missing a value: defina POSTGRES_PASSWORD no .env

Precedência

Para a interpolação do compose.yaml, vence o que estiver mais acima:

  1. variável no shell (ou do CI) onde você roda o docker compose;
  2. arquivo indicado por --env-file, ou o .env da pasta do projeto;
  3. o valor padrão da própria sintaxe (:-padrao).

Para o ambiente do container, do que mais vence ao que menos vence:

  1. docker compose run -e VAR=valor na linha de comando;
  2. environment do serviço (inclusive o valor interpolado);
  3. env_file do serviço (com vários arquivos, o último vence);
  4. ENV da imagem (Dockerfile).
# ver o resultado final, com tudo resolvido
docker compose config

# demonstração: o shell vence o .env na interpolação
echo "API_PORT=3000" > .env
API_PORT=4000 docker compose config | grep published
#   published: "4000"
Armadilhas de variáveis
  • "Mudei o .env e nada mudou." O container já foi criado com os valores antigos. Rode docker compose up -d (ele detecta a mudança de configuração e recria o serviço); restart não relê configuração.
  • Uma variável exportada no seu terminal sobrepõe o .env e ninguém lembra: "na minha máquina funciona". Confirme com docker compose config e env | grep VAR.
  • O .env não é o ambiente do container. Para a aplicação ler POSTGRES_PASSWORD, é preciso repassá-la em environment ou em env_file.
  • Segredos no compose.yaml versionado. Senha em texto no repositório é incidente. Use .env ignorado pelo Git para valores locais, e Docker secrets ou um cofre em ambientes compartilhados (módulos 07 e 09).
  • Aspas no .env: em geral são tratadas como delimitadores do valor e removidas, mas o comportamento varia entre ferramentas; evite espaços e caracteres especiais em valores quando puder e confira com docker compose config.
  • $ em senhas é interpretado como variável. Escape como $$.
Regra de bolso

Valores que variam por máquina (porta, tag, senha local) vão no .env e entram no YAML por ${VAR:-padrao}; use ${VAR:?erro} para o que não tem padrão seguro (senha). Versione .env.example, nunca o .env.

Na entrevista

"Qual a diferença entre .env, env_file e environment?" O .env alimenta a interpolação do próprio arquivo Compose; environment e env_file definem variáveis dentro do container. Precedência no container: run -e, depois environment, depois env_file, depois o ENV da imagem. Para interpolação: o shell vence o .env.

Para gestores

Política simples e auditável: .env no .gitignore, .env.example versionado, varredura de segredos no CI e rotação de qualquer credencial que já tenha sido commitada (apagar do histórico não basta). Em saúde, uma senha de banco no repositório pode significar acesso a dados de pacientes.

5Intermediário

depends_on, healthchecks e ordem de inicialização

O problema clássico: a API sobe antes de o banco aceitar conexões e cai com connection refused. Subir e estar pronto são coisas diferentes: o Postgres leva alguns segundos para inicializar o cluster (e, na primeira vez, para executar os scripts de init); o Oracle Free leva minutos na criação do banco.

O que o depends_on faz

FormaEspera até...Uso
depends_on: [db]o container db ter iniciado (não que o banco esteja pronto)Só ordem de criação e de desligamento.
condition: service_startedigual à forma curtaPadrão explícito.
condition: service_healthyo healthcheck do serviço reportar healthyBanco, broker, qualquer coisa que a API exige pronta.
condition: service_completed_successfullyo serviço terminar com código 0Jobs únicos: migrações, seed, geração de certificados.

Também existem restart: true (reinicia este serviço quando a dependência for reiniciada pelo Compose) e required: false (dependência opcional; não bloqueia se o serviço não for iniciado, por exemplo por perfil).

Healthcheck: como o Docker decide o que é "saudável"

O healthcheck roda um comando periodicamente dentro do container. O estado passa por três valores: starting (período inicial, falhas não contam), healthy (o comando saiu com código 0) e unhealthy (falhou retries vezes seguidas). O Docker não reinicia container unhealthy por conta própria: o estado serve para depends_on, para docker ps e para orquestradores.

CampoSignificadoPadrão
testO comando. ["CMD", ...] (sem shell), ["CMD-SHELL", "..."] (com shell) ou ["NONE"] (desliga um healthcheck herdado da imagem).sem padrão
intervalTempo entre execuções.30s
timeoutTempo máximo de cada execução.30s
retriesFalhas seguidas para virar unhealthy.3
start_periodJanela inicial em que falhas não contam (banco lento para subir).0s
start_intervalIntervalo entre execuções durante o start_period (versões recentes do Docker Engine e do Compose).5s

Healthchecks bem escritos

services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: dev
      POSTGRES_DB: app
    healthcheck:
      # $$ evita que o COMPOSE interpole; o shell do container expande a variável
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s

  api:
    build: ./api
    depends_on:
      db:
        condition: service_healthy        # espera o Postgres responder
    healthcheck:
      test: ["CMD", "wget", "-q", "--spider", "http://localhost:3000/health"]   # Alpine/busybox
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 15s

  cache:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
  • Teste a prontidão real. pg_isready verifica se o servidor aceita conexões. Para um HTTP, chame um endpoint /health que verifique as dependências críticas da aplicação (com cuidado: um health que consulta o banco inteiro a cada 5 s vira carga).
  • A ferramenta precisa existir na imagem. Imagens enxutas (Alpine, slim, distroless) podem não ter curl. Em Alpine, o wget do busybox costuma existir; em distroless não há nada: use um binário próprio de healthcheck ou o próprio executável da aplicação com um modo --health. O curl -f falha com código diferente de zero em respostas 4xx/5xx, o que se quer num healthcheck.
  • Use localhost e a porta interna: o healthcheck roda dentro do container do serviço.
  • Intervalos razoáveis. interval curto demais gera carga; start_period curto demais marca o serviço lento como falho. Para o Oracle Free na primeira subida, planeje minutos.
  • Ver o estado: docker compose ps mostra (healthy), (unhealthy) ou (health: starting); docker inspect --format '{{json .State.Health}}' container mostra o histórico das últimas execuções.
  • docker compose up -d --wait sobe e só retorna quando os serviços estiverem running/healthy. Ideal para scripts e CI.

Job de migração com service_completed_successfully

services:
  migrar:
    build: ./api
    command: ["npm", "run", "migrate"]       # roda e termina
    depends_on:
      db:
        condition: service_healthy
    restart: "no"
  api:
    build: ./api
    depends_on:
      migrar:
        condition: service_completed_successfully   # só sobe depois que as migrações terminam com sucesso
Armadilha: healthcheck não substitui retry na aplicação

Healthcheck e depends_on só controlam a ordem de subida. O banco pode reiniciar depois, a rede pode piscar, a conexão pode cair. Uma aplicação robusta reconecta com retry e backoff (veja a trilha de APIs, APIs 06: Confiabilidade). Quem confia só na ordem de subida tem um ambiente que "funciona hoje".

Armadilha: healthcheck que sempre passa

test: ["CMD", "true"] ou checar só se o processo existe dá healthy antes de o serviço estar pronto. E um healthcheck que depende de ferramenta ausente falha para sempre (o serviço fica unhealthy e o depends_on nunca libera): veja os logs do healthcheck no docker inspect.

Na entrevista

"A API sobe antes do banco e quebra. Como resolver?" Healthcheck no banco (pg_isready) e depends_on com condition: service_healthy na API, mais retry com backoff na própria aplicação, porque a ordem de subida não cobre quedas posteriores. Mencione service_completed_successfully para migrações.

Para gestores

Healthcheck é contrato de operação: o que "pronto" significa para cada serviço. Exija um endpoint de saúde em toda API e que ele seja o mesmo usado pelo Compose, pelo balanceador e pelo monitoramento. Evita três definições diferentes de "saudável" em três ferramentas.

Armadilha: down -v e restart
  • docker compose down -v é o comando mais destrutivo do dia a dia: apaga o banco do projeto. Ótimo para "recomeçar do zero" em desenvolvimento; desastre em um servidor. Em ambientes compartilhados, declare o volume do banco como external: true (o Compose não remove volumes externos) e evite dar o -v a quem não precisa.
  • docker compose restart não aplica mudanças de environment, portas ou imagem. Para aplicar, rode up -d (recria só o que mudou) ou up -d --force-recreate.
  • exec exige o container em execução; run cria um novo. Um comando de manutenção (migração) que escreve em arquivos deve usar run --rm, para não depender do container "principal".

Quando o Compose recria um container

O up compara a configuração desejada com a de cada container existente. Mudou algo que o afeta (imagem, variável, porta, volume, comando), recria aquele serviço; não mudou, mantém. Alterar apenas o código não muda a configuração: para uma imagem construída, use up -d --build. Dependentes costumam ser recriados também.

Ciclo de desenvolvimento: bind mount e hot reload

Reconstruir a imagem a cada alteração de código é lento demais para o dia a dia. O ciclo de desenvolvimento usa um bind mount do código e um processo que observa os arquivos e reinicia sozinho (hot reload). Você edita no host, o container enxerga a mudança e recarrega.

services:
  api:
    build:
      context: ./api
      target: dev                       # estágio de desenvolvimento do Dockerfile
    command: ["npm", "run", "dev"]      # nodemon / node --watch / uvicorn --reload ...
    ports:
      - "127.0.0.1:3000:3000"
    volumes:
      - ./api/src:/app/src              # só o código-fonte, não a pasta inteira
      - /app/node_modules               # volume anônimo: preserva as dependências da imagem
    environment:
      CHOKIDAR_USEPOLLING: "true"       # só se o hot reload não detectar mudanças (Mac/Windows)
  • Por que não montar ./api:/app inteiro? O bind mount esconde o que a imagem tinha em /app, inclusive node_modules. Se o host não tem as dependências (ou as tem para outro sistema operacional), a aplicação quebra. Monte só o código, ou proteja node_modules com um volume, como acima.
  • O servidor precisa escutar em 0.0.0.0 e o dev server do framework precisa de --host 0.0.0.0 (Vite, Next, uvicorn, Flask) para a porta publicada funcionar.
  • Ferramentas de recarga por linguagem: Node (nodemon, ou node --watch nas versões recentes), Python (uvicorn --reload, Flask em modo debug), Java (Spring DevTools), .NET (dotnet watch).
  • Mac e Windows: eventos de arquivo podem não atravessar o compartilhamento; habilite polling (ver módulo 05) ou use o recurso abaixo. No Windows, mantenha o projeto dentro do WSL 2.
  • Arquivos de override: o Compose lê automaticamente um compose.override.yaml ao lado do compose.yaml e o mescla por cima. Padrão comum: o compose.yaml com o essencial e o override com bind mounts e portas de desenvolvimento (aprofundado no módulo 07).

Compose Watch: alternativa ao bind mount

Versões recentes do Compose v2 têm o recurso develop.watch: em vez de montar o código, o Compose observa arquivos no host e os sincroniza com o container, ou reconstrói a imagem quando um arquivo de dependências muda. Evita os problemas de desempenho e de permissão de bind mount, ao custo de ser um mecanismo a mais.

services:
  api:
    build: ./api
    develop:
      watch:
        - action: sync                  # copia a mudança para o container (o watcher interno recarrega)
          path: ./api/src
          target: /app/src
        - action: rebuild               # mudou dependências: reconstrói a imagem e recria o container
          path: ./api/package.json
docker compose up --watch        # sobe e observa (ou: docker compose watch)
Regra de bolso

Desenvolvimento: código por bind mount (ou watch), dependências na imagem, servidor em modo de recarga. Produção: imagem imutável, sem bind mount de código. O compose.yaml base é de "produção-like"; o que é de desenvolvimento fica no override.

Na entrevista

"Qual a diferença entre docker compose exec e run?" exec executa um comando dentro de um container já em execução; run cria um novo container do serviço (com a mesma configuração) para o comando e, com --rm, o remove ao fim. E "diferença entre down e down -v?" O segundo também apaga os volumes: os dados.

Para gestores

Um ambiente de desenvolvimento que sobe com um comando e recarrega o código sozinho é produtividade direta. Meça: quanto tempo um dev novo leva do clone até a primeira requisição funcionando? Meta razoável: menos de 30 minutos, dos quais a maior parte é download de imagens.

O banco tem volume nomeado e healthcheck; a API só sobe com o banco saudável; as portas administrativas ficam só em 127.0.0.1.

Variações úteis

  • Segredos: troque a senha em environment por POSTGRES_PASSWORD_FILE com Docker secrets em ambientes compartilhados (módulos 07 e 09).
  • Oracle em vez de Postgres: mesmo desenho, com a imagem do Oracle Free (módulo 05), start_period de minutos e o healthcheck da imagem.

E mantenha o .env.example atualizado a cada nova variável: é o contrato de configuração da aplicação.

Erros comuns e como diagnosticar

Quase todo problema de Compose cai numa das categorias abaixo. O primeiro passo é sempre o mesmo: docker compose config (o que o Compose entendeu), docker compose ps -a (quem está de pé, quem saiu) e docker compose logs (por que saiu).

Os quatro clássicos em detalhe

1. localhost dentro do container

services:
  api:
    environment:
      # errado: dentro do container da api, "localhost" é a própria api
      # DATABASE_URL: postgres://app:dev@localhost:5432/app
      DATABASE_URL: postgres://app:dev@db:5432/app     # certo: nome do serviço e porta interna

Regra: localhost só serve para o que roda no mesmo container. Para outro serviço, o nome dele; para o host, host.docker.internal (módulo 05). O mesmo vale ao contrário: o seu navegador usa localhost:PORTA_PUBLICADA, porque ele está no host.

2. Ordem de inicialização sem healthcheck

Sintoma intermitente: "às vezes sobe, às vezes não", pior em máquinas lentas e no CI. É uma condição de corrida entre a API e o banco. O conserto completo está na seção 5; evite as "soluções" frágeis: sleep 10 no entrypoint (lento quando o banco é rápido, insuficiente quando é lento) e scripts wait-for-it copiados sem entender.

3. Porta já em uso

docker compose up -d
# Error response from daemon: ... Bind for 127.0.0.1:5432 failed: port is already allocated

docker ps --filter publish=5432                  # algum container publicando a 5432?
ss -ltnp | grep 5432                             # Linux: processo do host
lsof -iTCP:5432 -sTCP:LISTEN                     # Mac
netstat -ano | findstr :5432                     # Windows (PID na última coluna)

# solução permanente: porta do host configurável
#   ports: ["127.0.0.1:${DB_PORT:-5432}:5432"]  e DB_PORT=5433 no .env

Um Postgres local instalado fora do Docker e o do container disputando a 5432 é o caso mais comum. Entre containers, nunca há conflito de porta interna (cada um tem seu namespace), só de porta publicada no host.

4. Volumes órfãos e o projeto que "mudou de nome"

O volume pertence ao projeto (clinica_pgdata). Renomear a pasta (sem name: fixo), clonar em outro diretório ou usar -p diferente cria um projeto novo, com volume novo e vazio: parece que "o banco sumiu", mas os dados antigos continuam em um volume que ninguém usa mais, ocupando disco.

docker volume ls                                  # procure pgdata com prefixos diferentes
docker volume ls -f dangling=true                 # volumes sem container associado
docker system df -v                               # quanto cada volume e imagem ocupa

# conteúdo de um volume órfão, sem montar nada de verdade
docker run --rm -v projetoantigo_pgdata:/d:ro alpine ls -la /d

# apague só o que você tem certeza de que é lixo
docker volume rm projetoantigo_pgdata
Armadilha: docker volume prune como faxina

Ele apaga volumes sem container associado, e um banco com o stack parado (compose down) está exatamente nessa condição. Com -a, apaga também os nomeados. Nunca rode em um servidor sem listar antes (docker volume ls -f dangling=true) e sem backup.

Regra de bolso

Depurou o Compose? Sempre nesta ordem: config (o que o Compose entendeu) → ps -a (estado) → logs (causa) → exec ou run (investigar por dentro). Antes de qualquer -v ou prune: docker volume ls e backup.

Na entrevista

"Seu compose funciona na sua máquina e falha no CI. Por quê?" Hipóteses em ordem: ordem de inicialização sem healthcheck (CI é mais lento), porta ocupada por outro job (use nomes de projeto e portas aleatórias/sem publicar), variáveis do .env inexistentes no CI (use :?erro para falhar cedo), bind mount com UID diferente, e imagens desatualizadas (--build/--pull).

Para gestores

Reduza a classe inteira de erros com um modelo de projeto: name: fixo, .env.example, healthchecks, portas configuráveis em 127.0.0.1, volumes nomeados e um comando único de verificação (docker compose config -q && docker compose up -d --wait) no CI.

10Intermediário

Cenários práticos de trabalho

1. "O ambiente sobe, mas a API reinicia em loop nos primeiros segundos"

O log mostra ECONNREFUSED ao banco; depois de algumas reinicializações, funciona.

O que fazer
  • Diagnóstico: a API subiu antes do Postgres aceitar conexões. Confirme em docker compose logs db (o ready to accept connections chega depois do primeiro erro da API).
  • Correção: healthcheck com pg_isready no banco, depends_on: condition: service_healthy na API e retry com backoff no código de conexão.
  • Não use sleep fixo: o tempo de subida varia entre máquinas.

2. "Clonei o projeto em outra pasta e o banco veio vazio"

O colega diz que "sumiu tudo" depois que renomeou a pasta do repositório.

O que fazer
  • Explique: sem name:, o nome do projeto vem da pasta, e o volume é <projeto>_pgdata. A pasta nova gerou um projeto e um volume novos e vazios.
  • Recupere: docker volume ls mostra o volume antigo; copie para o novo (cp -a entre volumes, módulo 05) ou suba com -p nome-antigo.
  • Previna: name: fixo no compose.yaml e, quando os dados importam, volume external.

3. "Troquei a senha no .env e o banco continua aceitando a antiga"

Depois de um docker compose up -d, a API falha na autenticação com a senha nova.

O que fazer
  • Explique: POSTGRES_PASSWORD só é usada na inicialização do cluster (volume vazio). O volume antigo mantém a senha antiga.
  • Em desenvolvimento, sem dados importantes: down -v e subir de novo. Com dados: troque a senha dentro do banco (ALTER USER ... PASSWORD ...) e atualize o .env da aplicação.
  • Registre a regra: variáveis de inicialização do banco não são "configuração viva".

4. "O disco do servidor de CI encheu"

Um servidor de integração contínua com Docker fica sem espaço depois de semanas.

O que fazer
  • Meça antes de apagar: docker system df -v (imagens, containers, volumes, cache de build).
  • Pipelines devem terminar com docker compose down -v --remove-orphans (em CI, os volumes são descartáveis) e usar nome de projeto único por execução (-p).
  • Limpeza periódica agendada de imagens e cache sem uso (docker image prune, docker builder prune); docker volume prune só depois de listar o que será apagado.

5. "O Compose está lento e o hot reload não funciona no Windows"

Um desenvolvedor reclama que npm install leva minutos e as mudanças de código não recarregam.

O que fazer
  • Verifique onde está o projeto: se em C:\, mova-o para o sistema de arquivos do WSL 2 e rode o Docker de lá (módulo 05).
  • Mantenha node_modules num volume da imagem (não no bind mount) e monte só o src.
  • Se o watcher não detecta mudanças, habilite polling ou migre para docker compose watch.
11Referência

Glossário

Compose Specification
Especificação aberta do formato do arquivo Compose, usada pelo Compose v2.
Compose v2
Plugin do Docker CLI (docker compose). O v1 (docker-compose) está descontinuado.
Serviço
Definição de um componente da aplicação (imagem, portas, volumes). Gera um ou mais containers.
Projeto
Conjunto de serviços, redes e volumes com um nome; prefixa tudo que o Compose cria.
Rede padrão
Rede <projeto>_default criada pelo Compose, com DNS pelo nome do serviço.
Interpolação
Substituição de ${VAR} no compose.yaml por valores do shell ou do .env.
.env
Arquivo da pasta do projeto com valores para interpolação; não vai ao container por si só.
env_file
Chave do serviço que carrega variáveis de arquivo para dentro do container.
Healthcheck
Comando periódico que define se o serviço está healthy, unhealthy ou starting.
depends_on
Declara dependências entre serviços; com condition, espera início, saúde ou término com sucesso.
Bind mount
Pasta do host montada no container; base do ciclo de desenvolvimento com hot reload.
Hot reload
Recarga automática da aplicação quando o código muda, sem reconstruir a imagem.
Volume órfão
Volume sem container associado, normalmente de um projeto antigo ou renomeado.
Container órfão
Container de um serviço que já não existe no arquivo; removido com --remove-orphans.
12Entrevista

Perguntas de entrevista

01O que é o Docker Compose e qual problema resolve?

É a ferramenta que descreve uma aplicação multi-container num arquivo YAML (serviços, redes, volumes, variáveis) e a sobe com docker compose up. Resolve a reprodutibilidade e o trabalho de orquestrar vários docker run com muitas flags, e torna o ambiente versionável junto com o código.

02Qual a diferença entre docker compose e docker-compose?

O primeiro é o Compose v2, plugin do Docker CLI em Go, atual e mantido. O segundo é o v1, programa em Python, descontinuado. Os nomes de container mudam (hífen no v2, sublinhado no v1) e o campo version do arquivo é obsoleto em ambos os casos atuais.

03Qual a diferença entre image e build num serviço?

image usa uma imagem pronta (pull do registry); build constrói a imagem de um Dockerfile local. Com os dois, constrói e nomeia a imagem. O Compose não reconstrói sozinho quando o código muda: é preciso --build.

04Como os serviços se encontram dentro do Compose?

O Compose cria uma rede bridge definida pelo usuário por projeto, com DNS embutido: cada serviço é encontrado pelo seu nome e pela porta interna (db:5432). ports só é necessário para acesso de fora do Docker.

05Como o nome do projeto é definido e por que importa?

Por precedência: -p, COMPOSE_PROJECT_NAME, name: no arquivo, nome da pasta. Importa porque prefixa containers, redes e volumes: mudar o nome gera recursos novos (volume vazio). Fixar name: evita surpresas.

06Diferença entre .env, env_file e environment?

.env alimenta a interpolação do compose.yaml (e variáveis do próprio Compose) e não vai ao container sozinho; environment e env_file definem variáveis dentro do container. No container: run -e vence environment, que vence env_file, que vence o ENV da imagem. Na interpolação, o shell vence o .env.

07Explique ${VAR:-padrao} e ${VAR:?erro}.

O primeiro usa padrao quando VAR não existe ou está vazia. O segundo aborta com a mensagem quando VAR não existe ou está vazia: serve para falhar cedo em variáveis obrigatórias, como senha. Sem :, a checagem considera só "não definida".

08depends_on garante que o banco está pronto?

Não, na forma curta só ordena o início dos containers. Para esperar prontidão, use condition: service_healthy com um healthcheck no banco (pg_isready). Ainda assim, a aplicação deve reconectar com retry, porque a ordem de subida não cobre quedas posteriores.

09Como escrever um bom healthcheck?

Testar a prontidão real, com o comando disponível na imagem (pg_isready, wget --spider/curl -f no endpoint /health), usando localhost e a porta interna, com interval, timeout, retries e um start_period adequado. Em CMD-SHELL com variáveis, escapar o cifrão como $$.

10Qual a diferença entre docker compose down e down -v?

down remove containers e redes e mantém volumes e imagens. down -v também remove os volumes nomeados do arquivo e os anônimos: apaga os dados. Em produção, volumes external não são removidos pelo Compose.

11Mudei uma variável e rodei restart, mas nada mudou. Por quê?

O restart reinicia o processo no mesmo container e não relê a configuração. Para aplicar, docker compose up -d detecta a diferença e recria o serviço (ou --force-recreate).

12Diferença entre exec e run?

exec roda um comando num container já em execução. run cria um container novo do serviço (sobe as dependências, não publica portas por padrão) para um comando pontual, e com --rm o remove ao terminar. Use run --rm para migrações e testes.

13Como montar um ambiente de desenvolvimento com hot reload?

Bind mount do código-fonte (só ./src, preservando as dependências da imagem com um volume), comando de desenvolvimento com recarga (nodemon, --reload), servidor escutando em 0.0.0.0, polling se os eventos de arquivo não atravessarem a VM e, alternativamente, develop.watch. Configurações de desenvolvimento no compose.override.yaml.

14A API não conecta ao banco com localhost:5432 dentro do Compose. Por quê?

Dentro do container, localhost é o próprio container da API. O banco está em outro container: o endereço é o nome do serviço (db:5432), resolvido pelo DNS da rede do projeto.

15O que é docker compose config e quando usar?

Mostra o arquivo final já mesclado (overrides, -f múltiplos) e com variáveis interpoladas, e valida a sintaxe. É a primeira coisa a rodar ao depurar "o Compose não fez o que eu esperava"; -q serve de verificação no CI.

16Dois projetos precisam do mesmo banco em porta fixa e entram em conflito. Como resolver?

Tornar a porta do host configurável (${DB_PORT:-5432}:5432), publicar só em 127.0.0.1, ou não publicar (os serviços do próprio projeto acessam por nome). Em CI, usar nomes de projeto únicos e evitar publicar portas.

17Quando o Compose deixa de bastar?

Quando se precisa de vários hosts, failover automático, rolling updates sofisticados, autoscaling ou gestão centralizada de segredos e configuração. Aí entram Swarm ou Kubernetes (módulo 10). Para ambiente de desenvolvimento, CI e produção simples em um host, o Compose atende bem.

18Gestão: que padrões você exige nos compose.yaml do time?

name: fixo; tags de imagem fixadas; segredos fora do repositório (.env ignorado, .env.example versionado); healthchecks e service_healthy; volumes nomeados para dados; portas em 127.0.0.1 e só as necessárias; um comando de verificação no CI (config -q e up --wait); e a mesma stack no desenvolvimento e nos testes de integração.
