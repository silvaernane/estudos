MÓDULO 06 · Intermediário Avançado

Escrita, transações e modelagem

Como gravar dados sem corrompê-los: DML, upsert, transações, constraints, tipos e normalização, mais o que muda em produção (LGPD, cargas em lote, migrações sem parada).

Ao final você saberá
  • Usar INSERT, UPDATE com join, DELETE, MERGE, ON CONFLICT e RETURNING nos dois bancos, evitando as armadilhas de cada sintaxe
  • Explicar ACID, COMMIT/ROLLBACK/SAVEPOINT, autocommit e as diferenças de DDL e isolamento entre Oracle e PostgreSQL
  • Desenhar constraints, chaves, identity e índices em FKs, e normalizar até a 3FN sabendo quando desnormalizar
  • Escolher tipos certos para dinheiro, datas e fuso, e tratar exclusão lógica e retenção sob a LGPD
  • Conduzir cargas em lote e migrações de esquema com expandir/contrair, sem derrubar produção
1Intermediário

Escrever dados: INSERT, UPDATE, DELETE, MERGE e RETURNING

Consulta errada devolve resposta errada, e dá para refazer. Escrita errada altera o dado, e o dado errado já foi lido, replicado e faturado quando alguém percebe. Por isso este módulo trata escrita com mais cuidado que leitura: o raio de ação de cada comando, o que o banco garante (transações) e como o desenho das tabelas (constraints, tipos) impede o erro antes que ele aconteça.

INSERT

-- Sempre liste as colunas: o INSERT sobrevive a uma coluna nova na tabela
INSERT INTO atendimento (id_paciente, id_medico, id_setor, dt_atendimento, tipo, status, valor)
VALUES (7, 12, 3, TIMESTAMP '2025-03-10 08:30:00', 'CONSULTA', 'AGENDADO', 180.00);

-- INSERT ... SELECT: copia o resultado de uma consulta (arquivar, popular, materializar)
INSERT INTO atendimento_hist (id_atendimento, id_paciente, dt_atendimento, valor)
SELECT id_atendimento, id_paciente, dt_atendimento, valor
FROM atendimento
WHERE dt_atendimento < TIMESTAMP '2020-01-01 00:00:00';

Várias linhas de uma vez: VALUES (...), (...), (...) no PostgreSQL (e no Oracle 23ai); em versões anteriores do Oracle, INSERT ALL INTO t (...) VALUES (...) INTO t (...) VALUES (...) SELECT 1 FROM dual. Menos idas e vindas à rede é o ganho principal (seção 7). Colunas omitidas recebem o DEFAULT (ou NULL). Colunas de identity e sequências geram a chave (seção 3).

UPDATE com base em outra tabela

A sintaxe do join dentro do UPDATE não é portável. O exemplo cancela agendamentos de convênios inativos:

-- Subconsulta correlacionada: o EXISTS é obrigatório (veja a armadilha)
UPDATE atendimento a
SET a.status = 'CANCELADO'
WHERE a.status = 'AGENDADO'
  AND EXISTS (SELECT 1 FROM convenio c
              WHERE c.id_convenio = a.id_convenio AND c.ativo = 'N');

-- Para copiar valores de outra tabela, MERGE é o mais legível:
MERGE INTO atendimento a
USING (SELECT id_atendimento, valor_tabela FROM tabela_preco_dia) s
   ON (a.id_atendimento = s.id_atendimento)
WHEN MATCHED THEN UPDATE SET a.valor = s.valor_tabela;
-- UPDATE ... FROM: junta a outra tabela direto
UPDATE atendimento a
SET status = 'CANCELADO'
FROM convenio c
WHERE c.id_convenio = a.id_convenio
  AND c.ativo = false
  AND a.status = 'AGENDADO';

-- Copiar valores:
UPDATE atendimento a
SET valor = s.valor_tabela
FROM tabela_preco_dia s
WHERE s.id_atendimento = a.id_atendimento;
Armadilhas do UPDATE com outra tabela
  • Oracle: SET valor = (SELECT valor_tabela FROM ... WHERE ...) sem o EXISTS no WHERE atualiza todas as linhas, gravando NULL onde a subconsulta não acha nada. Se a subconsulta devolve mais de uma linha: erro ORA-01427.
  • PostgreSQL: se o FROM casa mais de uma linha para a mesma linha do alvo, o UPDATE não dá erro: aplica uma delas, sem garantia de qual. Garanta a unicidade da junção.
  • No MERGE, o mesmo problema vira erro (ORA-30926 no Oracle, "cannot affect row a second time" no PostgreSQL): é melhor assim, porque o erro avisa.

DELETE e TRUNCATE

-- Oracle e PostgreSQL: use EXISTS/IN para filtrar por outra tabela
DELETE FROM atendimento a
WHERE a.status = 'CANCELADO'
  AND a.dt_atendimento < TIMESTAMP '2023-01-01 00:00:00'
  AND NOT EXISTS (SELECT 1 FROM atendimento_item i WHERE i.id_atendimento = a.id_atendimento);
-- PostgreSQL também aceita DELETE ... USING outra_tabela WHERE ...

Upsert: MERGE e INSERT ... ON CONFLICT

"Se existe, atualiza; se não, insere" é tão comum que tem comando próprio. Fazer SELECT para checar e depois INSERT ou UPDATE tem uma condição de corrida: duas sessões checam ao mesmo tempo, as duas não acham, as duas inserem.

MERGE INTO paciente p
USING (SELECT :cpf AS cpf, :nome AS nome FROM dual) s
   ON (p.cpf = s.cpf)
WHEN MATCHED THEN
  UPDATE SET p.nome = s.nome
WHEN NOT MATCHED THEN
  INSERT (id_paciente, cpf, nome)
  VALUES (seq_paciente.NEXTVAL, s.cpf, s.nome);
-- Também aceita DELETE WHERE dentro do WHEN MATCHED (apaga as linhas atualizadas que satisfazem a condição)
-- Requer UNIQUE (ou índice único) em cpf. Atômico: sem corrida.
INSERT INTO paciente (cpf, nome)
VALUES ($1, $2)
ON CONFLICT (cpf)
DO UPDATE SET nome = EXCLUDED.nome;     -- EXCLUDED = a linha que tentou entrar

-- Só ignorar duplicatas:
INSERT INTO paciente (cpf, nome) VALUES ($1, $2) ON CONFLICT (cpf) DO NOTHING;
MERGE INTO paciente p
USING (SELECT $1::varchar AS cpf, $2::varchar AS nome) s
   ON p.cpf = s.cpf
WHEN MATCHED THEN UPDATE SET nome = s.nome
WHEN NOT MATCHED THEN INSERT (cpf, nome) VALUES (s.cpf, s.nome);

No PostgreSQL, ON CONFLICT é a escolha para upsert de uma linha ou poucas, concorrente: o banco garante que um dos dois caminhos vence, sem erro, mesmo com duas sessões simultâneas. O MERGE (15+) é mais geral (várias cláusulas, DELETE, condições) e serve melhor a cargas de uma tabela de staging inteira, mas sob concorrência pode falhar com violação de unicidade se outra sessão inserir a mesma chave entre a checagem e a inserção: trate com retry. Versões mais recentes do PostgreSQL acrescentaram mais recursos ao MERGE (por exemplo, RETURNING na 17); confira a documentação da sua versão.

RETURNING: devolver o que foi gravado

Depois de inserir, você quase sempre precisa do id gerado. Reconsultar (SELECT MAX(id)) é errado sob concorrência. O banco devolve na mesma operação:

-- RETURNING ... INTO: variável de PL/SQL ou bind de saída do driver
INSERT INTO paciente (id_paciente, cpf, nome)
VALUES (seq_paciente.NEXTVAL, :cpf, :nome)
RETURNING id_paciente INTO :id_novo;
-- RETURNING devolve linhas como um SELECT (também em UPDATE e DELETE)
INSERT INTO paciente (cpf, nome) VALUES ($1, $2)
RETURNING id_paciente;

UPDATE atendimento SET status = 'CANCELADO' WHERE id_atendimento = $1
RETURNING id_atendimento, status;

É também a forma de ver exatamente quais linhas um UPDATE ou DELETE atingiu (útil em auditoria e para encadear comandos). No Oracle, o RETURNING INTO de várias linhas usa BULK COLLECT INTO.

Hábito de segurança para quem escreve em produção
  1. Rode o mesmo WHERE como SELECT COUNT(*). Se o número não for o esperado, pare.
  2. Abra transação explícita (BEGIN no PostgreSQL; no Oracle, a transação já está aberta, e saiba que o cliente não está em autocommit).
  3. Execute, confira o número de linhas afetadas, confira por amostra com SELECT.
  4. Só então COMMIT. Na dúvida, ROLLBACK.
Na entrevista

"Como fazer upsert com segurança?" Em PostgreSQL, INSERT ... ON CONFLICT (atômico, exige índice único); em Oracle, MERGE. Explique por que SELECT-depois-INSERT falha sob concorrência e que o UNIQUE é quem garante a regra, não o código da aplicação.

Para gestores

Defina o processo de alteração manual em produção: ticket, script revisado por outra pessoa, contagem prévia, transação explícita, registro de quem executou. "UPDATE sem WHERE" é o incidente clássico, e o resto da conversa (backup, restauração parcial) fica muito mais caro que a revisão que o teria evitado. Dê ao time um caminho feliz e rápido para correções legítimas, para que ninguém seja tentado a atalhos.

2Intermediário

Transações: ACID, COMMIT, ROLLBACK, SAVEPOINT e DDL

Uma transação agrupa comandos que precisam acontecer juntos: ao dar baixa numa guia você grava o pagamento, atualiza o status do atendimento e lança o item de faturamento. Ou tudo vira realidade (COMMIT) ou nada (ROLLBACK). Sem isso, uma queda no meio deixa o banco com um pagamento sem guia.

  • Atomicidade: tudo ou nada.
  • Consistência: ao final, as constraints (PK, FK, CHECK, NOT NULL, UNIQUE) valem. É a garantia do banco sobre o dado, que só é tão boa quanto as regras que você declarou (seção 3).
  • Isolamento: transações concorrentes não enxergam o trabalho incompleto umas das outras. O padrão dos dois bancos é READ COMMITTED. Detalhes no módulo 10.
  • Durabilidade: depois do COMMIT, sobrevive a uma queda do servidor (o log de transações, redo no Oracle e WAL no PostgreSQL, foi gravado em disco antes de confirmar).
-- PostgreSQL: BEGIN abre a transação. Oracle: ela já está aberta (no SQL*Plus/SQL Developer).
BEGIN;
UPDATE atendimento SET status = 'REALIZADO' WHERE id_atendimento = 5001;
SAVEPOINT sp1;
INSERT INTO atendimento_item (id_atendimento, cod_procedimento, qtd, valor_unit)
VALUES (5001, '10101012', 1, 150.00);          -- suponha que falhe
ROLLBACK TO SAVEPOINT sp1;                      -- desfaz só o INSERT
COMMIT;                                         -- grava o UPDATE

Autocommit: saiba em que modo você está

Em autocommit, cada comando é uma transação que se confirma sozinha: não há como desfazer. Muitos clientes de PostgreSQL (psql, por padrão) trabalham em autocommit; SQL*Plus e SQL Developer, no Oracle, não: o UPDATE fica pendente até o COMMIT, segurando locks para os outros. Drivers e ORMs variam: confira a configuração do pool. A sessão esquecida com transação aberta é um dos causadores mais comuns de bloqueio em produção (módulo 10).

Em nenhum dos dois bancos uma leitura comum bloqueia escritores, nem o contrário (MVCC, módulo 10). O que as transações concorrentes podem sofrer (atualização perdida, write skew, bloqueios, deadlock) e como se defender (SELECT ... FOR UPDATE, SKIP LOCKED, versionamento otimista) é assunto do módulo 10.

Transação longa é custo para todo mundo

Uma transação aberta por minutos ou horas (um script que pede confirmação, uma tela esquecida, um job que processa tudo de uma vez) segura locks, impede o aproveitamento de undo/espaço (no PostgreSQL, atrasa o vacuum), aumenta o risco de deadlock e, se cair, faz um rollback demorado. Transação curta, só com o que precisa ser atômico; trabalho demorado em blocos (seção 7).

Na entrevista

"O que acontece se você der um CREATE TABLE no meio de uma transação?" No Oracle, ela é confirmada implicitamente. No PostgreSQL, o DDL entra na transação e pode ser desfeito. Quem sabe essa diferença já foi vítima dela: cite um script que gravou pela metade.

Para gestores

Padronize: transações curtas, nunca com interação humana no meio, timeouts configurados (de comando, de ocioso em transação, de lock) e retry com idempotência para os erros que o banco manda repetir. Monitore sessões "idle in transaction" (PostgreSQL) ou transações antigas (Oracle): são o alerta precoce de bloqueios futuros.

3Intermediário

Constraints, chaves, sequências e índices em chaves estrangeiras

Uma constraint é uma regra que o banco verifica em toda escrita, de qualquer aplicação, script ou correção manual. Ela é, ao mesmo tempo, documentação (quem lê o esquema entende as regras) e proteção (dado inválido não entra). Validação só na aplicação falha no dia em que existir um segundo sistema, uma carga ou um UPDATE manual.

UNIQUESem repetição (NULL é caso especial). Cria índice.paciente.cpf, medico.crm
CHECKCondição sobre a linha.status IN ('AGENDADO','REALIZADO','CANCELADO'), valor >= 0
NOT NULLObrigatoriedade.dt_atendimento
DEFAULTValor quando omitido (não é constraint, mas faz parte do contrato).status DEFAULT 'AGENDADO'

Dê nomes às constraints (pk_, fk_, ck_, ux_): a mensagem de erro dirá qual regra foi violada, em vez de um nome gerado automaticamente.

Detalhes que pegam

  • FK e ON DELETE: o padrão (NO ACTION/RESTRICT) impede apagar um pai que tem filhos. CASCADE apaga os filhos junto (perigoso em prontuário: apagar um paciente apagaria o histórico); SET NULL zera a referência. Escolha de propósito, e prefira RESTRICT em dados clínicos e financeiros.
  • UNIQUE e NULL: no PostgreSQL, dois NULL não violam UNIQUE (cada NULL é "diferente"); a partir da versão 15, UNIQUE NULLS NOT DISTINCT muda isso. No Oracle, uma coluna única aceita vários NULL; em índice composto, linhas com todas as colunas nulas não colidem, mas uma combinação parcialmente nula é comparada como valor.
  • CHECK só vê a própria linha: não consulta outras tabelas nem outras linhas. Regra entre linhas ("não pode haver dois atendimentos do mesmo médico no mesmo horário") pede UNIQUE, índice de exclusão (PostgreSQL, EXCLUDE) ou lógica transacional.
  • Constraint em tabela grande já populada: criar com validação varre a tabela inteira sob lock. PostgreSQL: ADD CONSTRAINT ... NOT VALID e depois VALIDATE CONSTRAINT. Oracle: ENABLE NOVALIDATE e depois VALIDATE. Veja a seção 8.
  • Constraints diferidas (DEFERRABLE INITIALLY DEFERRED, nos dois) verificam no COMMIT, e não a cada comando: útil para carregar tabelas com FKs circulares.

Índice na chave estrangeira

A PK e a UNIQUE ganham índice automaticamente. A FK, não, em nenhum dos dois bancos. Sem índice em atendimento.id_paciente, duas coisas ficam lentas:

Regra: toda FK de tabela grande ganha índice, em geral com a coluna da FK na frente ((id_paciente, dt_atendimento) serve à FK e às consultas por paciente ordenadas por data). Exceções raras: FK para tabela de domínio minúscula que nunca é apagada, ou coluna já coberta pelo prefixo de outro índice. Para achar as FKs sem índice: no PostgreSQL, compare pg_constraint com pg_index; no Oracle, consulte DBA_CONSTRAINTS e DBA_IND_COLUMNS. Índices a fundo no módulo 08.

Sequências e identity

-- Oracle 12c+ e PostgreSQL 10+: coluna de identidade (padrão SQL)
id_atendimento bigint GENERATED ALWAYS AS IDENTITY            -- recusa valor informado à mão
id_atendimento bigint GENERATED BY DEFAULT AS IDENTITY        -- aceita valor informado (útil em cargas)

-- Clássico: sequência separada
CREATE SEQUENCE seq_paciente START WITH 1 INCREMENT BY 1 CACHE 100;   -- Oracle: seq_paciente.NEXTVAL
-- PostgreSQL: nextval('seq_paciente')   (e o tipo legado serial usa isso por baixo)
  • Sequência não é transacional: um ROLLBACK não devolve o número. Buracos são normais (rollbacks, falhas, CACHE, queda). Número de guia ou de protocolo "sem buracos" por exigência legal não é tarefa para sequência: precisa de tabela de controle com lock (e custo de concorrência).
  • Depois de carregar dados com ids explícitos, reposicione a sequência (PostgreSQL: setval; Oracle: ajuste da sequência/identity), ou o próximo INSERT colide com uma chave existente.
  • Ordem da sequência não é ordem cronológica estrita sob concorrência (e no Oracle RAC com CACHE). Para "o mais recente", ordene por data, não por id.

Chave natural vs chave substituta

Natural (CPF, CRM, código TUSS)Substituta (identity, UUID)
OrigemExiste no mundo realGerada pelo banco, sem significado
EstabilidadePode mudar, vir errada, faltar (estrangeiro, recém-nascido sem CPF), ser compartilhadaImutável
Tamanho / joinsMaior, composta às vezesPequena, uniforme, joins simples
RiscoDado pessoal na chave espalha-se por todas as tabelas filhas e logs (LGPD)Não identifica ninguém, mas não impede duplicata real

Prática comum e saudável: chave substituta como PK e a chave natural com UNIQUE (CPF único quando informado). Em UUID: gen_random_uuid() está disponível no núcleo do PostgreSQL a partir da 13 (antes, extensão); no Oracle, SYS_GUID(). UUID aleatório espalha as inserções pelo índice (menos localidade, mais páginas divididas) e pesa 16 bytes; use quando precisa gerar ids fora do banco ou expor um identificador que não revele volume. UUIDs ordenados por tempo reduzem o problema; confira o suporte na sua versão.

CPF como PK, ou como número

CPF guardado como número perde zeros à esquerda (00123456789 vira 123456789); guarde como VARCHAR(11) (e valide o dígito verificador na aplicação ou em CHECK). Usar CPF como PK trava o cadastro de quem não tem, mistura pessoas quando o CPF é de um responsável e espalha dado pessoal por todas as tabelas.

Na entrevista

"Por que criar índice em chave estrangeira?" Porque o banco não cria sozinho, e sem ele o DELETE/UPDATE no pai e o join pai-filho varrem a tabela filha. "Chave natural ou substituta?" Substituta como PK, natural como UNIQUE, com a justificativa de estabilidade e de LGPD.

Para gestores

Constraint é o controle de qualidade mais barato que existe: roda sempre, em todo sistema. Quando o time argumenta "a aplicação já valida", pergunte quantas aplicações, scripts e cargas escrevem na tabela. Revise esquemas novos procurando o oposto: tabela sem PK, FK sem índice, coluna de status sem CHECK, datas como texto.

4Intermediário

Normalização: 1FN a 3FN e quando desnormalizar

Normalizar é organizar as tabelas para que cada fato esteja em um lugar só. O objetivo não é elegância, é evitar três defeitos: a anomalia de atualização (o nome do médico está em 40 mil linhas; corrigir um erro exige mudar todas, e as que sobram ficam inconsistentes), a de inserção (não dá para cadastrar um médico sem atendimento) e a de exclusão (apagar o último atendimento de um paciente apaga o cadastro dele junto).

1FNValores atômicos: uma coluna, um valor; sem listas nem grupos repetidos.procedimentos = '10101012; 40304361', ou telefone1, telefone2, telefone3. Correção: uma linha por item (atendimento_item), tabela filha de telefones.
2FNJá em 1FN, e cada coluna não-chave depende da chave inteira (importa só para chave composta).item(id_atendimento, cod_procedimento, nome_procedimento): o nome depende só de cod_procedimento. Correção: tabela procedimento.
3FNJá em 2FN, e nenhuma coluna não-chave depende de outra coluna não-chave (dependência transitiva).atendimento(id_medico, especialidade_medico): a especialidade é do médico, não do atendimento. paciente(cidade, uf) repetindo o par para todos os pacientes: cidade determina uf. Correção: tabela de cidades (ou aceitar a redundância por pragmatismo).

Resumo clássico: cada coluna depende "da chave, de toda a chave e só da chave". A 3FN costuma ser o ponto de parada em sistemas transacionais (OLTP). Existem formas superiores (Boyce-Codd, 4FN, 5FN), raramente discutidas na prática.

Quando desnormalizar (e quando não é desnormalização)

  • Histórico congelado não é redundância. atendimento_item.valor_unit guarda o preço no dia do atendimento. O preço da tabela muda; o valor cobrado, não. Do mesmo modo, o endereço do paciente no momento do faturamento. Isso é um fato histórico, não cópia a sincronizar.
  • Leitura intensiva: relatórios sobre milhões de linhas, painéis. Soluções: tabela de resumo (por dia, convênio), visão materializada (módulo 11), modelo dimensional em data warehouse. Preserve o modelo normalizado como fonte da verdade e derive o resto.
  • Contadores e totais (qtd_atendimentos no paciente) trazem a obrigação de manter o valor em dia, em trigger, job ou na aplicação. Faça só quando medir ganho e saiba quem é responsável pela consistência.
  • Atributos variáveis ou documentos externos (recursos FHIR, respostas de formulários) podem ir em coluna JSONB (PostgreSQL) ou JSON (Oracle 21c+ tipo nativo; antes, CLOB/VARCHAR2 com IS JSON) quando a estrutura não é consultada com frequência. Coluna JSON para tudo vira esquema sem constraints e SQL ilegível. Interoperabilidade em saúde: trilha de APIs, módulo 09.
Regra de bolso

Normalize até a 3FN no modelo transacional. Desnormalize depois de medir, em estruturas derivadas (resumo, visão materializada, réplica de leitura), com dono e mecanismo de atualização definidos. Desnormalizar "por desempenho" sem medição costuma trocar um problema barato (join) por um caro (inconsistência).

Na entrevista

"O que é 3FN?" Dê a frase da chave e um exemplo seu (especialidade no atendimento em vez de no médico). Depois mostre maturidade: "em relatório eu desnormalizo numa estrutura derivada, e valor histórico como o preço do procedimento no dia não é redundância".

Para gestores

A maioria das tabelas "monstro" nasce de pressa: uma coluna a mais para entregar a tela. Cada coluna que repete dado de outra tabela é uma dívida de consistência. No design review, pergunte "onde mora a verdade deste dado?" e exija uma resposta única.

Fuso horário: TIMESTAMP WITH TIME ZONE

Um instante ("a consulta começou às 08:30 em Salvador") é uma coisa; uma hora de relógio ("o consultório abre às 08:00") é outra. Para instantes, use TIMESTAMP WITH TIME ZONE. No PostgreSQL, o timestamptz guarda o instante normalizado (em UTC) e converte para o fuso da sessão ao exibir; o fuso informado na entrada é usado na conversão e não é guardado. No Oracle, TIMESTAMP WITH TIME ZONE guarda o instante com o fuso informado; TIMESTAMP WITH LOCAL TIME ZONE normaliza para o fuso do banco e converte para o da sessão na leitura, como o timestamptz. O TIMESTAMP simples, sem fuso, guarda só a hora de relógio: ambíguo assim que um servidor, um usuário ou um sistema integrado esteja em outro fuso.

SELECT SYSTIMESTAMP AT TIME ZONE 'America/Sao_Paulo' AS agora_sp,
       SYSTIMESTAMP AT TIME ZONE 'UTC'               AS agora_utc
FROM dual;

-- Constante com fuso explícito
SELECT TIMESTAMP '2025-03-10 08:30:00 -03:00' FROM dual;
SELECT now() AT TIME ZONE 'America/Sao_Paulo' AS agora_sp_sem_fuso,   -- timestamp sem fuso, em SP
       now()                                  AS agora_na_sessao;     -- timestamptz, exibido no fuso da sessão

SET TIME ZONE 'America/Sao_Paulo';

O Brasil tem fusos e já teve horário de verão
  • Sem horário de verão desde 2019: foi abolido por decreto federal em 2019 (o último período terminou em fevereiro de 2019). Mesmo assim, dados anteriores a 2019 têm as transições: a diferença entre duas datas de janeiro e de março de 2018 deve considerar a hora a mais ou a menos. Bancos com tabelas de fuso (tzdata, arquivo de fusos do Oracle) desatualizadas calculam errado e exigem aplicação de patch ao banco quando as regras mudam.
  • Mais de um fuso: Brasília (UTC-3), Amazonas e Mato Grosso (UTC-4), Acre (UTC-5), Fernando de Noronha (UTC-2). Guarde o instante com fuso e use o nome da região (America/Sao_Paulo), não um deslocamento fixo como -03:00, para o banco aplicar a regra histórica correta.
  • "Dia" depende do fuso: um atendimento às 22:30 em Brasília é do dia seguinte em UTC. Relatório por dia converte para o fuso de negócio antes de truncar.
  • Filtro por dia: use intervalo semiaberto (dt >= :dia AND dt < :dia + 1), e não TRUNC(dt) = :dia nem BETWEEN com 23:59:59: o primeiro derruba o índice (módulo 08) e o segundo perde frações de segundo.
Oracle: string vazia é NULL

No Oracle, '' é tratado como NULL: WHERE nome = '' nunca é verdadeiro, e LENGTH('') devolve NULL. No PostgreSQL, '' é um texto de tamanho zero, diferente de NULL. Código e testes portáveis não devem depender dessa diferença: defina na modelagem se "sem valor" é NULL e proíba o resto com CHECK.

Na entrevista

"Como guardar dinheiro?" NUMERIC/NUMBER com escala fixa, nunca ponto flutuante; alternativa de inteiro em centavos quando o ecossistema da aplicação prefere. "E datas?" Instante em timestamp with time zone, comparações por intervalo semiaberto, fuso de negócio explícito, e ciência de que o Brasil teve horário de verão até 2019.

Para gestores

Padronize no guia de modelagem: tipo de dinheiro, tipo de data/hora e de identificadores, nomes e convenções. Erros de tipo aparecem anos depois como "o relatório de março de 2018 está uma hora diferente" ou "o CPF perdeu um zero", e custam migração de dados em tabela grande.

Exclusão lógica vs física, retenção e LGPD

Apagar uma linha de verdade (exclusão física, DELETE) é irreversível sem backup e pode violar a integridade (filhos órfãos, histórico perdido). A exclusão lógica marca a linha como excluída e a mantém: uma coluna dt_exclusao TIMESTAMP (ou ativo). Em saúde, quase sempre é a escolha certa: atendimento cancelado, cadastro duplicado inativado e paciente que pede o encerramento do cadastro deixam rastro, e o prontuário tem prazo legal de guarda.

ReversívelSimSó por backup

ConsultasTodas precisam filtrar dt_exclusao IS NULL (esquecer é bug clássico)Nada a filtrar
UNIQUEPede índice parcial/funcional (abaixo)Simples
Tabela cresceSim: índices e estatísticas incluem o lixoNão (mas a área só é reaproveitada após limpeza)

-- PostgreSQL: índice parcial
CREATE UNIQUE INDEX ux_paciente_cpf_ativo ON paciente (cpf) WHERE dt_exclusao IS NULL;

-- Oracle: índice funcional (B-tree não indexa linhas em que todas as colunas são NULL)
CREATE UNIQUE INDEX ux_paciente_cpf_ativo
  ON paciente (CASE WHEN dt_exclusao IS NULL THEN cpf END);

-- Nos dois: a aplicação consulta a visão, não a tabela
CREATE VIEW paciente_ativo AS SELECT * FROM paciente WHERE dt_exclusao IS NULL;

LGPD: eliminar, anonimizar, reter

A Lei Geral de Proteção de Dados (Lei 13.709/2018) trata dados de saúde como dados pessoais sensíveis. Três regras de partida para quem modela e opera o banco (esta seção é orientação técnica, não parecer jurídico: confirme prazos e bases legais com o jurídico e o encarregado/DPO):

  • Término do tratamento = eliminação, salvo as hipóteses de conservação previstas na lei, como o cumprimento de obrigação legal ou regulatória. No prontuário do paciente há guarda obrigatória por prazo definido em norma (a legislação sobre prontuário eletrônico e as resoluções do CFM fixam o mínimo, hoje de 20 anos a partir do último registro; confirme a norma vigente). Um pedido de eliminação do titular não apaga o prontuário durante esse prazo; os dados que não têm obrigação de guarda (marketing, contatos extras) podem e devem ser eliminados.
  • Anonimização: dado que não permite identificar o titular por meios razoáveis deixa de ser dado pessoal. É irreversível. Substituir o nome por "ANONIMIZADO" não basta se data de nascimento + cidade + sexo ainda identificam a pessoa: generalize (ano de nascimento, UF, faixa etária) ou remova.
  • Pseudonimização: troca o identificador por um código, e a tabela de correspondência fica separada e protegida. O dado continua pessoal, com risco reduzido. Serve a análise e a pesquisa.
UPDATE paciente
SET nome          = 'ANONIMIZADO',
    cpf           = NULL,
    dt_nascimento = DATE '1900-01-01',        -- ou generalizar para o ano
    cidade        = NULL
WHERE id_paciente = :id
  AND dt_exclusao IS NOT NULL;
-- + registrar na tabela de auditoria QUEM executou e QUANDO, sem gravar o dado apagado
-- + tratar tabelas relacionadas (contatos, endereços, anexos) e as cópias em backup e logs
Onde o dado pessoal se esconde
  • Backups, réplicas e exportações: o DELETE não os alcança. A política de retenção de backup precisa estar alinhada com a de eliminação.
  • Logs e mensagens de erro: log_statement, planos com parâmetros, traces de ORM e erros de constraint (o PostgreSQL mostra o valor duplicado no DETAIL) podem registrar CPF e nome.
  • Ambientes de teste e homologação: cópia de produção sem mascaramento é um vazamento esperando acontecer. Mascare ou gere dados sintéticos.
  • Chaves naturais: CPF como chave primária ou em índices/colunas filhas multiplica os lugares a anonimizar (seção 3).
  • Acesso: privilégios mínimos, visões para telas que não precisam do CPF completo, auditoria de leitura de prontuário (PostgreSQL: row-level security; Oracle: VPD e Data Redaction, que podem exigir licença/edição específica).
Na entrevista

"Exclusão lógica ou física?" Lógica por padrão em dados que têm histórico e guarda obrigatória, com índice parcial/visão para as regras de unicidade e consultas; física quando o dado deve realmente sumir, após prazo de retenção e em todas as cópias. Aponte a tensão com a LGPD: soft delete não é eliminação.

Para gestores

Crie, com o DPO, um mapa de retenção por tipo de dado (prazo, base legal, forma de eliminação) e um job auditável que o execute. Sem isso, a empresa guarda tudo para sempre (risco de vazamento maior, custo de armazenamento) ou apaga o que não podia. Responda a uma solicitação de titular com um procedimento testado, não com a criatividade do dia.

7Avançado

Cargas em lote e commits por bloco

Inserir ou apagar milhões de linhas em um único comando e uma única transação parece simples, e é uma das formas mais comuns de derrubar um banco. A transação grande segura locks por muito tempo, enche o espaço de undo (Oracle) ou de WAL e de linhas mortas (PostgreSQL), e, se falhar na hora 3 de 4, o rollback leva quase o mesmo tempo. O outro extremo também é ruim: um COMMIT por linha obriga uma gravação síncrona do log a cada linha e a carga demora dez vezes mais.

EstratégiaEfeito
Um comando, uma transação giganteRápido se der certo; locks e undo/WAL enormes; rollback lento; sem ponto de retomada
Um commit por linhaSeguro, mas lento: espera de gravação do log a cada linha, mais idas e vindas pela rede
Commit por bloco (milhares de linhas)Equilíbrio: locks curtos, undo/WAL limitados, retomável a partir do último bloco confirmado

O tamanho do bloco (de mil a algumas dezenas de milhares de linhas) é medido, não chutado: cresça enquanto o tempo por linha cai e pare quando locks, memória ou latência dos demais começarem a sofrer. A carga em blocos precisa ser idempotente e retomável: se parar no meio, reexecutar não duplica nem pula nada (chave de controle, ON CONFLICT/MERGE, marca de lote processado).

Apagar ou atualizar em blocos

BEGIN
  LOOP
    DELETE FROM atendimento_hist
    WHERE dt_atendimento < TIMESTAMP '2015-01-01 00:00:00'
      AND ROWNUM <= 10000;
    EXIT WHEN SQL%ROWCOUNT = 0;
    COMMIT;
  END LOOP;
  COMMIT;
END;
/
CREATE OR REPLACE PROCEDURE limpar_hist() LANGUAGE plpgsql AS $$
DECLARE n integer;
BEGIN
  LOOP
    DELETE FROM atendimento_hist
    WHERE id_atendimento IN (SELECT id_atendimento FROM atendimento_hist
                             WHERE dt_atendimento < '2015-01-01'
                             LIMIT 10000);
    GET DIAGNOSTICS n = ROW_COUNT;
    EXIT WHEN n = 0;
    COMMIT;                       -- só em CALL de procedimento, fora de transação externa
  END LOOP;
END $$;
CALL limpar_hist();

Nem DELETE nem UPDATE têm LIMIT nos dois bancos, daí o ROWNUM no Oracle e a subconsulta com LIMIT no PostgreSQL. A condição precisa continuar achando linhas só enquanto houver trabalho, e ser apoiada por índice, ou cada bloco varre a tabela inteira.

Carregar rápido

  • Lote em vez de linha: INSERT de várias linhas, FORALL/executemany com array no Oracle, COPY no PostgreSQL (o caminho mais rápido para arquivo CSV; \copy no psql lê do cliente). Reduz idas e vindas ao servidor, que dominam o tempo em cargas por linha.
  • Direct-path (Oracle): INSERT /*+ APPEND */ ... SELECT e SQL*Loader gravam acima da marca d'água, gerando pouco undo; a tabela fica bloqueada até o commit, e o uso de NOLOGGING afeta a recuperação (backup logo depois). Saiba o que sua política de backup exige.
  • Staging: carregue o arquivo bruto numa tabela de passagem (sem constraints, só VARCHAR), valide e transforme com SQL, e só então grave nas tabelas finais com INSERT ... SELECT ou MERGE. Registros rejeitados vão para uma tabela de erros, com o motivo.
  • Índices e constraints: numa carga inicial enorme, criar os índices depois é mais rápido que mantê-los linha a linha. Em tabela viva, não desative: use blocos.
  • Estatísticas: depois de mudar muito a tabela, atualize-as (ANALYZE no PostgreSQL; DBMS_STATS no Oracle) para o otimizador não planejar com números velhos (módulo 07).
  • Particionamento: apagar um mês de dados antigo é DROP PARTITION/DETACH (instantâneo) em vez de milhões de DELETEs. No Oracle, particionamento é uma opção paga da Enterprise Edition; no PostgreSQL é nativo (módulo 11).
Carga em produção no horário de pico

Mesmo em blocos, a carga compete por I/O, CPU, locks e log com os usuários. Rode em janela de baixa carga, com pausas entre blocos (sleep), acompanhando atraso de réplica e tamanho do WAL/undo, e com um botão de parar que não deixe nada pela metade.

Na entrevista

"Como apagar 50 milhões de linhas de uma tabela em uso?" Em blocos com commit a cada N mil linhas apoiados por índice, com monitoramento; ou, se os dados são por período, particionar e descartar a partição. Cite undo/WAL e rollback, e o fato de a operação ser retomável.

Para gestores

Toda carga ou limpeza grande em produção deve ter: plano de ensaio com volume real, janela aprovada, critério de parada, plano de retomada e responsável acompanhando. O custo desses cuidados é pequeno perto de uma lentidão geral num dia de movimento.

8Avançado

Migrações de esquema seguras: expandir e contrair

Mudar a estrutura de uma tabela viva é mais perigoso que mudar o código, porque o banco é compartilhado: durante um deploy convivem versões antigas e novas da aplicação, e um ALTER TABLE pode pedir um lock exclusivo que enfileira todas as consultas atrás dele. A técnica expandir e contrair (expand/contract) divide a mudança em passos pequenos, cada um compatível com o código anterior e o seguinte.

Mudanças comuns e como fazê-las sem derrubar

MudançaRiscoForma segura
Adicionar coluna com defaultReescrever a tabela inteira sob lockPostgreSQL 11+: ADD COLUMN ... DEFAULT constante é só metadados (default volátil reescreve). Oracle: nas versões atuais, adicionar coluna com default também é, em geral, só metadados; confirme para a sua versão.
Criar índiceBloquear escrita durante a construçãoPostgreSQL: CREATE INDEX CONCURRENTLY (mais lento, não pode ficar dentro de transação, deixa índice inválido se falhar: dropar e refazer). Oracle: CREATE INDEX ... ONLINE (construção online pode depender da edição).
Adicionar FK/CHECK em tabela grandeVarredura completa sob lockPostgreSQL: ADD CONSTRAINT ... NOT VALID e depois VALIDATE CONSTRAINT (lock mais leve). Oracle: ENABLE NOVALIDATE e depois VALIDATE.
SET NOT NULLVarredura sob lockPostgreSQL 12+: com um CHECK (col IS NOT NULL) já validado, o SET NOT NULL dispensa a varredura. Preencha os nulos antes, em lotes.
Mudar tipo de colunaReescrita completa e incompatibilidade de leituraColuna nova do tipo certo, backfill em lotes, troca e remoção (expandir/contrair).
Renomear coluna ou tabelaQuebra o código antigo no mesmo instanteNão renomeie no lugar: crie a nova, migre, remova a velha. Ou use uma visão com o nome antigo durante a transição.
Remover colunaIrreversível; código antigo ainda pode lê-laSó depois de nenhuma versão em produção usar a coluna (confirme em logs/estatísticas). Antes, pare de escrever e, se preciso, torne-a opcional.

O lock que enfileira o mundo

Um ALTER TABLE precisa de lock forte, mas só por um instante, se conseguir entrar. Se há uma transação longa tocando a tabela, o ALTER espera; e todas as consultas que chegam depois dele esperam atrás dele: em segundos, a aplicação inteira parece travada por causa de um DDL "inofensivo". Defesas: no PostgreSQL, SET lock_timeout = '3s' antes do DDL (falha rápido, tenta de novo depois); no Oracle, o DDL sem espera dá ORA-00054, e a espera é controlada por DDL_LOCK_TIMEOUT. Rode migrações fora de picos e verifique transações longas antes.

Outras práticas: migrações versionadas e em git (Flyway, Liquibase ou equivalente), executadas pelo pipeline e não à mão; ensaio num ambiente com volume de produção; reverter por "rolar para frente" com uma nova migração, não por scripts de desfazer nunca testados; no Oracle, para mudanças complexas existem a redefinição online (DBMS_REDEFINITION) e a Edition-Based Redefinition, esta última com requisitos próprios. Aproveite o DDL transacional do PostgreSQL: a migração aplica inteira ou nada (com a exceção de comandos como CONCURRENTLY).

Backfill de uma vez só

Um UPDATE paciente SET nova_coluna = f(antiga) sem lotes é a transação gigante da seção anterior, com locks em todas as linhas e crescimento da tabela por versões mortas (PostgreSQL). Faça o backfill em blocos, com índice no critério de progresso, e com pausas.

Na entrevista

"Como renomear uma coluna sem downtime?" Não se renomeia no lugar: expande (coluna nova), escreve nos dois, preenche em lotes, troca a leitura, contrai (remove a antiga). Cite o lock_timeout e o ensaio com volume real.

Para gestores

Exija que toda mudança de esquema tenha: migração versionada, ensaio com volume, análise de lock, plano de volta e janela. Evite a combinação "DDL manual + sexta à tarde + transação longa em aberto". O time que domina expandir/contrair faz deploys no meio do dia sem avisar ninguém, o que vale mais que qualquer ferramenta.

Pontos: lista de colunas explícita, mesmo WHERE nas duas pontas, transação explícita, e NOT EXISTS contra o histórico para a rotina ser repetível sem duplicar.

E2Cancele os atendimentos AGENDADO cujo convênio está inativo, em Oracle e em PostgreSQL. Que erro silencioso acontece no Oracle se você esquecer o EXISTS?

É o exemplo da seção 1. PostgreSQL: UPDATE ... FROM convenio c WHERE c.id_convenio = a.id_convenio AND c.ativo = false AND a.status = 'AGENDADO'. Oracle: UPDATE ... SET status = 'CANCELADO' WHERE status = 'AGENDADO' AND EXISTS (SELECT 1 FROM convenio c WHERE c.id_convenio = a.id_convenio AND c.ativo = 'N'). Num SET coluna = (subconsulta) sem EXISTS, o Oracle atualiza todas as linhas do filtro e grava NULL onde a subconsulta não acha nada. Antes de executar: SELECT COUNT(*) com o mesmo WHERE.

E3Escreva um upsert de paciente por CPF seguro para duas sessões simultâneas e diga o que garante a segurança.

PostgreSQL: INSERT INTO paciente (cpf, nome) VALUES ($1, $2) ON CONFLICT (cpf) DO UPDATE SET nome = EXCLUDED.nome RETURNING id_paciente;. Oracle: MERGE da seção 1 (com UNIQUE em cpf; se duas sessões inserirem a mesma chave ao mesmo tempo, uma recebe ORA-00001 e deve repetir). Quem garante a regra é a constraint UNIQUE: sem ela, nenhum dos dois comandos impede duplicata. O RETURNING devolve o id sem nova consulta.

E4Em PostgreSQL, a sequência BEGIN; UPDATE a; INSERT b (viola FK); UPDATE c; COMMIT; o que grava? E no Oracle, com autocommit desligado? Como proteger só o INSERT?

PostgreSQL: o erro do INSERT aborta a transação; o UPDATE c responde "current transaction is aborted" e o COMMIT equivale a ROLLBACK: nada é gravado. Oracle: só o INSERT é desfeito; o UPDATE a e o UPDATE c continuam pendentes e o COMMIT os grava (possivelmente um estado incoerente, se a regra de negócio os queria juntos). Para tratar só o INSERT, use SAVEPOINT sp1 antes e ROLLBACK TO SAVEPOINT sp1 depois do erro: nos dois bancos a transação segue consistente. Na aplicação, trate o erro e decida entre repetir e abortar tudo.

E5A tabela guia(id_guia, id_paciente, nome_paciente, cpf_paciente, cod_proc, nome_proc, valor_proc, id_operadora, nome_operadora, telefone_operadora) tem PK composta (id_guia, cod_proc). Indique as violações de 1FN a 3FN e proponha as tabelas.

2FN: nome_proc depende só de cod_proc (parte da chave); id_paciente, nome_paciente, cpf_paciente, id_operadora dependem só de id_guia. 3FN: nome_paciente e cpf_paciente dependem de id_paciente (não-chave); nome_operadora e telefone_operadora dependem de id_operadora. 1FN: se telefone_operadora guardar vários números, viola. Resultado: paciente(id_paciente, nome, cpf), operadora(id_operadora, nome) + operadora_telefone, procedimento(cod_proc, nome), guia(id_guia, id_paciente, id_operadora) e guia_item(id_guia, cod_proc, valor_proc). O valor_proc fica no item porque é o valor cobrado naquela guia (histórico), e não redundância.

E6Você precisa trocar paciente.telefone VARCHAR(50) (texto livre) por paciente_contato(id_paciente, tipo, numero) numa tabela de 8 milhões de linhas, sem parada. Descreva os passos.
  1. Expandir: criar paciente_contato com PK, FK para paciente e índice na FK. Deploy da aplicação que ainda usa só telefone.
  2. Migrar: aplicação passa a gravar nos dois lugares; backfill em lotes de 10 mil, com commit por bloco, pausa entre eles e tratamento dos textos sujos (vários números em um campo, formatos), registrando os rejeitados.
  3. Validar: comparar contagens e amostras entre o campo antigo e a tabela nova.
  4. Trocar: aplicação lê da tabela nova (com feature flag, para voltar rápido).
  5. Contrair: parar de escrever em telefone; depois de um período sem leituras, remover a coluna em migração separada, com lock_timeout (PostgreSQL) ou DDL_LOCK_TIMEOUT (Oracle).
10Avançado

Cenários práticos de trabalho

Cenário 1: um UPDATE sem WHERE rodou em produção

Um analista rodou UPDATE atendimento SET status = 'CANCELADO' sem o WHERE, com autocommit ligado. Dez minutos depois, a recepção percebe agendamentos "sumindo".

O que fazer
  • Parar o dano: comunicar o incidente, pausar fluxos que consomem o status (integrações, envio de mensagens), impedir novas escritas se preciso.
  • Avaliar a recuperação: no Oracle, consulta ao passado (AS OF TIMESTAMP, via undo) pode recuperar os valores antigos se o undo ainda os guarda; no PostgreSQL, não existe "desfazer": restaurar backup em instância separada (recuperação até um ponto no tempo) e comparar. Nos dois, corrigir só as linhas afetadas, em lotes, sem restaurar o banco todo.
  • Reconciliar o que mudou depois do erro (atendimentos legitimamente cancelados nesse intervalo) para não sobrescrever o correto.
  • Prevenir: acesso de escrita manual restrito, transação explícita por padrão nos clientes, revisão por segunda pessoa, contagem prévia, e um postmortem sem culpa.

Cenário 2: pacientes duplicados mesmo com "validação" no cadastro

O cadastro verifica "CPF já existe?" antes de inserir, e aparecem duplicatas a cada semana, principalmente em horários de pico.

O que fazer
  • Diagnóstico: é a condição de corrida do SELECT-depois-INSERT (duas recepções em paralelo). Confirme pela diferença de milissegundos entre os dt_cadastro duplicados.
  • Correção: limpar e mesclar as duplicatas existentes (módulo 05, deduplicação com FKs reapontadas), criar UNIQUE em cpf (índice parcial se houver exclusão lógica ou CPF opcional) e trocar o fluxo para INSERT ... ON CONFLICT/MERGE e tratar o erro de unicidade na tela ("já cadastrado: abrir o registro").
  • Atenção a dados reais: pessoas sem CPF, CPF do responsável em criança e CPF digitado errado: o UNIQUE expõe o caso, e a regra de negócio precisa dizer o que fazer.

Cenário 3: a migração de sexta travou o sistema por 4 minutos

Um ALTER TABLE atendimento ADD CONSTRAINT ... FOREIGN KEY foi aplicado às 17h. A aplicação inteira ficou sem resposta, e voltou sozinha.

O que fazer
  • Causa provável: o DDL esperou por uma transação longa e a fila de consultas formou-se atrás dele; depois, a validação varreu a tabela de 80 milhões de linhas sob lock.
  • Refazer certo: PostgreSQL com NOT VALID e VALIDATE CONSTRAINT depois; Oracle com ENABLE NOVALIDATE e VALIDATE; lock_timeout/DDL_LOCK_TIMEOUT curtos e nova tentativa; horário de baixa carga; verificar transações longas antes.
  • Processo: ensaio com volume real, checklist de lock na revisão de migração e migrações aplicadas pelo pipeline, não à mão.

Cenário 4: pedido de eliminação de dados de um paciente

Um paciente pede, por e-mail, "apague todos os meus dados". Ele foi atendido há 3 anos e tem prontuário.

O que fazer
  • Não apagar às cegas: acionar o encarregado (DPO) e o jurídico; o prontuário tem guarda obrigatória, então a resposta ao titular explica o que será eliminado e o que será mantido, e por quê (base legal).
  • Eliminar o que não tem obrigação de guarda: contatos de marketing, consentimentos revogados, cópias em sistemas secundários; restringir acesso ao que fica.
  • Executar com procedimento: script revisado, em transação, com registro de auditoria sem o dado apagado, e verificação em réplicas, backups (política de retenção) e logs.
  • Responder no prazo e guardar a evidência. Para o futuro, o mapa de retenção por tipo de dado (seção 6) transforma isso em rotina.
11Básico

Glossário

ACID
Atomicidade, Consistência, Isolamento, Durabilidade: as garantias de uma transação.
Autocommit
Modo em que cada comando se confirma sozinho, sem possibilidade de desfazer.
SAVEPOINT
Ponto de retorno dentro de uma transação, para desfazer só uma parte.
Upsert
Inserir ou, se já existe, atualizar: MERGE ou ON CONFLICT.
RETURNING
Devolve as linhas gravadas (por exemplo, o id gerado) na própria operação.
Constraint
Regra verificada pelo banco em toda escrita: PK, FK, UNIQUE, CHECK, NOT NULL.
Chave substituta
Identificador técnico sem significado de negócio (identity, UUID), em contraste com a chave natural (CPF).
Identity / sequência
Gerador de números de chave; não é transacional, então aceita buracos.
Normalização
Organizar tabelas para que cada fato esteja em um lugar só (1FN, 2FN, 3FN).
Desnormalização
Redundância deliberada, em geral em estruturas derivadas, para ganhar leitura.
timestamptz
Tipo PostgreSQL de instante com fuso: guarda em UTC e exibe no fuso da sessão.
Exclusão lógica
Marcar a linha como excluída em vez de apagá-la.
Anonimização
Tornar o dado irreversivelmente não identificável; sai do alcance da LGPD.
Pseudonimização
Trocar o identificador por um código com tabela de correspondência separada; o dado segue pessoal.
Expandir/contrair
Mudança de esquema em etapas compatíveis: adicionar, migrar, trocar, remover.
Backfill
Preenchimento em lotes de uma coluna ou tabela nova com dados existentes.
12IntermediárioAvançado

Perguntas de entrevista

01O que é uma transação e o que significa ACID?

Grupo de comandos que se confirma ou se desfaz como uma unidade. Atomicidade (tudo ou nada), Consistência (constraints valem ao final), Isolamento (transações concorrentes não veem o trabalho incompleto umas das outras) e Durabilidade (após o COMMIT, sobrevive a uma queda).

02Qual a diferença entre DELETE e TRUNCATE?

DELETE é DML, linha a linha, aceita WHERE e pode ser desfeito. TRUNCATE é DDL, esvazia a tabela quase instantaneamente; no Oracle faz commit implícito e não volta, no PostgreSQL é transacional. Falha se houver FK de outra tabela apontando para ela.

03Como fazer UPDATE com dados de outra tabela em Oracle e PostgreSQL?

PostgreSQL: UPDATE ... SET ... FROM outra WHERE .... Oracle: subconsulta correlacionada com EXISTS ou MERGE. Cuidados: sem EXISTS, o Oracle grava NULL nas linhas sem correspondência; no PostgreSQL, junção com mais de uma correspondência aplica uma delas sem aviso.

04O que é upsert e como fazer com segurança?

Inserir ou atualizar se existir. PostgreSQL: INSERT ... ON CONFLICT DO UPDATE (atômico, exige índice único); Oracle e PostgreSQL 15+: MERGE. O padrão SELECT-depois-INSERT tem condição de corrida; quem garante a unicidade é a constraint.

05Para que serve o RETURNING?

Devolver as linhas afetadas (por exemplo, o id gerado) na mesma operação, sem nova consulta e sem corrida. PostgreSQL: RETURNING em INSERT/UPDATE/DELETE; Oracle: RETURNING ... INTO variáveis, com BULK COLLECT para várias linhas.

06Diferença de DDL e transações entre Oracle e PostgreSQL?

No Oracle, todo DDL faz commit implícito antes e depois. No PostgreSQL, DDL é transacional e pode ser desfeito. Também: no PostgreSQL um erro aborta a transação inteira até um ROLLBACK (ou ROLLBACK TO SAVEPOINT); no Oracle só o comando que falhou é desfeito.

07Qual o nível de isolamento padrão e como Oracle e PostgreSQL diferem?

Os dois usam READ COMMITTED por padrão. O Oracle não oferece REPEATABLE READ (tem SERIALIZABLE por snapshot e READ ONLY); o PostgreSQL tem REPEATABLE READ por snapshot e SERIALIZABLE verdadeiro (SSI), com erro de serialização a repetir. Nenhum dos dois faz leitura suja. Detalhes no módulo 10.

08Por que criar índice em chave estrangeira?

O banco não o cria sozinho. Sem ele, apagar ou alterar o pai e o join pai-filho varrem a tabela filha (e, no Oracle, podem exigir locks mais fortes). A regra é indexar toda FK de tabela grande, com a coluna da FK à frente.

09Chave natural ou substituta?

Substituta (identity/UUID) como PK, pela estabilidade, tamanho e por não espalhar dado pessoal; natural (CPF, CRM) com UNIQUE, que também previne duplicatas. Em saúde, CPF pode faltar, ser errado ou ser do responsável, o que o desqualifica como PK.

10Uma sequência pode ter buracos? Por quê?

Sim. Sequências não são transacionais: rollback não devolve o número, e CACHE e quedas perdem valores. Numeração legal sem buracos exige tabela de controle com lock, não sequência.

11Explique 1FN, 2FN e 3FN com um exemplo.

1FN: valores atômicos (não guardar lista de procedimentos numa coluna). 2FN: cada coluna depende da chave inteira (nome do procedimento não fica no item da guia). 3FN: nenhuma coluna depende de outra não-chave (especialidade pertence ao médico, não ao atendimento). "Da chave, de toda a chave e só da chave."

12Quando desnormalizar?

Depois de medir, em estruturas derivadas (tabelas de resumo, visões materializadas, data warehouse), com um dono e um mecanismo de atualização. Valor histórico (preço do procedimento no dia do atendimento) não é redundância, é fato. Coluna JSON só para atributos variáveis, não para fugir da modelagem.

13Como guardar dinheiro e datas?

Dinheiro em NUMERIC/NUMBER com escala fixa (nunca float). Instantes em timestamp with time zone usando nome de região (America/Sao_Paulo), filtros por intervalo semiaberto, e atenção ao fato de o Brasil não ter horário de verão desde 2019, mas os dados anteriores terem. CPF e CEP em texto.

14Exclusão lógica ou física? E a LGPD?

Lógica quando há histórico e guarda obrigatória (índice parcial/visão para unicidade e consultas); física quando o dado deve sumir após o prazo de retenção, inclusive em backups, réplicas e logs. Soft delete não é eliminação para a LGPD. Anonimização é irreversível e tira o dado do alcance da lei; pseudonimização continua sendo dado pessoal. Prazos e bases legais, com jurídico e DPO.

15Como apagar 50 milhões de linhas de uma tabela em uso?

Em blocos (milhares de linhas) com commit por bloco, apoiados por índice, com pausas e monitoramento de undo/WAL e de atraso de réplica, de forma retomável; ou, se os dados são por período, particionar e descartar a partição. Evitar a transação gigante e o commit por linha.

16Como mudar o tipo de uma coluna grande sem parada?

Expandir/contrair: coluna nova, escrita nos dois lados, backfill em lotes, troca da leitura e só depois remoção da antiga. Cada etapa é um deploy reversível, com lock_timeout nos DDLs e ensaio em volume de produção.

17Um ALTER TABLE simples travou a aplicação inteira. Por quê e como evitar?

O DDL esperou por uma transação longa e as consultas que chegaram depois ficaram na fila atrás dele. Evitar com lock_timeout (PostgreSQL) ou DDL_LOCK_TIMEOUT (Oracle) e nova tentativa, checar transações longas antes, usar NOT VALID/NOVALIDATE para constraints e CONCURRENTLY/ONLINE para índices, e rodar fora do pico.

18Como você estrutura o processo de mudanças de dados e de esquema no seu time?

Esquema por migrações versionadas no git, aplicadas pelo pipeline, ensaiadas em volume real, com análise de locks e plano de volta (rolar para frente). Alterações manuais em produção só por ticket, script revisado, contagem prévia, transação explícita e registro. Constraints e tipos certos no desenho como controle de qualidade; mapa de retenção com o DPO; e postmortem sem culpa quando algo escapa.
