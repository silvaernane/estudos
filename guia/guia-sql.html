Do SELECT ao plano de execução

Uma trilha para quem já escreve SELECT e JOIN e quer entender o que o banco faz com a consulta, por que ela fica lenta e como deixá-la rápida. Os exemplos usam um esquema de clínica e mostram Oracle e PostgreSQL lado a lado.

Básico consolida o que você já usa Intermediário recursos que substituem muito código Avançado desempenho e funcionamento interno

Use o seletor no topo para escolher o banco dos exemplos. Ao terminar um capítulo, marque como estudado: o progresso fica salvo neste navegador.

00

O esquema de exemplo

Todos os exemplos usam quatro tabelas. Vale ler com atenção, porque os nomes voltam em todos os capítulos.

paciente     (id_paciente PK, nome, cpf VARCHAR(11), dt_nascimento, cidade)
medico       (id_medico PK, nome, especialidade)
convenio     (id_convenio PK, nome)
atendimento  (id_atendimento PK,
              id_paciente  FK → paciente,
              id_medico    FK → medico,
              id_convenio  FK → convenio  -- NULL = particular
              dt_atendimento  TIMESTAMP,
              tipo    -- 'CONSULTA' | 'EXAME' | 'RETORNO'
              status  -- 'AGENDADO' | 'REALIZADO' | 'CANCELADO'
              valor   NUMERIC(10,2))

Pense em atendimento como a tabela grande (milhões de linhas, cresce todo dia) e nas outras como tabelas de cadastro (milhares de linhas). Essa diferença de tamanho é o que torna a otimização interessante.

01Básico

A ordem lógica de execução

Você escreve SELECT primeiro, mas o banco o avalia quase por último. Entender essa ordem explica metade dos erros que parecem misteriosos.

  1. FROM / JOIN
  2. WHERE
  3. GROUP BY
  4. HAVING
  5. SELECT
  6. DISTINCT
  7. ORDER BY
  8. FETCH / LIMIT

Consequências práticas:

  • Um alias do SELECT não existe no WHERE. O WHERE roda antes. Repita a expressão ou use uma subconsulta/CTE.
  • O ORDER BY enxerga os aliases, porque roda depois do SELECT.
  • WHERE filtra linhas; HAVING filtra grupos. Um filtro que não depende de agregação deve ir no WHERE, para descartar linhas antes de agrupar.
  • Funções de janela (capítulo 6) são calculadas na etapa do SELECT, por isso não podem aparecer no WHERE.
-- (sintaxe Oracle; no PostgreSQL a idade seria date_part('year', age(dt_nascimento)))
-- ERRO: o alias "idade" ainda não existe quando o WHERE é avaliado
SELECT nome, TRUNC(MONTHS_BETWEEN(SYSDATE, dt_nascimento) / 12) AS idade
FROM paciente
WHERE idade >= 60;

-- Certo: calcule numa subconsulta e filtre por fora
SELECT *
FROM (SELECT nome, TRUNC(MONTHS_BETWEEN(SYSDATE, dt_nascimento) / 12) AS idade
      FROM paciente) p
WHERE p.idade >= 60;
Ordem lógica não é ordem física

Essa é a ordem de significado. O otimizador pode executar em outra ordem física (aplicar um filtro dentro de um join, usar um índice para evitar o sort), desde que o resultado seja o mesmo. Os capítulos avançados tratam dessa ordem física.

02Básico

NULL e a lógica de três valores

NULL significa "valor desconhecido". Qualquer comparação com NULL resulta em UNKNOWN, que não é verdadeiro nem falso, e o WHERE só devolve linhas em que a condição é verdadeira.

ExpressãoResultado
NULL = NULLUNKNOWN (não é verdadeiro)
NULL <> 5UNKNOWN
col IS NULLa forma certa de testar
TRUE OR UNKNOWNTRUE
FALSE AND UNKNOWNFALSE
NOT UNKNOWNUNKNOWN

Onde isso morde

-- Quer os atendimentos que NÃO são do convênio 10.
-- Os particulares (id_convenio NULL) somem do resultado!
SELECT * FROM atendimento WHERE id_convenio <> 10;

-- Correto
SELECT * FROM atendimento
WHERE id_convenio <> 10 OR id_convenio IS NULL;
  • COUNT(*) conta linhas. COUNT(id_convenio) conta só os valores não nulos. COUNT(DISTINCT x) ignora nulos.
  • SUM, AVG, MIN e MAX ignoram NULL. Um AVG sobre uma coluna com nulos divide apenas pelos não nulos.
  • Para trocar NULL por um valor padrão, use COALESCE(id_convenio, 0) (padrão SQL, funciona nos dois bancos). No Oracle existe também NVL.
Particularidade do Oracle

No Oracle, string vazia '' é NULL. WHERE nome = '' nunca retorna nada; use WHERE nome IS NULL. No PostgreSQL, '' e NULL são coisas diferentes.

03Básico

JOINs sem surpresas

TipoDevolve
INNER JOINsó os pares que casam dos dois lados
LEFT JOINtodas as linhas da esquerda; a direita vem NULL quando não casa
FULL JOINtodas as linhas dos dois lados
CROSS JOINtodas as combinações (produto cartesiano)

Filtro no ON ou no WHERE?

Em INNER JOIN tanto faz. Em LEFT JOIN, muda o resultado. Um filtro sobre a tabela da direita colocado no WHERE elimina as linhas que vieram com NULL, e o LEFT JOIN vira um INNER JOIN disfarçado.

-- Objetivo: todos os médicos, com o total de consultas realizadas (zero se não tiver)

-- ERRADO: médicos sem atendimento somem, pois a.status é NULL para eles
SELECT m.nome, COUNT(a.id_atendimento) AS qtd
FROM medico m
LEFT JOIN atendimento a ON a.id_medico = m.id_medico
WHERE a.status = 'REALIZADO'
GROUP BY m.nome;

-- CERTO: o filtro da tabela da direita vai no ON
SELECT m.nome, COUNT(a.id_atendimento) AS qtd
FROM medico m
LEFT JOIN atendimento a ON a.id_medico = m.id_medico
                       AND a.status = 'REALIZADO'
GROUP BY m.nome;

Semi-join e anti-join: EXISTS e NOT EXISTS

Quando você só quer saber se existe correspondência, sem trazer colunas do outro lado, não faça JOIN. O JOIN multiplica linhas; o EXISTS para no primeiro registro encontrado.

-- Pacientes que tiveram pelo menos um exame (semi-join)
SELECT p.id_paciente, p.nome
FROM paciente p
WHERE EXISTS (SELECT 1 FROM atendimento a
              WHERE a.id_paciente = p.id_paciente
                AND a.tipo = 'EXAME');

-- Pacientes que NUNCA foram atendidos (anti-join)
SELECT p.id_paciente, p.nome
FROM paciente p
WHERE NOT EXISTS (SELECT 1 FROM atendimento a
                  WHERE a.id_paciente = p.id_paciente);
Armadilha clássica: NOT IN com NULL

WHERE x NOT IN (SELECT id_convenio FROM atendimento) devolve zero linhas se a subconsulta tiver um único NULL, porque x <> NULL é UNKNOWN. Para anti-join, prefira sempre NOT EXISTS.

Fan-out: o JOIN que multiplica linhas

Ao juntar uma tabela "um" com uma tabela "muitos", cada linha do lado "um" se repete. Se você juntar duas tabelas "muitos" ao mesmo pai, as linhas se multiplicam entre si e as somas ficam erradas. O sintoma típico é alguém colocar DISTINCT para "consertar". A correção real é agregar antes de juntar:

-- Total faturado por paciente, já agregado, depois juntado ao cadastro
WITH fat AS (
  SELECT id_paciente, SUM(valor) AS total
  FROM atendimento
  WHERE status = 'REALIZADO'
  GROUP BY id_paciente
)
SELECT p.nome, f.total
FROM paciente p
JOIN fat f ON f.id_paciente = p.id_paciente;
Regra de bolso

Se você precisou de DISTINCT para o resultado "ficar certo", desconfie do JOIN. Quase sempre há um join faltando condição ou uma tabela que deveria ser EXISTS.

04Básico

Agregação

Toda coluna do SELECT precisa estar no GROUP BY ou dentro de uma função de agregação. HAVING filtra depois de agrupar.

-- Médicos com mais de 100 consultas realizadas em 2026
SELECT id_medico, COUNT(*) AS qtd, SUM(valor) AS faturado
FROM atendimento
WHERE status = 'REALIZADO'                         -- filtra linhas (antes)
  AND dt_atendimento >= DATE '2026-01-01'
  AND dt_atendimento <  DATE '2027-01-01'
GROUP BY id_medico
HAVING COUNT(*) > 100;                             -- filtra grupos (depois)

Agregação condicional: várias contagens numa passada

Em vez de três consultas (uma por status), leia a tabela uma vez só:

SELECT id_medico,
       COUNT(*)                                              AS total,
       SUM(CASE WHEN status = 'REALIZADO' THEN 1 ELSE 0 END) AS realizados,
       SUM(CASE WHEN status = 'CANCELADO' THEN 1 ELSE 0 END) AS cancelados,
       SUM(CASE WHEN status = 'REALIZADO' THEN valor END)    AS faturado
FROM atendimento
GROUP BY id_medico;
-- O PostgreSQL tem a cláusula FILTER, mais legível (CASE também funciona)
SELECT id_medico,
       COUNT(*)                                       AS total,
       COUNT(*)   FILTER (WHERE status = 'REALIZADO') AS realizados,
       COUNT(*)   FILTER (WHERE status = 'CANCELADO') AS cancelados,
       SUM(valor) FILTER (WHERE status = 'REALIZADO') AS faturado
FROM atendimento
GROUP BY id_medico;

Esse padrão também resolve "pivotar" linhas em colunas (um mês por coluna, por exemplo) sem precisar de PIVOT.

Subtotais com ROLLUP

-- Totais por médico e tipo, com subtotal por médico e total geral
SELECT id_medico, tipo, SUM(valor) AS total
FROM atendimento
GROUP BY ROLLUP (id_medico, tipo);
-- As linhas de subtotal vêm com tipo = NULL; GROUPING(tipo) = 1 as identifica.
05Intermediário

Subconsultas e CTEs

Há três lugares onde uma subconsulta pode morar, e cada um tem um custo diferente:

  • No FROM (tabela derivada): vira uma tabela temporária lógica. Ótimo para quebrar o problema em etapas.
  • No WHERE (IN, EXISTS): o otimizador costuma reescrever como semi-join. Bom.
  • No SELECT (subconsulta escalar): pode rodar uma vez por linha. Em consultas grandes, reescreva como JOIN.
-- Lento em tabelas grandes: uma subconsulta por paciente
SELECT p.nome,
       (SELECT MAX(a.dt_atendimento) FROM atendimento a
         WHERE a.id_paciente = p.id_paciente) AS ultimo
FROM paciente p;

-- Normalmente melhor: agrega uma vez e junta
SELECT p.nome, u.ultimo
FROM paciente p
LEFT JOIN (SELECT id_paciente, MAX(dt_atendimento) AS ultimo
           FROM atendimento GROUP BY id_paciente) u
       ON u.id_paciente = p.id_paciente;
Depende

Se você vai trazer só 20 pacientes (com paginação), a subconsulta escalar com um bom índice em (id_paciente, dt_atendimento) pode ser mais rápida que agregar a tabela inteira. Otimização é sempre sobre volume. Meça.

CTE (WITH): legibilidade

A CTE dá nome a uma etapa. Ela torna consultas longas legíveis de cima para baixo.

WITH realizados AS (
  SELECT * FROM atendimento WHERE status = 'REALIZADO'
),
por_medico AS (
  SELECT id_medico, COUNT(*) AS qtd, SUM(valor) AS total
  FROM realizados GROUP BY id_medico
)
SELECT m.nome, pm.qtd, pm.total, pm.total / pm.qtd AS ticket_medio
FROM por_medico pm
JOIN medico m ON m.id_medico = pm.id_medico
ORDER BY pm.total DESC;
CTE e desempenho
  • PostgreSQL 12+: a CTE é "embutida" na consulta principal, a menos que seja referenciada mais de uma vez. Para forçar que seja calculada uma vez só: WITH x AS MATERIALIZED (...). Antes do 12, toda CTE era materializada, o que impedia otimizações.
  • Oracle: decide sozinho entre embutir ou materializar numa tabela temporária. Os hints /*+ MATERIALIZE */ e /*+ INLINE */ forçam um dos dois.

CTE recursiva: hierarquias

-- Gerar um calendário com todos os dias de novembro (útil para "dias sem atendimento")
WITH RECURSIVE dias (dia) AS (         -- no Oracle, omita a palavra RECURSIVE
  SELECT DATE '2026-11-01' FROM dual   -- no PostgreSQL, sem "FROM dual"
  UNION ALL
  SELECT dia + 1 FROM dias WHERE dia < DATE '2026-11-30'
)
SELECT d.dia, COUNT(a.id_atendimento) AS qtd
FROM dias d
LEFT JOIN atendimento a
       ON a.dt_atendimento >= d.dia AND a.dt_atendimento < d.dia + 1
GROUP BY d.dia
ORDER BY d.dia;

No PostgreSQL, generate_series(DATE '2026-11-01', DATE '2026-11-30', INTERVAL '1 day') faz o calendário diretamente. No Oracle há também CONNECT BY LEVEL <= 30.

06Intermediário

Funções de janela

É o recurso que mais economiza código. Uma função de janela calcula algo sobre um grupo de linhas sem colapsar as linhas, como faria o GROUP BY.

funcao() OVER (PARTITION BY grupo   -- divide em grupos (opcional)
               ORDER BY coluna      -- ordem dentro do grupo (opcional)
               ROWS BETWEEN ...)    -- moldura (opcional)

Top-1 por grupo: o último atendimento de cada paciente

SELECT *
FROM (
  SELECT a.*,
         ROW_NUMBER() OVER (PARTITION BY id_paciente
                            ORDER BY dt_atendimento DESC) AS rn
  FROM atendimento a
) x
WHERE rn = 1;
FunçãoEmpates (mesma data)
ROW_NUMBER()1, 2, 3, 4: numeração única, desempate arbitrário
RANK()1, 1, 3, 4: empatados dividem a posição e pulam a seguinte
DENSE_RANK()1, 1, 2, 3: empatados dividem, sem pular

Comparar com a linha anterior: LAG e LEAD

-- Intervalo em dias entre atendimentos consecutivos do mesmo paciente
SELECT id_paciente, dt_atendimento,
       LAG(dt_atendimento) OVER (PARTITION BY id_paciente
                                 ORDER BY dt_atendimento) AS anterior,
       CAST(dt_atendimento AS DATE)
         - CAST(LAG(dt_atendimento) OVER (PARTITION BY id_paciente
                                          ORDER BY dt_atendimento) AS DATE) AS dias
FROM atendimento;

Útil para achar retornos em menos de 30 dias, gaps em sequências e variações mês a mês.

Totais acumulados e médias móveis

WITH mensal AS (
  SELECT TRUNC(dt_atendimento, 'MM') AS mes, SUM(valor) AS total   -- PG: DATE_TRUNC('month', dt_atendimento)
  FROM atendimento WHERE status = 'REALIZADO'
  GROUP BY TRUNC(dt_atendimento, 'MM')
)
SELECT mes, total,
       SUM(total) OVER (ORDER BY mes)                                  AS acumulado,
       AVG(total) OVER (ORDER BY mes ROWS BETWEEN 2 PRECEDING
                                          AND CURRENT ROW)             AS media_3m,
       total / SUM(total) OVER ()                                      AS pct_do_total
FROM mensal
ORDER BY mes;
A moldura padrão

Com ORDER BY e sem moldura explícita, o padrão é RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. Com RANGE, linhas com o mesmo valor de ordenação entram juntas no cálculo, o que surpreende em acumulados com datas repetidas. Escreva ROWS BETWEEN ... quando quiser linha a linha.

07Intermediário

Conjuntos, top-N e paginação

UNION ou UNION ALL

UNION remove duplicatas, o que exige ordenar ou fazer hash de todo o resultado. UNION ALL só concatena. Se você sabe que as partes não se sobrepõem, ou se duplicatas não importam, use UNION ALL. Os outros operadores são INTERSECT e EXCEPT (no Oracle, MINUS; o 21c aceita os dois).

Top-N

-- Padrão SQL: Oracle 12c+ e PostgreSQL
SELECT * FROM atendimento
ORDER BY valor DESC
FETCH FIRST 10 ROWS ONLY;      -- PG também aceita LIMIT 10
Oracle legado: ROWNUM

ROWNUM é atribuído antes do ORDER BY. WHERE ROWNUM <= 10 ORDER BY valor DESC pega 10 linhas quaisquer e depois as ordena. O jeito certo com ROWNUM é ordenar numa subconsulta e filtrar por fora.

Paginação: OFFSET fica mais lento a cada página

OFFSET 100000 obriga o banco a ler e descartar 100 mil linhas. A página 5000 é muito mais lenta que a página 1. A alternativa é a paginação por chave (keyset, ou "seek"): guarde a última linha vista e peça "as próximas depois dela".

-- Índice ideal: (dt_atendimento, id_atendimento)
-- :dt e :id são os valores da última linha da página anterior
SELECT *
FROM atendimento
WHERE dt_atendimento < :dt
   OR (dt_atendimento = :dt AND id_atendimento < :id)
ORDER BY dt_atendimento DESC, id_atendimento DESC
FETCH FIRST 50 ROWS ONLY;
-- Índice ideal: (dt_atendimento, id_atendimento)
-- O PostgreSQL aceita comparação de tuplas, que usa o índice diretamente
SELECT *
FROM atendimento
WHERE (dt_atendimento, id_atendimento) < ($1, $2)
ORDER BY dt_atendimento DESC, id_atendimento DESC
LIMIT 50;

O id_atendimento serve de desempate, para a ordenação ser única e nenhuma linha se perder entre páginas. O custo da página 5000 fica igual ao da página 1. A desvantagem é não dar para pular direto para "página 37".

08Intermediário

Escrita de dados e transações

Upsert: inserir ou atualizar

MERGE INTO paciente p
USING (SELECT :cpf AS cpf, :nome AS nome FROM dual) s
   ON (p.cpf = s.cpf)
WHEN MATCHED THEN
  UPDATE SET p.nome = s.nome
WHEN NOT MATCHED THEN
  INSERT (id_paciente, cpf, nome)
  VALUES (seq_paciente.NEXTVAL, s.cpf, s.nome);
-- Requer um índice UNIQUE em cpf
INSERT INTO paciente (cpf, nome)
VALUES ($1, $2)
ON CONFLICT (cpf)
DO UPDATE SET nome = EXCLUDED.nome;
-- O PostgreSQL 15+ também tem MERGE.

UPDATE com base em outra tabela

-- Cancela agendamentos de médicos inativos
UPDATE atendimento a
SET status = 'CANCELADO'
WHERE a.status = 'AGENDADO'
  AND EXISTS (SELECT 1 FROM medico m
              WHERE m.id_medico = a.id_medico
                AND m.ativo = 'N');
UPDATE atendimento a
SET status = 'CANCELADO'
FROM medico m
WHERE m.id_medico = a.id_medico
  AND m.ativo = false
  AND a.status = 'AGENDADO';

Transações e ACID

Uma transação agrupa comandos que precisam acontecer juntos. Ou tudo é gravado (COMMIT) ou nada (ROLLBACK).

  • Atomicidade: tudo ou nada.
  • Consistência: constraints (PK, FK, CHECK, NOT NULL) valem ao final.
  • Isolamento: transações concorrentes não enxergam o trabalho incompleto umas das outras. O padrão dos dois bancos é READ COMMITTED: cada comando vê o que já estava commitado quando ele começou.
  • Durabilidade: depois do COMMIT, sobrevive a uma queda do servidor.
Diferenças que pegam
  • Oracle: todo DDL (CREATE, ALTER, TRUNCATE) faz COMMIT implícito antes e depois. Um CREATE INDEX no meio de um script grava o que estava pendente.
  • PostgreSQL: DDL é transacional. Dá para criar uma tabela e desfazer com ROLLBACK.
  • Ferramentas mudam o comportamento: muitos clientes PostgreSQL trabalham em autocommit; SQL Developer e SQL*Plus não. Saiba em qual modo você está antes de rodar um UPDATE.
Hábito de segurança

Antes de um UPDATE ou DELETE, rode o mesmo WHERE como SELECT COUNT(*). Se o número não for o esperado, não execute.

09Avançado

Como o banco executa uma consulta

SQL é declarativo: você diz o que quer, e o otimizador decide como buscar. Otimizar consultas é, em grande parte, entender e influenciar essa decisão.

  1. Parse: verifica sintaxe e permissões e resolve nomes de tabelas e colunas.
  2. Otimização: gera planos candidatos (qual índice, qual ordem de join, qual algoritmo) e estima o custo de cada um.
  3. Execução: roda o plano escolhido.

Custo vem de estimativa de linhas

O otimizador não sabe quantas linhas sua consulta vai retornar: ele estima a partir de estatísticas (número de linhas, valores distintos, histogramas). A estimativa de linhas em cada etapa se chama cardinalidade. Ela decide tudo:

  • Se estimar que o filtro retorna 5 linhas, escolhe índice e nested loops.
  • Se estimar 2 milhões, escolhe full scan e hash join.
A ideia central desta trilha

Quase todo plano ruim nasce de uma estimativa de cardinalidade errada. Ao investigar uma consulta lenta, a pergunta principal é "onde o banco achou que viriam N linhas e vieram 1000×N?".

Seletividade

Seletividade é a fração de linhas que um filtro deixa passar. id_atendimento = 123 é muito seletivo (1 linha). status = 'REALIZADO' pode ser pouco seletivo (80% da tabela). Índice compensa para filtros seletivos. Para filtros pouco seletivos, ler a tabela inteira de forma sequencial costuma ser mais barato que milhões de leituras aleatórias via índice.

Não existe um número mágico. Dependendo de como os dados estão dispostos no disco, o ponto de virada fica entre menos de 1% e uns 20% das linhas.

10Avançado

Índices por dentro

O índice padrão nos dois bancos é a B-tree: uma árvore balanceada cujas folhas guardam os valores indexados em ordem, cada um com um ponteiro para a linha na tabela (ROWID no Oracle, TID no PostgreSQL). As folhas são ligadas entre si, o que permite percorrer um intervalo em ordem.

Uma busca com índice tem até três partes. Só a primeira é sempre barata:

  1. Descer a árvore até a primeira folha: poucas leituras.
  2. Percorrer as folhas do intervalo: proporcional a quantas entradas casam.
  3. Ir à tabela buscar as colunas que não estão no índice: uma leitura aleatória por linha. Com 200 mil linhas, essa etapa domina o custo.

Índice composto: a ordem das colunas importa

Um índice em (id_medico, dt_atendimento) está ordenado primeiro por médico e, dentro de cada médico, por data, como uma lista telefônica ordenada por sobrenome e depois por nome.

FiltroUsa bem o índice (id_medico, dt_atendimento)?
id_medico = 7Sim, pelo prefixo
id_medico = 7 AND dt_atendimento >= :iniSim, o caso ideal
id_medico = 7 ORDER BY dt_atendimentoSim, e dispensa o sort
dt_atendimento >= :iniMal. Seria como procurar todos os "João" numa lista ordenada por sobrenome.
id_medico IN (7, 9) AND dt_atendimento >= :iniSim, uma busca por valor do IN
Regra para montar índices compostos
  1. Colunas filtradas por igualdade primeiro.
  2. Depois, uma coluna de intervalo (>, BETWEEN, LIKE 'abc%') ou de ORDER BY.
  3. Colunas depois de um intervalo ajudam pouco a navegar, mas ainda servem para filtrar dentro do índice ou cobrir a consulta.

O Oracle (index skip scan) e o PostgreSQL 18+ conseguem às vezes usar um índice sem a primeira coluna, quando ela tem poucos valores distintos. É uma rede de segurança; não projete contando com isso.

Índice que cobre a consulta

Se todas as colunas que a consulta usa estão no índice, o banco não precisa visitar a tabela (etapa 3 some). No Oracle aparece como só INDEX RANGE SCAN, sem TABLE ACCESS; no PostgreSQL, como Index Only Scan.

-- Consulta frequente: faturamento de um médico num período
CREATE INDEX ix_atend_med_dt_valor
  ON atendimento (id_medico, dt_atendimento, status, valor);
-- INCLUDE guarda colunas só na folha, sem fazer parte da chave de busca
CREATE INDEX ix_atend_med_dt
  ON atendimento (id_medico, dt_atendimento)
  INCLUDE (status, valor);
-- Index Only Scan depende do visibility map: tabelas com VACUUM em dia.

Índices de expressão e índices parciais

-- Busca por nome sem diferenciar maiúsculas
CREATE INDEX ix_pac_nome_up ON paciente (UPPER(nome));
-- usado por: WHERE UPPER(nome) = UPPER(:nome)

-- Índice "parcial": o Oracle não guarda entradas totalmente NULL.
-- Só os agendados entram no índice, que fica pequeno.
CREATE INDEX ix_atend_agendado
  ON atendimento (CASE WHEN status = 'AGENDADO' THEN id_medico END);
-- usado por (a expressão precisa ser idêntica):
-- WHERE CASE WHEN status = 'AGENDADO' THEN id_medico END = :med
-- Busca por nome sem diferenciar maiúsculas
CREATE INDEX ix_pac_nome_up ON paciente (upper(nome));
-- usado por: WHERE upper(nome) = upper($1)

-- Índice parcial: só os agendados entram no índice
CREATE INDEX ix_atend_agendado
  ON atendimento (id_medico, dt_atendimento)
  WHERE status = 'AGENDADO';
-- usado quando a consulta inclui WHERE status = 'AGENDADO'
Oracle: IS NULL e índice

Como entradas totalmente nulas não entram em B-tree no Oracle, WHERE id_convenio IS NULL não usa um índice só em id_convenio. Truque conhecido: CREATE INDEX ... ON atendimento (id_convenio, 0). A constante garante que toda linha tenha entrada. O PostgreSQL indexa NULLs normalmente.

Outros tipos de índice

  • Bitmap (Oracle): bom para colunas de poucos valores em data warehouse. Em tabelas com muitas escritas concorrentes causa bloqueios sérios; evite em OLTP.
  • GIN + pg_trgm (PostgreSQL): acelera LIKE '%texto%' e buscas em JSONB e arrays.
  • BRIN (PostgreSQL): minúsculo, para tabelas enormes cuja ordem física acompanha a coluna (datas de inserção).
  • Oracle Text: busca textual em documentos.

Índice tem custo

  • Todo INSERT, DELETE e UPDATE de coluna indexada precisa atualizar cada índice. Dez índices numa tabela = onze escritas por linha.
  • Antes de criar um índice novo, veja se dá para estender um existente. (id_medico) e (id_medico, dt_atendimento) juntos são redundantes: o segundo atende os dois casos.
  • Indexe as chaves estrangeiras usadas em joins e deletes. No Oracle, uma FK sem índice causa bloqueio da tabela filha inteira quando a PK da mãe é alterada ou excluída, e cada DELETE na mãe vira full scan na filha.
  • Em produção, crie índices sem travar escritas: CREATE INDEX ... ONLINE (Oracle) ou CREATE INDEX CONCURRENTLY (PostgreSQL).
11Avançado

Anti-padrões que matam índices

Uma condição é sargável (de Search ARGument ABLE) quando o banco consegue usá-la para navegar no índice. A regra geral: deixe a coluna "nua" de um lado da comparação. Qualquer transformação sobre a coluna obriga o banco a calcular a expressão para cada linha.

1. Função sobre a coluna

-- Ruim: TRUNC é aplicado a todas as linhas, o índice em dt_atendimento não é usado
WHERE TRUNC(dt_atendimento) = DATE '2026-11-10'
WHERE TO_CHAR(dt_atendimento, 'YYYY-MM') = '2026-11'
WHERE EXTRACT(YEAR FROM dt_atendimento) = 2026

-- Bom: intervalo semiaberto [início, fim)
WHERE dt_atendimento >= DATE '2026-11-10'
  AND dt_atendimento <  DATE '2026-11-11'

Use sempre >= início AND < fim. BETWEEN '2026-11-01' AND '2026-11-30' perde tudo o que aconteceu depois de 00:00 do dia 30.

2. Conversão implícita de tipo

-- cpf é VARCHAR2. Comparar com número faz o Oracle aplicar TO_NUMBER(cpf)
-- em cada linha: full scan (e erro ORA-01722 se houver um cpf não numérico)
WHERE cpf = 12345678901

-- Bom: mesmo tipo dos dois lados
WHERE cpf = '12345678901'

Acontece muito com parâmetros vindos da aplicação (número passado para coluna texto, TIMESTAMP comparado com DATE). O PostgreSQL é mais rígido e costuma dar erro em vez de converter em silêncio. No Oracle, procure INTERNAL_FUNCTION ou TO_NUMBER na seção de predicados do plano.

3. Curinga no início do LIKE

WHERE nome LIKE 'MARIA%'      -- usa índice (prefixo conhecido)
WHERE nome LIKE '%SILVA%'     -- B-tree não ajuda: precisa de pg_trgm/Oracle Text

4. Aritmética sobre a coluna

WHERE valor * 1.1 > 500       -- ruim
WHERE valor > 500 / 1.1       -- bom: a conta fica do lado da constante
WHERE dt_atendimento + 30 > SYSDATE   -- ruim
WHERE dt_atendimento > SYSDATE - 30   -- bom

5. OR entre colunas diferentes

-- Difícil para um índice só
WHERE id_medico = :m OR id_paciente = :p

-- Os bancos podem combinar dois índices (BitmapOr no PG, OR-expansion no Oracle).
-- Se não fizerem, reescreva:
SELECT * FROM atendimento WHERE id_medico = :m
UNION ALL
SELECT * FROM atendimento WHERE id_paciente = :p
                            AND (id_medico <> :m OR id_medico IS NULL);

6. NVL/COALESCE "para cobrir parâmetro opcional"

-- Padrão comum em telas de busca, péssimo para o otimizador
WHERE id_medico = NVL(:medico, id_medico)
  AND (:dt_ini IS NULL OR dt_atendimento >= :dt_ini)

Um único plano precisa servir tanto para "filtrou por médico" quanto para "não filtrou". Quando a tela tem muitos filtros opcionais, monte o SQL dinamicamente na aplicação, incluindo só os filtros preenchidos, sempre com bind variables (capítulo 13).

7. SELECT *

Traz colunas que você não usa, impede índices de cobrir a consulta e trafega mais dados pela rede. Liste as colunas.

8. N+1 na aplicação

Buscar 500 atendimentos e depois fazer 500 consultas, uma para o nome de cada paciente, custa 501 idas e voltas ao banco. Faça um JOIN, ou busque os 500 nomes com um IN. A consulta pode ser rápida e o sistema lento por causa da latência repetida.

9. COUNT para verificar existência

-- Conta tudo só para saber se é maior que zero
SELECT COUNT(*) FROM atendimento WHERE id_paciente = :p;

-- Para no primeiro
SELECT 1 FROM atendimento WHERE id_paciente = :p FETCH FIRST 1 ROWS ONLY;

10. Negações e diferente

status <> 'CANCELADO' e NOT IN (...) costumam ser pouco seletivos e não navegam no índice. Se a lista de valores desejados é pequena e conhecida, prefira a forma positiva: status IN ('AGENDADO','REALIZADO').

Lendo planos de execução

O plano é a resposta do otimizador à pergunta "como você vai buscar isso?". Há dois tipos, e a diferença importa:

  • Plano estimado: o que o otimizador pretende fazer, com números estimados. Não executa a consulta.
  • Plano real: o que aconteceu, com linhas e tempos medidos. Executa a consulta. É o que você quer para diagnosticar.
-- Estimado
EXPLAIN PLAN FOR
SELECT ... ;
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

-- Real: rode a consulta com o hint e, na mesma sessão, peça o plano do último cursor
SELECT /*+ GATHER_PLAN_STATISTICS */ ... ;
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));
-- Compare E-Rows (estimado) com A-Rows (real) linha a linha
-- Estimado
EXPLAIN SELECT ... ;

-- Real: ANALYZE executa de verdade, BUFFERS mostra leituras de páginas
EXPLAIN (ANALYZE, BUFFERS) SELECT ... ;

-- Para UPDATE/DELETE, proteja-se: ANALYZE executa a alteração!
BEGIN;
EXPLAIN (ANALYZE, BUFFERS) DELETE FROM ... ;
ROLLBACK;

O plano é uma árvore. Os nós mais internos (mais indentados) produzem linhas para os nós de cima. Leia de dentro para fora: comece pelas folhas (os acessos a tabelas) e suba até a raiz.

Algoritmos de JOIN

AlgoritmoComo funcionaBom quando

O desastre clássico: o otimizador estima 1 linha no lado de fora, escolhe nested loops, e vêm 500 mil. O lado de dentro roda 500 mil vezes. No Oracle, veja a coluna Starts; no PostgreSQL, loops.

PostgreSQL: rows é por loop

Em actual ... rows=40 loops=10000, o total de linhas é 400 mil, não 40. O tempo também é por loop.

O que procurar num plano real

  1. Diferença grande entre estimado e real (E-Rows vs A-Rows; rows= estimado vs actual rows). O primeiro nó, de baixo para cima, onde a diferença passa de 10× é geralmente a causa raiz.
  2. Muitas linhas descartadas (Rows Removed by Filter, ou A-Rows alto num acesso seguido de filtro que derruba quase tudo): falta índice ou a condição não é sargável.
  3. Nested loops com muitas iterações (Starts/loops altos).
  4. Sort ou hash usando disco: Sort Method: external merge Disk no PG (aumente work_mem só para a sessão, ou reduza o volume); uso de TEMP no Oracle.
  5. Onde está o tempo: A-Time (Oracle) ou actual time (PG) mostram o nó mais caro. Ataque esse primeiro.
13Avançado

Bind variables e cache de planos

Otimizar uma consulta custa CPU. Por isso os bancos guardam planos para reaproveitar. Mas só reaproveitam se o texto do SQL for idêntico.

-- Literal: cada paciente gera um SQL diferente, e cada um passa pelo otimizador
SELECT * FROM atendimento WHERE id_paciente = 1001;
SELECT * FROM atendimento WHERE id_paciente = 1002;

-- Bind: um texto só, otimizado uma vez e reaproveitado
SELECT * FROM atendimento WHERE id_paciente = :id;    -- Oracle
SELECT * FROM atendimento WHERE id_paciente = $1;     -- PostgreSQL (prepared statement)
  • Oracle: SQL com literais gera hard parse a cada execução, enche a shared pool e, em sistemas com muitos usuários, causa contenção que trava o banco inteiro. Em Oracle, binds são obrigatórios em OLTP.
  • PostgreSQL: cada conexão tem seu cache. Um prepared statement usa planos "custom" nas 5 primeiras execuções e depois pode passar para um plano "genérico", se ele não parecer pior.
  • Segurança: binds são também a proteção principal contra SQL injection. Nunca concatene entrada do usuário no texto do SQL.

O lado ruim: dados desbalanceados

Se 95% dos atendimentos são 'REALIZADO' e 0,1% são 'AGENDADO', o plano ideal para cada valor é diferente: full scan para um, índice para o outro. Com bind, um plano só serve aos dois.

  • O Oracle olha o valor do bind na primeira execução (bind peeking) e, desde o 11g, pode manter planos diferentes por faixa de valores (adaptive cursor sharing), se houver histograma na coluna.
  • O PostgreSQL controla esse comportamento com plan_cache_mode (auto, force_custom_plan, force_generic_plan).
  • Colunas com poucos valores fixos e muito desbalanceados podem ficar como literal (ex.: status = 'AGENDADO'), mantendo os binds nos valores que variam por usuário.
14Avançado

Estatísticas e estimativas

As estatísticas são o "mapa" que o otimizador usa para estimar cardinalidade. Mapa desatualizado gera plano ruim.

-- Quando foram coletadas?
SELECT table_name, num_rows, last_analyzed
FROM user_tables WHERE table_name = 'ATENDIMENTO';

-- Coletar manualmente (ex.: depois de uma carga grande)
EXEC DBMS_STATS.GATHER_TABLE_STATS(USER, 'ATENDIMENTO');

-- Colunas correlacionadas (tipo e status não são independentes)
SELECT DBMS_STATS.CREATE_EXTENDED_STATS(USER, 'ATENDIMENTO', '(TIPO,STATUS)')
FROM dual;
-- Quando foram coletadas?
SELECT relname, n_live_tup, last_analyze, last_autoanalyze
FROM pg_stat_user_tables WHERE relname = 'atendimento';

-- Coletar manualmente
ANALYZE atendimento;

-- Colunas correlacionadas
CREATE STATISTICS st_atend_tipo_status (dependencies, mcv)
  ON tipo, status FROM atendimento;
ANALYZE atendimento;

Por que as estimativas erram

  • Estatísticas velhas: a tabela tinha 10 mil linhas na coleta e agora tem 10 milhões. É comum em tabelas carregadas por ETL logo antes de serem consultadas.
  • Datas além do máximo conhecido: a estatística diz que a maior data é ontem; o filtro pede "hoje", e o otimizador estima quase zero linhas.
  • Distribuição desigual sem histograma: o banco assume que todos os valores têm a mesma frequência.
  • Colunas correlacionadas: o otimizador multiplica as seletividades como se fossem independentes (cidade = 'BH' e estado = 'MG' vira uma estimativa pequena demais). Estatísticas estendidas resolvem.
  • Expressões e funções: o banco não sabe estimar UPPER(nome) = ... sem estatística sobre a expressão. Criar um índice de expressão gera essa estatística no PostgreSQL; no Oracle, use estatísticas estendidas sobre a expressão.
Cuidado em produção

Coletar estatísticas muda planos de todas as consultas da tabela, para melhor ou para pior. Os dois bancos já coletam automaticamente (job noturno no Oracle, autovacuum/autoanalyze no PG). Coleta manual em produção é algo para combinar com o DBA.

15Avançado

Concorrência, locks e MVCC

Oracle e PostgreSQL usam MVCC (controle de concorrência por múltiplas versões): quem lê vê uma "foto" consistente dos dados e leitura não bloqueia escrita, nem escrita bloqueia leitura. Só escritas na mesma linha esperam uma pela outra.

Bloqueios e deadlocks

  • UPDATE e DELETE travam as linhas afetadas até o COMMIT ou ROLLBACK. Transação aberta esquecida = linhas travadas para todo mundo.
  • Deadlock: a sessão A trava a linha 1 e espera a 2; a sessão B trava a 2 e espera a 1. O banco detecta e cancela uma delas (ORA-00060 / deadlock detected). A prevenção é sempre alterar linhas na mesma ordem (por exemplo, por id crescente).
  • Transações curtas: não deixe uma transação aberta enquanto espera o usuário ou uma API externa.

Fila de processamento com SKIP LOCKED

Para vários workers consumindo a mesma tabela de tarefas (fila de notificações, por exemplo) sem pegar o mesmo item:

-- Cada worker pega até 10 itens que ninguém está processando
SELECT id, payload
FROM fila_notificacao
WHERE status = 'PENDENTE'
ORDER BY id
FETCH FIRST 10 ROWS ONLY
FOR UPDATE SKIP LOCKED;
-- processa, faz UPDATE status = 'ENVIADO' e COMMIT
Oracle: FETCH FIRST com FOR UPDATE

No Oracle, FETCH FIRST junto com FOR UPDATE gera erro (ORA-02014), e ROWNUM <= 10 é aplicado antes de pular as linhas travadas, então pode trazer menos itens que o pedido. O padrão no Oracle é abrir um cursor FOR UPDATE SKIP LOCKED e fazer fetch de N linhas (ou usar Advanced Queuing). No PostgreSQL a consulta acima funciona como está, ou com LIMIT 10.

O custo do MVCC

  • PostgreSQL: UPDATE grava uma versão nova da linha e deixa a antiga como "morta". O VACUUM (normalmente o autovacuum) recicla esse espaço. Uma transação aberta por horas impede essa limpeza, e as tabelas incham (bloat). Fique de olho em sessões idle in transaction em pg_stat_activity.
  • Oracle: as versões antigas ficam no UNDO. Uma consulta muito longa pode precisar de uma versão que já foi sobrescrita e falhar com ORA-01555 snapshot too old. Fazer COMMIT dentro de um loop que lê o mesmo cursor é uma causa clássica.
16Avançado

Particionamento, views materializadas e hints

Particionamento

Divide uma tabela grande em pedaços físicos, por exemplo uma partição por mês de dt_atendimento. Os ganhos:

  • Partition pruning: uma consulta de novembro lê só a partição de novembro. Só funciona se o filtro for sobre a chave de partição e sargável.
  • Manutenção: apagar dados antigos vira DROP PARTITION (instantâneo) em vez de um DELETE de milhões de linhas.

Particionamento não é acelerador universal: consultas que não filtram pela chave de partição podem ficar mais lentas, porque visitam todas as partições. No Oracle, é uma opção paga da edição Enterprise.

Views materializadas

Guardam o resultado de uma consulta pesada, como um painel de faturamento mensal. Leitura instantânea, mas os dados ficam tão atualizados quanto o último refresh.

CREATE MATERIALIZED VIEW mv_fat_mensal
  BUILD IMMEDIATE REFRESH COMPLETE ON DEMAND AS
SELECT TRUNC(dt_atendimento, 'MM') AS mes, id_medico, SUM(valor) AS total
FROM atendimento WHERE status = 'REALIZADO'
GROUP BY TRUNC(dt_atendimento, 'MM'), id_medico;

EXEC DBMS_MVIEW.REFRESH('MV_FAT_MENSAL');
CREATE MATERIALIZED VIEW mv_fat_mensal AS
SELECT date_trunc('month', dt_atendimento) AS mes, id_medico, SUM(valor) AS total
FROM atendimento WHERE status = 'REALIZADO'
GROUP BY 1, 2;

CREATE UNIQUE INDEX ON mv_fat_mensal (mes, id_medico);
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_fat_mensal;  -- não bloqueia leitores

Hints: último recurso

Hints forçam uma decisão do otimizador. São tentadores e perigosos: congelam um plano que pode ficar ruim quando os dados mudarem. Antes de usar, corrija a causa (estatística, índice, SQL não sargável).

SELECT /*+ INDEX(a ix_atend_med_dt) LEADING(m a) USE_NL(a) */ ...
FROM medico m JOIN atendimento a ON ...
-- Um hint com erro de sintaxe é ignorado em silêncio.
-- Para fixar planos de forma gerenciada, existem SQL Plan Baselines e SQL Profiles.
-- O PostgreSQL não tem hints nativos (é uma decisão do projeto).
-- Existe a extensão pg_hint_plan. Para testes de sessão, dá para desligar estratégias:
SET enable_nestloop = off;   -- só para investigar, nunca em produção global
EXPLAIN (ANALYZE) SELECT ... ;
RESET enable_nestloop;

Paralelismo

Os dois bancos podem dividir um scan grande entre vários processos (PARALLEL no Oracle, Gather e Parallel Seq Scan no PG). Ajuda relatórios pesados; em sistemas OLTP com muitos usuários, paralelismo demais disputa CPU com todo mundo.

17Prática

Roteiro de diagnóstico de uma consulta lenta

Na ordem em que costuma dar resultado:

  1. Defina "lento" com números. Quanto tempo leva, quantas linhas devolve, quantas vezes por dia roda. Uma consulta de 50 ms executada 2 milhões de vezes pesa mais que um relatório de 2 minutos.
  2. Ache as consultas que mais custam. Oracle: V$SQL ordenado por elapsed_time ou buffer_gets (AWR/ASH se licenciado). PostgreSQL: extensão pg_stat_statements ordenada por total_exec_time.
  3. Pegue o plano real (ALLSTATS LAST / EXPLAIN (ANALYZE, BUFFERS)), com valores de parâmetros realistas.
  4. Ache o nó mais caro e o primeiro ponto onde estimado e real divergem mais de 10×.
  5. Se a estimativa está errada: verifique a data das estatísticas, histogramas, colunas correlacionadas, funções na coluna e conversões implícitas.
  6. Se a estimativa está certa mas o acesso é ruim: falta um índice, ou a ordem das colunas do índice não serve, ou a condição não é sargável.
  7. Reduza o trabalho, não só o acesso: menos colunas, agregar antes de juntar, EXISTS no lugar de JOIN+DISTINCT, paginação por chave, UNION ALL no lugar de UNION.
  8. Meça de novo, no mesmo ambiente, e compare leituras lógicas (Buffers / buffer_gets), não só tempo: tempo varia com o cache, leituras são mais estáveis.
  9. Considere o efeito colateral: índice novo pesa nas escritas; mudar estatísticas muda outros planos. Teste antes em homologação.

Exercícios

Tente resolver antes de abrir a resposta. Todos usam o esquema do capítulo 00.

Básico 1. Liste os pacientes que nunca tiveram um atendimento realizado (podem ter agendados ou cancelados).
Ver resposta 
SELECT p.id_paciente, p.nome
FROM paciente p
WHERE NOT EXISTS (SELECT 1 FROM atendimento a
                  WHERE a.id_paciente = p.id_paciente
                    AND a.status = 'REALIZADO');

Note que o filtro de status fica dentro do NOT EXISTS. Fora, mudaria o significado.

Básico 2. Por que esta consulta retorna zero linhas, mesmo havendo convênios sem atendimento? 
SELECT * FROM convenio
WHERE id_convenio NOT IN (SELECT id_convenio FROM atendimento);
Ver resposta

Os atendimentos particulares têm id_convenio NULL. x NOT IN (1, 2, NULL) equivale a x<>1 AND x<>2 AND x<>NULL, e o último termo é sempre UNKNOWN. Correção:

SELECT c.* FROM convenio c
WHERE NOT EXISTS (SELECT 1 FROM atendimento a
                  WHERE a.id_convenio = c.id_convenio);
Básico 3. Em uma linha por médico, mostre: total de atendimentos, quantos foram cancelados e a taxa de cancelamento em %.
Ver resposta 
SELECT id_medico,
       COUNT(*) AS total,
       SUM(CASE WHEN status = 'CANCELADO' THEN 1 ELSE 0 END) AS cancelados,
       ROUND(100.0 * SUM(CASE WHEN status = 'CANCELADO' THEN 1 ELSE 0 END)
             / COUNT(*), 1) AS taxa_pct
FROM atendimento
GROUP BY id_medico;

O 100.0 evita divisão inteira no PostgreSQL, que trunca 1/3 para 0 quando os dois lados são inteiros.

Intermediário 4. Traga, para cada paciente, apenas o atendimento mais recente, com o nome do médico.
Ver resposta 
SELECT x.id_paciente, x.dt_atendimento, m.nome AS medico
FROM (
  SELECT a.*,
         ROW_NUMBER() OVER (PARTITION BY a.id_paciente
                            ORDER BY a.dt_atendimento DESC, a.id_atendimento DESC) AS rn
  FROM atendimento a
) x
JOIN medico m ON m.id_medico = x.id_medico
WHERE x.rn = 1;

O id_atendimento DESC desempata atendimentos no mesmo horário e torna o resultado determinístico.

Intermediário 5. Encontre os retornos: atendimentos do mesmo paciente que aconteceram até 30 dias depois do atendimento anterior.
Ver resposta 
SELECT *
FROM (
  SELECT id_paciente, id_atendimento, dt_atendimento,
         LAG(dt_atendimento) OVER (PARTITION BY id_paciente
                                   ORDER BY dt_atendimento) AS anterior
  FROM atendimento
  WHERE status = 'REALIZADO'
) x
WHERE x.anterior IS NOT NULL
  AND x.dt_atendimento < x.anterior + INTERVAL '30' DAY;
-- PostgreSQL também aceita INTERVAL '30 days'

O LAG precisa estar numa subconsulta, porque funções de janela não podem aparecer no WHERE (capítulo 1).

Avançado 6. Reescreva para que um índice em dt_atendimento possa ser usado: 
SELECT COUNT(*) FROM atendimento
WHERE TO_CHAR(dt_atendimento, 'YYYY-MM') = '2026-10';
Ver resposta 
SELECT COUNT(*) FROM atendimento
WHERE dt_atendimento >= DATE '2026-10-01'
  AND dt_atendimento <  DATE '2026-11-01';

Com um índice em dt_atendimento, o COUNT pode ser resolvido só no índice, sem tocar na tabela.

Avançado 7. A tela da agenda roda esta consulta milhares de vezes por dia. Qual índice você criaria, e em que ordem de colunas?

Igualdades primeiro, depois o intervalo, que também atende o ORDER BY:

CREATE INDEX ix_agenda ON atendimento (id_medico, status, dt_atendimento);
-- Para cobrir a consulta e evitar ir à tabela:
--   Oracle: (id_medico, status, dt_atendimento, id_paciente, tipo)
--   PG:     (id_medico, status, dt_atendimento) INCLUDE (id_paciente, tipo)
-- No PG, um índice parcial WHERE status = 'AGENDADO' fica bem menor.

Com dt_atendimento antes de status, o banco percorreria todos os status do período e filtraria depois. Funciona, mas lê mais.

Avançado 8. No plano real, um NESTED LOOPS tem o lado de fora com E-Rows = 1 e A-Rows = 480.000, e a consulta leva 6 minutos. O filtro desse lado é dt_atendimento >= TRUNC(SYSDATE), e a tabela é carregada toda madrugada. O que provavelmente está acontecendo, e o que você verificaria?
Ver resposta

Estatísticas desatualizadas com o problema da "data além do máximo": na última coleta, a maior data da tabela era anterior a hoje, então o otimizador estimou ~1 linha para "a partir de hoje". Com 1 linha, nested loops parece ótimo; com 480 mil, o lado de dentro roda 480 mil vezes.

  • Confira last_analyzed / last_autoanalyze da tabela.
  • Colete estatísticas logo após a carga diária, como passo final do ETL.
  • Rode de novo e confira se E-Rows ficou próximo de A-Rows e se o join virou hash join.

Forçar USE_HASH com hint resolveria hoje e esconderia a causa.

Avançado 9. Uma busca de pacientes usa WHERE UPPER(nome) LIKE UPPER(:txt) || '%' e faz full scan numa tabela de 3 milhões de pacientes. Como acelerar?
Ver resposta

Crie um índice na mesma expressão: CREATE INDEX ix_pac_nome_up ON paciente (UPPER(nome)). Como o curinga está só no final, o LIKE vira range scan nesse índice. No PostgreSQL com collation diferente de "C", pode ser preciso criar o índice com text_pattern_ops para o LIKE com prefixo usar a B-tree: CREATE INDEX ON paciente (upper(nome) text_pattern_ops). Se a busca precisar achar o texto no meio do nome ('%' || :txt || '%'), a B-tree não resolve: use pg_trgm (GIN) no PostgreSQL ou Oracle Text.

19Prática

Para ir além

  • Use The Index, Luke (use-the-index-luke.com), de Markus Winand: o melhor material gratuito sobre índices e desempenho, com exemplos para Oracle e PostgreSQL. Aprofunda os capítulos 10 a 12.
  • Documentação do PostgreSQL, capítulo "Using EXPLAIN" e "Performance Tips".
  • Oracle Database SQL Tuning Guide, na documentação oficial da Oracle: a referência de planos, estatísticas e otimizador.
  • Modern SQL (modern-sql.com), também de Winand: funções de janela, CTEs e recursos do padrão SQL e qual banco suporta cada um.

Como praticar

  1. Escolha uma consulta real e lenta do seu dia a dia, num banco de homologação.
  2. Tire o plano real e anote tempo, linhas e leituras.
  3. Aplique o roteiro do capítulo 17 e mude uma coisa de cada vez.
  4. Compare os planos antes e depois e anote o que mudou e por quê.

Fazer isso com dez consultas reais ensina mais que qualquer livro.

Os planos de execução mostrados são ilustrativos. Detalhes de sintaxe variam com a versão: os exemplos assumem Oracle 12c+ e PostgreSQL 12+.
