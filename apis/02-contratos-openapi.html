Contratos e OpenAPI

Como escrever, revisar e proteger o contrato de uma API com OpenAPI 3.1, e transformá-lo na fonte da verdade que gera documentação, mocks, SDKs, validação e testes.

Ao final você saberá
  • Explicar o que é um contrato de API e escolher entre design-first e code-first
  • Ler e escrever um documento OpenAPI 3.1 real, com components, $ref e segurança
  • Aplicar as diferenças entre OpenAPI 3.0 e 3.1 e o alinhamento ao JSON Schema 2020-12
  • Escrever schemas que evoluem sem quebrar clientes (required, enums, oneOf)
  • Montar o ciclo: lint, mock, documentação, SDKs e testes de contrato
  • Bloquear breaking changes na CI e conduzir a revisão de contrato em PR
1Básico

O que é um contrato de API e por que importa

Uma API é uma promessa entre dois times: quem fornece (provedor) e quem consome (cliente). O contrato é a forma escrita e verificável dessa promessa: quais endpoints existem, que parâmetros aceitam, que corpos trocam, que erros devolvem, como autenticar. Sem contrato escrito, a promessa mora na cabeça de quem implementou e no código; o consumidor descobre o comportamento por tentativa e erro, e o provedor descobre que quebrou alguém quando o telefone toca.

O padrão de mercado para APIs HTTP é a OpenAPI Specification (OAS), um documento YAML ou JSON, legível por humanos e por máquinas, mantido pela OpenAPI Initiative. O módulo 01 desenhou a API de agendamentos; neste módulo vamos escrevê-la como contrato e ligar esse contrato a todo o ciclo: revisão, mock, documentação, código, testes e CI.

O que o contrato resolve

  • Trabalho em paralelo. Front-end, parceiros e QA começam a trabalhar contra um mock do contrato antes de existir backend.
  • Uma fonte da verdade. Documentação, SDKs, validação, testes e portal saem do mesmo arquivo e não divergem.
  • Revisão barata. Discutir 40 linhas de YAML num pull request custa uma tarde; discutir uma API em produção custa meses de compatibilidade.
  • Automação de governança. Lint de padrões e detecção de mudanças incompatíveis rodam na CI, sem depender da memória de ninguém.
  • Integração com terceiros. Em saúde, convênios, laboratórios e parceiros integram com a clínica; o contrato é o que se entrega e se versiona.

O que o contrato NÃO é

Não é documentação "bonita" gerada no fim do projeto, nem garante que o servidor o cumpra: um contrato que ninguém valida é uma opinião. O valor aparece quando ele é verificado (lint, testes de contrato, validação em runtime, diff na CI). Também descreve a interface, não regras de negócio profundas: "não é possível cancelar com menos de 2 horas" vai no texto e nos exemplos de erro, não em um schema.

Na entrevista

"Por que escrever OpenAPI?" Resposta curta: "Para ter uma fonte única da verdade que gera documentação, mocks, SDKs e testes, e para revisar e proteger compatibilidade na CI antes de o código existir. Contrato verificado automaticamente evita que a documentação minta."

Para gestores

Contrato é ativo da empresa, não artefato de um squad. Defina quem é o dono de cada contrato (um time, um CODEOWNERS), onde ele mora (repositório próprio ou junto do código, mas sempre versionado) e como mudanças são aprovadas. Métrica simples: porcentagem das APIs de produção que têm contrato publicado e validado na CI.

Design-first vs code-first

Há dois fluxos para chegar ao contrato. A diferença é quem é a fonte da verdade e quando a discussão acontece.

Design-first (contrato primeiro)Code-first (código primeiro)
Fonte da verdadeO arquivo OpenAPIO código (o YAML é derivado)
PrósRevisão barata; mock e SDK antes do backend; consumidores participam; API pensada para quem usaRápido para começar; baixa fricção para devs; o contrato nunca fica desatualizado por construção
ContrasExige disciplina e ferramentas; risco de o código divergir do contrato se não houver validação; escrever YAML à mão cansaA API vira um reflexo da implementação (vazam nomes de tabelas, tipos internos); revisão tardia; gerador pode produzir contrato ruim; difícil impor padrões
Quando usarAPIs públicas, de parceiros e entre times; integrações com convênios; muitos consumidoresAPIs internas simples, protótipos, serviços com um único consumidor controlado pelo mesmo time
Risco típicoContrato e implementação divergemMudança incompatível passa despercebida porque "só mudei o DTO"

Na prática existe um meio-termo bastante usado: escrever o contrato à mão (design-first), gerar stubs/interfaces do servidor a partir dele e validar o código contra o contrato na CI. Outra variante é code-first com revisão obrigatória do YAML gerado no pull request, com lint e diff de breaking changes: o que importa é que o contrato seja revisado como um artefato e protegido por automação, qualquer que seja a direção em que é produzido.

Armadilha comum

Declarar "somos design-first" e deixar o YAML num wiki ou numa pasta sem CI. Em três meses ele diverge do código e ninguém confia nele. Todo fluxo precisa de um ponto de verificação automático que falha quando contrato e implementação discordam.

Na entrevista

"Design-first ou code-first?" Resposta sênior: "Depende do número e do tipo de consumidores. Para APIs externas ou entre times, design-first: a discussão acontece antes do código e mock e SDK liberam os consumidores. Para API interna de um consumidor só, code-first com YAML gerado e revisado no PR é suficiente. Nos dois casos, a CI precisa garantir que contrato e código não divergem."

Para gestores

Escolha por risco de quebra: quanto mais consumidores fora do seu controle, mais design-first. Cobre uma definição de pronto que inclua "contrato revisado e atualizado". Cuidado com o time que "gera o YAML no fim para cumprir tabela": é code-first sem revisão, o pior dos mundos.

3Intermediário

Anatomia de um documento OpenAPI 3.1

O documento tem poucos blocos de topo. Conhecê-los é o suficiente para ler qualquer contrato:

BlocoPara que serve
openapiVersão da especificação usada (3.1.0)
infoTítulo, descrição, version (versão do contrato, não da OpenAPI), contato, licença
serversURLs base (produção, sandbox); aceitam variáveis
pathsCada caminho com suas operações (get, post, patch…)
operaçãooperationId (único, estável: vira nome de método no SDK), summary, tags, parameters, requestBody, responses, security
parametersEntradas fora do corpo: in: path | query | header | cookie
requestBodyCorpo enviado, por tipo de mídia (application/json)
responsesUma entrada por status ("200", "409", default), com cabeçalhos e corpo
componentsPeças reutilizáveis: schemas, parameters, responses, examples, securitySchemes…
$refReferência a um componente: "#/components/schemas/Agendamento"; também aponta para outros arquivos
security / securitySchemesComo autenticar (OAuth 2.0, API key, HTTP bearer, OpenID Connect) e quais escopos cada operação exige
tagsAgrupam operações na documentação
examplesExemplos de requisição/resposta: alimentam documentação, mock e testes
webhooksChamadas que a API faz para o cliente (novidade da 3.1; módulo 04)

Regra de organização: defina uma vez em components e referencie com $ref. Parâmetros de paginação, o formato de erro e os schemas principais ficam lá; as operações apenas apontam. Isso garante consistência e é o que permite ao lint verificar "toda operação de lista usa os parâmetros padrão".

Regra de bolso

operationId é uma API dentro da API: o SDK gerado chama client.criarAgendamento(). Escolha nomes verbo+substantivo, únicos e estáveis; renomear é uma mudança incompatível para quem usa o SDK.

Na entrevista

"Mostre a estrutura de um OpenAPI." Cite os blocos na ordem em que lê: info e servers, paths com operações (parâmetros, corpo, respostas), e components com schemas, parâmetros e securitySchemes reaproveitados por $ref. Mencionar operationId estável mostra experiência com SDKs.

Para gestores

Arquivos de contrato crescem. Defina cedo a convenção de organização: um arquivo por serviço, components compartilhados (erro, paginação, tipos como Dinheiro) num repositório comum versionado, e uma ferramenta de bundling para publicar um único arquivo.

Um contrato real: a API de agendamentos em YAML

A seguir, um contrato coerente da API do módulo 01, em três partes: cabeçalho e segurança, operações e componentes. É um recorte (não cobre todos os endpoints), mas é válido e consistente: tudo que as operações referenciam está definido em components.

Parte 1: cabeçalho, servidores, segurança

openapi: 3.1.0
info:
  title: API de Agendamento de Consultas
  summary: Agenda, consulta e cancelamento de consultas
  description: |
    API da Rede Clínica (exemplo fictício).
    Instantes em UTC (RFC 3339). Erros em application/problem+json (RFC 9457).
  version: 1.2.0
  contact:
    name: Time de Plataforma
    email: plataforma@clinica.example
servers:
  - url: https://api.clinica.example/v1
    description: Produção
  - url: https://sandbox.api.clinica.example/v1
    description: Sandbox (dados fictícios)
tags:
  - name: Agendamentos
    description: Criar, consultar e cancelar agendamentos
security:
  - oauth2: ["agendamentos:ler"]

Repare em decisões que vêm do módulo 01: o erro é application/problem+json; o cursor é opaco (type: string); Idempotency-Key é parâmetro obrigatório; o cancelamento é um sub-recurso substantivo; o 404 do cancelamento descreve explicitamente "fora do escopo". O contrato é onde essas decisões ficam registradas e verificáveis.

Armadilha comum

Contratos que só descrevem o caminho feliz (200) e ignoram erros. O consumidor passa a depender de comportamento não documentado. Documente os erros relevantes de cada operação (400/422, 401, 403/404, 409, 429) e reaproveite via components/responses.

Na entrevista

Pode ser pedido para "escrever um endpoint em OpenAPI" no papel. Mostre: operationId, parâmetros com in e schema, requestBody com $ref, respostas incluindo erro, e a reutilização via components. Explique o porquê de cada pedaço, não decore a sintaxe.

Para gestores

O arquivo acima é revisável por alguém de negócio: nomes de campos, enums e mensagens de erro são vocabulário do domínio. Convide produto e a área clínica para a revisão do contrato; é a oportunidade mais barata de descobrir que "faltou" e "não compareceu" são conceitos diferentes.

OpenAPI 3.1 e JSON Schema 2020-12: o que mudou da 3.0

Na versão 3.0, o "schema" do OpenAPI era um subconjunto modificado de uma versão antiga do JSON Schema, com extensões próprias (nullable, example) e incompatibilidades. A 3.1 alinhou-se totalmente ao JSON Schema 2020-12: um schema do OpenAPI passou a ser um schema JSON Schema válido, e as mesmas ferramentas e bibliotecas de validação servem aos dois mundos. Esse é o principal motivo para preferir 3.1 em contratos novos.

AssuntoOpenAPI 3.0OpenAPI 3.1
Nulotype: string + nullable: truetype: [string, "null"] (nullable foi removido)
typeUm único valorPode ser uma lista de tipos
Exemplos no schemaexample: valorexamples: [valor, ...] (array; example está obsoleto)
Limites exclusivosexclusiveMinimum: true (booleano, junto de minimum)exclusiveMinimum: 0 (número, como em JSON Schema)
Binário e conteúdo codificadoformat: binary / format: bytecontentMediaType e contentEncoding
$ref com vizinhosIrmãos de $ref eram ignoradosPermitidos (ex.: $ref + description)
Valor fixoenum com um itemconst
Recursos novos-if/then/else, prefixItems, unevaluatedProperties, $defs, webhooks no topo
Documento mínimopaths obrigatórioBasta ter paths, components ou webhooks
 
# OpenAPI 3.0
observacao:
  type: string
  nullable: true
  example: "Retorno em 30 dias"

# OpenAPI 3.1
observacao:
  type: [string, "null"]
  examples: ["Retorno em 30 dias"]

Consequências práticas

  • Migrar de 3.0 para 3.1 não é só trocar a versão: nullable precisa ser reescrito e geradores/validadores precisam suportar 3.1. O suporte de ferramentas é desigual; verifique os que você usa antes de migrar um portfólio inteiro.
  • Reuso do ecossistema JSON Schema: o mesmo schema pode validar mensagens de eventos, configuração e respostas de API.
  • Documentos 3.0 e 3.1 coexistem numa empresa durante a migração; o lint e o diff precisam entender ambos.
Regra de bolso

Contrato novo: 3.1. Contrato antigo em 3.0 funcionando: migre quando houver ganho concreto (por exemplo, uma biblioteca de validação que só fala 2020-12) e depois de confirmar o suporte nas ferramentas da CI.

Na entrevista

"O que mudou do OpenAPI 3.0 para o 3.1?" "Alinhamento completo com JSON Schema 2020-12: sai o nullable e entra type como lista com null; examples vira array; exclusiveMinimum vira numérico; $ref aceita irmãos; e webhooks entram como cidadão de primeira classe." Quem lembra três diferenças específicas demonstra que já usou.

Para gestores

Migração de versão do contrato é projeto de plataforma, não tarefa de cada time: concentre num pacote de lint/CI que suporte as duas versões, defina prazo e meça adesão. Evite deixar cada squad migrar por conta própria com ferramentas diferentes.

Boas práticas de schema: required, additionalProperties, formatos, enums, oneOf

O schema é a parte do contrato que mais gera bugs sutis, porque ele decide o que é válido e como as ferramentas (validadores, geradores, mocks) interpretam isso. Cada escolha tem um efeito prático.

required: o que o cliente pode assumir

Em respostas, required é uma promessa do provedor: "este campo sempre vem". Cada campo marcado como obrigatório reduz a liberdade de evolução (remover é incompatível) e, em SDKs tipados, vira tipo não nulo. Marque como obrigatório só o que você garante para sempre. Em requisições, required é uma exigência ao cliente: adicionar um campo obrigatório a uma requisição existente é uma mudança incompatível.

Não confunda opcional com anulável: o campo pode estar ausente (fora de required), presente com null (type: [string, "null"]), ou ambos. Defina cada caso (veja a seção de nulos no módulo 01).

additionalProperties: estrito ou tolerante?

Estrito (false)Aberto (padrão)
PróPega erro de digitação do cliente (telefne) e evita "mass assignment"Permite evoluir sem quebrar: clientes ignoram campos novos
ContraQualquer campo novo enviado por cliente mais novo é rejeitado; clientes que validam respostas estritamente quebram quando o servidor adiciona campoErros de digitação passam despercebidos; dados indesejados podem chegar ao modelo
RecomendaçãoRequisições: estrito, para falhar cedo (e proteger contra atribuição em massa)Respostas: aberto; o cliente deve seguir a "regra do leitor tolerante" e ignorar o que não conhece

Detalhe técnico: additionalProperties: false não "enxerga" propriedades vindas de allOf/$ref em outro subschema; para composição com allOf use unevaluatedProperties: false (disponível por causa do alinhamento da 3.1 ao JSON Schema 2020-12).

Formatos e restrições

  • Formatos comuns: date-time (RFC 3339), date, uuid, email, uri, uri-reference. Atenção: em JSON Schema 2020-12, format é por padrão anotação; se o validador será assertivo ou não depende da configuração. Não presuma.
  • Restrições que protegem: maxLength em toda string, maxItems em todo array, minimum/maximum em números, pattern para identificadores. Sem limites, o contrato aceita um corpo de 50 MB num campo de observação; isso é vetor de negação de serviço (OWASP API Security: consumo irrestrito de recursos, módulo 05).
  • Dinheiro e decimais: type: string com pattern numérico, ou inteiro em centavos; evite number para valores exatos.
  • Separe schemas de entrada e saída (NovoAgendamento vs Agendamento) em vez de reaproveitar um schema com readOnly/writeOnly em tudo. Facilita leitura, geração de código e evolução independente.

Enums e sua evolução

Enums parecem inofensivos e são uma das maiores fontes de quebra silenciosa. Em respostas, adicionar um valor ao enum (status: "reagendado") pode derrubar clientes que usam enums fechados (SDKs gerados em Java/TypeScript com desserialização estrita lançam exceção para valor desconhecido). Em requisições, adicionar valor é seguro e remover é incompatível.

  • Documente que clientes devem tolerar valores desconhecidos em enums de resposta (enum "aberto"), e trate isso como parte do contrato.
  • Nos testes de SDK, inclua um valor de enum que o cliente não conhece.
  • Para enums muito voláteis (tipos de exame, especialidades), prefira uma coleção consultável (GET /especialidades) em vez de enum fixo no schema.
  • Valores em minúsculas, sem acento nem espaço, estáveis: paciente_desistiu, não "Paciente desistiu".

oneOf, anyOf, allOf e discriminator

allOf combina (todos precisam valer, útil para composição), oneOf escolhe exatamente um, anyOf ao menos um. Para polimorfismo (a forma de pagamento é convênio ou particular), use oneOf com discriminator: um campo (tipo) diz qual variante é, e o validador e os geradores não precisam testar todas as variantes.

pagamento:
  oneOf:
    - $ref: "#/components/schemas/PagamentoConvenio"
    - $ref: "#/components/schemas/PagamentoParticular"
  discriminator:
    propertyName: tipo
    mapping:
      convenio: "#/components/schemas/PagamentoConvenio"
      particular: "#/components/schemas/PagamentoParticular"
Armadilha comum

Usar oneOf com variantes que se sobrepõem (ambas aceitam o mesmo objeto): a validação falha porque o valor casa com mais de uma. E discriminator é uma palavra do OpenAPI, não do JSON Schema: validadores genéricos podem ignorá-la, e o suporte em geradores de código é irregular. Teste a geração com o seu gerador antes de adotar polimorfismo em larga escala.

Regra de bolso

Contrato para evoluir: respostas abertas e poucos required; requisições estritas com limites; enums de resposta tratados como abertos; polimorfismo só quando o domínio realmente tem variantes.

Na entrevista

"additionalProperties false é bom?" "Na requisição sim, para falhar cedo e evitar atribuição em massa. Na resposta não, porque impede o servidor de adicionar campos sem quebrar quem valida estritamente." E "como adicionar um valor a um enum sem quebrar?" mostra maturidade: "Em resposta é potencialmente incompatível; por isso a regra do leitor tolerante deve estar no contrato."

Para gestores

Escreva as regras de evolução no style guide (o que é compatível, o que não é) e automatize. Quando alguém pergunta "posso adicionar este valor ao enum?", a resposta deve estar numa página e na CI, não numa reunião. Pergunta de revisão: "como um cliente antigo se comporta com esta mudança?"

Na entrevista

"Você gera SDKs a partir do OpenAPI?" "Sim, na CI, com versão semântica e testes contra o mock, mas sem confiar às cegas: oneOf e enums são os pontos frágeis. No servidor gero só as interfaces, para não acoplar o domínio ao código gerado."

Para gestores

SDK é produto com ciclo de vida: quem mantém, quem dá suporte, qual a política de versões. Se não houver dono, não publique. A alternativa barata (contrato + exemplos + sandbox) frequentemente entrega 80% do valor. Meça: tempo para o primeiro parceiro integrar e número de chamados de suporte por integração.

8Intermediário

Lint, mocks, documentação e experiência do desenvolvedor

Com um contrato bom, ferramentas fazem o trabalho repetitivo. O contrato é o centro de uma cadeia de automações:

Lint e style guide automatizado (Spectral)

O Spectral (Stoplight) valida um documento OpenAPI contra um conjunto de regras: as regras padrão do OpenAPI (spectral:oas) e as suas, que codificam o style guide da empresa. Transforma "regra no wiki" em falha na CI.

extends: ["spectral:oas"]
rules:
  caminho-em-kebab-case:
    description: Caminhos em minúsculas, com hífen
    severity: error
    given: "$.paths[*]~"
    then:
      function: pattern
      functionOptions:
        match: "^(/([a-z0-9-]+|\\{[a-zA-Z]+\\}))+$"
  operacao-com-resumo:
    description: Toda operação precisa de summary
    severity: error
    given: "$.paths[*][get,post,put,patch,delete]"
    then:
      field: summary
      function: truthy
npx @stoplight/spectral-cli lint openapi.yaml --ruleset .spectral.yaml

Regras úteis para uma empresa de saúde: operationId obrigatório e único; erros em application/problem+json; toda coleção com limite e cursor; strings com maxLength; operações de escrita com security explícita; exemplos presentes; nada de dado pessoal em parâmetros de query (cpf, nome).

Mocks a partir do contrato (Prism)

O Prism (Stoplight) sobe um servidor falso a partir do OpenAPI, respondendo com os exemplos do contrato. O front-end e os parceiros avançam sem esperar o backend, e o próprio mock valida as requisições contra o contrato.

npx @stoplight/prism-cli mock openapi.yaml            # sobe em http://127.0.0.1:4010

curl -i -X POST http://127.0.0.1:4010/agendamentos \
  -H "Idempotency-Key: 8c0f1f6e-2c1b" -H "Content-Type: application/json" \
  -H "Prefer: code=409" -d '{}'                       # força o cenário de erro 409

O cabeçalho Prefer escolhe o código de status ou um exemplo nomeado (Prefer: example=convenio); o modo proxy repassa ao servidor real validando tráfego contra o contrato. Mock bom exige exemplos bons no contrato, inclusive para os erros.

Documentação: Swagger UI, Redoc, Scalar

FerramentaPerfil

RedocLeitura em três painéis (navegação, descrição, exemplos); excelente como referência pública; sem execução de chamadas na versão aberta.

Escolher é secundário; o que importa é que a documentação seja gerada do contrato e publicada automaticamente a cada merge, com a versão visível.

Portal do desenvolvedor e DX

A métrica central de experiência do desenvolvedor é o tempo até a primeira chamada bem-sucedida (time to first call, TTFC). Um parceiro de convênio que leva 3 semanas para integrar custa dinheiro a ambos os lados. O que reduz o TTFC:

  • Um quickstart de cinco minutos: obter credencial, chamar um endpoint, ver a resposta.
  • Uma sandbox com dados fictícios e credenciais de teste, sem risco para produção (sem dados reais de pacientes).
  • Exemplos reais por operação, incluindo erros; coleção importável (Postman, arquivo .http) gerada do contrato.
  • Um catálogo de erros com cada type do Problem Details explicado e a ação do cliente.
  • Um changelog e uma política de depreciação visíveis (módulo 07).
  • Um canal de suporte e status da API.
Armadilha comum

Publicar o Swagger UI apontando para produção, com "Try it out" habilitado e sem controle: qualquer pessoa pode disparar chamadas reais. Aponte a documentação interativa para a sandbox, exija autenticação e não exponha endpoints internos no contrato público (use filtros por tag para publicar só o que é externo).

Na entrevista

"Como garante consistência entre 30 APIs?" "Style guide em regras do Spectral rodando na CI, com um pacote de regras compartilhado; mocks e documentação gerados do contrato; e métricas de DX como tempo até a primeira chamada."

Para gestores

Trate o portal do desenvolvedor como produto com dono e métrica. Investimento barato e de alto retorno: lint na CI (horas de configuração, anos de consistência). Cuidado com o excesso de regras: comece com poucas, severidade warning, e promova a error quando o legado estiver adequado, ou o time vai desabilitar o lint.

Breaking changes na CI e o fluxo de trabalho do time

O valor máximo do contrato aparece quando a CI compara a versão nova com a que está em produção e falha se a mudança for incompatível. Isso impede aquele "só renomeei um campo" que derruba um parceiro numa sexta à noite.

O que é uma mudança incompatível (breaking)

Quebra clientes existentesEm geral é compatível
Remover ou renomear endpoint, parâmetro ou campo de respostaAdicionar endpoint novo
Tornar obrigatório um campo ou parâmetro de requisiçãoAdicionar campo opcional à requisição ou parâmetro opcional
Mudar tipo ou formato (string para integer, date para date-time)Adicionar campo novo à resposta (se os clientes forem tolerantes)
Remover valor de enum de requisição; em resposta, adicionar valor pode quebrar clientes estritosAdicionar valor a enum de requisição
Apertar restrições (maxLength menor, pattern mais restrito) em requisiçãoAfrouxar restrições de requisição
Mudar status code ou formato de erro; exigir nova permissão (escopo)Melhorar descrições e exemplos

Ferramentas de diff entendem essas regras. O oasdiff compara dois contratos e classifica as mudanças (erro, aviso, informação):

oasdiff breaking base.yaml openapi.yaml --fail-on ERR   # falha se houver quebra
oasdiff changelog base.yaml openapi.yaml                # lista de mudanças para o changelog
name: contrato
on: pull_request
jobs:
  contrato:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Lint
        run: npx @stoplight/spectral-cli lint openapi.yaml
      - name: Breaking changes
        run: |
          git show origin/main:openapi.yaml > base.yaml
          oasdiff breaking base.yaml openapi.yaml --fail-on ERR

Fluxo de trabalho do time

  1. Proposta. Quem quer a mudança abre um PR só com o YAML (e exemplos), descrevendo o problema e os clientes afetados.
  2. Revisão do contrato. O CODEOWNERS do contrato inclui o time dono e um representante dos consumidores (front, parceiros). Revisam nomes, erros, evolução. A CI roda lint e diff.
  3. Mock disponível. Com o PR aprovado, publica-se o mock; consumidores começam em paralelo.
  4. Implementação. O backend implementa e a CI roda testes de contrato contra o serviço; divergência falha a build.
  5. Publicação. No merge, documentação e SDKs são publicados com versão e changelog gerado do diff.

O contrato é a fonte da verdade: se o servidor e o YAML discordam, é um bug a corrigir (normalmente no código; no contrato só com a revisão do passo 2).

Outras especificações do ecossistema

  • AsyncAPI: o equivalente do OpenAPI para APIs assíncronas e orientadas a eventos (filas, WebSockets, mensagens). Será visto no módulo 04.
  • Arazzo (OpenAPI Initiative): descreve fluxos de trabalho que encadeiam chamadas a uma ou mais APIs (por exemplo, "consultar horários, criar agendamento, confirmar"), úteis para documentação de jornadas e testes. É relativamente novo; avalie a maturidade das ferramentas antes de adotar.
  • JSON Schema puro para validar eventos e configurações com o mesmo vocabulário do OpenAPI 3.1.
Regra de bolso

Mudança incompatível não é proibida, é cara e deliberada: exige nova versão ou plano de migração aprovado, aviso aos consumidores e prazo. A CI deve tornar o caminho certo o mais fácil e o caminho errado impossível de fazer sem querer.

Na entrevista

"Como evita quebrar clientes?" "Diff do contrato na CI contra a versão em produção com bloqueio de breaking changes, revisão do contrato por consumidores e testes de contrato. Mudança incompatível só com nova versão ou plano de migração aprovado."

Para gestores

Defina o processo de exceção (quem aprova uma mudança incompatível, com que prazo de aviso) e meça: número de breaking changes bloqueados na CI (indicador saudável!) e incidentes por quebra de contrato (deve tender a zero). Se ninguém nunca é bloqueado, o gate provavelmente não está funcionando.

Cenários práticos e glossário

Cenário 1: a documentação mente

O PDF/Swagger publicado diz que observacao é obrigatório, mas o servidor aceita sem. Um parceiro implementou do jeito errado e agora a correção "quebra" a integração dele.

O que fazer

Decidir qual é a verdade (normalmente o comportamento real); alinhar contrato e código; adotar testes de contrato e validação de resposta em staging para detectar divergência; comunicar o parceiro com prazo. Daqui para frente, documentação gerada do contrato, nunca à mão.

Cenário 2: o SDK quebrou depois de um valor novo no enum

Adicionamos status: "reagendado". O app Android, com SDK gerado, passou a lançar exceção ao listar agendamentos.

O que fazer

Hotfix: o SDK deve mapear valor desconhecido para um desconhecido padrão. Processo: documentar "enums de resposta são abertos", testar SDKs com valor desconhecido na CI e incluir a regra de enum no style guide e no revisor de PR.

Cenário 3: o "só renomeei o campo"

Um dev renomeou inicio para dataHoraInicio num DTO; no code-first o YAML mudou sozinho e ninguém notou. O sistema do convênio parou.

O que fazer

Reverter ou manter os dois campos durante uma janela de depreciação; adicionar o gate de oasdiff na CI e a revisão obrigatória do YAML gerado no PR (CODEOWNERS); medir incidentes de quebra de contrato.

Cenário 4: parceiro leva um mês para integrar

O laboratório parceiro reclama que a integração demora, com muitas dúvidas sobre erros e formatos.

O que fazer

Medir o TTFC; criar sandbox e quickstart; enriquecer o contrato com exemplos e um catálogo de erros; publicar coleção de requisições; abrir um canal de suporte. Reavaliar o TTFC no próximo parceiro.

Cenário 5: o design-first travou

Os times reclamam que a revisão do contrato demora e vira gargalo; alguns voltaram a codificar primeiro.

O que fazer

Revisão com SLA curto (por exemplo 1 dia útil), PRs pequenos, regras mecânicas passadas para o lint (o revisor humano discute só design), revisores rotativos e um template de proposta. Para APIs internas de baixo risco, permitir code-first com YAML revisado no PR.

11Avançado

Perguntas de entrevista

01O que é OpenAPI e para que serve?

Uma especificação para descrever APIs HTTP em YAML/JSON: endpoints, parâmetros, corpos, respostas, erros e segurança. Serve de contrato legível por humanos e máquinas e gera documentação, mocks, SDKs, validação e testes.

02O que é um contrato de API e por que importa para os times?

É a promessa verificável entre provedor e consumidor. Permite trabalho em paralelo, revisão antes do código e proteção contra quebras, e reduz dependência de conhecimento tácito entre equipes.

03Design-first ou code-first?

Design-first para APIs com vários consumidores ou externas: discussão barata e mock antecipado. Code-first para APIs internas simples, com YAML gerado e revisado no PR. Nos dois, a CI deve impedir divergência entre código e contrato.

04Cite os blocos principais de um documento OpenAPI.

openapi, info, servers, paths (operações com parâmetros, requestBody e responses), components (schemas, parameters, responses, securitySchemes), security e tags; webhooks na 3.1.

05Para que servem components e $ref?

Para definir uma vez e reutilizar: schemas, parâmetros de paginação, respostas de erro. Garante consistência, reduz tamanho e permite que o lint verifique padrões.

06O que mudou do OpenAPI 3.0 para o 3.1?

Alinhamento total ao JSON Schema 2020-12: nullable some e type vira lista com "null"; examples é array; exclusiveMinimum é numérico; $ref aceita irmãos; contentMediaType substitui format: binary; webhooks no topo.

07Como representar um campo anulável em 3.1?

type: [string, "null"]. Distingo de campo opcional (fora de required): um campo pode ser opcional, anulável ou ambos, e o contrato deve dizer qual.

08Quando usar additionalProperties: false?

Em requisições, para falhar cedo com campos desconhecidos e evitar atribuição em massa. Em respostas, não: o servidor precisa poder adicionar campos, e os clientes devem ignorar o que não conhecem. Com allOf, usar unevaluatedProperties.

09Adicionar um valor a um enum é compatível?

Em requisição, sim. Em resposta, pode quebrar clientes com enum fechado (SDKs que lançam exceção). Por isso o contrato deve declarar que enums de resposta são abertos, e os SDKs devem ser testados com valor desconhecido.

10Como modelar polimorfismo (convênio ou particular)?

oneOf com discriminator (propertyName: tipo e mapping), garantindo variantes mutuamente exclusivas. Verifico o suporte do gerador de código, que é irregular nesse ponto.

11Como garantir que a implementação cumpre o contrato?

Validação de requisição em runtime (middleware ou gateway), validação de resposta em testes e staging, e testes de contrato na CI (por exemplo gerados a partir do OpenAPI, ou dirigidos pelo consumidor). Divergência é bug e falha a build.

12Quais os riscos de gerar código e SDKs a partir do OpenAPI?

Qualidade irregular por gerador (oneOf, nulos, 3.1), enums fechados quebrando, regeneração sobrescrevendo edições, acoplamento do domínio ao código gerado e custo de manter o SDK como produto. Mitigo gerando na CI, só interfaces no servidor e testando os SDKs.

13Como automatiza um style guide de API?

Com Spectral: regras padrão do OAS mais regras da empresa (kebab-case nos caminhos, operationId obrigatório, erros em Problem Details, paginação padronizada). Roda na CI, começa em warning e é promovido a error.

14Como destrava o front-end antes de o backend existir?

Mock gerado do contrato com Prism, com exemplos de sucesso e de erro, mais SDK ou tipos gerados. O mock também valida as requisições do cliente contra o contrato.

15O que é uma mudança incompatível e como detectar na CI?

Remover ou renomear campo/endpoint, tornar obrigatório um campo de requisição, mudar tipos ou status, apertar restrições. Na CI comparo o contrato do PR com o da main usando oasdiff e falho o build em quebra, salvo exceção aprovada com plano de migração.

16Swagger UI, Redoc ou Scalar? (e portal do desenvolvedor)

Todos geram documentação do contrato: Swagger UI com "Try it out", Redoc como referência de leitura, Scalar com cliente de API moderno. A escolha é secundária; o essencial é publicar automaticamente a cada merge, apontando para sandbox, e medir o tempo até a primeira chamada.

17Como é o fluxo de trabalho com contrato em PR? (sênior)

PR só com o YAML e exemplos; CODEOWNERS com o time dono e consumidores; lint e diff na CI; mock publicado após aprovação; implementação com testes de contrato; publicação automática de docs e SDKs com changelog do diff. O contrato é a fonte da verdade.

18Como você implantaria contratos numa empresa que não tem? (gestão)

Começo pelas APIs mais críticas e com mais consumidores externos (convênios, parceiros). Contrato versionado no repositório, lint básico em warning, documentação gerada, depois o gate de breaking changes e testes de contrato. Defino donos, SLA de revisão e métricas: cobertura de APIs com contrato, breaking changes bloqueados, tempo até a primeira chamada.
