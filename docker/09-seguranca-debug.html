MÓDULO 09 · Avançado

Segurança e troubleshooting

Um container não é uma caixa-forte: é um processo do host com visão limitada do sistema. Este módulo mostra como endurecer esse processo e, quando algo dá errado de madrugada, como diagnosticar com método em vez de tentativa e erro.

Ao final você saberá
  • Desenhar o modelo de ameaças de um ambiente com Docker e dizer onde cada defesa atua
  • Explicar por que o socket do Docker equivale a root e quando usar rootless, user namespaces e usuário não-root
  • Aplicar capabilities mínimas, filesystem somente leitura, no-new-privileges e limites de recursos
  • Tratar segredos, varredura de imagens e dados de saúde (LGPD) em containers
  • Seguir um roteiro de diagnóstico: exit code, OOM, rede, permissão de volume, disco, cache, lentidão e imagem sem shell
1Básico

Modelo de ameaças de containers

Segurança começa por perguntar quem ataca, por onde entra e o que ganha. Num ambiente Docker há cinco superfícies, e cada uma tem defesas diferentes. O ponto-chave: containers compartilham o kernel do host. Uma máquina virtual tem um kernel próprio atrás de um hypervisor; o container é um processo comum, isolado por namespaces e limitado por cgroups (módulo 01). Se o isolamento falhar, o invasor está no host.

Regra de bolso

Defesa em camadas: assuma que a aplicação será explorada um dia e projete para que o dano fique dentro do container. Cada controle desta trilha (não-root, caps, read-only, limites) reduz o que o invasor consegue fazer depois de entrar.

Na entrevista

"Container é seguro?" A resposta madura: é isolamento de processo, não de kernel. Seguro o bastante para a maioria das cargas se configurado com privilégio mínimo; para código não confiável de terceiros, use isolamento mais forte (microVMs como Firecracker, ou runtimes como gVisor e Kata Containers).

Para gestores

Segurança de containers é majoritariamente padrão de equipe, não ferramenta: uma imagem base aprovada, um template de Compose/Kubernetes com os controles já ligados e um item de checklist na revisão de código. O custo de fazer certo no início é pequeno; retrofit em dezenas de serviços não é.

2Intermediário

O socket é root; rootless, userns e usuário não-root

Por que o socket do Docker é root

O cliente docker é só um cliente HTTP. Ele conversa com o daemon pelo socket Unix /var/run/docker.sock (dono root, grupo docker), e o daemon roda como root. Quem consegue escrever nesse socket pode pedir ao daemon qualquer coisa, inclusive um container que monta o disco inteiro do host:

$ ls -l /var/run/docker.sock
srw-rw---- 1 root docker 0 Nov 26 08:12 /var/run/docker.sock

# qualquer membro do grupo docker consegue isto, sem sudo:
docker run --rm -it -v /:/host alpine chroot /host sh
# agora é root no sistema de arquivos do host (leia /etc/shadow, instale chave SSH...)

Consequências práticas:

  • Estar no grupo docker é ser root. Trate a lista desse grupo como a lista de administradores do servidor.
  • Nunca monte /var/run/docker.sock num container sem necessidade comprovada. Quem comprometer esse container controla o host. Montar com :ro não ajuda: o modo somente leitura protege o arquivo do socket, não impede de enviar requisições por ele.
  • API em TCP: a porta 2375 é HTTP sem autenticação (equivale a root remoto para qualquer um que alcance a porta; é alvo clássico de mineradores de criptomoeda). Se for preciso, use 2376 com TLS mútuo, ou melhor, SSH (docker context create remoto --docker "host=ssh://usuario@servidor").

Armadilha comum

"Montei o socket como :ro, então está seguro." Não está. Um container com o socket, mesmo "somente leitura", pode criar outro container privilegiado com / do host montado.

Rootless mode: o daemon sem root

No modo rootless, tanto o daemon quanto os containers rodam sob um usuário comum, usando user namespaces. O "root" dentro do container é um UID sem privilégio no host. Se alguém escapar do container, cai numa conta sem poder. Instalação típica no Linux:

dockerd-rootless-setuptool.sh install      # vem no pacote docker-ce-rootless-extras
export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock
docker info --format '{{.SecurityOptions}}'   # deve listar rootless

Limitações a conhecer: portas abaixo de 1024 exigem ajuste (net.ipv4.ip_unprivileged_port_start); a rede passa por uma camada em espaço de usuário (menor desempenho); o IP de origem das conexões pode aparecer mascarado; alguns recursos dependem de cgroup v2 com systemd; --privileged perde o sentido. O Podman é rootless por padrão (veja as alternativas no módulo 10).

User namespaces com userns-remap

Alternativa quando o daemon precisa continuar como root: o remapeamento de user namespace mapeia o UID 0 do container para uma faixa de UIDs sem privilégio no host (definida em /etc/subuid e /etc/subgid). Liga-se no /etc/docker/daemon.json:

{ "userns-remap": "default" }

O preço: o daemon usa um espaço de armazenamento separado (as imagens são baixadas de novo), volumes e bind mounts passam a ter donos "estranhos" no host e alguns recursos (como --privileged e --network host) ficam restritos. É poderoso, mas exige planejamento.

Usuário não-root dentro da imagem

É a defesa mais barata e a mais esquecida. Sem USER, o processo roda como root (UID 0) no container: com as capabilities padrão do Docker ele ainda faz muita coisa dentro do container, e qualquer falha de isolamento vira root no host. Prefira UID numérico: o Kubernetes (runAsNonRoot) só consegue verificar o usuário se ele for numérico:

FROM node:22-slim
WORKDIR /app
COPY --chown=10001:10001 package*.json ./
RUN npm ci --omit=dev
COPY --chown=10001:10001 . .
USER 10001:10001
EXPOSE 3000
CMD ["node", "server.js"]
docker run --rm app id            # uid=10001 gid=10001
docker exec api whoami            # confirma num container em execução
docker run --rm --user 10001:10001 imagem-sem-user   # força o usuário sem mudar a imagem

Consequências de rodar sem root: porta abaixo de 1024 não pode ser aberta (use 8080 internamente e publique -p 80:8080; imagens como nginxinc/nginx-unprivileged já fazem isso) e escrita em pastas exige dono correto (--chown no COPY, ou mkdir + chown antes do USER). Permissão em volumes é tratada na seção 8.

Na entrevista

Se perguntarem "por que o grupo docker é perigoso?", mostre o chroot /host acima. Se perguntarem a diferença entre rootless e USER: USER reduz o poder do processo dentro do container; rootless reduz o poder do daemon e de tudo que ele cria. São camadas complementares.

Para gestores

Faça um inventário: quais servidores têm o socket montado em algum container e quem está no grupo docker. Em geral há surpresas (runner de CI antigo, painel esquecido). Regra de equipe: pedido de acesso ao grupo docker passa pela mesma aprovação de acesso root.

3Avançado

Capabilities, privileged, seccomp e AppArmor/SELinux

Tradicionalmente, "root" é tudo ou nada. O Linux dividiu esse poder em dezenas de capabilities (ligar em porta baixa, mudar dono de arquivo, criar socket bruto, montar sistemas de arquivos...). O Docker já inicia o container sem a maioria delas, mas deixa um conjunto padrão que quase nenhuma aplicação usa. Sobre isso, camadas adicionais filtram o que o processo pode pedir ao kernel.

Capabilities: tirar tudo e devolver só o necessário

O conjunto padrão do Docker inclui, entre outras, CHOWN, DAC_OVERRIDE, SETUID, SETGID, KILL, NET_RAW, NET_BIND_SERVICE e SYS_CHROOT. Uma API web raramente precisa de qualquer uma. A prática segura é descartar todas e adicionar só a que a aplicação exigir:

docker run --rm alpine sh -c 'grep CapEff /proc/self/status'
CapEff: 00000000a80425fb          # conjunto padrão (root no container)

docker run --rm --cap-drop ALL alpine sh -c 'grep CapEff /proc/self/status'
CapEff: 0000000000000000          # nenhuma capability

# nginx que precisa abrir a porta 80 como root, sem o resto:
docker run -d --cap-drop ALL --cap-add NET_BIND_SERVICE \
  --cap-add CHOWN --cap-add SETUID --cap-add SETGID nginx:1.27

Descubra o necessário por tentativa: suba com --cap-drop ALL, leia o erro (Operation not permitted) e adicione a capability correspondente, uma de cada vez. Com usuário não-root em porta alta (8080), em geral nenhuma é necessária.

--privileged e por que evitar

--privileged dá todas as capabilities, acesso a todos os dispositivos do host e relaxa seccomp e o módulo de segurança. É praticamente "root no host com uma camada de namespaces". De dentro, é possível montar o disco do host:

docker run --rm --privileged alpine sh -c 'mkdir /h && mount /dev/sda1 /h && ls /h'
# lista o disco do host: nenhum isolamento de sistema de arquivos restou
Necessidade realEm vez de --privileged
acessar um dispositivo (USB, GPU, porta serial)--device /dev/ttyUSB0 (GPU: runtime e flags do fabricante)
uma operação de rede específica (ping, tcpdump)--cap-add NET_RAW ou NET_ADMIN, só no container de diagnóstico
Docker dentro de Docker no CIdaemon rootless, runtime Sysbox, builder remoto, ou VM efêmera por job
depurar o hostsessão SSH no host, não um container privilegiado esquecido em produção

no-new-privileges, seccomp e AppArmor/SELinux

  • --security-opt no-new-privileges: o processo e seus filhos não ganham privilégios extras por binários setuid ou capabilities de arquivo. Bloqueia uma classe inteira de escalada local. Custo quase zero; ligue sempre.
  • seccomp: filtro de chamadas de sistema. O perfil padrão do Docker bloqueia algumas dezenas de syscalls perigosas ou obsoletas e já vem ligado. Pode-se fornecer um perfil próprio, mais restrito, com --security-opt seccomp=perfil.json. Nunca use seccomp=unconfined para "fazer funcionar"; descubra qual syscall o app precisa e libere só ela.
  • AppArmor (distribuições Debian/Ubuntu) e SELinux (família Red Hat/Fedora): módulos de segurança do kernel que aplicam políticas de acesso obrigatório. O Docker aplica um perfil padrão (docker-default no AppArmor; rótulos de container no SELinux). Em hosts com SELinux, volumes de bind mount podem exigir o sufixo :z ou :Z para o rótulo correto. Desligar o módulo para "resolver" um erro de permissão é a armadilha clássica.
docker info --format '{{.SecurityOptions}}'
# [name=seccomp,profile=builtin name=cgroupns]  (e name=apparmor ou name=selinux, conforme o host)
Armadilha comum

Receitas de internet que resolvem "permission denied" com --privileged, seccomp=unconfined ou setenforce 0. Resolvem o sintoma e abrem mão de todas as camadas ao mesmo tempo. Investigue a causa (dono do volume, rótulo SELinux, capability específica).

Na entrevista

Pergunta clássica: "o que o --privileged faz?". Resposta curta: todas as capabilities, todos os dispositivos e sem as restrições de seccomp/AppArmor; o container vira quase um processo root do host. Complete com a alternativa (--device, --cap-add pontual).

Para gestores

Transforme isso em política verificável: "nenhum serviço em produção com privileged, seccomp=unconfined ou socket montado sem exceção documentada e aprovada". Ferramentas de política (Kubernetes Pod Security Standards, regras no CI que leem o Compose) fazem o cumprimento automático.

4Intermediário

Hardening em execução: read-only, tmpfs e limites de recursos

Sistema de arquivos somente leitura

Se o invasor não consegue gravar no container, não instala ferramenta, não altera o código nem planta um binário. Com --read-only, a camada gravável some e a aplicação só escreve onde você permitir: tmpfs (memória, some ao parar) para arquivos temporários e volumes para dados reais.

docker run -d --name api \
  --read-only --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  -v api-uploads:/app/uploads \
  --user 10001:10001 --cap-drop ALL \
  --security-opt no-new-privileges \
  --pids-limit 200 --memory 512m --cpus 1.0 \
  -p 127.0.0.1:8080:8080 \
  reg.exemplo.com/clinica/api:1.4.2

docker inspect -f 'ro={{.HostConfig.ReadonlyRootfs}} caps={{.HostConfig.CapDrop}} pids={{.HostConfig.PidsLimit}}' api
ro=true caps=[ALL] pids=200

Aplicações costumam falhar na primeira tentativa com Read-only file system. O erro mostra o caminho: ele vira um tmpfs ou um volume. Casos comuns: /tmp, /var/run, /var/cache/nginx, diretório de upload, cache do framework.

Limites de recursos: segurança também é disponibilidade

Sem limites, um container com defeito (ou invadido) consome toda a memória, CPU ou número de processos do host, e derruba os vizinhos. É a forma mais simples de negação de serviço, acidental ou não.

RecursoFlag do docker runComportamento ao estourar
Memória--memory 512m (e --memory-swap para controlar swap)o kernel mata o processo (OOM kill, exit code 137, OOMKilled=true)
CPU--cpus 1.5 (cota), --cpu-shares (peso relativo)o container é estrangulado (throttling): fica lento, não morre
Processos--pids-limit 200novos processos/threads falham (fork: Resource temporarily unavailable): contém fork bombs
Arquivos abertos--ulimit nofile=4096:8192erro too many open files

Equivalente em Compose (Compose v2 respeita deploy.resources.limits fora do Swarm):

services:
  api:
    image: reg.exemplo.com/clinica/api:1.4.2
    user: "10001:10001"
    read_only: true
    tmpfs:
      - /tmp:rw,noexec,nosuid,size=64m
    cap_drop: [ALL]
    security_opt:
      - no-new-privileges:true
    pids_limit: 200
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
    ports:
      - "127.0.0.1:8080:8080"     # só o proxy local alcança
    volumes:
      - api-uploads:/app/uploads
volumes:
  api-uploads:

Outros ajustes baratos

  • Publique só o necessário e só onde precisa: banco e cache não têm ports; ficam numa rede interna. -p 5432:5432 abre o banco para a rede inteira (e o Docker contorna regras de UFW/firewalld ao inserir as próprias regras de iptables). Use 127.0.0.1:porta:porta quando só o host precisa acessar.
  • Redes separadas: internal: true numa rede Compose impede saída para a internet (útil para o banco). Veja o módulo 05.
  • --init: processo mínimo como PID 1 que repassa sinais e colhe zumbis.
  • Imagens por digest e pacotes mínimos: menos binários, menos ferramentas para o invasor.
Regra de bolso

O "kit mínimo" de todo serviço: USER não-root, cap_drop: ALL, no-new-privileges, read_only + tmpfs, limites de memória/CPU/pids, e porta publicada só quando necessária. Leva dez linhas de YAML.

Na entrevista

"Como você preveniria que um container consuma todos os recursos do host?" Limites de memória, CPU e pids; monitoramento (docker stats, métricas) e política de restart. Mencione que estouro de memória mata o container e estouro de CPU só o desacelera.

Para gestores

Limites são também planejamento de capacidade: sem eles, você não sabe quanto cada serviço custa nem dimensiona o servidor com segurança. Exija limites em todo serviço novo e revise-os com dados reais (média e pico) após o primeiro mês em produção.

5Intermediário

Segredos, varredura de imagens e CIS Benchmark

Onde os segredos vazam

LugarPor que é ruim
ENV no Dockerfilegravado na imagem: qualquer um que puxe a imagem lê com docker inspect ou docker history
ARG no Dockerfilesome do container, mas fica no histórico da imagem e nos metadados do build

Segredos no build (BuildKit)

Precisa de um token para baixar pacote privado durante o build? Use o mount de secret do BuildKit: o arquivo existe só durante aquela instrução RUN e não entra em nenhuma camada.

# syntax=docker/dockerfile:1
FROM node:22-slim AS deps
WORKDIR /app
COPY package*.json ./
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci --omit=dev
docker build --secret id=npmrc,src=$HOME/.npmrc -t app:1.0 .
docker history app:1.0 | grep -i npmrc    # nada: o segredo não ficou na imagem

Segredos em runtime

  • Arquivo montado: secrets do Compose aparecem em /run/secrets/nome (em memória, tmpfs). A aplicação lê o arquivo. Muitas imagens oficiais aceitam o sufixo _FILE (por exemplo POSTGRES_PASSWORD_FILE).
  • Cofre: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager. A aplicação (ou um agente sidecar) busca na inicialização, com identidade própria e acesso auditado, e permite rotação sem rebuild.
  • Kubernetes Secret: é codificado em base64, não criptografado por padrão. Habilite criptografia em repouso e, de preferência, integre a um cofre externo.
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
secrets:
  db_password:
    file: ./secrets/db_password.txt     # fora do git (.gitignore)
Armadilha comum

Apagar o segredo e fazer commit novo. O histórico do git e as camadas da imagem preservam o valor. Segredo vazado se revoga e troca; reescrever histórico é complemento, não solução. Use varredura de segredos no CI (gitleaks, trufflehog) para pegar o vazamento antes do push.

Varredura de vulnerabilidades

Scanners comparam os pacotes e dependências da imagem com bases de CVEs. Os mais usados: Trivy, Grype e o Docker Scout (integrado ao Docker; os recursos disponíveis variam conforme o plano).

trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 reg.exemplo.com/clinica/api:1.4.2
docker scout cves reg.exemplo.com/clinica/api:1.4.2
docker scout recommendations reg.exemplo.com/clinica/api:1.4.2   # sugere base melhor

Como ler o resultado sem pânico: priorize CVEs com correção disponível em pacotes que o programa realmente usa; a maioria cai com a troca da imagem base por uma versão recente ou mínima (slim, distroless). Falso positivo e "sem correção" entram numa lista de exceções com prazo (arquivo .trivyignore ou VEX), nunca no silêncio. O gate de CI (--exit-code 1) deve ser calibrado: bloquear CRITICAL com correção, alertar o resto. SBOM, assinatura e provenance estão no módulo 08.

CIS Docker Benchmark e docker-bench-security

O CIS Docker Benchmark é um guia de configuração segura publicado pelo Center for Internet Security, com recomendações organizadas em: configuração do host, configuração do daemon, arquivos do daemon, imagens e Dockerfiles, runtime dos containers, operações e Swarm. O projeto docker-bench-security (mantido pela Docker) é um script que verifica essas recomendações no host e imprime [PASS], [WARN], [INFO] e [NOTE]:

git clone https://github.com/docker/docker-bench-security.git
cd docker-bench-security && sudo sh docker-bench-security.sh
[WARN] 2.1  - Ensure network traffic is restricted between containers on the default bridge
[PASS] 4.1  - Ensure a user for the container has been created
[WARN] 5.10 - Ensure memory usage for container is limited

Use como auditoria periódica, não como lista a zerar às cegas: alguns itens não se aplicam ao seu cenário, outros exigem decisão (por exemplo, auditoria do daemon, userns-remap). Os números e os textos dos itens mudam entre versões do benchmark; consulte a versão vigente.

Na entrevista

"Como você evita segredo na imagem?" Build: --mount=type=secret. Runtime: arquivo em /run/secrets ou cofre, nunca ENV/ARG/COPY. Prevenção: .dockerignore com .env, varredura de segredos no CI e rotação periódica.

Para gestores

Defina quem é o dono do "plano de segredos": onde ficam, como são rotacionados e quem é avisado num vazamento. Defina também a política de CVE: prazos por severidade (por exemplo, crítico com correção em 7 dias) e quem decide exceções. Sem política, o relatório do scanner vira ruído.

6Intermediário

Dados de saúde em containers e LGPD

Numa empresa de saúde, quase todo serviço toca dado pessoal, e boa parte é dado pessoal sensível (a LGPD, Lei 13.709/2018, trata dado referente à saúde como sensível, art. 5º, II, e art. 11). O art. 46 exige medidas técnicas de segurança para proteger esses dados de acessos não autorizados e de situações acidentais ou ilícitas. Docker não muda a lei, mas muda onde o dado se esconde: ele aparece em lugares que a equipe esquece de mapear.

Exclusão e ciclo de vida

O titular pode pedir eliminação de dados (art. 18). Dado em volume, em backup e em log tem de ter política de retenção que permita atender isso ou justifique a exceção. Para ambientes efêmeros, docker compose down -v apaga volumes; para servidores descomissionados, apague discos de forma segura.

Incidente

Se um container for comprometido ou um volume vazar, o incidente com dados pessoais tem comunicação obrigatória à ANPD e aos titulares quando há risco relevante (art. 48; pela Resolução CD/ANPD nº 15/2024, o prazo é de 3 dias úteis a partir do conhecimento do incidente). Ter inventário de quais containers e volumes guardam dado pessoal é o que torna essa resposta rápida.

Armadilha comum

Imagem de debug com dump de produção "só para reproduzir um bug", enviada a um registry público ou compartilhada por mensagem. Dado de paciente na camada de uma imagem é vazamento permanente: o histórico de camadas o preserva.

Na entrevista

Se a vaga é em saúde, cite espontaneamente: logs sem dado pessoal, volumes e backups criptografados, retenção, ambientes de teste com dados anonimizados e acesso auditado ao host. Mostra que você liga a tecnologia ao risco do negócio.

Para gestores

Peça ao time um mapa de dados dos containers: serviço, tipo de dado, onde persiste (volume/log/backup), por quanto tempo e quem acessa. É a base do registro de operações (ROPA) e do relatório de impacto, e deixa a conversa com o encarregado (DPO) concreta. Trate backup e log como parte do escopo, não como detalhe.

7Intermediário

Roteiro de diagnóstico e exit codes

Diagnosticar bem é estreitar o problema antes de mexer. Em vez de reiniciar e rezar, siga uma ordem fixa: estado, logs, inspeção, visão por dentro, visão por fora e recursos. A cada passo você elimina uma família de causas.

  1. O que mudou? Deploy, imagem nova, variável, rede, disco, certificado, o horário. A maior parte dos incidentes começa numa mudança.
  2. Estado: docker ps -a (Up, Exited, Restarting; há quanto tempo; (unhealthy)).
  3. Logs: docker logs --tail 100 --timestamps x. Se está em loop, veja o primeiro erro, não o último.
  4. Inspeção: docker inspect para exit code, OOM, variáveis, mounts, rede, health.
  5. Por dentro: docker exec -it x sh e teste o serviço em localhost, o DNS e a conectividade com as dependências.
  6. Por fora: porta publicada, firewall, proxy reverso, rede entre containers.
  7. Recursos: docker stats, docker system df, limites e cota de CPU.
$ docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Image}}'
NAMES    STATUS                         IMAGE
api      Restarting (1) 8 seconds ago   clinica/api:1.4.2
db       Up 3 days (healthy)            postgres:17
nginx    Up 3 days                      nginx:1.27

$ docker inspect api --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}} restarts={{.RestartCount}} err={{.State.Error}}'
exit=1 oom=false restarts=14 err=

$ docker logs --tail 3 api
Error: connect ECONNREFUSED 127.0.0.1:5432

Leitura do exemplo: exit=1 sem OOM é erro da aplicação, e a mensagem mostra a causa: ela tenta o banco em 127.0.0.1, mas o banco é outro container. Deveria usar o nome do serviço (db). Diagnóstico em três comandos.

Regra de bolso

Leia o primeiro erro dos logs, confirme o exit code e só então mexa em algo. Mudar duas coisas ao mesmo tempo apaga a evidência do que resolveu.

Na entrevista

Quando pedirem "container não sobe, o que você faz?", narre o roteiro: ps -a, logs, inspect (exit code e OOM), run --entrypoint sh para entrar na imagem, e só depois hipóteses. Quem mostra método passa mais confiança do que quem recita causas.

Para gestores

Padronize o runbook de primeiros socorros (esses sete passos numa página) e exija que todo serviço tenha: health check, logs em stdout e um dono. Tempo para diagnosticar cai muito quando o plantão sabe por onde começar.

Problemas frequentes: do container que sai ao que não tem shell

Container que sai na hora

Um container vive enquanto o processo PID 1 viver. Se o comando termina ou vai para segundo plano, o container sai com exit code 0. Causas clássicas:

  • Serviço iniciado como daemon: CMD service nginx start ou CMD ["nginx"] sem -g "daemon off;" (a imagem oficial já usa o certo). O init do daemon retorna e o container acaba. O processo precisa rodar em primeiro plano.
  • CMD em forma shell: CMD node server.js vira /bin/sh -c "node server.js"; o shell é o PID 1 e não repassa SIGTERM. O docker stop espera 10 s e envia SIGKILL (exit 137). Use a forma exec: CMD ["node","server.js"].
  • ENTRYPOINT errado: caminho inexistente (127), script sem permissão de execução (126), ou script com fim de linha CRLF (do Windows): aparece como exec /entrypoint.sh: no such file or directory mesmo existindo, porque o interpretador procurado é /bin/sh^M. Corrija com .gitattributes (*.sh text eol=lf).
  • Script de entrada sem exec: o último comando do script precisa ser exec "$@", para o app assumir o PID 1 e receber os sinais.
# entrar na imagem ignorando o ENTRYPOINT, para olhar de dentro
docker run --rm -it --entrypoint sh clinica/api:1.4.2
ls -l /entrypoint.sh; head -1 /entrypoint.sh | od -c | head -2     # procure \r (CRLF)

# medir o prazo do stop: forma shell x forma exec
time docker stop api        # ~10 s = não tratou SIGTERM; ~1 s = encerrou limpo

OOMKilled e exit 137; exit 139

docker inspect api --format 'oom={{.State.OOMKilled}} exit={{.State.ExitCode}}'
oom=true exit=137
docker events --filter event=oom --since 24h        # quando aconteceu
docker stats --no-stream api                        # uso atual x limite

O que fazer, nesta ordem: confirme que é OOM do container (limite --memory) e não do host (dmesg | grep -i "killed process"); procure vazamento ou pico; ajuste o runtime da linguagem ao limite (JVM e Node não "enxergam" o limite automaticamente em versões antigas; Java moderno respeita cgroups, e no Node costuma-se definir --max-old-space-size); só então aumente o limite. Sem OOMKilled=true e com 137, foi docker stop/kill (prazo estourado). O 139 é falha de segmentação: investigue código nativo, bibliotecas incompatíveis (binário compilado para glibc rodando em Alpine/musl) e arquitetura errada.

Rede e DNS

docker network ls
docker network inspect clinica_default --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
docker exec api getent hosts db                      # resolve o nome do serviço?
docker run --rm -it --network clinica_default nicolaka/netshoot   # dig, curl, ss, tcpdump
  • Nome não resolve: containers em redes diferentes, ou na rede bridge padrão (que não tem DNS por nome). Use rede definida pelo usuário (módulo 05).
  • localhost dentro do container é o próprio container.
  • Aplicação em 127.0.0.1: o publish não alcança; escute em 0.0.0.0.
  • DNS externo falha (comum com VPN corporativa ou DNS interno): configure "dns": ["10.0.0.2"] no daemon.json ou dns: no serviço.
  • Conexões que "penduram" no TLS ou em transferências grandes: suspeite de MTU menor na VPN; teste com "mtu": 1400 no daemon ou na rede. Conceitos em Redes e HTTP na trilha web.

Permissão negada em volume

O kernel compara UIDs numéricos, não nomes. Se a pasta do host pertence ao UID 1000 e o container roda como 10001, a escrita falha.

ls -ln /dados/uploads                        # dono numérico no host
docker exec api id                           # uid=10001
# correções, da melhor para a pior:
#  1) volume nomeado + chown na imagem (mkdir /app/uploads && chown 10001 antes do USER)
#  2) em desenvolvimento: docker run --user "$(id -u):$(id -g)" ...
#  3) ajustar o dono no host: sudo chown -R 10001:10001 /dados/uploads
#  nunca: chmod 777
# host com SELinux: acrescente :z ao bind mount (-v /dados:/app/dados:z)

"No space left on device"

$ docker system df
TYPE            TOTAL   ACTIVE   SIZE      RECLAIMABLE
Images          48      6        21.3GB    17.9GB (84%)
Containers      12      5        1.2GB     640MB (53%)
Local Volumes   9       4        8.1GB     2.0GB (24%)
Build Cache     210     0        14.6GB    14.6GB

docker builder prune --filter until=168h     # cache de build com mais de 7 dias
docker image prune -a --filter until=720h    # imagens sem uso há 30 dias
docker system prune                          # parados, redes e imagens sem tag
# CUIDADO: docker system prune -a --volumes apaga volumes sem uso (bancos de dados!)

Se o disco encheu e nada disso explica, olhe os logs: o driver padrão json-file não rotaciona. Localize o arquivo (docker inspect -f '{{.LogPath}}' api), veja o tamanho e configure a rotação para o host inteiro em /etc/docker/daemon.json:

{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}

Reinicie o daemon e recrie os containers: a configuração só vale para containers criados depois. Em Compose, o equivalente por serviço é logging: { driver: json-file, options: { max-size: "10m", max-file: "3" } }.

Build que não usa cache

  • COPY . . antes de instalar dependências: qualquer arquivo alterado invalida tudo abaixo. Copie primeiro só o manifesto (package*.json, requirements.txt).
  • Sem .dockerignore: .git, node_modules e logs mudam e invalidam o COPY.
  • ARG com valor que muda a cada build (data, SHA do commit) declarado cedo: invalida as instruções seguintes. Declare-o o mais tarde possível.
  • CI com runner limpo: cache só existe se exportado (--cache-from/--cache-to, módulo 08).
  • Diagnóstico: docker build --progress=plain . mostra CACHED por passo; a primeira instrução sem CACHED é a culpada.

Container lento

$ docker stats --no-stream
NAME    CPU %    MEM USAGE / LIMIT    MEM %    NET I/O       BLOCK I/O     PIDS
api     99.8%    498MiB / 512MiB      97.3%    1.2GB/0.9GB   2.1GB/10MB    41

docker exec api cat /sys/fs/cgroup/cpu.stat    # cgroup v2: nr_throttled e throttled_usec crescendo = limite de CPU

CPU em 100% do limite com nr_throttled subindo indica throttling: a aplicação está sendo desacelerada pela cota, não pelo código. Memória colada no limite leva a swap ou a OOM iminente. Em Docker Desktop (Windows/macOS), bind mounts de pastas do sistema hospedeiro são lentos; mantenha o projeto no sistema de arquivos do WSL 2 ou use volume. Outras causas: DNS lento (resolve cada conexão), disco saturado (BLOCK I/O) e poucos workers.

Depurar imagem sem shell

Imagens distroless ou scratch não têm sh, curl nem ps: docker exec -it x sh falha. Opções:

# 1) container efêmero nos mesmos namespaces (funciona em qualquer Docker Engine)
docker run --rm -it --network container:api --pid container:api \
  --cap-add SYS_PTRACE nicolaka/netshoot
ss -tlnp ; curl -s localhost:8080/health ; ls /proc/1/root/app   # sistema de arquivos do alvo

# 2) docker debug: depuração com caixa de ferramentas própria, sem alterar a imagem
docker debug api

# 3) copiar arquivos para analisar fora
docker cp api:/app/config.json ./config.json

# 4) Kubernetes: container efêmero no Pod
kubectl debug -it pod/api-7d9f --image=busybox --target=api
Sobre o docker debug

É um recurso do Docker Desktop (a CLI padrão do Engine puro não traz o subcomando). No lançamento exigia assinatura paga; versões recentes do Docker Desktop passaram a oferecê-lo também no plano gratuito. Como as regras de licença mudam, confirme na documentação e no seu plano antes de depender dele; a opção 1 funciona em qualquer ambiente e não tem esse risco.

Eventos do daemon

docker events --since 1h --filter type=container --filter event=die
2026-11-26T09:41:12.000000000-03:00 container die 3f9c1a... (exitCode=137, image=clinica/api:1.4.2, name=api)
docker events --filter event=oom --filter event=health_status
docker events --since 30m --until 0s --format '{{.Time}} {{.Action}} {{.Actor.Attributes.name}}'

Os eventos contam a história: die com exitCode, oom, health_status: unhealthy, kill (quem enviou qual sinal), restart. Útil para reconstruir "o que aconteceu às 03:00" e para alimentar alertas.

Armadilha comum

Deixar uma ferramenta de depuração na imagem de produção "para facilitar". Um shell, curl e um compilador dentro da imagem são exatamente o que um invasor quer encontrar. Depure com container efêmero e mantenha a imagem mínima.

Na entrevista

"A imagem é distroless e preciso investigar." Resposta: container efêmero compartilhando --network container: e --pid container: (ou kubectl debug, ou docker debug no Desktop), sem alterar a imagem. Cite também docker cp e docker inspect.

Para gestores

Disco cheio por log sem rotação é uma das quedas mais evitáveis. Padronize max-size/max-file no daemon.json de todos os hosts e na imagem de VM, e monitore disco do host e do diretório do Docker com alerta em 80%.

Exercícios

Laboratórios práticos, em ordem crescente. Faça num Docker de teste (nunca em produção). Tente primeiro; abra a resolução depois.

E1Crie uma imagem que rode como usuário não-root (UID 10001) e prove que ela não consegue escrever em /etc.
FROM alpine
RUN addgroup -S -g 10001 app && adduser -S -u 10001 -G app app
USER 10001:10001
CMD ["sleep", "3600"]
docker build -t lab-naoroot .
docker run -d --name t1 lab-naoroot
docker exec t1 id
uid=10001(app) gid=10001(app) groups=10001(app)
docker exec t1 sh -c 'echo x > /etc/teste'
sh: can't create /etc/teste: Permission denied
docker exec -u 0 t1 sh -c 'echo x > /etc/teste && echo escreveu como root'   # contraste
docker rm -f t1

Observe que a imagem decide o padrão, mas docker exec -u 0 ainda entra como root: por isso o acesso ao daemon também precisa ser controlado.

E2Compare as capabilities de um container padrão com --cap-drop ALL e mostre uma operação que quebra sem NET_RAW.
docker run --rm alpine grep CapEff /proc/self/status
CapEff: 00000000a80425fb
docker run --rm --cap-drop ALL alpine grep CapEff /proc/self/status
CapEff: 0000000000000000

docker run --rm alpine ping -c1 127.0.0.1                     # funciona
docker run --rm --cap-drop ALL alpine ping -c1 127.0.0.1      # permission denied
docker run --rm --cap-drop ALL --cap-add NET_RAW alpine ping -c1 127.0.0.1   # volta a funcionar

Lição: a capability necessária aparece como erro Operation not permitted/permission denied; você devolve uma de cada vez. A API do dia a dia raramente precisa de nenhuma.

E3Rode o nginx com --read-only, leia o erro e corrija usando tmpfs.
docker run -d --name web --read-only -p 8081:80 nginx:1.27
docker logs web | grep -i "read-only"
# erros como: mkdir() "/var/cache/nginx/client_temp" failed (30: Read-only file system)
# ou falha ao criar o pid file em /var/run

docker rm -f web
docker run -d --name web --read-only \
  --tmpfs /var/cache/nginx --tmpfs /var/run --tmpfs /tmp \
  -p 8081:80 nginx:1.27
curl -sI localhost:8081 | head -1
HTTP/1.1 200 OK
docker exec web sh -c 'echo x > /usr/share/nginx/html/novo.txt'    # falha: read-only

O método vale para qualquer app: rode, leia o caminho do erro, transforme-o em tmpfs ou volume. Os caminhos exatos podem variar com a versão da imagem; guie-se pelo erro.

E4Provoque um OOM kill e confirme a causa sem olhar os logs da aplicação.
docker run -d --name oom --memory 64m --memory-swap 64m python:3.13-slim \
  python -c "x = [bytearray(10**6) for _ in range(500)]"
sleep 3
docker ps -a --filter name=oom --format '{{.Status}}'
Exited (137) 2 seconds ago
docker inspect oom --format 'oom={{.State.OOMKilled}} exit={{.State.ExitCode}}'
oom=true exit=137
docker events --since 5m --filter event=oom
docker rm oom

O --memory-swap igual a --memory desliga o swap do container, para o OOM ocorrer de forma previsível. A correção real, numa aplicação, é achar o consumo ou subir o limite com base em medição.

E5Meça quanto demora o docker stop com CMD em forma shell e com --init. Explique a diferença.
FROM alpine
CMD sleep 300; echo fim
docker build -t lab-shell .
docker run -d --name s1 lab-shell
time docker stop s1                      # perto de 10 s: o sh é PID 1 e não repassa o SIGTERM
docker inspect s1 --format '{{.State.ExitCode}}'     # 137: veio SIGKILL

docker run -d --init --name s2 alpine sleep 300
time docker stop s2                      # rápido: o tini é PID 1 e repassa o SIGTERM ao sleep
docker rm s1 s2

No Linux, o PID 1 de um namespace não recebe a ação padrão de sinais como SIGTERM: só reage se o programa instalou um tratador. Um shell em PID 1 não repassa o sinal; um init mínimo (--init, tini) resolve. Programas em forma exec sem tratador de sinal também tendem a ignorar o SIGTERM como PID 1, por isso aplicações devem tratar o sinal (encerramento limpo, módulo 10).

E6Gere logs em excesso e configure rotação para o container não encher o disco.
docker run -d --name ruido --log-opt max-size=1m --log-opt max-file=3 alpine \
  sh -c 'while true; do echo linha-de-log-bem-comprida-para-encher-rapido; done'
sleep 30
docker inspect -f '{{.HostConfig.LogConfig}}' ruido
ls -lh "$(dirname "$(docker inspect -f '{{.LogPath}}' ruido)")"     # no máximo 3 arquivos de ~1 MB
docker rm -f ruido

Num host Linux, o caminho é acessível diretamente (com permissão). No Docker Desktop os arquivos ficam dentro da VM. Para valer em todos os containers, coloque log-opts no daemon.json e recrie os containers (seção 8).

Cenários práticos de trabalho

1. O painel de gestão que pede o socket

Um desenvolvedor quer subir uma ferramenta web de administração de containers no servidor de homologação, e o Compose dela monta /var/run/docker.sock. A homologação tem cópia de dados reais.

O que fazer
  • Explique que o socket equivale a root no host e que a homologação com dados reais é alvo de valor.
  • Se a ferramenta for realmente necessária: exposição só em rede interna, autenticação forte com MFA, atrás de VPN/proxy, versão fixa e atualizada; ou um socket proxy limitando a API a leitura.
  • Considere alternativas: docker context via SSH para quem precisa administrar, métricas e logs em ferramenta de observabilidade.
  • Registre a exceção, o dono e a data de revisão.

2. O serviço que cai todo dia às 03:00 com exit 137

O relatório noturno da API reinicia o container às 03:00; ninguém viu erro nos logs.

O que fazer
  • docker inspect mostra OOMKilled=true, e docker events --since 24h --filter event=oom confirma o horário: coincide com o job de relatório.
  • Meça o pico (docker stats durante o job, ou métricas); verifique se a consulta carrega tudo em memória e se há paginação/streaming possível.
  • Curto prazo: aumentar o limite com base no pico medido. Médio prazo: mover o relatório para um worker separado, com limite próprio, para que o pico não derrube a API.
  • Garanta alerta de restart e de OOM, e restart: unless-stopped como rede de proteção, não como solução.

3. Servidor com disco 100% numa sexta à tarde

Um host de Compose parou de aceitar escritas. O banco entra em modo de erro.

O que fazer
  • Descubra o que ocupa o espaço: df -h, docker system df, du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail.
  • Se for log: com cuidado, truncar o arquivo (truncate -s 0 arquivo) libera o espaço de imediato sem reiniciar o container; depois configurar max-size/max-file e recriar.
  • Se for cache/imagens: docker builder prune e docker image prune -a. Não use --volumes sem conferir quais volumes seriam apagados.
  • Pós-incidente: rotação padrão no daemon.json de todos os hosts, alerta de disco em 80%, limpeza agendada de cache e imagens antigas.

4. Dados de pacientes aparecendo nos logs

Numa revisão, o time de segurança encontra CPF e nome completo em logs de requisição da API, coletados por um serviço centralizado com retenção de um ano.

O que fazer
  • Conter: parar de registrar o payload (ajuste de nível/configuração da biblioteca de log) e restringir o acesso ao armazenamento de logs.
  • Corrigir na origem: logar identificador interno em vez de CPF/nome; filtro de mascaramento como segunda barreira; revisar APM e ferramentas de erro.
  • Tratar o passivo: avaliar com o encarregado (DPO) a eliminação ou anonimização dos logs antigos e se há incidente a comunicar.
  • Prevenir: teste automatizado que falha se logs contiverem padrão de CPF; item de revisão de código; mapa de dados atualizado.

Socket Unix pelo qual o cliente fala com o daemon. Acesso a ele equivale a root no host.

Modo em que o daemon e os containers rodam sem root, via user namespaces.

Filtro de chamadas de sistema que o processo pode fazer ao kernel.

12Entrevista

Perguntas de entrevista

Responda em voz alta antes de abrir. Ordem: básico, operação, segurança avançada e gestão.

01Containers são seguros? Qual a diferença de segurança para uma VM?

Container é isolamento de processo (namespaces e cgroups) sobre o kernel compartilhado; a VM tem kernel próprio atrás de um hypervisor, com superfície de ataque menor entre cargas. Container é seguro o bastante para a maioria dos casos com privilégio mínimo; para código não confiável, use isolamento mais forte (microVM, gVisor, Kata).

02Por que não rodar o container como root?

O root do container é UID 0 no host, apenas com capabilities reduzidas. Se a aplicação for explorada e houver falha de isolamento (kernel, volume sensível, socket), o invasor ganha root no host. Com USER não-root, cap_drop: ALL e no-new-privileges, o estrago fica contido. Corrige-se na imagem (USER 10001, --chown) e reforça-se no runtime (user: no Compose, runAsNonRoot no Kubernetes).

03Por que montar /var/run/docker.sock num container é perigoso?

O socket é a API do daemon, que roda como root. Com ele, o container pode criar outro container com / do host montado e privilégios totais. Montar como :ro não ajuda. Alternativas: socket proxy com permissões mínimas, builders sem daemon, runners rootless/VM efêmera.

04Por que o grupo docker equivale a root?

Quem está no grupo escreve no socket, e pode executar docker run -v /:/host alpine chroot /host, obtendo root no sistema de arquivos do host sem sudo e sem rastro de sudo. Trate a lista do grupo como a lista de administradores.

05Rootless mode, user namespaces (userns-remap) e USER na imagem: qual a diferença?

USER reduz o poder do processo dentro do container. userns-remap mapeia o root do container para um UID sem privilégio no host, mas o daemon continua root. Rootless roda o daemon inteiro sem root. São camadas complementares; rootless tem limitações (portas baixas, rede em espaço de usuário), e userns-remap muda a propriedade de volumes.

06O que são capabilities e como você as usa?

São frações do poder do root no Linux. O Docker concede um conjunto padrão; a prática segura é --cap-drop ALL e adicionar só o necessário (NET_BIND_SERVICE para porta baixa, por exemplo). Descobre-se o necessário subindo sem nenhuma e atendendo aos erros Operation not permitted.

07O que faz o --privileged e o que usar no lugar?

Dá todas as capabilities e acesso a todos os dispositivos, e relaxa seccomp e o módulo de segurança: o container vira praticamente root no host. Em vez disso: --device para um dispositivo, --cap-add pontual, e para Docker-em-Docker um daemon rootless, Sysbox ou builder remoto.

08Para que servem no-new-privileges e seccomp?

no-new-privileges impede ganhar privilégio por binários setuid; seccomp filtra as syscalls que o processo pode chamar (o perfil padrão do Docker já bloqueia as mais perigosas). Nunca use seccomp=unconfined para "resolver" erros; identifique a syscall necessária e libere só ela. AppArmor/SELinux completam com política de acesso a arquivos.

09Por que usar --read-only e como lidar com apps que precisam gravar?

Impede o invasor de gravar binários e alterar o código no container. O que a aplicação precisa gravar vai para tmpfs (temporários) ou volume (dados). Leva-se o caminho de cada erro Read-only file system para um desses dois destinos.

10Como evitar que um container derrube o host por consumo de recursos?

Limites: --memory (estouro mata o container, exit 137), --cpus (estouro estrangula), --pids-limit (contém fork bomb) e --ulimit. Mais monitoramento e alertas. Também vale limitar disco de logs e tmpfs.

11Como você trata segredos em imagens e containers?

Nunca em imagem (ENV, ARG, COPY) nem no git. No build: RUN --mount=type=secret. Em runtime: arquivo em /run/secrets (Compose/Swarm/Kubernetes) ou cofre (Vault, Secrets Manager), com rotação. Segredo vazado se revoga e troca. Complementos: .dockerignore, varredura de segredos no CI.

12Como você lida com as vulnerabilidades que o scanner encontra?

Priorizo CRITICAL/HIGH com correção disponível em pacotes realmente usados; a maioria resolve com base atualizada ou mínima. Rebuild periódico da imagem base, scanner no CI com gate calibrado, exceções registradas com prazo e dono. Política de prazo por severidade, definida com a gestão.

13O que é o CIS Docker Benchmark e o docker-bench-security?

O benchmark é um conjunto de recomendações de configuração segura (host, daemon, imagens, runtime). O docker-bench-security é um script que verifica essas recomendações e devolve PASS/WARN/INFO/NOTE. Uso como auditoria periódica, avaliando cada item no contexto, não zerando às cegas.

14O container saiu com 137. E com 139? Como você investiga?

137 = SIGKILL. docker inspect: se OOMKilled=true, é memória (limite ou vazamento); se não, foi docker stop que esgotou o prazo (CMD em forma shell ou sem tratar SIGTERM) ou um kill. docker events dá o horário. 139 = SIGSEGV: código nativo, biblioteca incompatível (glibc x musl) ou arquitetura errada.

15O container sobe e sai imediatamente. Passo a passo?
  1. docker ps -a e docker logs: o primeiro erro.
  2. docker inspect: exit code, OOM.
  3. Exit 0: o processo principal terminou (serviço em segundo plano, CMD errado).
  4. 126/127: permissão ou comando inexistente; CRLF no script.
  5. docker run --rm -it --entrypoint sh img para olhar por dentro.
16O disco do servidor encheu. O que você verifica?

docker system df para separar imagens, containers, volumes e cache; logs do json-file sem rotação são a causa frequente (max-size/max-file no daemon.json, que só vale para containers recriados). Limpe com builder prune e image prune; cuidado com --volumes.

17Como depurar um container de imagem distroless, sem shell?

Container efêmero com ferramentas (netshoot) nos mesmos namespaces: --network container:alvo --pid container:alvo; no Kubernetes, kubectl debug com container efêmero; no Docker Desktop, docker debug (confirmar licença/disponibilidade). Também docker cp e docker inspect. A imagem de produção não é alterada.

18Como estabelecer um padrão de segurança de containers numa equipe e cuidar de dados de saúde (LGPD)?
  • Baseline: imagem base aprovada, template de Compose/Kubernetes com não-root, cap_drop, no-new-privileges, read-only e limites já ligados.
  • Verificação automática: scanner e checagem de configuração no CI, política de exceções.
  • Acesso: grupo docker controlado, socket nunca exposto sem exceção aprovada.
  • LGPD: mapa de dados (logs, volumes, backups), logs sem dado pessoal, criptografia em repouso, backup criptografado com restauração testada, retenção definida, ambientes de teste anonimizados.
  • Operação: runbook de diagnóstico, rotação de logs, alertas de disco, OOM e restart.
